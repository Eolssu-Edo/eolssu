얼쑤에서 사용자가 연주 녹음을 보내면 앱은 분석 접수를 확인하고 결과를 기다립니다. 분석 서버에 일시적으로 연결하지 못해도 원본 파일은 서버에 남습니다. 저는 사용자가 그 녹음으로 분석을 다시 요청할 수 있게 했습니다.

이때 같은 세션 안에 시도가 여럿 생깁니다. 첫 시도가 시간 초과로 끝난 뒤 두 번째 시도를 시작했는데 첫 시도의 성공 응답이 도착할 수 있습니다. 두 결과는 세션 ID가 같습니다. 그대로 저장하면 앱이 두 번째 시도를 기다리는 동안 첫 시도의 점수를 보여줄 수 있습니다.

## 같은 세션에 새 시도를 만들기

어떤 실패가 났는지부터 구분했습니다. 제한 시간 초과나 서버 오류라면 원본 녹음으로 다시 분석할 수 있습니다. 소리가 없거나, 파일이 너무 짧거나, 디코딩할 수 없으면 다시 연주해 새 녹음을 받습니다.

재시도할 수 있는 세션은 기존 녹음과 세션 ID를 유지합니다. 새 분석을 시작할 때는 DB에서 상태를 `FAILED`에서 `PENDING`으로 바꾸고, 시도 번호를 하나 늘리면서 시작 시각을 기록합니다. 이 세 변경은 한 `UPDATE`에 들어갑니다. 갱신 조건에는 실패 사유와 녹음 존재 여부에 더해, 요청이 처음 읽었던 시도 번호도 넣었습니다.

두 요청이 동시에 같은 실패를 읽으면 먼저 갱신한 쪽이 시도 번호를 바꿉니다. 다른 요청은 자신이 읽었던 번호가 달라져 갱신에 실패합니다. 그 요청이 상태를 다시 읽어 분석이 진행 중임을 확인하면 같은 `202 Accepted`를 돌려줍니다. 갱신에 성공한 요청만 변경이 커밋된 뒤 백그라운드 실행기에 작업을 넘깁니다.

`202`를 받은 앱은 상태 조회를 시작하거나 이어갑니다. 처음 요청의 응답이 끊겨 다시 요청했을 때도 이미 진행 중이면 같은 흐름을 탑니다. 요청의 `Idempotency-Key`는 형식만 검사하고 저장하지 않으므로, 중복 시작을 막는 범위는 현재 진행 중인 시도입니다. 그 시도가 다시 실패하면 같은 키로도 다음 시도를 요청할 수 있습니다. 최종 결과는 상태 조회에서 `DONE`이나 `FAILED`를 받았을 때 확인합니다. [RFC 9110의 202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

## 결과를 받는 순간에도 시도 번호를 확인하기

시도 2가 진행 중인데 시도 1의 결과가 늦게 오면, 세션이 `PENDING`이라는 사실만으로는 그 결과를 걸러낼 수 없습니다. 그래서 분석을 시작할 때 읽은 시도 번호를 결과를 저장할 때까지 들고 갑니다. 성공 결과의 저장 여부를 결정하는 갱신은 핵심 조건만 뽑으면 아래와 같습니다.

```sql
UPDATE practice_sessions
SET status = 'DONE'
WHERE id = :session_id
  AND status = 'PENDING'
  AND analysis_attempt = :attempt
  AND analysis_started_at >= :started_after
```

`:started_after`는 결과 저장 시점에 서버 시계로 구한 현재 시각에서 제한 시간을 뺀 값입니다. 시도 번호가 같아도 이미 제한 시간을 넘겼다면 갱신은 0행입니다. 실패 결과를 기록할 때도 같은 조건을 씁니다. 성공으로 상태를 바꾼 경우에만 평가와 음표별 결과를 저장하며, 상태 변경과 평가 저장은 같은 트랜잭션에서 처리합니다.

서버가 재시작되면 실행 중이던 분석은 사라지고 DB에 `PENDING`만 남을 수 있습니다. 그 경우에도 앱이 상태를 조회하면 서버가 DB에 저장된 시작 시각을 확인합니다. 마감이 지난 시도는 조건부 갱신으로 상태를 `FAILED`로 바꾸고 실패 사유를 `TIMEOUT`으로 기록합니다. 이렇게 하면 작업이 사라진 뒤에도 상태 조회로 해당 시도를 끝낼 수 있습니다.

## 늦은 결과와 장애 복구를 따로 확인하기

MySQL 통합 테스트에는 시도 2가 진행 중인 세션을 만들고 시도 1의 성공 결과를 넣었습니다. 갱신은 거절됐고 평가 행은 0건이었습니다. 현재 시도의 결과도 마감을 넘기면 저장되지 않았고, 제한 시간과 정확히 같은 시점의 결과는 저장됐습니다. 재시도 API 테스트에서는 이미 진행 중인 세션이 같은 `202`를 반환하고, 시도 번호가 유지되며, 실행기 대역에 작업이 추가로 전달되지 않는지 확인했습니다.

운영에서는 분석 서비스를 중단한 상태에서 두 음을 합성한 녹음을 올려 봤습니다. 업로드는 접수됐고 최종 상태는 `FAILED`와 `SERVER_ERROR`였습니다. 서비스를 복구해 상태가 `healthy`로 표시된 직후의 첫 재시도도 같은 오류로 끝났습니다. 이 재실패의 상세 원인은 확인하지 못했습니다.

이후 같은 세션에서 한 번 더 재시도해 `DONE`을 받았습니다. API 응답, DB, 분석 로그를 대조하니 시도 번호는 3이었고, 원본 녹음이 유지된 채 평가 한 건과 음표 결과 두 건이 저장돼 있었습니다. 이 실험에서 확인한 범위는 합성 녹음 한 건의 서버 재시도와 결과 저장까지입니다.
