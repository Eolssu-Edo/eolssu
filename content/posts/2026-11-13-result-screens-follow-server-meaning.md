연주 결과 쪽 화면은 서버 응답의 값을 사용자에게 해석해서 보여줍니다. 이때 앱이 응답의 한 값을 다른 의미로 재사용하거나, 서버가 주지 않은 값을 앱이 계산해 채우면 화면이 틀린 말을 하게 됩니다.

이 글은 결과 쪽 화면에서 이런 일이 생길 뻔한 세 곳을 다룹니다. 각 경우에 응답 값이 실제로 뜻하는 범위를 먼저 확인하고, 그 범위 안에서만 화면을 그렸습니다.

## 다시 시도할 수 있는가와 누구의 문제인가는 다른 질문이다

연주 분석이 실패하면 하나의 실패 화면이 사유별로 다른 문구와 버튼을 보여줍니다. 그런데 그림은 모든 사유가 하나를 같이 쓰고 있었습니다. 녹음에 소리가 없어서 실패했을 때 쓰는 머리 긁는 호랑이 그림을 다른 사유에도 쓰려면 기준이 필요했습니다.

응답에는 `retryable`이 있습니다. 이 값을 "사용자 쪽 문제"로 읽고 싶어지지만, 실제 의미는 **같은 녹음으로 다시 분석할 수 있는지**뿐입니다. 예를 들어 업로드 시간 초과는 `retryable=false`라서 버튼은 "다시 연주하기"입니다. 하지만 문구는 "시간이 지나 보낼 수 없게 됐어요. 죄송해요"인 서버·전송 쪽 문제입니다. `!retryable`을 그림 기준으로 쓰면 이 경우에 연주자를 탓하는 그림이 나옵니다.

그래서 축을 나눴습니다.

| 결정 | 기준 |
| --- | --- |
| 버튼(다시 분석 / 다시 연주) | `retryable` |
| 그림과 경고 톤 | 실패 원인이 녹음 쪽인지 |

녹음 쪽 문제는 소리 없음, 녹음이 너무 짧음, 파일 읽기 실패 세 가지만 두고 머리 긁는 호랑이를 보여줍니다. 나머지는 실패 그림과 경고 아이콘을 둡니다. 판정 함수는 실패 사유 여섯 개를 `when`에 모두 나열했습니다. 새 사유가 추가되면 컴파일러가 이 화면에서 어떻게 보일지 정하라고 요구하게 하려는 것입니다.

## 점수 차이는 앱이 빼서 만들지 않는다

이전 연주와 비교하는 화면에서는 두 점수의 차이를 보여줍니다. 두 점수가 모두 화면에 있으니 앱에서 빼면 될 것 같지만, 차이는 서버 비교 결과의 `totalScoreDelta`만 씁니다. 서버는 악보 판본, 채점 모델, 속도가 다르면 두 연주를 비교할 수 없다고 판정하고 `scoreComparable=false`와 함께 차이를 비워 보냅니다.

차이가 비어 있으면 점수 차이 대신 "두 연주의 점수는 비교할 수 없어요"를 보여줍니다. 당시 화면에 있던 점수 상승 도장도 찍지 않았습니다. 휴대폰의 아리랑 40점 → 80점 기록은 둘 다 48 BPM이었는데도 비교 불가로 판정돼 도장이 나오지 않았습니다. 앱이 점수를 빼서 "+40점"을 보였다면, 서버가 막은 비교를 화면이 다시 만든 셈입니다. 같은 속도라도 판본이나 채점 모델이 다르면 비교할 수 없으므로, 판정은 서버에 그대로 맡겼습니다. 도장 자체는 예시 데이터를 넣은 웹 미리보기로 확인했습니다.

## 응답에 없는 필드는 ID로 이어 붙이고, 못 찾으면 숨기지 않는다

연습 기록 목록에 악기별 필터를 넣으려고 보니 기록 API 응답에는 악기가 없었습니다. 목록에는 '아리랑'이 세 번 보였는데, 이름은 같아도 악기마다 곡 ID가 달랐습니다.

곡 목록(`GET /api/songs`)에 있는 `instrumentId`를 악기 목록의 코드로 바꿔 `songId → 악기` Map을 만들었습니다. 공개 목록에서 숨긴 곡처럼 큰 목록에 없는 ID는 곡 상세를 한 번씩 더 조회하고, 시도한 ID를 기억해 반복 조회하지 않게 했습니다. 원본 기록 목록은 고치지 않고, 필터는 표시할 때 계산합니다.

```kotlin
records.filter { songInstruments[it.songId] == selected }
```

악기를 끝내 알 수 없는 기록은 특정 악기에 억지로 넣지 않고 '전체'에서만 보이게 했습니다. 보완 조회가 실패해 Map이 비면 악기를 골랐을 때 목록이 비지만, '전체'는 항상 원본 그대로 보여 기록이 사라지지 않습니다. 계정이 바뀌어 상태를 초기화할 때도 곡의 악기처럼 계정과 무관한 공개 정보는 남겨 둡니다. 서버가 나중에 기록 응답에 악기를 넣어 주면 이 연결은 지울 예정입니다.

## 정리

세 경우 모두 응답 값이 무엇을 뜻하는지가 화면 결정의 기준이었습니다.

- 한 값을 다른 질문의 답으로 재사용하지 않습니다.
- 서버가 판정을 막은 값은 앱이 계산해서 채우지 않습니다.
- 응답에 없는 값을 보완할 때는 못 찾은 항목이 화면에서 사라지지 않게 합니다.
