얼쑤의 분석 API는 요청을 검증하고, 서명 URL로 녹음을 내려받은 뒤 채점합니다. 필수 필드가 빠진 요청이 다운로드까지 도달하지 않는지와, 저장소 접속이 실패했을 때 다운로드 코드가 주소를 담은 예외를 어떻게 처리하는지는 서로 다른 질문입니다. 첫 번째 검사를 위해 다운로드 함수를 바꾸면 두 번째 검사에서 확인하려던 코드까지 건너뛰게 됩니다.

## API 요청 검사에서는 다운로드를 교체했다

FastAPI 테스트 클라이언트는 실제 앱 객체로 요청을 보냈습니다. `dependency_overrides`에서 다운로드 의존성만 바꿨습니다. 대역은 호출되면 받은 주소를 목록에 기록하고 준비한 바이트를 파일에 쓰거나, 지정한 예외를 던졌습니다. 각 검사가 끝나면 재정의 설정을 비웠습니다. [FastAPI의 테스트 의존성 재정의](https://fastapi.tiangolo.com/advanced/testing-dependencies/)

`bpm` 필드를 뺀 요청은 HTTP **422**였고 대역이 기록한 호출은 **0회**였습니다. 오류 응답에 테스트용 서명값도 없었습니다. 다른 검사에서는 다운로드 대역이 `DownloadError`를 던지면 API가 HTTP **502**로 응답하는지 확인했습니다. 여기서 본 것은 앱의 요청 검증과 예외 응답이며, 다운로드 내부의 저장소 요청은 별도 검사에 맡겼습니다.

## 다운로드 검사에서는 HTTP 전송을 교체했다

두 번째 검사에서는 다운로드 함수를 그대로 실행했습니다. 다운로드 함수가 호출하는 `httpx.stream`을 `MockTransport`가 연결된 테스트 클라이언트의 `stream`으로 바꿔, 저장소 응답을 테스트 코드에서 정했습니다. 정상 응답에서는 받은 바이트가 파일에 그대로 쓰였는지 봤습니다. [HTTPX의 MockTransport](https://www.python-httpx.org/advanced/transports/#mock-transports)

오류는 **세 가지**를 만들었습니다. 저장소가 **403**을 반환하는 경우, 본문이 설정한 크기 제한보다 **1바이트** 큰 경우, 연결 예외가 나는 경우입니다. 403 응답이나 연결 예외에 테스트용 서명 주소를 넣었습니다. 세 경우 모두 다운로드 오류로 처리됐고, 연결된 예외까지 포함한 전체 예외 출력에 서명값이 없는지 확인했습니다. 오류의 표면 메시지만 비교하면 원래 예외에 주소가 남아 있는 경우를 놓칠 수 있기 때문입니다.

API 검사에서는 입력이 어디까지 도달했는지를 호출 목록으로 확인했습니다. 다운로드 검사에서는 실제 함수가 외부 응답을 어떻게 읽고 오류로 바꾸는지를 확인했습니다. 두 검사 모두 저장소 접속을 대역으로 제어했으므로, 실제 버킷의 접근 권한과 네트워크 동작은 별도 검증 범위입니다.
