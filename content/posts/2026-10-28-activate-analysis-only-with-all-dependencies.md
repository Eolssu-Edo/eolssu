얼쑤의 백엔드에서 녹음 분석을 연결하려면 세 가지가 필요했습니다. 악보를 채점용 음표로 바꾸는 구현, 녹음의 읽기 주소를 만드는 구현, 분석 서버의 주소입니다. 팀에서 이 부분들을 나눠 개발하는 동안에는 세 가지가 항상 함께 들어오지 않았습니다. 분석 연결이 준비되지 않은 상태에서도 앱이 기동할 수 있도록, 기능을 켜는 조건을 따로 정했습니다.

## 분석을 켜는 세 가지 조건 {#의존성을-하나씩-확인하고-분석을-연결했다}

설정 메서드는 악보 변환기와 녹음 읽기 주소 제공자를 `ObjectProvider`로 받았습니다. 기동할 때 각 제공자의 `ifAvailable`을 읽고, 분석 서버 주소가 비었는지도 확인했습니다. 세 가지가 갖춰졌을 때 HTTP 클라이언트와 분석기를 만들어 업로드 뒤 실행할 작업으로 연결합니다.

빠진 항목이 있으면 이름을 모아 분석 기능이 꺼진 `AnalysisOnUpload`를 반환합니다. 이 상태에서 업로드 완료 이벤트가 들어오면 누락 항목을 로그에 남기고 작업 제출을 건너뜁니다. 명시적인 재시도 요청으로 작업을 제출하는 경로에서는 실행기 거절 예외를 올려 재시도 처리기가 해당 시도를 닫을 수 있게 했습니다. 이 판단은 앱 컨텍스트가 만들어질 때 이루어집니다.

## 필요한 Bean만 조합해 검증 {#전체-앱-대신-필요한-bean만-조합했다}

확인하고 싶었던 것은 웹 서버나 DB의 응답보다 이 설정의 조합이었습니다. `StaticListableBeanFactory`에 테스트마다 필요한 객체만 넣고, 그 팩터리에서 타입별 `ObjectProvider`를 만들었습니다. 설정 메서드를 직접 호출한 뒤 반환된 객체의 `ready` 값을 읽었습니다.

| 설정 조합 | 분석 준비 상태 |
| --- | --- |
| 분석 서버 주소만 있음 | 꺼짐 |
| 분석 서버 주소와 악보 변환기만 있음 | 꺼짐 |
| 분석 서버 주소와 녹음 읽기 주소 제공자만 있음 | 꺼짐 |
| 두 제공자는 있지만 분석 서버 주소가 비어 있음 | 꺼짐 |
| 세 가지가 모두 있음 | 켜짐 |

설정 검사에서 미충족 조합 **네 가지**는 모두 `ready=false`였고 세 조건이 갖춰진 **한 가지**는 `ready=true`였습니다. 실행기가 만들어진 조합은 테스트가 끝날 때 닫았습니다. 별도 단위 검사에서는 분석 연결을 비운 객체에 업로드 이벤트를 줘도 분석 시작 기록이 **0건**이고, 명시적으로 제출하면 거절 예외가 나는지 확인했습니다.

여기서 `ready`는 분석을 실행할 구성 요소가 연결됐다는 표시입니다. 분석 서버에 접속하고 녹음을 채점하는 동작은 별도의 통합 검증 범위였습니다.
