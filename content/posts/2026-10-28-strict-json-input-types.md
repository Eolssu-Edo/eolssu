연습 세션을 시작할 때 앱은 곡과 템포를 서버에 보냅니다. 템포는 JSON 정수만 받기로 했는데, 리뷰 중 `"bpm": 96.7`을 보냈더니 서버는 **96 BPM으로 처리하고 HTTP 201**을 돌려줬습니다. 숫자가 허용 범위에 드는지는 검사했지만, 그 전에 소수점이 사라졌습니다.

## 검증기에 도착한 값은 이미 정수였다

당시 프로젝트의 Jackson 3.1.5 설정으로 입력 모양을 바꿔 봤습니다. 정수 칸에 보낸 문자열 `"96"`도 96이 됐고, 문자열이어야 하는 곡 ID에는 숫자 7을 보내도 `"7"`이 됐습니다. 불리언 칸에 보낸 1은 `true`가 됐습니다.

이 상태에서 `@Min`이나 `@Pattern`을 붙이면 변환 결과만 봅니다. 검증기는 원래 숫자였던 ID와 처음부터 문자열이었던 ID를 구별할 수 없습니다. 타입이 API 계약의 일부라면 그 정보가 남아 있을 때 판정해야 합니다.

## 변환 전에 JSON 토큰을 본다

요청의 각 칸에 필요한 타입을 명시했습니다. BPM과 음표 구간은 `Int` 범위 안의 JSON 정수, ID는 JSON 문자열, 장단 소리 설정은 JSON 불리언으로 받습니다. 정수용 역직렬화기는 파서의 현재 토큰이 정수이고 숫자 타입이 `INT`일 때만 값을 꺼냅니다. 그 밖의 값은 요청 오류로 보냅니다.

템포 단위에는 한 가지 경계가 더 있었습니다. enum으로 바로 읽으면 숫자 0이 선언 순서의 첫 값이 될 수 있었습니다. 먼저 문자열로 받은 다음 허용된 이름을 확인하고 enum으로 바꿨습니다. 요청에서 허용하는 표기와 Kotlin 내부에서 쓰는 타입을 이렇게 연결했습니다.

## 400 응답과 DB 상태를 함께 확인했다

컨트롤러 검사에 자동 변환되던 입력 **10가지**를 추가했습니다. 수정 전에는 이 검사가 실패했고 토큰 검사를 넣은 뒤에는 입력을 400으로 거절했습니다. 기존 실제 HTTP·DB 통합 검사에서는 별도의 잘못된 본문 **11종**에 대해 400과 저장 0행을 확인했습니다.

정수 96을 보낸 정상 요청에서는 201과 저장된 세션을 확인했습니다. 이 검사는 요청을 거절했다는 응답과 서버가 실제로 아무것도 만들지 않았다는 결과를 함께 고정합니다.
