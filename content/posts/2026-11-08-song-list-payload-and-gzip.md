얼쑤의 곡 목록 API를 Swagger UI에서 열었더니 `Could not render responses`가 표시됐습니다. 브라우저 콘솔에는 `Maximum call stack size exceeded`가 남았습니다. 응답을 살펴보니 111곡을 담은 JSON이 약 1.76 MB였고, 그중 약 99%가 곡마다 붙은 `score`였습니다. 곡 하나를 고르는 화면에서 111곡의 악보까지 받고 있었습니다.

## 곡을 고를 때 필요한 필드만 목록에 남겼다

곡 하나당 메타데이터는 평균 189바이트였고, 악보는 평균 약 16 KB였습니다. 악보가 들어간 응답 타입을 목록과 상세에서 함께 쓴 결과였습니다. 곡이 늘면 각 곡의 악보 크기만큼 목록 응답도 함께 커지는 구조였습니다.

저는 목록 항목을 `SongListItem`으로 분리했습니다. 목록의 `result.items`에는 제목, 악기, 난이도, 기본 BPM처럼 곡을 고르는 데 쓰는 필드와 악보 버전 등의 메타데이터를 담았습니다. 원본 악보가 필요한 쪽은 상세 응답이나 곡별 악보 조회에서 선택한 곡의 본문을 받습니다. 백엔드도 목록 항목을 만드는 경로에서는 `scoreJson`을 JSON 트리로 읽을 필요가 없어졌습니다.

이미 앱이 사용하는 응답에서 필드를 빼는 변경이어서 소비 코드를 먼저 확인했습니다. 앱의 역직렬화 모델에서 `score`는 기본값이 `null`인 선택 필드였고, 상세 화면은 곡별 악보를 별도로 조회하고 있었습니다. 실제 HTTP와 MySQL을 연결한 통합 테스트에서 목록 응답은 `scoreVersion`을 제공했고 `score` 필드는 빠졌습니다. 같은 곡의 악보 API는 HTTP 200을 반환했고 응답의 악보 JSON은 DB에서 읽은 원본과 일치했습니다.

111곡의 메타데이터 평균에 곡 수를 곱하면 약 21 KB입니다. 이 값은 필드를 분리했을 때 목록이 어느 정도 작아질지 계산한 추정치입니다.

## 남은 JSON은 프록시에서 압축했다

응답에서 어떤 필드를 보낼지 정한 뒤, 전송량은 따로 살펴봤습니다. 브라우저에서 남긴 별도의 압축 비교 기록에는 당시 곡 목록이 약 1.8 MB에서 129 KB로, 가장 큰 곡 응답은 98 KB에서 8.3 KB로 줄어든 값이 있었습니다. gzip이 줄인 것은 전송할 바이트입니다. 클라이언트가 압축을 풀면 JSON 구조와 필드가 복원되므로, 목록에서 악보를 빼는 일과는 다른 층에서 효과가 납니다.

Nginx에서는 `/api/`의 `application/json`을 압축 대상으로 지정하고, `Content-Length`를 기준으로 최소 길이를 1,024바이트로 설정했습니다. 클라이언트가 `Accept-Encoding: gzip`을 보낸 경우에 gzip 응답을 받을 수 있게 하고, `Vary: Accept-Encoding`으로 캐시가 압축본과 원본을 구분할 수 있게 했습니다.

가짜 백엔드와 실제 Nginx를 Docker에서 함께 띄워 응답 헤더를 확인했습니다. 큰 JSON은 gzip을 요청했을 때 `Content-Encoding: gzip`이 붙었습니다. `identity`로 요청한 같은 JSON과 짧은 JSON, 오디오 응답은 압축 없이 받았습니다.

## 운영 응답에서는 헤더와 바이트를 함께 확인했다

저장소에 설정을 병합한 뒤에도 운영 응답에는 gzip이 없었습니다. 서버가 컨테이너에 별도의 운영 설정 파일을 연결하고 있었기 때문입니다. 컨테이너의 마운트 목록을 읽어 실제로 연결된 파일부터 찾았습니다. HTTP 설정은 저장소 버전과 비교했을 때 gzip 설정 **7줄**만 달랐습니다. HTTPS 설정에는 운영에서만 쓰는 iOS 테스트 설치 경로도 있었습니다. HTTP 설정은 저장소 버전과 맞추고, HTTPS 설정에는 기존 경로를 보존한 채 gzip 부분만 추가했습니다. Nginx 설정 검사와 reload를 거친 뒤 같은 API에 다시 요청했습니다.

| 운영에서 비교한 요청 | 관측 결과 |
| --- | --- |
| 곡 목록, gzip 요청 없음 | 원본 19,827바이트, `Vary: Accept-Encoding` |
| 곡 목록, gzip 요청 | 2,206바이트, `Content-Encoding: gzip`, `Vary: Accept-Encoding` |
| 약관, gzip 요청 | 원본 896바이트 |

표의 두 크기는 악보를 분리한 뒤 같은 운영 목록을 압축 요청 여부만 바꿔 받아 잰 값입니다. 처음 확인한 약 1.76 MB는 다른 시점의 목록에서 측정했습니다. 수정 결과는 곡 목록과 상세의 HTTP 응답, 운영에서 전송한 목록의 바이트 수까지 확인했습니다.
