메일로 받은 인증번호를 55초 만에 입력했는데, 화면에는 2:05가 남아 있으면서 "입력 시간 3분이 지났어요"라는 안내가 나왔습니다. 회원가입 화면은 서버 규칙을 사용자에게 옮겨 보여 주는 곳입니다. 앱이 서버 응답을 잘못 읽거나 서버 규칙을 화면마다 따로 구현하면, 사용자는 안내를 믿을 수 없게 됩니다.

얼쑤 이메일 회원가입을 다듬으며 고친 네 가지를 정리합니다.

## 410은 "시간 초과"만 뜻하지 않았다

처음에는 기기와 서버의 시계 차이를 의심했습니다. 그래서 기기 시각(`adb shell date +%s`), 서버 응답의 `Date` 헤더와 PC 시각을 비교했는데 모두 같았습니다.

원인은 응답 코드를 읽는 방식에 있었습니다. 서버의 인증번호 확인은 다음 세 경우를 모두 같은 `410 Gone`으로 돌려줍니다.

- 만료 시각이 지난 경우
- 같은 이메일로 새 번호를 보내 이전 번호가 무효가 된 경우
- 이미 인증에 사용한 번호인 경우

앱은 410을 모두 시간 초과로 읽고 있었습니다. 응답만으로는 세 원인을 구분할 수 없으므로, 앱이 알고 있는 만료 시각으로 나눴습니다. 시간이 남았으면 "더 이상 쓸 수 없는 번호"로, 지났으면 "입력 시간이 지났다"로 안내합니다. 이번에 받은 410의 실제 원인이 재발송인지 재확인인지는 확인하지 못했습니다. 그래서 안내 문구도 확실히 아는 범위까지만 말하도록 했습니다.

## 막힌 버튼에는 언제 풀리는지 적는다

서버는 마지막 발송 뒤 60초 동안 재발송을 받지 않습니다. 새 번호가 필요한 상황에서도 마찬가지라 앱이 이 간격을 풀어 줄 수 없습니다. 문제는 라벨이었습니다. 라벨 분기가 "새 번호가 필요한가"를 "기다려야 하는가"보다 먼저 확인해서, 버튼은 비활성인데 "새 인증번호 받기"라는 행동만 보였습니다. 흐린 회색 버튼은 사용자에게 "눌렀는데 반응이 없다"로 읽힙니다.

버튼을 막는 조건을 라벨 분기의 첫 줄로 올렸습니다.

```kotlin
label = when {
    state.resendSecondsLeft(now) > 0 -> stringResource(
        if (needsNewCode) Res.string.auth_code_new_wait else Res.string.auth_code_resend_wait, time)
    needsNewCode -> stringResource(Res.string.auth_code_new)
    else -> stringResource(Res.string.auth_code_resend)
}
```

에뮬레이터에서 "새 인증번호 받기 · 0:42"가 0초가 되자 진한 "새 인증번호 받기"로 바뀌고 눌리는 것을 확인했습니다. 새 번호가 필요해지면 의미가 없어지는 인증번호 남은 시간은 숨겨, 화면에 두 개의 숫자가 동시에 줄어들지 않게 했습니다.

두 상황은 실서버에서 일부러 만들기 어렵고 메일도 실제로 발송됩니다. 그래서 PC에 일부 API만 가짜로 답하는 로컬 프록시를 띄워, 인증번호 발송은 202, 확인은 항상 410으로 답하게 하고 화면을 확인했습니다.

## 체크리스트와 제출 검사는 같은 함수를 본다

비밀번호 입력칸 아래에는 조건 체크리스트가 있습니다. 체크리스트와 제출 가능 여부를 따로 구현하면 "다 체크됐는데 제출이 막힘" 같은 어긋남이 생기기 쉽습니다. 조건별 판정을 `PasswordRule.checks(password)` 하나로 만들었습니다. 체크리스트는 이 함수가 돌려준 조건 집합을 그리고, 제출 검사는 "네 조건 모두 충족 + 128자 이하"를 봅니다.

- 판정 세부도 서버와 맞췄습니다. 한글은 영문으로 세지 않고, 공백은 특수문자로 세지 않습니다.
- 화면에 없는 규칙인 128자 제한은 체크리스트가 모두 켜져도 걸릴 수 있으니 별도 오류 문구로 알립니다. `"a1!" + "x".repeat(126)`(129자)는 네 칸이 모두 체크되지만 길이 오류가 나는 것을 테스트로 고정했습니다.
- 긴 붙여넣기를 128자로 잘라 맞추지 않았습니다. 비밀번호 관리자에 저장된 값과 달라져 다음 로그인이 실패하기 때문입니다.

조건을 덜 채운 상태로 제출하면 문장 오류를 따로 띄우지 않고 체크리스트의 남은 항목을 강조합니다. 같은 정보를 두 번 쓰지 않기 위해서입니다.

## 글자 수 제한은 상태를 바꾸는 쪽에서 막는다

닉네임은 10자까지입니다. 문자열 상태를 쓰는 Compose 입력칸에는 길이 제한 속성이 없고, 새 문자열 전체만 넘겨줍니다. 어디에 글자를 끼워 넣었는지 모르므로 `take(10)`만 하면 가운데에 입력했을 때 끝 글자가 지워집니다.

ViewModel에서 이전 값과 비교해 걸렀습니다.

```kotlin
fun limit(previous: String, input: String): String {
    if (input.length <= MAX_LENGTH) return input
    if (previous.length >= MAX_LENGTH && input.length > previous.length) return previous
    val end = if (input[MAX_LENGTH - 1].isHighSurrogate()) MAX_LENGTH - 1 else MAX_LENGTH
    return input.substring(0, end)
}
```

이미 10자인 칸에 더 입력하면 이전 값을 유지하고, 붙여넣기처럼 한 번에 넘친 경우에만 앞 10자를 남깁니다. 자를 위치가 이모지의 앞 절반이면 한 칸 덜 잘라 글자가 깨지지 않게 했습니다. 세는 기준은 서버와 같은 `String.length`입니다. 앱만 코드 포인트로 세면 이모지 닉네임이 서버에서 거절됩니다. 입력을 막더라도 제출 직전의 길이 검사는 그대로 남겼습니다.

에뮬레이터에서 영문 15자를 입력하자 `abcdefghij`만 남고 카운터가 `10/10`이 됐습니다. adb 입력은 한 글자씩 보내는 방식이라 실제 붙여넣기와 한글 조합의 10자 경계는 이 작업에서 확인하지 못했습니다.

## 앱 검사와 서버 판단의 경계

로그인 화면에도 같은 기준을 적용했습니다. 빈칸과 이메일 형식처럼 입력만 보고 틀린 줄 아는 것은 요청 전에 막습니다. 빈 이메일로 로그인을 누르면 서버 호출 없이 "이메일을 입력해 주세요."만 보입니다. 계정이 있는지, 비밀번호가 맞는지는 서버에 맡깁니다. 로그인에는 가입용 비밀번호 규칙(8자 이상 등)을 걸지 않았습니다. 앱 검사는 빠른 안내를 위한 것이고, 같은 규칙은 서버가 다시 검사합니다.

회원가입 화면에서 지킨 원칙은 두 가지입니다. 서버가 정한 규칙은 앱에서 한곳에만 두고, 서버 응답이 말해 주지 않는 원인은 앱이 아는 사실로만 나눕니다. 같은 비밀번호 규칙을 쓰는 마이페이지 비밀번호 변경 화면에는 체크리스트를 아직 적용하지 않았습니다.
