화면을 고칠 때 가장 오래 걸리는 일은 코드를 바꾸는 일보다 그 화면을 다시 띄우는 일일 때가 많습니다. 인증번호가 시간이 남았는데도 410을 받는 상황, 녹음 직후에만 보이는 결과 화면, 실서버에서 거의 나오지 않는 악보 모양, 한 프레임만 보이는 깜빡임이 그랬습니다.

얼쑤 프론트엔드에서 이런 상태를 재현할 때 쓴 네 가지 방법을 정리합니다. 각 방법은 확인을 마친 뒤 되돌리는 절차까지 함께 정했습니다.

## 1. 일부 API만 가짜로 답하는 로컬 프록시

인증번호 확인 응답이 410일 때의 안내와 재발송 대기를 확인해야 했습니다. 실서버에서 이 응답을 일부러 만들기는 어렵고, 인증번호를 요청할 때마다 실제 메일도 발송됩니다.

PC에 작은 프록시를 띄워 필요한 API만 가로챘습니다.

- 인증번호 발송(`POST /api/auth/email-verifications`)은 메일 없이 `202`로 답합니다.
- 인증번호 확인(`.../{id}/confirm`)은 항상 `410`으로 답합니다.
- 약관 조회 같은 나머지 요청은 그대로 운영 서버로 넘겨, 앞 화면들은 평소처럼 지나갑니다.

디버그 빌드는 빌드 속성 `-Peolssu.debugApiBaseUrl=http://<loopback 주소>:<포트>`로 PC 자신을 가리키는 loopback 주소만 받도록 되어 있고, release 빌드는 이 값을 무시합니다. 에뮬레이터에서 PC의 loopback 주소에 닿도록 `adb -s <기기> reverse tcp:<포트> tcp:<포트>`를 걸었습니다. 앱 코드를 바꾸지 않으므로 지울 임시 코드가 없습니다. 끝나면 프록시를 끄고 `adb reverse --remove`를 실행한 뒤 일반 빌드를 다시 설치합니다.

주의할 점은 응답 모양입니다. 가로챈 응답이 앱이 읽는 공통 형식(`{isSuccess, code, result}`)과 다르면 앱은 서버를 쓸 수 없는 상태로 처리해 엉뚱한 화면이 나옵니다. 그래서 앱 DTO의 필드를 코드에서 확인하고 응답을 만들었습니다. 기기가 여러 대 연결돼 있으면 `installDebug`가 모든 기기에 설치하므로 `adb -s`로 대상 기기를 지정했습니다.

## 2. 커밋하지 않는 딥링크 훅

녹음을 마친 직후의 결과 화면은 앱 안에서 바로 갈 길이 없습니다. 확인하려면 매번 연주하고 분석을 기다려야 합니다.

앱이 이미 받고 있는 링크 수신부(간편 로그인 복귀 주소)에 임시 분기를 한 줄 넣었습니다. 링크에 `debugResult=<id>`가 있으면 결과 화면 경로로 이동합니다. 필요한 기록 ID는 기존 화면 경로에 임시 로그를 넣어 logcat에서 얻었습니다. 그다음 `am start`로 링크를 열었습니다.

```sh
adb shell am force-stop <패키지>
adb shell am start -a android.intent.action.VIEW \
  -d "<앱이 받는 복귀 주소>?debugResult=<기록 ID>" <패키지>
```

앱이 떠 있으면 링크가 닿지 않을 수 있어 강제 종료한 뒤 콜드 스타트로 열었습니다. 빌드한 직후 소스를 되돌리고, 최종 테스트와 빌드는 훅을 뺀 코드로 다시 실행했습니다. 훅이 든 빌드는 기기에 남으므로 확인이 끝나면 정상 빌드로 다시 설치합니다. 이미 저장된 기록을 녹음 직후 화면으로 연 것이라 "기록 저장" 같은 동작은 실제 흐름과 다를 수 있습니다. 그런 동작은 이 방법으로 판정하지 않았습니다.

## 3. Screen에 예시 상태를 넣는 임시 웹 미리보기

화면 코드는 `Route`와 `Screen`으로 나뉘어 있습니다. `Screen`은 `UiState`와 동작 묶음만 받으므로 ViewModel, 의존성 주입, API 없이도 그릴 수 있습니다.

웹 진입점 `App()` 맨 앞에 "주소의 해시가 `#wp…`로 시작하면 미리보기 composable을 그리고 끝낸다"는 한 줄을 임시로 넣었습니다. 예시 데이터에는 실서버에서 만들기 어려운 경우를 일부러 넣었습니다. 구간 반복 화면에 3분할 정간과 오류 다섯 종류를 넣자 율명이 잘리는 문제가 재현됐고, 고친 뒤 같은 주소에서 결과를 확인했습니다.

- `App()`은 해시를 처음에 한 번만 읽으므로, 다른 미리보기로 바꿀 때는 해시를 바꾼 뒤 페이지를 새로고침해야 합니다.
- 웹 쪽 임시 파일도 웹 테스트 묶음에 포함됩니다. 검증을 실행하기 전에 미리보기 파일과 한 줄을 지웠습니다.
- 웹 글꼴은 일부 드문 한자(예: 하배중 㣡)를 □로 그립니다. 글꼴에 관한 판단은 실기기에서 다시 확인했습니다.

## 4. 녹화 영상을 브라우저 canvas로 프레임별로 보기

연주 평가에 들어갈 때 악보가 한 번 줄어드는 깜빡임은 스크린샷으로는 잡히지 않았습니다. 화면을 녹화했지만 PC에 영상 도구가 없었습니다.

브라우저의 `video` 요소로 원하는 시각으로 이동하고, `seeked` 이벤트를 기다린 뒤 canvas에 그렸습니다. 휴대폰 화면 부분만 잘라 여러 장을 나란히 그리면 작은 크기에서도 글자를 읽을 수 있습니다.

```js
for (const t of times) {
  await new Promise(r => { v.onseeked = r; v.currentTime = t; });
  ctx.drawImage(v, 60, 60, 700, 1500, 0, 0, c.width, c.height);
}
```

0.6~1.0초를 0.04초 간격으로 그려, 로딩 화면과 카운트다운 사이에 연습 준비 배치가 한 프레임 끼어 있는 것을 찾았습니다. 로컬 파일을 직접 열면 스크립트가 막힐 수 있어 영상 폴더를 `python -m http.server`로 띄웠습니다. 탐색 위치는 가까운 프레임으로 맞춰지므로, 녹화 프레임 간격보다 촘촘히 잡으면 같은 장면이 반복될 수 있습니다.

## 정리

네 방법은 확인하려는 대상만 바꾸고 나머지는 실제 환경을 그대로 쓴다는 점이 같습니다. 프록시는 API 두 개만, 딥링크 훅은 진입 경로만, 웹 미리보기는 상태만 바꿉니다. 대신 바꾼 부분으로 확인한 결과는 그 범위 안에서만 판단했습니다. 가짜 응답으로 본 화면을 실서버 동작 확인으로, 웹 미리보기로 본 글꼴을 실기기 확인으로 기록하지 않았습니다.
