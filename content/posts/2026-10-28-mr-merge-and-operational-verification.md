새 약관 API를 운영에서 호출해 HTTP 200을 받는 것이 한 작업의 완료 조건이었습니다. MR이 병합되자 Jira는 작업을 완료로 표시했습니다. 같은 시점에 운영 API는 **404**를 반환했습니다. 컨테이너가 시작한 시각과 실행 중인 JAR을 확인하니 이전 버전이 아직 요청을 받고 있었습니다. 병합 결과와 운영 응답은 서로 다른 증거였습니다.

## 자동 종료가 가리키는 작업을 확인했다

저희 프로젝트는 MR이 병합되면 연결된 작업을 완료로 전환했습니다. 약관 사례에서는 배포 이력과 운영 응답을 계속 확인했고, 새 버전이 올라간 뒤 약관 API의 **200** 응답을 확인했습니다. 작업 목록의 상태만 읽었으면 404가 나오는 동안에도 운영 확인이 끝난 것으로 보였을 겁니다.

반대로 문서 참조만 고친 MR에서는 다른 작업에 남은 실기기 확인을 유지해야 했습니다. 이 프로젝트에서는 닫는 문구가 없어도 제목이나 본문에 전체 작업 키가 들어가면 자동화의 대상이 될 수 있었습니다. 문서 MR에는 계속 진행할 작업의 전체 키가 들어가지 않도록 참조 표기를 정리했고, 병합 뒤 실기기 점검 작업을 다시 읽어 진행 중임을 확인했습니다. 확인 범위는 당시 프로젝트의 자동화와 그 작업의 상태입니다.

## 편집 화면에 나타난 문구와 실제 상태를 나눠 본다

한 MR에서 미리 입력한 설명 아래에 양식이 닫는 문구를 더 붙였습니다. 편집 화면에서 같은 참조가 **두 줄**이었고, 텍스트 편집 모드로 설명을 다시 넣어 **한 줄**로 맞췄습니다. 이때 남은 기록은 편집 화면의 문구까지입니다. 저장된 설명을 다시 읽는 절차를 두면 편집 과정에서 추가된 종료 참조도 발견할 수 있습니다. MR을 API로 만드는 흐름이라면 생성 응답 뒤에 같은 MR을 다시 조회하는 방식으로도 이 확인을 할 수 있습니다. [GitLab MR 조회 문서](https://docs.gitlab.com/api/merge_requests/#retrieve-a-merge-request)

MR이 없는 운영 설정 작업에서는 반대로 자동 종료에 기대지 않았습니다. 인증 메일 설정을 바꾼 뒤 요청 응답과 실제 받은편지함의 수신을 확인해 결과를 남겼습니다. 확인을 마친 뒤에 작업을 직접 완료로 전환했습니다. 병합 여부는 MR에서, 작업의 완료 조건은 그 조건이 요구하는 응답이나 사용자 결과에서 확인했습니다.
