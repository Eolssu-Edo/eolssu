얼쑤의 연습 화면은 남은 높이에 맞춰 정간보의 크기와 줄 수를 계산합니다. 그래서 화면 아래쪽 요소가 조금만 커져도 악보가 다시 배치됩니다. 연주하면서 악보를 따라 읽는 사용자에게는 이 작은 움직임도 읽던 위치를 놓치게 만드는 흔들림입니다.

이 글에서는 화면이 덜컥거린 네 가지 상황과, 각각 **배치에 쓰는 크기**와 **그리는 모습**을 어떻게 나눴는지 정리합니다.

## 1. 조건부 안내는 자리를 미리 잡아 둔다

연주 중 소리가 들어오지 않으면 하단에 입력 없음 안내가 나타납니다. 안내가 생길 때 하단 영역이 커지면 악보에 남는 높이가 줄어 악보가 다시 계산됩니다.

그래서 안내를 항상 배치하고, 보여 줄 필요가 없을 때는 투명하게 그렸습니다. 문구가 여러 줄로 감겨도 실제 크기만큼 자리가 잡히므로 경고 전후에 악보가 받는 공간이 같습니다. 이때 투명하게 만든다고 접근성 정보까지 사라지지는 않습니다. 보이지 않는 안내를 화면 읽기 도구가 읽지 않도록 의미 정보도 함께 지웠습니다.

영역 전체가 새로 생기는 경우에도 같은 방법을 썼습니다. 평가 연주의 카운트다운 동안에는 연주 중 하단 막대를 투명하게 먼저 그려 높이를 맞추고, 그 위 가운데에 `준비`만 겹쳤습니다. 카운트다운 뒤 연주가 시작돼도 악보는 같은 자리에 있습니다.

```kotlin
// 연주 중 막대를 보이지 않게 그려 자리만 잡고, 그 위에 '준비'를 겹친다
Box(Modifier.alpha(0f).clearAndSetSemantics {}) { RecordingBarContent(state, actions, stacked) }
```

## 2. 잠깐 보이는 장식은 배치 밖에서 겹쳐 그린다

이전 연주와 비교하는 화면에 점수가 오르면 `+40점!` 도장이 찍혔다가 사라지는 효과를 넣은 적이 있습니다. 도장을 일반 자식으로 두자, 도장이 사라질 때 아래 정간보가 위로 올라왔습니다. 도장의 높이가 부모 크기 계산에 들어갔기 때문입니다.

도장은 `matchParentSize()`로 만든 겹침 칸 안으로 옮겼습니다. 이 자식은 부모 크기 계산에 참여하지 않고 부모 크기를 따라가기만 합니다. 그 안에서 `wrapContentSize(unbounded = true)`를 쓰면 도장이 부모보다 커도 잘리지 않습니다. 크기와 투명도는 `graphicsLayer`의 scale과 alpha로 바꿔 배치를 다시 계산하지 않게 했습니다.

```kotlin
Box(Modifier.fillMaxWidth()) {
    Column { /* 점수·범례 */ }
    Box(Modifier.matchParentSize(), contentAlignment = Alignment.CenterEnd) {
        ScoreStampBurst(label, key, Modifier.wrapContentSize(unbounded = true))
    }
}
```

겹쳐 그리면 다른 요소를 가릴 수 있습니다. 처음에 화면 위쪽에 둔 도장은 '이번' 카드의 날짜를 가려서 오른쪽 가운데로 옮겼습니다. 이 도장은 이후 비교 화면을 다시 디자인하면서 빠졌지만, 겹침 칸을 쓰는 방법은 다른 일시적 표시에도 그대로 쓸 수 있습니다.

## 3. 한 요소만 옮길 때는 offset을 쓴다

뒤로 가기 버튼의 원 테두리를 없애자 꺽쇠가 안쪽으로 들어가 보였습니다. 버튼을 왼쪽으로 4dp 옮기고 싶었지만, `padding`을 바꾸면 버튼이 차지하는 폭이 달라져 옆의 제목까지 움직입니다.

`Modifier.offset`은 측정된 크기와 부모가 정한 자리를 그대로 둔 채, 그리는 위치와 터치 영역만 옮깁니다. 버튼에 `.offset(x = (-4).dp)`를 붙이자 제목과 오른쪽 칸은 그대로 있고 버튼만 옮겨졌습니다. 에뮬레이터 캡처에서도 버튼 왼쪽 끝이 약 10px, 즉 4dp만큼 옮겨진 것을 확인했습니다.

| 바꾸는 것 | 이웃에 미치는 영향 |
| --- | --- |
| `padding`, `Spacer` | 크기나 간격이 바뀌어 이웃이 밀립니다 |
| `offset` | 자리는 그대로라 이웃이 움직이지 않고, 대신 겹칠 수 있습니다 |

## 4. 효과로 바꾸는 상태는 첫 프레임에 이미 보인다

곡 정보에서 `연주 평가 시작`으로 들어오면, 곡을 불러온 뒤 첫 프레임은 연습 준비 상태였고 `LaunchedEffect`가 상태를 카운트다운으로 바꿨습니다. 두 상태의 하단 배치가 달라서 그 사이에 악보가 한 번 줄어들었습니다.

`LaunchedEffect`는 컴포지션이 적용된 뒤에 실행되므로, 그 안에서 바꾼 상태는 다음 프레임부터 보입니다. 이렇게 짧은 변화는 스크린샷 몇 장으로는 잡히지 않아서, 녹화 영상을 프레임 단위로 나눠 0.76~0.8초 사이에 끼어 있는 한 프레임을 찾았습니다.

효과를 더 앞당기는 대신, 화면 상태가 진입 목적을 알게 했습니다. 지금은 연주 평가로 들어오면 처음부터 시작 대기 상태(`awaitingStart`)가 되고, 이 상태의 하단은 연주 중 막대와 같은 자리를 씁니다. `평가 시작`을 눌러 카운트다운과 녹음으로 넘어가도 악보 배치가 바뀌지 않습니다. 상태를 ViewModel을 만들 때 곧바로 카운트다운으로 바꾸는 방법은 쓰지 않았습니다. 마이크 권한 확인과 로딩 실패 분기를 건너뛸 수 있기 때문입니다.

## 정리

네 경우 모두 "보이는가"와 "자리를 차지하는가"를 따로 정했습니다.

- 나타났다 사라지는 안내는 자리를 미리 잡고 투명도만 바꿉니다.
- 잠깐 보이는 장식은 자리를 차지하지 않는 겹침 칸에 그립니다.
- 한 요소만 옮길 때는 자리를 두고 그리는 위치만 옮깁니다.
- 곧 바뀔 상태는 첫 프레임부터 최종 배치로 그립니다.

입력 없음 안내가 켜지는 순간과 투명한 안내를 화면 읽기 도구가 건너뛰는 동작은 당시 에뮬레이터에서 직접 확인하지 못했습니다. 이 두 가지는 실기기 접근성 검증 범위로 남아 있습니다.
