다음 작업을 고르려고 `coco-start`를 호출했을 때 테스트와 병합 미리보기까지 이어졌습니다. 답변까지 147초가 걸렸지만, 사용자가 원한 결과는 다음 작업 경로였습니다. 1.0.0을 준비하며 한 사용자의 Claude Code 호출 11건을 살펴봤습니다. 요청에 필요한 확인과 스킬이 덧붙인 절차를 구분해야, 오래 걸리는 이유를 찾고 필요한 검사도 지킬 수 있었습니다. [대기 시간 진단](https://github.com/thisis-joe/skills/blob/v1.0.0/docs/evaluation/latency/README.md)

## 시작 안내에 필요한 작업만 {#지금-받은-요청만-처리하게-만들다}

`coco-start`에 구체적인 작업 없이 도움을 요청한 경우에는 경로를 안내하는 데 필요한 사실만 확인하도록 바꿨습니다. 검증이나 배포 점검이 필요한 경우에도 변경이 미치는 영향에 맞춰 절차를 골랐습니다. 예를 들어 마이그레이션은 수정 줄 수가 적어도 실제 실행 검사가 필요한 변경으로 다뤘습니다.

같은 예제에서 조정 전후를 한 번씩 실행했을 때, 시작 안내는 87초에서 51초로 줄었습니다. 마이그레이션이 포함된 출시 점검은 144초에서 98초로 줄었고, 두 실행 모두 실제 실행에서 실패를 찾아 출시를 보류했습니다. 반면 간단한 문구 수정이나 리뷰 예제에서는 시간이 줄지 않았습니다. 스킬 파일을 직접 읽게 한 단회 비교였으므로, 실제 팀 사용 시간이나 릴리스 간 평균으로 해석하기는 어렵습니다. [재측정 결과와 조건](https://github.com/thisis-joe/skills/blob/v1.0.0/docs/evaluation/latency/results.md)

## 프로젝트별 설치 범위 {#설치-범위도-프로젝트에-맞춰-고르다}

1.0.0에서는 프로젝트에만 스킬을 설치하거나, 모든 프로젝트에 공통으로 설치하는 방식을 명시적으로 선택할 수 있게 했습니다. Codex와 Claude Code는 각자의 설치 경로를 사용하고, 설치·업데이트·제거 중 직접 수정한 파일이나 다른 스킬과 충돌하면 작업을 멈춥니다. 스킬 29개를 묶어 배포하면서, 필요한 프로젝트에서 사용 범위를 고를 수 있도록 한 변경입니다. [1.0.0 설치 안내](https://github.com/thisis-joe/skills/blob/v1.0.0/docs/distribution.md)

실행할 범위를 좁히면 다음 질문이 남습니다. 기능의 동작을 결정할 때 에이전트가 직접 확인해도 되는 사실과 사람에게 물어야 하는 선택은 어떻게 가를까요? 1.1.0에서는 그 구분을 개발 절차에 넣었습니다.
