얼쑤의 빌드 서버에는 Jenkins 실행 자리(executor)가 하나뿐이었습니다. 백엔드 잡과 웹 수동 배포 잡이 모두 `agent any`였기 때문에, 백엔드 빌드가 도는 동안 웹 배포는 대기열에서 기다려야 했습니다. 이 대기가 빌드 시간에서 얼마나 차지했는지는 [Jenkins Wasm 최적화 956초에서 237초로](https://team-edo.github.io/posts/2026/11/jenkins-wasm-build-bottleneck/)에서 측정했습니다. 웹 배포에만 자리를 보장하려고 전용 노드를 추가했는데, 그 노드의 첫 빌드가 중간에 끊겼습니다. 이 글은 자리를 나눈 방식과, 끊긴 빌드의 원인을 찾은 과정을 정리합니다.

## executor를 늘리지 않고 전용 노드를 둔 이유

가장 쉬운 방법은 기존 노드의 executor를 2개로 늘리는 것입니다. 하지만 늘어난 자리는 `agent any`인 잡이라면 무엇이든 가져갈 수 있습니다. 백엔드 잡 두 개가 두 자리를 모두 차지하면 웹 잡은 다시 기다리게 되고, 원하지 않던 백엔드 빌드끼리의 병행까지 열립니다.

Jenkins 노드를 **EXCLUSIVE** 모드로 두면 그 노드의 라벨을 지정한 잡만 받습니다. 그래서 같은 서버에 Jenkins 에이전트 프로세스를 하나 더 띄워 웹 전용 노드로 등록했습니다. 블로그 빌드용으로 이미 쓰던 방식과 같습니다.

| 항목 | 정리 |
| --- | --- |
| 실행 | 별도 systemd 서비스로 에이전트를 하나 더 실행 |
| 작업 공간 | 기존 노드와 분리된 전용 폴더 |
| 인증 | 노드 전용 secret |
| 잡 연결 | 웹 Pipeline만 `agent { label '<웹 전용 라벨>' }`로 변경 |

실제 운영 배포가 동시에 일어나지 않게 막는 일은 실행 자리와 별개입니다. 이 부분은 기존 배포 도구의 공유 lock이 계속 맡습니다. 같은 서버라 CPU는 나눠 쓰므로, 두 빌드가 겹치면 각각 느려질 수 있다는 점도 감수했습니다. 작업 공간이 새로 생기기 때문에 전환 뒤 첫 빌드는 프로젝트 캐시 없이 시작해 오래 걸린다는 점도 미리 고려했습니다.

적용하면서 두 가지에 걸렸습니다.

- 웹 잡은 Pipeline 정의가 잡 설정 안에 들어 있었습니다. 저장소의 Jenkinsfile만 고쳐서는 적용되지 않아 잡 설정도 함께 바꿨습니다.
- 노드 secret을 Jenkins CLI의 `groovy` 명령으로 받을 때, 웹 스크립트 콘솔과 달리 `Jenkins` 클래스를 자동으로 가져오지 않아 `MissingPropertyException`이 났습니다. `jenkins.model.Jenkins`로 전체 이름을 써야 했습니다. 또 줄바꿈 없는 `print`는 오류 없이 끝났지만 저장된 파일 크기가 0이었습니다. CLI가 줄바꿈으로 끝나지 않은 마지막 출력을 내보내지 않은 것으로 추정합니다. `println`으로 출력하고 받는 쪽에서 줄바꿈을 지우자 secret이 저장되고 에이전트가 연결됐습니다. 셸의 `> 파일` 리다이렉트는 명령이 실패해도 빈 파일을 만든다는 점도 함께 기억해 둘 만합니다. 오류가 없다는 것만으로 성공이라 보지 않고, 값을 화면에 띄우지 않은 채 파일 크기와 연결 로그로 확인했습니다.

## 첫 빌드가 wasm-opt 도중 끊겼다

11월 11일, 전용 노드에서 시작한 첫 웹 빌드는 Wasm 최적화(`wasm-opt`) 도중 `exit code -1`로 끊겼습니다. 최적화 단계는 메모리를 많이 쓰기 때문에 처음에는 메모리 부족을 의심했습니다.

그런데 커널 OOM 기록이 없었습니다. 에이전트 서비스의 종료 상태는 143이었고, 로그에는 systemd의 `Stopping ...`이 먼저 찍혀 있었습니다.

- 메모리 부족으로 강제 종료됐다면 systemd에는 `code=killed`로 남습니다.
- 143은 SIGTERM을 받고 끝났다는 뜻입니다.
- `Stopping`이 먼저 찍혔다면 프로세스가 혼자 죽은 것이 아니라 systemd가 서비스를 멈춘 것입니다.

그렇다면 누가 서비스를 멈췄는지가 문제였습니다. 재시작 시각 앞뒤의 전체 journal과 `/var/log/apt/history.log`를 나란히 놓고 보니 시각이 맞았습니다.

| 시각 (UTC) | 일 |
| --- | --- |
| 06:33:00 | Ubuntu 자동 보안 업데이트(unattended-upgrade)가 OpenJDK 21을 올림 |
| 06:33:08 | `/usr/bin/java`로 도는 Jenkins 에이전트 3개가 동시에 재시작됨 |

자동 업데이트는 패키지를 올린 뒤 **needrestart**로 옛 실행 파일·라이브러리를 아직 쓰는 서비스를 찾아 재시작합니다. Java가 바뀌었으니 Java로 도는 에이전트가 모두 대상이 됐고, systemd가 서비스를 멈추면서 그 안에서 돌던 빌드 명령도 함께 종료됐습니다. Docker 컨테이너 안의 Java로 도는 Jenkins 컨트롤러는 호스트 패키지와 무관해서 재시작되지 않았습니다.

같은 시각에 돌던 빌드라도 그 순간 실행 중인 명령이 없던 단계였다면 살아남을 수 있습니다. 그래서 "다른 빌드는 멀쩡했다"는 이유만으로 이 원인을 제외하지 않았습니다.

## 다시 실행한 결과

다시 실행한 웹 빌드는 전용 노드에서 checkout, 배포 도구 테스트, JS/Wasm 브라우저 테스트, 최적화(6분 25초), 이미지 생성, 아티팩트 보관까지 통과했습니다. 마지막 배포 단계는 그사이 운영에 더 새 버전이 배포돼 있어서 `candidate is older than the deployed release`로 거부됐습니다. 오래된 소스가 운영을 덮어쓰지 않도록 둔 배포 순서 검사가 의도대로 동작한 결과입니다.

## 남은 일

- **동시 실행 관찰:** 백엔드 빌드가 도는 동안 웹 잡이 대기 없이 시작하는지는 아직 따로 관찰하지 않았습니다.
- **재발 방지:** needrestart가 빌드 에이전트를 재시작하지 않게 하는 조치는 아직 적용하지 않았고, 별도 작업으로 남겨 두었습니다. 빌드 서비스를 needrestart 대상에서 빼면, 새 Java는 사람이 빌드가 없는 시간에 재시작해야 적용된다는 비용이 생깁니다.

빌드가 이유 없이 끊겼을 때는 먼저 종료 상태와 systemd 로그로 "혼자 죽었는지, 누가 멈췄는지"를 가르고, 멈춘 시각 앞뒤의 패키지 관리 기록을 함께 보는 것이 빨랐습니다.
