얼쑤는 Compose Multiplatform으로 Android, iOS, 웹 화면을 한 코드에서 만듭니다. 화면을 조금씩 고치며 확인할 때는 Android 빌드보다 웹 개발 서버가 빠르고 간편합니다. 하지만 Kotlin/Wasm 개발 루프에는 처음 쓸 때 헷갈리는 지점이 몇 가지 있었습니다.

이 글은 코드를 고친 뒤 브라우저에서 확인하기까지의 루프를 짧게 만든 방법과, 그 과정에서 앱 결함으로 착각하기 쉬운 현상 세 가지를 정리합니다.

## 서버는 켜 두고 CompileSync만 다시 돌린다

`wasmJsBrowserDevelopmentRun`은 "컴파일 → 산출물 폴더에 동기화 → webpack 개발 서버 실행"을 묶은 태스크입니다. 서버 태스크가 Gradle 데몬을 잡은 채 멈춰 있으므로, 코드를 고칠 때마다 서버를 내렸다 올리면 시간이 오래 걸립니다.

webpack 개발 서버는 진입 모듈이 참조하는 `.wasm` 파일을 모듈로 추적합니다. 그래서 그 파일이 바뀌면 다시 번들하고 브라우저에 갱신을 보냅니다. 서버는 그대로 두고, 다른 터미널에서 동기화 태스크만 실행하면 됩니다.

```sh
cd frontend
./gradlew :webApp:wasmJsDevelopmentExecutableCompileSync :webApp:wasmJsProcessResources --max-workers=2
# 끝나면 열려 있는 개발 서버 탭이 스스로 새로고침된다
```

반영 여부는 빌드 성공 메시지보다 산출물 시각으로 판단했습니다. 서빙 중인 `.wasm`의 수정 시각이 소스보다 오래됐다면 아직 반영되지 않은 것입니다. `--continuous`로 띄운 서버가 Kotlin 수정 뒤 5분 넘게 다시 빌드하지 않은 적이 있었습니다. 원인은 찾지 못했고, 이후에는 CompileSync를 직접 실행하는 방법이 더 믿을 만했습니다. 같은 프로젝트에서 데몬 두 개가 동시에 돌면 리소스 태스크가 잠금을 기다릴 수 있습니다. 이번에는 충돌이 없었지만 항상 그렇다고 보장할 수는 없습니다.

## 로컬의 404는 앱 결함이 아니다

웹 빌드는 같은 origin의 `/api`를 호출합니다. 운영에서는 같은 도메인이 앱과 API를 함께 서빙하므로 상대 경로가 맞습니다. 하지만 당시 로컬 webpack 개발 서버에는 정적 파일만 있고 API 프록시가 없었습니다. 그래서 첫 요청인 약관 조회부터 404가 나고, 첫 실행 흐름이 동의 화면의 "다시 시도"에서 멈췄습니다.

화면만 확인할 때는 해시 주소로 바로 이동했습니다. 웹 앱은 브라우저 주소와 내비게이션을 연결하므로, 내비게이션 경로 문자열을 `#` 뒤에 붙이면 그 화면이 바로 열립니다.

```text
<개발 서버 주소>/#home             홈
<개발 서버 주소>/#guide/fingering  운지법 보기
<개발 서버 주소>/#records          연습 기록 (로컬에서는 '불러오지 못했어요')
```

이 방법으로는 홈이나 학습 안내처럼 정적인 화면만 점검할 수 있습니다. 서버 데이터가 필요한 화면은 오류 상태로 보이고, 인자가 필요한 경로는 실제 값이 있어야 열립니다. 해시로 연 화면의 API 오류는 기능 검증 실패로 기록하지 않았습니다. 서버 데이터가 필요한 상태는 예시 상태를 넣은 임시 미리보기나 실제 API가 있는 환경에서 확인했습니다.

## 숨은 패널에서는 애니메이션이 멈춘다

에디터 옆 미리보기 패널에서 웹 화면을 조작하다가, 속도 단계 이름을 여러 번 눌러도 서서히 나타나야 할 BPM 줄이 끝내 보이지 않았습니다. 클릭 물결은 보였기 때문에 코드 문제로 의심했습니다.

웹 Compose는 브라우저의 화면 갱신(`requestAnimationFrame`)에 맞춰 프레임을 그립니다. 패널이 숨겨져 배경 페이지가 되면 브라우저가 프레임 갱신을 멈추거나 늦추고, `animateFloatAsState` 같은 애니메이션이 0에 머문 채 캡처됩니다. 패널을 보이게 한 뒤 다시 누르자 같은 코드에서 `BPM · 기준 60의 80%`가 나타났다가 약 1.8초 뒤 사라졌습니다.

그 뒤로는 애니메이션만 멈춘 것처럼 보이면 코드를 고치기 전에 패널이 보이는 상태인지부터 확인했습니다. 같은 이유로 숨은 패널에서 잰 시간이나 성능 값은 기준으로 쓰지 않습니다.

## Android에서 되는 코드가 Wasm에서만 멈출 때

정간보 배치 코드를 고친 뒤 Android 컴파일은 통과했는데 Wasm 컴파일만 멈췄습니다. 오류는 위치가 표시되는 `e:` 줄이 아니라 컴파일러 내부 예외로 나와서 어디를 고쳐야 할지 알 수 없었습니다.

직전에 넣은 구조 중 흔치 않은 것부터 의심했습니다. Compose `Layout` 측정 람다 안에 지역 `data class`를 선언한 부분이었습니다. 이 클래스를 파일 최상위 `private data class`로 옮기자 Wasm 컴파일이 통과했습니다.

```kotlin
// 전: 측정 람다 안에 선언 — Wasm 백엔드 내부 예외
Layout(content) { m, c -> data class Area(val l: Float, val t: Float); /* ... */ }
// 후: 파일 최상위로 이동
private data class Area(val left: Float, val top: Float, val right: Float, val bottom: Float)
```

인라인되거나 변환되는 람다 안의 지역 클래스를 Wasm 백엔드가 처리하지 못한 것으로 보입니다. 다만 정확한 원인과 버전 조건은 확인하지 않았습니다. 당시 환경은 Kotlin 2.4.20, Compose Multiplatform 1.12.1이었습니다. 이 경험 뒤로는 공통 코드를 바꾸면 Android와 웹 컴파일을 함께 돌립니다.

## 정리

| 현상 | 먼저 확인한 것 |
| --- | --- |
| 고친 코드가 브라우저에 안 보임 | 서빙 중인 `.wasm`의 수정 시각 |
| 첫 화면이 "다시 시도"에서 멈춤 | 로컬 서버에 API가 있는지 |
| 애니메이션만 멈춤 | 미리보기 패널이 보이는 상태인지 |
| Wasm 컴파일만 내부 예외 | 직전에 넣은 흔치 않은 구조 |

웹 개발 서버는 빠르게 화면을 고쳐 보기 좋은 도구입니다. 다만 실행 환경이 운영이나 실기기와 다르므로, 거기서 본 결과가 어디까지 유효한지 함께 적어 두는 편이 안전했습니다.
