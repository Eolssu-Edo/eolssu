# 업로드 악보 원본의 임시 수명주기

- Task: S15P31E102-534. 사용자 확정: 원본 장기 보관 없음, 최대 30분, 성공·실패 시 즉시 삭제. R2 설정은 보류한다.
- 원본용 임시 저장소와 M4A·MIDI용 R2를 분리한다. 입력을 R2에 올렸다가 나중에 삭제하는 방식 대신 backend 임시 파일만 사용한다. 기존 OMR는 HTTP URL을 읽으므로 추측 불가능한 만료 토큰의 내부 읽기 경로를 제공한다. 외부 Nginx는 이 경로를 막고 로그도 끈다.
- 내부 URL은 앱 응답에 넣지 않는다. 원본 페이지·파생 PNG 렌더링도 없애며 과거 결과의 페이지 키도 새 서명 URL로 바꾸지 않는다. 이미 발급된 과거 URL은 만료까지 유효할 수 있다.
- 접수 실패는 시도한 임시 키부터 정리한다. 작업자는 성공·실패·삭제 경합에서 finally로 파일을 지운다. 삭제 실패는 읽기 권한을 먼저 취소한 뒤 다음 정리에서 재시도한다. 만료된 대기·진행 작업은 TIMEOUT, 재시작 시 잃은 작업은 SERVER_ERROR로 끝낸다.
- Spring multipart 임시 파일도 원본이다. 위치를 `eolssu.sheet-import.multipart-directory`로 고정하고 임시 저장소가 만든다. 파일명을 컨테이너가 정하므로 1초 주기 정리가 처음 본 시각부터 30분을 세고, 정상 요청은 컨테이너가 요청 종료 시 지운다. 이 정리는 DB 정리와 따로 돌아 DB가 막혀도 늦어지지 않는다. 실패하면 1분에 한 번 경고 로그를 남기고 다음 주기에 다시 지우며, 폴더가 사라지면 다시 만든다(Tomcat은 만들지 않는다). 두 임시 폴더의 남은 파일은 저장소 Bean을 만들 때 지운다. 웹 서버가 열리기 전이어서 진행 중 요청의 파일을 지우지 않는다. 같은 폴더를 녹음 업로드도 쓰므로 30분 넘게 정체한 녹음 요청은 파일을 잃고 실패한다. 파일이 사라진 SHT-07 요청은 `files`·`metadata` 어느 쪽을 읽다 실패해도 503 `CONVERSION_UNAVAILABLE`이다.
- 대기열 사본은 요청 복사본의 만료를 물려받아 요청이 오래 걸려도 30분을 새로 얻지 않는다. 파일 기한은 요청 복사본을 만든 때부터이고 DB 기한은 접수 시각부터여서 파일이 먼저 끝날 수 있다. 그 사이에 선점된 작업과, 인식기가 만료로 원본을 받지 못한 작업은 TIMEOUT으로 끝낸다. 저장소가 만료 기록을 `delete()`까지 유지해 만료와 파일 소실(SERVER_ERROR)을 구분한다. 요청 복사본의 30분은 컨트롤러 진입 시 시작하므로, multipart 파싱과 컨트롤러 진입 사이가 멈추면 합계가 30분을 넘을 수 있다. 이 구간에 대기 지점이 없어 별도 추적을 두지 않았다. Nginx가 본문을 받는 동안의 임시 파일은 이 정책의 승인된 예외다(2026-11-06 사용자 결정). 요청이 끝나면 지워지지만, 30분 넘게 조금씩 보내는 업로드를 막지는 않는다. 버퍼링을 끄면 느린 업로드가 backend 스레드를 오래 붙잡으므로 끄지 않는다. `client_body_timeout`은 읽기 간격 제한이어서 전체 시간을 제한하지 않는다.
- 업로드 검사에 쓰는 요청 복사본도 같은 비공개 디렉터리에서 추적한다. 요청 종료·30분 만료·재시작 시 삭제한다. OMR의 다운로드·쪽 그림 디렉터리는 종료 시 삭제하고 독립 watchdog이 30분에 삭제한다. 인식 스레드가 멈춰도 watchdog은 동작하며 파일 잠금 등 삭제 실패는 1초 뒤 재시도한다. 운영 OMR `/tmp`는 기존 tmpfs라 컨테이너 재시작 시 폐기된다.
- 원본을 보관하지 않으므로 기존 변환 재시도는 409다. 새 파일·새 멱등 키로 재업로드한다. 같은 키의 멱등 재요청은 기존 상태를 반환하며 원본을 다시 저장하지 않는다. 신규 요청은 시도 차수 1, 과거 차수는 보존한다.
- 검증은 실제 임시 파일과 HTTP·MySQL 경로를 사용한다. 인식 엔진 대역을 쓰는 검사는 데이터 전송·수명주기의 증거이며 실제 OMR 정확도나 앱 기기 E2E의 증거가 아니다.
- 기존 R2 원본의 대량 삭제, 운영 변경, FE API 연결 업무(S15P31E102-532)의 완료 처리는 이 기록으로 수행하지 않는다. 구현·검증 상태는 [534 계획](../../plans/S15P31E102-534.md)에 둔다.
