# 내 악보 음원 작업과 삭제 복구

[S15P31E102-481](https://ssafy.atlassian.net/browse/S15P31E102-481)의 [계약](../../specs/sheet-audio.md)과 [검증 기록](../../plans/S15P31E102-481.md)을 보완한다. 이 기록은 브랜치 구현 기준이며 운영 배포나 실제 R2 업로드 완료를 뜻하지 않는다.

## 삭제 구간의 소유권

`sheet_audios.deleting`만으로는 음원을 요청한 적 없는 악보의 삭제를 표현할 수 없다. 또 두 삭제가 겹친 상태에서 실패한 요청이 공통 표시를 풀면, 다른 삭제가 끝나기 전에 음원 접수가 열릴 수 있다. 그 사이 만든 파일을 마지막 DB 삭제가 참조 없이 남길 위험이 있다.

현재 배포 구성은 backend 한 인스턴스와 순차 음원 작업자다. 이 범위에서 `SheetAudios.beginDeletion`이 악보별 삭제 구간을 소유하고, 컨트롤러가 음원 정리·원본 정리·DB 삭제 전체를 마친 뒤 `finally`에서 해제한다. 소유하지 못한 삭제는 503이며 먼저 시작한 삭제의 DB 표시를 풀지 않는다. 접수의 두 스냅샷 검사도 이 구간을 확인하므로 최초 음원 접수까지 409로 막는다. 외부 파일 삭제 동안 DB 트랜잭션을 유지하지 않는다.

| 대안 | 판단 |
| --- | --- |
| 기존 음원 행의 `deleting`만 사용 | 음원 행이 없는 악보와 동시 삭제를 보호하지 못한다. |
| 파일 삭제 전체를 DB 잠금 안에서 수행 | 외부 저장소 지연 동안 연결과 행 잠금을 점유한다. |
| 단일 backend에서 삭제 구간 소유권 유지 | 현재 실행 범위에 맞고 새 테이블이 필요 없다. 여러 backend 인스턴스로 확장할 때는 이 조정을 공유 저장소의 소유권으로 옮겨야 한다. |

`SheetAudioDatabaseTests`의 `a second deletion cannot release the first deletion while it owns the sheet`, `deleting a sheet without an audio row still blocks its first generation`은 실제 Spring HTTP 요청과 고정 저장소 경계로 이 상황을 검사한다. 수정 전에는 각각 두 번째 삭제가 204로 완료되고 최초 생성이 접수됐다. 보호를 제거하는 별도 복사본 변이에서도 대응 검사가 실패했다.

## 재시작과 생성기 대기

재시작 시 살아 있는 기존 backend 작업자가 없다는 전제에서 RUNNING을 실패 처리하고, 미완료 객체를 삭제 대기 대상으로 옮기며, 남은 `deleting`을 해제한다. 이때 `result_json`도 비워 이미 삭제했거나 삭제 대기인 파일을 다시 서명하지 않는다. 실제 객체 삭제는 트랜잭션 뒤에 수행하고 실패한 키는 목록에 남겨 재시도한다.

생성기의 BUSY 응답은 작업을 QUEUED로 되돌린다. 순차 작업자가 같은 generation의 최초 BUSY 시각을 유지하고 기한을 넘으면 SERVER_ERROR로 끝낸다. 이 시각은 backend 프로세스 안의 상태라 재시작하면 새로 측정한다. 기한은 운영 설정의 전체 생성기 수신 제한에 5분을 더한다(기본 100초 + 5분 = 400초). 고착 RUNNING 검사에도 같은 기한을 쓴다.

일반 실패 로그에는 예외 종류만 남긴다. 저장소 예외의 메시지나 스택에는 객체 키가 들어갈 수 있으므로 예외 객체 자체를 로거에 전달하지 않는다. 관련 검사와 변이는 예외 종류가 남고 객체 키와 throwable이 남지 않는지 확인한다.

## 별도 확인이 필요한 범위

로컬 MySQL·실제 CAT HTTP 합성·S3 서명 구성 검사를 운영 R2의 PUT/GET/DELETE 확인으로 확대하지 않는다. 운영 서버 자원 여유, 음원 생성과 OMR 동시 실행, FE 기기 재생은 배포·연결 단계에서 별도로 확인한다. 재생성 중에는 최근 요청의 버전·설정과 이전 보관 파일이 함께 반환될 수 있으므로 앱은 파일의 최신 여부를 `outdated`로 판단해야 한다.

## 긴 단일 음의 메모리 경계 (2026-11-06)

총 길이가 같아도 짧은 음 여러 개와 긴 음 하나는 합성 메모리 사용이 다르다. 음높이 제어 곡선만 분할하면 긴 음의 샘플 위치·루프 위상·보간 출력 배열이 여전히 전체 길이로 만들어진다. 481 전체 리뷰에서 이 경계를 확인해 음별 65,536프레임 분할로 보완했다. 절대 적분·음량 인덱스를 사용해 위상과 연음의 연속성을 유지하며 분할 전후 PCM과 trace의 동일성을 검사한다.

실제 CAT 단소 단일 음 599초와 장단의 로컬 생성은 1CPU·1GiB·스왑 없음에서 17.594초에 완료됐다. 결과 길이는 599,550ms이고 Python 프로세스 최대 RSS는 603,356KiB다. 컨테이너 전체 메모리 정점이나 운영 서버 동시 부하 측정으로 해석하지 않는다. 검사 결과와 로그 위치는 [481 계획](../../plans/S15P31E102-481.md)의 같은 날짜 기록을 따른다.
