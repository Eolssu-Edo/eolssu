# 리프레시 토큰·이메일 인증번호 저장 방식

- 작업: [S15P31E102-142](https://ssafy.atlassian.net/browse/S15P31E102-142) (V2 스키마), 사용처 [S15P31E102-143](https://ssafy.atlassian.net/browse/S15P31E102-143) (인증·회원 API)
- 근거: Notion API 명세 AUTH-01·03·04·06·07, 회의 A1(토큰, 확정)·A2(인증번호 제한, 결정안)
- 채택한 계약: [DB 스키마](../../contracts/db-schema.md)의 `refresh_tokens`, `email_verifications`

## 결론

리프레시 토큰과 이메일 인증번호는 MySQL(`eolssu`)에 둔다. 원문은 저장하지 않는다. 리프레시 토큰은 SHA-256, 인증번호는 서버 비밀키 HMAC-SHA256으로 저장한다.

## 비교한 대안

| 기준 | Redis | MySQL(채택) |
| --- | --- | --- |
| 현재 인프라 | 없음. 새 컨테이너·백업·모니터링이 필요 | 이미 운영 중이며 Flyway로 관리 |
| 만료 처리 | TTL로 자동 삭제 | `expires_at`으로 판정하고 일괄 처리에서 지움 |
| 재사용 탐지(AUTH-04) | 폐기된 토큰도 기억해야 해 TTL만으로는 부족 | 폐기 행을 남겨 `revoked_at`으로 판정 |
| 회원 변경과 함께 처리 | 별도 저장소라 트랜잭션을 묶을 수 없음 | 비밀번호 변경·탈퇴와 같은 트랜잭션에서 회원 단위 폐기 |
| 조회 비용 | 매우 낮음 | 토큰 해시 유일키 조회 1회. 1차 사용량에서는 충분 |

회의 A1은 "Redis 또는 DB"로 열어 두었다. 1차 MVP에는 Redis가 없고 요청 빈도가 낮아, 저장소를 하나 더 늘리지 않는 쪽을 골랐다. 동시 접속이 늘어 조회가 병목이 되면 측정 후 다시 판단한다.

## 확인된 제약

- **재사용 시 폐기 범위:** AUTH-04는 이미 폐기된 토큰이 다시 오면 그 회원의 리프레시 토큰을 모두 폐기한다. 로그인 묶음(family) 단위가 아니어서 `family_id` 칸은 두지 않았다.
- **인증번호 해시:** 6자리는 경우의 수가 100만이라 솔트 없는 해시는 표를 만들어 바로 되찾을 수 있다. 3분·5회 제한만으로는 DB를 읽을 수 있는 사람을 막지 못하므로, 서버 비밀키가 있어야 계산되는 HMAC을 쓴다.
- **verificationToken·리프레시 토큰:** 임의 256비트 값이라 SHA-256만으로 충분하다. 원문은 응답·쿠키로만 나가고 로그에 남기지 않는다.
- **읽기 계정 노출:** 운영 모니터링 계정은 `eolssu.*` 전체 읽기 권한을 가진다. 해시만 있어도 인증 테이블을 대시보드에 보일 이유가 없으므로 권한을 테이블 단위로 줄이는 안을 인프라와 맞춘다([S15P31E102-142 전달 사항](../../plans/S15P31E102-142.md#인프라-전달-사항우동균)).

## 미확인

- 메일 발송 수단(SMTP·외부 서비스)과 비밀키 보관 위치는 인프라 결정이다.
- 만료·폐기 행을 지우는 주기와 보관 기간은 명세에 없다. 탈퇴 일괄 처리와 같은 배치에서 정리하는 안이다.

## 이메일 인증 구현의 동시성(2026-10-28)

- 새 이메일에는 잠글 행이 없어 `SELECT ... FOR UPDATE`만으로 최초 동시 발송의 간격·횟수를 보장하기 어렵다. 1차 전달 규모(하루 100통 안쪽)에서는 새 테이블 없이 DB별 MySQL named lock 하나로 발송·확인 트랜잭션을 직렬화했다. 이메일 collation에서 같은 식별자로 취급하는 문자열도 한 경계에서 처리한다. 서로 다른 이메일도 직렬화되므로 실제 발송량·지연이 커지면 측정 후 잠금 단위를 재검토한다. 다중 MySQL 서버를 지원하는 분산 잠금으로 보고하지 않는다.
- [MySQL 8.4 locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html): `GET_LOCK`은 연결 소유이며 commit/rollback으로 해제되지 않는다. 같은 연결의 `afterCompletion`에서 `RELEASE_LOCK`을 실행해 커밋 전에 다음 발송이 시작되는 틈을 막는다. 대기는 5초이며 실패 시 503이다.
- 실제 MySQL 8.4·HTTP 검사에서 동일 이메일 첫 요청 8개가 202 한 건·429 일곱 건, 동시 확인 2개가 200·410으로 나뉘었다. 가입 메일 장애 503 뒤 이전 코드 확인이 성공해 롤백·잠금 해제를 함께 확인했다. 실패 확인은 예외를 던지는 대신 결과 값으로 반환해 오답 횟수가 커밋되게 했다.
- PASSWORD_RESET의 메일 장애는 사용자 합의로 202를 유지한다. 미발송 행에는 임의 256비트 문자열의 HMAC을 저장해 정상적인 6자리 입력으로 확인할 수 없게 하고, 응답·횟수·남은 시도 처리에서 회원 여부를 드러내지 않는다. 실제 메일 어댑터 검증은 포함하지 않는다. 상세 정책·검증 명령은 [143 계획](../../plans/S15P31E102-143.md#3단계-작업-기록2026-10-28)에 둔다.
