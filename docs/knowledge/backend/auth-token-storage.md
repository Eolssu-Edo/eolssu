# 리프레시 토큰·이메일 인증번호 저장 방식

- 작업: [S15P31E102-142](https://ssafy.atlassian.net/browse/S15P31E102-142) (V2 스키마), 사용처 [S15P31E102-143](https://ssafy.atlassian.net/browse/S15P31E102-143) (인증·회원 API)
- 근거: Notion API 명세 AUTH-01·03·04·06·07, 회의 A1(토큰, 확정)·A2(인증번호 제한, 결정안)
- 채택한 계약: [DB 스키마](../../contracts/db-schema.md)의 `refresh_tokens`, `email_verifications`

## 결론

리프레시 토큰과 이메일 인증번호는 MySQL(`eolssu`)에 둔다. 원문은 저장하지 않는다. 리프레시 토큰은 SHA-256, 인증번호는 서버 비밀키 HMAC-SHA256으로 저장한다.

## 비교한 대안

| 기준 | Redis | MySQL(채택) |
| --- | --- | --- |
| 현재 인프라 | 없음. 새 컨테이너·백업·모니터링이 필요 | 이미 운영 중이며 Flyway로 관리 |
| 만료 처리 | TTL로 자동 삭제 | `expires_at`으로 판정하고 일괄 처리에서 지움 |
| 재사용 탐지(AUTH-04) | 폐기된 토큰도 기억해야 해 TTL만으로는 부족 | 폐기 행을 남겨 `revoked_at`으로 판정 |
| 회원 변경과 함께 처리 | 별도 저장소라 트랜잭션을 묶을 수 없음 | 비밀번호 변경·탈퇴와 같은 트랜잭션에서 회원 단위 폐기 |
| 조회 비용 | 매우 낮음 | 토큰 해시 유일키 조회 1회. 1차 사용량에서는 충분 |

회의 A1은 "Redis 또는 DB"로 열어 두었다. 1차 MVP에는 Redis가 없고 요청 빈도가 낮아, 저장소를 하나 더 늘리지 않는 쪽을 골랐다. 동시 접속이 늘어 조회가 병목이 되면 측정 후 다시 판단한다.

## 확인된 제약

- **재사용 시 폐기 범위:** AUTH-04는 재발급으로 폐기된(`ROTATED`) 토큰이 다시 오면 그 회원의 리프레시 토큰을 모두 폐기한다. 비밀번호 변경·로그아웃·탈퇴로 폐기된 토큰은 다른 기기에 남은 정상 토큰일 수 있어 401만 준다(2026-10-28, [S15P31E102-208](../../plans/S15P31E102-208.md)). 로그인 묶음(family) 단위가 아니어서 `family_id` 칸은 두지 않았다.
- **잠금 순서:** `users`와 `refresh_tokens`를 함께 다루는 흐름은 `users` 행을 먼저 잠근다. 새 토큰 INSERT가 외래 키로 `users` 행을 잠그므로, 순서가 어긋나면 동시 요청이 교착으로 500이 된다(208 DB 검사로 재현). 현재 로그인·가입·비밀번호 변경·재발급이 이 순서이고, 로그아웃은 `refresh_tokens`만 잠근다. 앞으로 만드는 탈퇴·일괄 삭제(S15P31E102-209)·계정 연결도 이 순서를 지킨다.
- **비밀번호 변경 뒤 access_token:** access_token은 서버에 저장하지 않는 JWT라, 비밀번호를 바꾸거나 로그아웃해도 이미 발급된 것은 만료(최대 30분)까지 쓸 수 있다. 리프레시 토큰만 즉시 폐기된다. 1차는 이 한계를 받아들이고, 즉시 끊어야 하면 회원별 토큰 기준 시각을 두는 안을 다시 본다.
- **인증번호 해시:** 6자리는 경우의 수가 100만이라 솔트 없는 해시는 표를 만들어 바로 되찾을 수 있다. 3분·5회 제한만으로는 DB를 읽을 수 있는 사람을 막지 못하므로, 서버 비밀키가 있어야 계산되는 HMAC을 쓴다.
- **verificationToken·리프레시 토큰:** 임의 256비트 값이라 SHA-256만으로 충분하다. 원문은 응답·쿠키로만 나가고 로그에 남기지 않는다.
- **읽기 계정 노출:** 운영 모니터링 계정은 `eolssu.*` 전체 읽기 권한을 가진다. 해시만 있어도 인증 테이블을 대시보드에 보일 이유가 없으므로 권한을 테이블 단위로 줄이는 안을 인프라와 맞춘다([S15P31E102-142 전달 사항](../../plans/S15P31E102-142.md#인프라-전달-사항우동균)).

## 미확인

- 메일 발송 수단(SMTP·외부 서비스)과 비밀키 보관 위치는 인프라 결정이다.
- 만료·폐기 행을 지우는 주기와 보관 기간은 명세에 없다. 탈퇴 일괄 처리와 같은 배치에서 정리하는 안이다.

## 이메일 인증 구현의 동시성(2026-10-28)

- 새 이메일에는 잠글 행이 없어 `SELECT ... FOR UPDATE`만으로 최초 동시 발송의 간격·횟수를 보장하기 어렵다. 1차 전달 규모(하루 100통 안쪽)에서는 새 테이블 없이 DB별 MySQL named lock 하나로 발송·확인 트랜잭션을 직렬화했다. 이메일 collation에서 같은 식별자로 취급하는 문자열도 한 경계에서 처리한다. 서로 다른 이메일도 직렬화되므로 실제 발송량·지연이 커지면 측정 후 잠금 단위를 재검토한다. 다중 MySQL 서버를 지원하는 분산 잠금으로 보고하지 않는다.
- 2026-10-28 리뷰: named lock만 쓰면 기다리는 요청이 Hikari 연결(기본 10개)을 최대 5초 잡아, 비로그인 요청 10여 개로 약관 같은 다른 DB API까지 멈췄다(잠금을 쥔 채 12건 동시 발송 시 관계없는 조회 약 4.8초 지연). 연결을 얻기 전에 서버 안 공정 잠금(`ReentrantLock.tryLock` 5초)으로 먼저 줄을 세우고 named lock은 서버가 여러 대일 때의 직렬화로 남겼다. 같은 조건에서 대기 중 풀 점유가 9개에서 2개 이하로 줄었다. 실제 SMTP를 붙일 때는 발송이 잠금·트랜잭션 안에서 길어지지 않게 커밋 뒤로 옮기는 것을 검토한다.
- [MySQL 8.4 locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html): `GET_LOCK`은 연결 소유이며 commit/rollback으로 해제되지 않는다. 같은 연결의 `afterCompletion`에서 `RELEASE_LOCK`을 실행해 커밋 전에 다음 발송이 시작되는 틈을 막는다. 대기는 5초이며 실패 시 503이다.
- 실제 MySQL 8.4·HTTP 검사에서 동일 이메일 첫 요청 8개가 202 한 건·429 일곱 건, 동시 확인 2개가 200·410으로 나뉘었다. 가입 메일 장애 503 뒤 이전 코드 확인이 성공해 롤백·잠금 해제를 함께 확인했다. 실패 확인은 예외를 던지는 대신 결과 값으로 반환해 오답 횟수가 커밋되게 했다.
- PASSWORD_RESET의 메일 장애는 사용자 합의로 202를 유지한다. 미발송 행에는 임의 256비트 문자열의 HMAC을 저장해 정상적인 6자리 입력으로 확인할 수 없게 하고, 응답·횟수·남은 시도 처리에서 회원 여부를 드러내지 않는다. 실제 메일 어댑터 검증은 포함하지 않는다. 상세 정책·검증 명령은 [143 계획](../../plans/S15P31E102-143.md#3단계-작업-기록2026-10-28)에 둔다.

## 비밀번호 재설정의 잠금과 원자성(210)

- 비밀번호 재설정은 인증 토큰 SHA-256으로 증명 행과 회원을 먼저 읽어 식별한다. 회원 잠금은 사전 조회한 ID의 PK FOR UPDATE로 수행한다. email 인덱스부터 잠그면 PK를 먼저 잡은 일괄 삭제의 email=NULL 갱신과 교착한다(MySQL 8.4 재현·210 리뷰 수정). Argon2id 비교·계산을 연결/잠금 밖에서 끝낸 뒤, 트랜잭션에서 users → email_verifications → refresh_tokens 순서로 잠근다. 209의 users → 인증 행 삭제, 208의 users → refresh 순서와 맞춘다.
- 잠금 아래에서 회원 ID·등록 이메일·기존 비밀번호 해시·토큰 목적/미소비/미무효화/만료를 다시 확인한다. 시각도 인증 행 잠금을 얻은 뒤 읽어 대기 중 만료를 허용하지 않는다. 저장·토큰 소비·refresh 전부 PASSWORD_CHANGED 폐기는 한 트랜잭션이며 실패하면 되돌린다.
- DB collation상 같은 주소라도 복구 메일과 인증 행은 DB 등록 이메일을 사용한다. 소비할 때도 증명의 이메일과 등록 이메일이 정확히 같은지 확인한다. 과거 입력 변형 주소로 발급된 증명은 거절한다.
- 사용자 확정: 로그인/현재 비밀번호 확인 잠금과 독립이며 성공해도 기존 카운터를 초기화하지 않는다. 자동 로그인·탈퇴 취소는 하지 않는다. 이미 발급한 access JWT는 기존 정책처럼 만료까지 유효하다.
- 근거와 재현: [210 계획](../../plans/S15P31E102-210.md), `PasswordResetServiceTests`, `PasswordResetApiDatabaseTests`. SMTP는 수신 대역으로 검사하며 실제 메일 연결은 별도다.

## 무기한 테스트 계정 예외 (S15P31E102-260)

위의 access 만료 최대 30분·폐기 한계는 일반 계정 기준입니다. 명시적으로 지정한 테스트 회원은 exp 없는 JWT를 발급하되 SHA-256 세션 해시를 넣고, 요청마다 DB의 같은 회원·같은 해시·NULL 만료·미폐기 세션을 확인합니다. 따라서 이 예외에서는 로그아웃·비밀번호 변경·탈퇴·토큰 회전·재사용 탐지로 이전 access도 거부합니다. 허용 목록 해제로 access·refresh 예외를 중단할 수 있습니다. 서버 시간 만료를 없애도 브라우저의 400일 쿠키 보관 상한이나 쿠키 삭제는 없앨 수 없습니다([Chrome 공식 안내](https://developer.chrome.com/blog/cookie-max-age-expires)). 기존 회원 정책과 기록은 보존합니다. [스펙·검증 범위](../../specs/non-expiring-test-account.md)를 참고합니다.
