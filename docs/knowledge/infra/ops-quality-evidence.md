# 운영·품질 실측 근거 표

- 작업: [S15P31E102-941](https://ssafy.atlassian.net/browse/S15P31E102-941). 기준 develop `25f7d263`, 정리일 2026-11-15. 동시 접속 리허설 행은 [S15P31E102-949](https://ssafy.atlassian.net/browse/S15P31E102-949)에서 develop `9495d9ac` 기준으로 추가했다.
- 목적: 최종 발표(11-18)에서 "운영과 품질을 어떻게 검증했는가"를 수치로 답할 때 쓴다. 저장소 문서에 이미 있는 실측값만 모았다. 이번 작업에서 새로 측정하거나 서버에 접속하지 않았다.
- 모든 수치는 출처 문서의 해당 행을 다시 열어 값과 조건을 대조했다. 문서로 확인되지 않은 값은 표에 넣지 않고 [미확인 항목](#미확인-항목)에 적었다.
- 논문·공식 자료의 근거는 [설계 근거 표](../domain/design-evidence-map.md), 구성 요소 위치는 [시스템 아키텍처](system-architecture.md)를 본다.

## 핵심 결론

- 배포 속도: 같은 커밋을 다시 빌드할 때 프론트 CI 공통 단계가 1195초에서 119초로 줄었다. 느린 원인이 빌드 자체보다 공유 executor 대기에 있다는 것도 실측으로 찾았다.
- 배포 안정성: 블루그린 전환·원복 중 연속 HTTPS 104건이 모두 성공했고, 배포 중 DB 마이그레이션 자동 적용은 0.23초였다.
- 장애 대비: 암호화 백업을 다른 서버에서 실제로 복원했고(89.86초), 장애 전환 리허설은 32.82초, 원복은 33.08초였다. 운영 DB는 edo2로 실시간 복제한다(지연 중앙값 86ms, 시험 환경).
- 운영 관측: 장애가 나면 사람이 명령을 치기 전에 알림이 온다(실제 시험에서 6분 7초). 디스크가 11-26 전후로 찰 것을 미리 잡아 여유를 125G에서 218G로 늘렸다.
- 사용자 체감: 웹 앱 Wasm 전송량이 10.6MB에서 3.0MB로, 마이페이지 점수 표시가 780.8ms에서 332ms로 줄었다.
- 채점 품질: 실제 입문자 녹음으로 재보니 맞게 분 음이 2/61개만 맞음으로 나왔다. 박자 판정을 고쳐 51/61로 올렸다.
- 시연 위험: 청중 30명이 한꺼번에 이메일로 가입하면 메일 발송 1초 가정에서 5명만 성공한다. 녹음 체험도 30명이 몰리면 분석 6초 가정에서 12명이 시간 초과다. 로그인과 조회는 30명에서 모두 성공했다. 두 위험은 서버 성능이 아니라 코드 구조에서 나와서, 시연 방식으로 피한다.

| 구분 | 뜻 |
| --- | --- |
| **운영** | 실제 운영 서버나 운영 데이터에서 잰 값 |
| **격리** | 운영과 같은 서버·이미지를 쓰되 운영 트래픽과 분리한 환경에서 잰 값 |
| **로컬** | 개발 PC, 에뮬레이터, 모의 서버에서 잰 값 |
| **실기기** | 실제 Android 기기에서 잰 값 |
| **실제 자료** | 사람이 분 실제 녹음이나 실제 악보로 잰 값 |
| **합성** | 실제 사용자 연주가 아닌 만든 입력으로 잰 값 |
| **문서** | 코드와 문서를 대조한 결과(실행 측정 아님) |
| **추정** | 실측값으로 계산한 값. 직접 실행한 결과가 아님 |

출처의 숫자는 해당 문서의 행 번호다. 경로는 저장소 기준이다.

## 발표용 검증 이야기

각 이야기는 문제 → 조치 → 수치 순서다. 수치 옆 조건을 함께 말한다.

1. **배포가 30분 가까이 걸렸다.**
   - 문제: 백엔드 빌드 한 번이 26분 34초였다.
   - 조치: 실제 빌드 기록을 다시 계산해 그중 약 14분이 빌드가 아니라 executor 대기라는 것을 찾았다. 웹 배포를 전용 노드로 나누고, 같은 입력은 다시 빌드하지 않도록 작업공간과 캐시를 보존했다.
   - 수치: 같은 커밋 재빌드의 공통 단계 1195초 → 119초. 결과물 76개의 해시가 모두 같아 캐시가 결과를 바꾸지 않음도 확인했다.
2. **배포하는 동안 서비스가 끊기면 안 된다.**
   - 문제: 백엔드를 교체하는 순간 요청이 실패할 수 있었다.
   - 조치: 블루그린 두 슬롯을 두고 새 슬롯이 준비됐을 때만 Nginx 경로를 바꾼다. DB 마이그레이션은 백업 → 적용 → 백업 순서로 배포에 넣었다.
   - 수치: 전환·원복 중 연속 HTTPS 104건 실패 0(격리). 운영 자동 마이그레이션 0.23초, 운영 이력 checksum 18개 일치.
3. **서버가 한 대뿐이면 장애가 곧 서비스 중단이다.**
   - 문제: 운영 서버 edo1이 멈추면 데이터와 서비스가 함께 멈춘다.
   - 조치: 매시 암호화 백업을 edo2로 보내고 매주 실제로 복원해 본다. 운영 DB를 edo2로 실시간 복제하고, 전환·원복을 리허설했다.
   - 수치: 첫 실제 복원 89.86초, 장애 전환 32.82초, 원복 33.08초, 복제 지연 중앙값 86ms(시험 환경).
4. **문제를 사람이 명령을 쳐야만 알았다.**
   - 문제: 장애·백업 실패·디스크 부족은 누군가 `/edo1`을 실행해야 드러났다. edo2 백업 디스크는 11-26 전후로 찰 것으로 추정됐다.
   - 조치: edo2에서 상태가 바뀔 때만 Mattermost로 알리고, 배포 산출물·백업 보존 정리를 자동화했다.
   - 수치: 실제 장애 시험에서 6분 7초 만에 알림 1건, 중복 0건. edo2 여유 125G → 218G, edo1 여유 117 → 163GiB.
5. **채점이 맞게 분 음을 틀렸다고 했다.**
   - 문제: 합성 입력에서는 잘 맞았지만, 실제 입문자 녹음에서는 맞게 분 음이 2/61개만 맞음으로 나왔다.
   - 조치: 실제 녹음으로 원인을 찾아 박자 판정을 고쳤다. 소리가 있는데 모두 틀린 연주가 '소리 없음'으로 나오던 오판도 실기기 원본으로 재현해 고쳤다.
   - 수치: 맞은 음 2/61 → 51/61, 정상 연주 평균 54 → 83점. 세션 22는 무음 실패 → 0점 채점.
6. **청중이 한꺼번에 쓰면 어디서 실패하는가.**
   - 문제: 발표장에서 청중 10~30명이 동시에 가입하고 녹음을 올릴 수 있다.
   - 조치: 발표 전에 운영과 같은 설정으로 동시 접속을 재현해 실패 지점을 찾고, 코드를 바꾸지 않는 시연 대책을 정했다. 청중 가입은 준비된 계정이나 소셜 로그인으로 받고, 녹음 체험은 10명 안쪽으로 나누며, 발표 직전 AI를 예열하고 배포를 멈춘다.
   - 수치: 이메일 가입 30명 동시 → 5명 성공(메일 1초 가정), 녹음 30명 → 12명 시간 초과(분석 6초 가정), 10명으로 나누면 모두 성공. 로그인·조회는 30명 모두 성공.

## 발표에서 주의할 표현

- 프론트 CI 90% 단축은 "같은 커밋을 다시 빌드할 때 공통 단계"의 값이다. "CI 전체가 10배 빨라졌다"고 말하지 않는다.
- 블루그린 104건, 복제 지연 86ms, 장애 전환 32.82초는 격리·시험 환경 값이다. 운영 DNS 전환과 공인 TLS 전환 시간은 포함하지 않는다.
- 백엔드 이미지 빌드 123.479초와 14.508초는 서로 다른 커밋의 표본이라 단축률로 말하지 않는다([jenkins-latency.md](jenkins-latency.md) 78).
- 합성 입력의 채점 정확도(81.7% 등)는 실제 사람 연주 정확도가 아니다.
- 평가 응답 7.909초는 개선 전 기준선이다. 개선 후 실기기 값은 아직 없다.
- 동시 접속 리허설은 로컬 PC에서 가짜 SMTP와 AI 대역으로 잰 값이다. 운영 서버 부하 시험이 아니고, 가입 한도는 운영 메일 발송 시간에 따라 달라진다. 두 위험은 코드 구조 때문이라 서버를 키워도 해결되지 않는다고 말한다.
- DTW 메모리 608.6MiB와 3.5GiB는 측정 대상이 달라 "몇 % 줄었다"고 말하지 않는다.
