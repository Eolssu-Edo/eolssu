후속: 같은 날 사용자가 edo2 보관·권장 주기 자동화·격리 실제 복원을 승인했다. 아래 S3 비교와 최초 현황은 조사 당시 기록이며, 채택한 구현·현재 실행 절차는 [백업 운영 안내](../../../infra/backup/README.md), 실제 검증·활성화 결과는 [Task 112 기록](../../plans/S15P31E102-112.md)을 따른다.

## 결론

확인한 백업은 변경 작업 직전의 수동·로컬 사본이다. 정기 앱 백업, 서버 외부 사본, 현재 DB의 격리 복원 성공은 확인되지 않았다. 확인한 SQL 덤프는 현재 운영 DB 구성보다 오래되어 복구 기준으로 사용할 수 있는지 검증이 필요하다.

기본안은 서울 리전의 전용 S3 버킷에 매시간 DB 전체 덤프를 보관하고, 설정은 매일 및 변경 직전에 백업하는 것이다. 현재 두 업무 DB의 데이터·인덱스 크기는 합계 약 6.4MiB이므로 우선 전체 논리 백업의 실제 시간·크기를 측정하는 편이 합리적이다. SQL 덤프의 실제 크기·압축률·소요 시간은 아직 측정하지 않았다.

## 보관 위치 권고

| 위치 | 권고 역할 | 조건·한계 |
| --- | --- | --- |
| edo1의 root 전용 `/opt/backups/eolssu/` | 생성·검사·업로드용 임시 보관, 최근 성공본 48시간 | 원본과 같은 서버이므로 단독 보관처로 사용하지 않음. 업로드 실패본은 보존·알림하며 디스크 상한도 관리 |
| 전용 S3 버킷·서울 리전·Standard | 기본 외부 보관처 | 버킷·접근 권한·과금 가능 여부는 확인 전. 비공개, 전송·저장 암호화, 버전 관리와 수명 주기 정책을 제안 |
| edo2의 별도 root 전용 경로 | S3 준비 전 임시 외부 사본 또는 선택적 복구용 캐시 | 여유 공간은 충분한 단일 시점 표본. 운영 서버이므로 관리·삭제·계정 장애가 연동될 수 있고 별도 백업 저장소를 완전히 대체하지 않음 |

S3는 버전 관리로 덮어쓰기·삭제 표식 이전 버전을 보존할 수 있다. 기본 저장 암호화와 공개 접근 차단을 명시적으로 확인하고, 업로드 주체의 영구 삭제·정책 변경 권한은 분리하는 구성을 제안한다. 버전 관리는 불변 저장소와 같지 않으며, 일반 만료 규칙만으로 과거 버전까지 삭제되지 않는다. 이전 버전 만료까지 함께 설계해야 보관 기간과 비용을 통제할 수 있다. [S3 버전 관리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html), [암호화](https://docs.aws.amazon.com/AmazonS3/latest/userguide/serv-side-encryption.html), [공개 접근 차단](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), [수명 주기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)

시간별·일별 사본은 고유 시각 경로와 검증 manifest를 사용하고 같은 파일을 계속 덮어쓰지 않는다. manifest에는 DB 스냅샷 시각과 외부 업로드 완료 시각을 구분해 기록한다. 실제 보관 비용은 첫 백업의 압축 크기·보관 수·전송·요청량을 측정한 뒤 계산한다. 소액·무료라고 확정하지 않는다. 같은 리전의 S3만으로 계정 전체 접근 상실이나 모든 리전 장애까지 대응했다고 보지 않는다.

모든 시간은 제안이며 서버의 UTC 설정과 혼동하지 않도록 구현 시 시간대를 명시한다. DB 백업·마이그레이션·관련 설정 변경의 동시 실행을 조율한다. 매시간 덤프가 실제 부하에 부담을 주면 측정 결과에 따라 주기·방식을 조정한다.

초기 목표는 DB 데이터 손실 약 1시간 수준, 앱·DB 복구 1시간 이내로 제안한다. 이는 합의·실측 전 목표다. 장애 시 손실 범위는 마지막 외부 보관 성공본이 담은 DB 스냅샷 시각부터 계산한다. 매시간 작업에서는 덤프·전송 지연이 더해지고, 작업 실패 시 이 간격이 더 늘어난다. 1시간을 엄격한 상한으로 보장하려면 더 짧은 주기나 binlog 외부 보관·재생 검증이 필요하다. 외부 업로드 완료를 성공 기준으로 삼고 실패·최신 성공본의 스냅샷 지연을 탐지해야 한다. RTO는 Jenkins 전체 복구와 분리해 앱·DB 기준으로 먼저 측정한다.

## 복구 대상과 주의할 경계

- DB: `eolssu`뿐 아니라 Metabase 자체 설정 DB인 `metabase`도 포함한다. 계정·권한·뷰의 DEFINER·루틴·트리거·이벤트와 복구 순서를 확인한다. 현재 모든 기본 테이블이 InnoDB이므로 동일 트랜잭션 시점의 논리 덤프를 우선 검토한다. 덤프 중 DDL을 조율하며 가동 중인 MySQL 볼륨의 단순 파일 복사는 사용하지 않는다. [MySQL 8.4 mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)
- binlog: 30일 로컬 보존은 서버 외부 백업이 아니다. 우선 현재 전체 백업의 복원을 확보하고, 요구 RPO가 더 짧아지면 덤프 좌표와 로그 보관·재생을 함께 검증한다. [MySQL 시점 복구](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html)
- 앱 설정: `/opt/eolssu/.env`, config·배포 도구·배포 기록, 실행 중인 JAR·웹 릴리스와 Git SHA, `/etc/letsencrypt`, 모니터링 설정, 필요한 systemd·sudoers 구성과 파일 소유권·권한을 포함할지 확정한다. Git만으로 실제 비밀값·릴리스·인증서가 복원되지는 않는다.
- Jenkins: 실제 홈은 `/var/lib/jenkins` bind mount다. 사용하지 않는 기본 `/var/jenkins_home` 볼륨과 구분한다. 일관성 있는 복사 방법과 유지보수 시간을 정하고, `master.key`는 일반 설정 백업과 분리해 복구자가 접근 가능한 안전한 위치에 보관한다. 파일·비밀값을 채팅이나 저장소로 복사하지 않는다. [Jenkins 백업·키 분리](https://www.jenkins.io/doc/book/system-administration/backing-up/)
- Grafana: `eolssu-monitoring_grafana-data` 볼륨을 포함한다. SQLite 사용 여부·백업 일관성·중단 필요성을 확인한 뒤 방법을 정한다. 이번 조사에서는 해당 DB를 열거나 서비스를 중단하지 않았다. [Grafana 백업](https://grafana.com/docs/grafana/latest/administration/back-up-grafana/)
- 비밀 설정은 보관처에 접근 가능한 주체도 제한하고 필요하면 업로드 전 암호화한다. 복호화 자료는 장애 난 edo1에만 두지 않는다. 키 분리·보관 정책은 구현 전 합의 항목이다.
- 이번 점검에서 `hey-*` PostgreSQL·n8n 등 별도 서비스 컨테이너도 보였다. 그 데이터·비밀값은 조회하지 않았으며 얼쑤 MySQL·설정 백업 범위에 자동 편입하지 않았다. 서버 전체 복구 범위에 포함할지는 별도로 확인해야 한다.

## 최초 조사 당시 검증 수준과 다음 단계

실행한 것은 파일 메타데이터·작은 아카이브의 항목 분류·SQL 완료 표식/DB 이름·스케줄 흔적·DB 메타데이터·mount·용량 조회다. SQL 행 데이터·환경변수 값·인증 파일·로그 본문은 출력하지 않았다. 대용량 Jenkins tar 전체 무결성 검사, SQL 복원, 신규 덤프, 외부 업로드, 권한·타이머 변경은 수행하지 않았다.

다음 단계는 보관 계정·위치·비용, 주기·기간과 RPO/RTO, 비밀키 보관자를 정한 뒤 같은 Task에서 최초 현재 DB 백업 → 외부 사본 읽기 검증 → 격리 복원 → 정기 실행·실패 감지를 검증하는 것이다. 기존 로컬 백업은 이 검증이 끝날 때까지 보존한다.

이 절은 읽기 전용 조사 종료 당시의 기록이다. 이후 승인받아 실행한 edo2 보관·복원·활성화 결과는 [Task 112 검증 기록](../../plans/S15P31E102-112.md), 운영 방법은 [백업 운영 안내](../../../infra/backup/README.md)를 따른다.
