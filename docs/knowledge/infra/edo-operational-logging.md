## 변경 범위와 근거

1. edo1 독립 HTTPS 점검은 관측 구간 62회가 모두 정상이었고 매회 결과 한 줄과 systemd 정보 메시지 세 줄을 남겼다. 분당 실행을 기준으로 journal 메시지 텍스트는 약 0.56 MiB/일이다. 두 접근 로그의 검사 요청분까지 합치면 약 0.9 MiB/일이다. 스크립트에는 대상별 장애 시작·복구를 기록하고 서비스 단위에서 정보 로그를 걸러낸다. 명령이 실패하면 systemd 실패와 Python 진단을 읽을 수 있다.
2. 같은 24시간에 edo1은 `GET /api/terms` 200을 220건, edo2는 `GET /healthz` 200을 89건 관측했다. 두 경로 모두 다른 출처의 요청이 있었고, edo2의 `/healthz`에는 502도 있었다. 경로·상태로 전체 성공 요청을 걸러내면 점검 이외의 접근 이력도 빠진다. 두 접근 로그는 현행 범위를 유지한다. 점검 전용 식별을 도입하더라도 HTTP 200의 잘못된 응답 본문은 Nginx 상태 조건으로 식별할 수 없으므로 클라이언트 판정을 계속 보존해야 한다. [Nginx 조건부 접근 로그](https://nginx.org/en/docs/http/ngx_http_log_module.html#access_log)
3. edo2 대기 OMR에서 최근 24시간에 정상 `GET /health` 약 8,400건과 Docker JSON 1.04 MiB가 발생했다. 호스트 Docker 기본값에 크기 회전이 없어 장기 누적을 제한할 필요가 있다. 재생성 시 기존 로그 보존이 필요한 서비스와 순서를 별도로 검토한다. [S15P31E102-713](https://ssafy.atlassian.net/browse/S15P31E102-713)
4. journal은 저장 비중이 크지만 두 호스트의 디스크 여유가 각각 약 145·180 GiB이고 기존 보존을 줄일 긴급 근거는 없다. 호스트 syslog 중복을 줄이려면 전달을 사용하는 운영 소비자와 오류·감사 로그 경로를 먼저 확인한다. Jenkins의 잡별 보존이 실제로 적용되어 있고 앱 일반 로그는 기존 14일 정책 범위에서 확인됐다. [앱 로그 보존 정책](../../../infra/privacy/README.md)

## 재검증

`journalctl --disk-usage`, `journalctl --since=-24h`, `systemd-analyze cat-config systemd/journald.conf`와 logrotate 설정을 대조한다. journal은 메시지 종류·우선순위별로 집계하고 Nginx는 경로·HTTP 상태·바이트만 집계한다. Docker는 `docker inspect`의 로그 드라이버와 회전 옵션, 최근 JSON 레코드의 시간과 크기를 대조한다. Jenkins는 잡별 보존 설정과 콘솔 파일 크기를 집계한다. 원문·주소·응답 본문은 집계에 포함하지 않는다.
