## 원인과 수정 전 실제 관찰

악보 OMR이 끝나도 편집기는 별도로 악기 목록·작성 지원 음역을 조회했다. `loadCompletionCatalog`·`openAdaptation`·음원 악기 목록이 같은 자료를 각자 읽었으며, `openAdaptation`은 탭을 열 때마다 추천 상태를 새로 만들었다. 작성 지원 음역을 받은 뒤 추천을 계산하는 FE 대기였고 OMR 재실행은 아니었다.

같은 Blue Valentine PDF(SHA-256 `07efe4304d2e8e9a81ed9cc33343d8ccf2a499107aa9ec2e81cce926de967c54`, 4쪽)를 격리된 실제 앱·Spring·MySQL·OMR에서 소금으로 업로드했다. 수정 전 `a6be2db7`의 실제 사용자 흐름에서 501 NOTE·527 이벤트·472 정간을 얻었다.

- 첫 편집 진입: 악기 목록 2회·소금 작성 지원 음역 2회·전체 율명 1회·장단 1회.
- 추천은 +6반음·옥타브 이동 5개·수정 필요 0개였다. +5반음을 선택한 뒤 율명·기호→음역 맞추기로 돌아오면 +6으로 초기화됐다. 이 재진입에서 악기 목록과 소금 지원 음역이 각각 1회 추가됐다.
- 추천을 적용하면 실제 화면은 율명·기호 탭으로 이동했다. 초안의 이조 +6, 이벤트 ID·정간 ID·종류·시작·길이 및 불변 source 보존을 서버 문서에서 확인했다.

수정 전 API 요청은 프록시의 실제 요청 시각·경로·상태·소요 시간으로 분리했다. 비밀번호·쿠키·인증 헤더는 증거 로그에 보관하지 않는다. 로컬 서비스와 일회성 계정만 사용하며 운영 데이터는 변경하지 않는다.

## 검증 경계

같은 악보로 확인하는 항목은 추천·음역·원본 보존·요청 재사용이다. PDF 전곡의 전문가 전사 대조나 새로운 OMR 정확도 평가는 아니다. 새 앱 세션의 최초 문서·필수 카탈로그 조회, 실제 통신 실패의 오류·재시도는 유지해야 한다.

Compose Web은 확인 모달을 닫은 뒤 브라우저 접근성 트리가 이전 모달을 유지한 경우가 있었다. 해당 구간은 실제 스크린샷과 서버 초안으로 교차 확인하며, 오래된 접근성 트리만으로 버튼 클릭이나 최종 상태를 판정하지 않는다.
