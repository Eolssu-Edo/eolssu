# 음역·이조의 준비 시점과 선택 유지

2026-11-13 · S15P31E102-879 · Story S15P31E102-319. [스펙](../../specs/sheet-adaptation-readiness.md)과 [작업·검증 기록](../../plans/S15P31E102-879.md)을 따른다.

## 원인과 수정 전 실제 관찰

악보 OMR이 끝나도 편집기는 별도로 악기 목록·작성 지원 음역을 조회했다. `loadCompletionCatalog`·`openAdaptation`·음원 악기 목록이 같은 자료를 각자 읽었으며, `openAdaptation`은 탭을 열 때마다 추천 상태를 새로 만들었다. 작성 지원 음역을 받은 뒤 추천을 계산하는 FE 대기였고 OMR 재실행은 아니었다.

같은 Blue Valentine PDF(SHA-256 `07efe4304d2e8e9a81ed9cc33343d8ccf2a499107aa9ec2e81cce926de967c54`, 4쪽)를 격리된 실제 앱·Spring·MySQL·OMR에서 소금으로 업로드했다. 수정 전 `a6be2db7`의 실제 사용자 흐름에서 501 NOTE·527 이벤트·472 정간을 얻었다.

- 첫 편집 진입: 악기 목록 2회·소금 작성 지원 음역 2회·전체 율명 1회·장단 1회.
- 추천은 +6반음·옥타브 이동 5개·수정 필요 0개였다. +5반음을 선택한 뒤 율명·기호→음역 맞추기로 돌아오면 +6으로 초기화됐다. 이 재진입에서 악기 목록과 소금 지원 음역이 각각 1회 추가됐다.
- 추천을 적용하면 실제 화면은 율명·기호 탭으로 이동했다. 초안의 이조 +6, 이벤트 ID·정간 ID·종류·시작·길이 및 불변 source 보존을 서버 문서에서 확인했다.

수정 전 API 요청은 프록시의 실제 요청 시각·경로·상태·소요 시간으로 분리했다. 비밀번호·쿠키·인증 헤더는 증거 로그에 보관하지 않는다. 로컬 서비스와 일회성 계정만 사용하며 운영 데이터는 변경하지 않는다.

## 변경과 같은 PDF 재검증

작성 전용 `SheetAuthoringCatalog`를 업로드·편집 화면에 공유한다. 성공한 목록·등록 음·악기별 지원 음역·장단을 회원 ID+epoch 단위로 재사용하고, 업로드 화면을 닫아도 앱 수명의 준비 작업은 이어진다. 일반 `InstrumentCatalog`와 `ApiReferenceCatalogRepository`의 조회 정책은 그대로다. 실패 응답은 저장하지 않으며 계정 변경 뒤 늦은 응답은 이전 세대를 채우지 못한다.

처음 편집 문서를 표시할 때 해당 악기의 추천도 함께 준비한다. 이후 같은 편집본의 탭 재진입·같은 악기 재선택은 현재 이조 값을 유지한다. 다른 편집으로 원본 연결이 바뀌면 제안을 다시 계산한다. 적용 뒤 새 baseline의 제안을 만들고 음역·이조 탭과 선택 값을 유지한다.

새 앱 세션에서 같은 PDF를 소금으로 다시 올렸다. 작성 자료 요청 7건(악기 목록·전체 율명·장단 각 1, 네 악기의 지원 음역 각 1)은 업로드 접수보다 6.9초 먼저 모두 200으로 끝났다. 실제 OMR은 4/4쪽·501 NOTE·527 이벤트·472 정간이며, 수정 전과 music·events·cells가 모두 동일했다. 새 업로드의 sourceId만 달랐다.

## 회귀와 리뷰

- 실제 ViewModel 회귀에서 재진입·재선택·적용 후 탭 유지가 수정 전 실패하고 수정 후 통과했다. 준비 자료 공유·동시 요청·실패 복구·화면 종료 뒤 준비 지속·계정 세대 경계도 검사했다.
- 별도 읽기 전용 리뷰에서 숨은 패널의 BackHandler와 실패한 악기 재시도 선택이 발견됐다. 표시 중인 탭으로 BackHandler를 판단하고 같은 baseline의 실패한 선택 악기로 재시도하도록 고쳤다. 재시도는 실제 ViewModel 경계에서 선택 expected 2/actual 1로 실패를 확인한 후 통과했다. 후속 리뷰에서 두 지적의 해소를 확인했다.
- 관련 회귀 50개 통과. 최종 Android host 전체 1,651개 중 1,646 통과·기존 제외 5·실패/오류 0. 최신 develop `c259b89d`를 포함한 검증 worktree와 게시 worktree의 frontend 전체 트리가 동일하다.
- 공유 Wasm 개발 실행 파일 컴파일·webpack 빌드 통과. 기존 Kotlin 사용 중단 경고와 webpack 동적 import 경고가 있다. 브라우저 콘솔은 수정 전·후 모두 같은 `wasmExports.memory` 사용 중단 경고이며 이 검증에서 새로운 오류는 관측하지 않았다.
- 근거: 주 작업 worktree의 `data/processed/sheet-adaptation-879/` 화면·빌드 로그, 구현 worktree의 `data/processed/sheet-ready-879/` red/green·전체 host 로그, runtime worktree의 `data/processed/sheet-adaptation-879/` 요청·실제 문서·보존 대조 JSON. 원본 PDF·전체 인식 결과·일회성 환경은 Git에 넣지 않는다.

핵심 실제 UI 흐름은 `20c3b9f6`에서 수행했고 후속 `c61b6e78`은 두 리뷰 지점과 회귀만 변경했다. 영향을 받지 않는 PDF 인식·선준비·적용·선택 유지 증거는 재사용했으며, 최종 제품 전체의 Android host 및 Wasm 빌드는 다시 통과했다. 추가로 계획한 프록시의 산조대금 지원 음역 1회 503→정상 복구 UI 검사는 프록시 백그라운드 재기동이 자동 승인 검토에서 `blocked by policy`로 거절돼 미실행이다. 추가 거절 사유는 제공되지 않았다. 실패 선택 재시도의 실제 ViewModel red→green 검사와 별도 코드 리뷰 결과를 이 UI 실행으로 확대하지 않는다.

## 검증 경계

같은 악보로 확인하는 항목은 추천·음역·원본 보존·요청 재사용이다. PDF 전곡의 전문가 전사 대조나 새로운 OMR 정확도 평가는 아니다. 새 앱 세션의 최초 문서·필수 카탈로그 조회, 실제 통신 실패의 오류·재시도는 유지해야 한다.

Compose Web은 확인 모달을 닫은 뒤 브라우저 접근성 트리가 이전 모달을 유지한 경우가 있었다. 해당 구간은 실제 스크린샷과 서버 초안으로 교차 확인하며, 오래된 접근성 트리만으로 버튼 클릭이나 최종 상태를 판정하지 않는다.
