## 관측과 원인

운영 `GET /api/instruments`의 이름은 단소·소금·정악대금·산조대금이었다. 이전 409 검증 캡처의 “서버 단소/소금”은 API 이름을 그대로 표시하는지 확인하려고 사용한 테스트 응답이다. 제품에 접두어를 붙이거나 지우는 로직은 없다.

동일 날짜 운영 공개 API를 한 번씩 읽은 결과는 다음과 같다. 측정은 전체 요청 시간이며, 반복 측정이나 서비스 지연 상한을 뜻하지 않는다.

| GET | HTTP | 시간 | 응답 크기 |
| --- | --- | --- | --- |
| `/api/instruments` | 200 | 0.096초 | 644B |
| `/api/reference-audios?datasetId=danso` | 200 | 0.358초 | 45,290B |
| `/api/reference-audios?datasetId=sogeum` | 200 | 0.162초 | 95,482B |
| `/api/reference-audios?datasetId=jeongak-daegeum` | 200 | 0.149초 | 71,041B |
| `/api/reference-audios?datasetId=sanjo-daegeum` | 200 | 0.175초 | 83,079B |

장시간 서버 지연은 이 표본에서 관측되지 않았다. 프론트는 `ReferenceAudioRoute`의 취법·학습 단계 `resetKey`가 바뀔 때 `open(instrument)`를 호출한다. 기존 ViewModel은 매번 목록을 비우고 같은 dataset 전체를 다시 요청했다. 악기별 응답에는 모든 취법의 녹음이 이미 들어 있으므로 취법 전환에 재조회가 필요하지 않았다.

수정 전 실제 Wasm 화면에서 단소 평취 → 역취 → 평취 → 소금 → 단소 순서로 조작하면 음원 목록 GET이 5회 발생했다. 첫 단소 조회가 끝난 다음 역취 전환의 두 번째 응답을 보류하자, 모든 카드가 다시 “자료를 불러오고 있어요.”로 바뀌었다. 즉, 이미 받아 둔 목록을 다시 요청하는 동안 나타나는 로딩을 재현했다. 테스트가 의도적으로 응답을 보류한 시간은 실제 운영 지연으로 해석하지 않는다.

## 수정

화면에 머무는 동안 성공한 목록을 악기별로 보관한다. 같은 악기의 취법·학습 단계 전환은 선택만 초기화하며, 진행 중인 요청이나 받은 목록을 유지한다. 다른 악기로 갔다 돌아올 때도 보관한 목록을 사용한다. 빈 목록은 성공으로 보관하고 실패는 보관하지 않는다.

명시적인 재시도는 이전 캐시를 지우고 새로 조회한다. 요청 중의 중복 재시도는 진행 중 요청을 유지한다. `dismiss()`는 요청을 취소하고 캐시를 비워 재진입 시 새 목록을 받는다. Route의 재생 정지와 카드 선택·재생 분리는 유지한다. 운지표·율명 대응·API·DB·플레이어 구현에는 변경이 없다.

목록 로딩·실패 안내를 “음원 목록”으로 구체화했다. 녹음 파일을 다운로드하거나 재생할 때의 안내, 녹음 자료가 없는 음의 안내는 그대로다.

## 검증 결과

- 관련 ViewModel 테스트: 기존 9개와 신규 5개, 총 14개. 변경 전 신규 요구 4개가 실패하고 수정 후 전체 통과했다. 같은 악기 재열기, 로딩 중 재열기·중복 재시도, 성공/빈 목록 재사용, 명시 갱신, 실패 비캐시, dismiss와 오래된 취소 요청을 확인한다.
- `./gradlew.bat :shared:testAndroidHostTest`: 총 667개, 실패 0, 오류 0, 기존 skip 3.
- `./gradlew.bat :webApp:wasmJsBrowserDevelopmentRun`: 개발용 Wasm 컴파일 및 webpack 완료. 기존 컴파일 경고와 webpack의 동적 의존성 경고가 있다.
- Edge의 실제 Wasm 화면(1280×1000): 위와 같은 동작에서 음원 목록 GET **5회 → 2회**. 단소 1회, 소금 1회이며 취법 왕복·단소 복귀에 추가 요청이 없다. 선택하지 않은 음원은 자동 재생되지 않고 `/play` 요청도 없었다.
- 390×844 화면: 초기 로딩, 503 실패와 버튼 재시도 성공, 빈 결과를 확인했다. 첫 목록 응답을 보류한 채 취법을 바꿔도 요청은 1회였으며 응답을 풀면 정상 표시됐다. 새 안내는 카드 안에서 읽히고 재시도 버튼과 겹치지 않는다. 브라우저 오류 0.
- 운영 이름을 담은 응답을 fixture로 재사용했으며, 화면에도 “단소/소금”이 표시된다. Compose popup의 접근성 DOM이 닫힌 뒤 남을 수 있어 드롭다운 결과는 네트워크와 실제 스크린샷으로 확인했다.

브라우저 비교는 응답을 통제한 로컬 실행이다. 운영 프론트 배포, 모바일 실기기·iOS, 실제 음원 재생 시간은 검증 범위에 포함하지 않았다. 성과는 반복 요청과 불필요한 재로딩 제거이며 운영 API 자체가 빨라졌다고 주장하지 않는다.
