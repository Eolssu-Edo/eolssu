# Android 장단 타격 누락 조사

- 작업: [S15P31E102-791](https://ssafy.atlassian.net/browse/S15P31E102-791), Story S15P31E102-319
- 조사일: 2026-11-12
- 대상: `e0bd8235`, QA 앱 `qa-20261111.155700-e0bd8235`, Galaxy S24+ SM-S926N, Android 17
- 상태: 재생·표시 수정 구현, Android host 검사와 공개곡 장단 모드의 실기기 전후 비교 수행. 추가 실기기 조작 검증은 USB 연결 종료로 미완료.

## 확인한 현상

‘파자마 파티즈의 노래’에서 장단 타격이 불규칙하게 빠지는 현상을 실기기에서 확인했다. 화면 처리와 같은 스레드에서 장단을 조회하면서 30ms보다 늦은 타격을 버리는 경로가 유력한 원인이다. 타격 호출과 UI 정지 구간을 함께 추적하지 않았으므로 이 경로를 단독 원인으로 확정하지 않는다.

사용자 보고는 Android의 **내 악보 연습 화면**이다. 연결된 QA 계정의 개인 악보 목록에는 해당 제목이 없었다. 실제 재생 검증은 **제공 곡 소금 판본 137**에서 했으며, 개인 악보의 내용·장단·생성 음원이 같다고 가정하지 않는다.

## 입력과 데이터 검증

운영 공개 API의 단소 136·소금 137을 조회했다. 두 판본은 각각 음표 535개, 154 BPM, `QUARTER`, 장단 12 ‘4박 기본 반주’다. 악보는 한 박 2tick, 장단 주기 8tick에 `덩·덕·궁·덕`이 배치되어 있다.

각 연주 시간표의 표시 구간 1,104개는 1tick당 194.805ms로 일정했다. 154 BPM으로 직접 계산한 시간과의 차이는 마지막 구간 시작에서도 약 0.215ms였다. **조회한 공개 판본에서는** 구간별 빠르기와 시작 BPM의 불일치를 원인에서 제외할 수 있다. 이 결과를 확인하지 못한 개인 악보에 적용하지 않는다.

조회 경로:

- `/api/songs/{136,137}/score`
- `/api/songs/{136,137}/model-audio`
- `/api/songs/{136,137}/model-audio/performance`

## 실기기 재현과 관찰

1. 소금을 선택하고 제공 곡의 ‘파자마 파티즈의 노래’를 연다.
2. 연습 설정에서 장단 소리를 켜고 기본 빠르기로 모범 연주를 재생한다.
3. ‘장단으로 연습’도 같은 악보에서 재생한다.
4. `adb shell dumpsys gfxinfo com.ssafy.eolssu.qa`와 기기 재생 출력 녹음을 확인한다.

모범 연주 재생 중 얻은 프레임 통계는 총 2,049프레임 중 지연 1,487프레임(72.57%), 중앙값 57ms, 90백분위 109ms였다. 이 통계는 해당 화면의 재생 관찰 구간이며 앱 전체 성능이나 다른 곡의 수치가 아니다.

기기 재생 출력은 scrcpy 4.1의 `--audio-source=playback --audio-dup --no-video --no-window --no-control --audio-codec=flac`으로 기록했다. 마이크 입력은 사용하지 않았다. 모범 연주 녹음은 연결 종료로 10.24초만 확보했고, 장단 단독 녹음은 7초 제한으로 정상 종료하여 6.229초의 오디오를 확보했다. 잘린 녹음을 전체 곡 검증으로 보고하지 않는다.

장단 단독 녹음과 앱이 사용하는 원본 샘플을 48kHz 모노로 디코딩해 파형 상관을 비교했다. 녹음 기준 2.646146초의 ‘덩’, 3.478146초의 ‘궁’은 각각 상관계수 약 1.0으로 검출됐다. 두 타격 사이는 **832ms**다. 정상 패턴의 한 박은 약 **389.61ms**이며 그 사이에 있어야 할 ‘덕’이 빠진 현상과 부합한다. 샘플 뒷부분의 상관 피크가 중복 검출될 수 있어 단순 검출 개수를 누락률로 사용하지 않았다.

음원·기기 캐시·녹음 원본은 Git에 넣지 않는다. 재현 자료는 조사 worktree의 Git 제외 `output/jangdan-sync-791/`에 보관했다. `baseline-combined.flac`, `baseline-rhythm.flac`, `analyze_capture.py`와 장구 샘플 3개가 비교 입력이다. `python output/jangdan-sync-791/analyze_capture.py baseline-rhythm.flac`으로 관찰값을 다시 계산할 수 있다. 로컬 PyAV·NumPy가 필요하다.

## 코드와 원인 가설

- [PracticeViewModel](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/practice/PracticeViewModel.kt)은 `viewModelScope`에서 만든 계정 범위를 [JangdanSession](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/practice/JangdanSession.kt)에 넘긴다.
- `JangdanSession.start`는 그 범위에서 `launch`하고 5ms 간격으로 현재 tick을 확인한다. 재생 루프를 UI와 분리하는 dispatcher 지정이 없다.
- [JangdanCursor](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/core/audio/JangdanPlan.kt)의 기본 `lateMs`는 30ms다. 이전 조회 이후의 타격이라도 이 창보다 과거이면 버리므로, UI 처리로 조회가 늦어질 때 타격이 사라질 수 있다.

큰 악보에서 관찰된 UI 지연, 실제 불규칙한 타격 간격과 이 코드 경로는 서로 부합한다. 다만 프레임 통계는 개별 타격 시각의 직접 추적을 대신하지 않는다. 오디오 출력 지연과 시계 보정의 기여도도 분리 측정하지 않았다.

## 수정 시 검증할 조건

장단 조회·출력을 UI 작업으로부터 분리하는 방안을 우선 검토한다. 지연 허용치만 늘리면 늦은 타격이 몰려 나올 수 있으므로 근본 해결로 취급하지 않는다. 별도 실행 문맥을 도입하면 샘플 준비·출력·정지·해제의 동시 접근, 모드 전환·일시 정지·탐색·변속·화면 이탈·오디오 포커스를 함께 검증해야 한다.

수정 전후에 같은 기기·앱 입력·154 BPM으로 타격 간격과 누락을 비교하고, UI 작업을 지연시켜도 타격 시계가 계속 진행되는 회귀 검사를 둔다. 사용자 개인 악보 원본 재현과 수정 후 청취 검증은 별도로 남아 있다.

## 구현과 회귀 결과

제품 수정 기준은 최신 `origin/develop=51d111ba`다. [수정 스펙](../../specs/practice-playback-timing.md)에 따라 다음을 구현했다.

- Android 장단 조회·출력만 전용 오디오 우선순위 스레드로 옮겼다. 준비·포커스·UI 상태 전환은 기존 소유자에 둔다. 샘플·스트림의 공유 상태를 동기화하고 정지 후 출력을 차단하며, 새 재생 전에 취소 중인 이전 작업의 종료를 기다린다.

## 실기기 전후 비교

기존 QA 앱과 로컬 debug 키가 달라 갱신 설치가 거부됐다. 별도 `com.ssafy.eolssu.qa791` 앱의 간편 로그인도 기존 QA로 복귀했다. 기존 앱을 삭제하거나 로그인 정보·쿠키를 복사하지 않았다. 이후 두 APK에 **같은 임시 공개곡 진입점**을 넣어 실제 `PracticeRoute`, DI, Repository, Android 플레이어를 실행했다. 제품 인증·회원 흐름과 개인 악보 원본을 검증한 결과는 아니다. 임시 진입점 소스는 제품 변경에서 제거했다.

같은 Galaxy S24+·Android 17, 공개 소금137·154 BPM의 ‘장단으로 연습’을 재생 시작부터 약 8초씩 교대로 측정했다. 매 실행마다 앱을 새로 열고 `gfxinfo`를 초기화했다. 양쪽 모두 scrcpy 4.1의 FLAC 재생 출력 캡처를 사용했다. 프로파일러를 켠 수치는 아니다. ART 샘플링 파일은 비어 있어 개별 함수별 CPU 비중을 얻지 못했다. 아래 결과는 타격 실행 분리와 화면 구성 제한을 함께 적용한 변화다.

원본 장구 파형과 상관계수 0.95 초과인 타격만, 각 녹음의 처음 0.8초와 끝 0.5초를 제외해 비교했다. 수정본에서는 15–16타의 `덩–덕–궁–덕` 순서가 이어졌고, 기준본에서는 4–8타만 검출됐다. 이는 보수적인 파형 검출 수이며 누락률 자체가 아니다. 기준본의 실행별 최대 검출 간격은 1,557–3,157ms, 수정본은 427–512ms였다. 수정본 한 구간에는 512ms 다음 256ms 간격이 관찰돼 **출력 타이밍의 잔여 변동까지 없어졌다고 단정하지 않는다.** 실제 출력과 캡처 경로의 기여도는 분리하지 못했다.

재현 자료: 로컬 `output/jangdan-sync-791/comparison.json`, 실행별 `*-gfx.txt`·FLAC·캡처 로그, `capture_run.py`, `ProbePracticeApp.kt`, 두 비교 APK. Python 3·PyAV·NumPy·ADB·scrcpy로 같은 입력을 다시 분석할 수 있다. 녹음과 APK는 Git에 넣지 않는다.

## 잔여 타격 간격 조사와 후속 수정

사용자가 남은 간격 변동의 해결도 요청하여 `7a6ac125` 이후 같은 Task에서 계속했다. 처음 수정의 전용 실행기는 유지하고, 타격 요청 시각과 실제 녹음의 파형 위치를 나눠 측정했다. 아래 수치는 앞의 UI 변경 전후 비교와 기준이 다르다.

30초 녹음 `trace-current-1`에서 SoundPool 호출 80타의 간격은 383.52–395.02ms였지만 고신뢰 파형 73타의 간격은 341.33–426.67ms였다. 캡처 소스를 `output`으로 바꾼 비교도 요청 384.92–394.80ms, 출력 362.67–448.00ms였다. 이 구간의 큰 변동은 호출 이후에 생겼다.

캡처의 시간 분해능을 확인하려고 같은 원본 샘플을 154 BPM의 정확한 PCM 샘플 위치에 배치한 36초 WAV를 만들고 단일 MediaPlayer로 재생했다. 동일 `playback+audio-dup+FLAC` 경로의 `calibration-1`은 70타의 간격이 389.604–389.625ms였다. FLAC timestamp에도 끊김이 없었다. 따라서 녹음 방식이 원래 약21ms 단위로만 측정한다는 가설은 지지되지 않았다. 개별 SoundPool 스트림의 시작 과정이 잔여 변동의 원인이라는 근거다.

### 유지한 구현

- Android는 준비할 때 검증된 AAC를 PCM으로 읽고 단일 AudioTrack 스트림에서 타격을 혼합한다. 128프레임 블록 경계에서도 잔향과 겹침을 보존하며 합산값이 int16 범위를 넘으면 포화시킨다.
- 기기의 native 출력률과 두 hardware burst의 활성 버퍼를 사용한다. Sonic의 출력률 변환은 준비 중에만 하며 속도·음높이는 바꾸지 않는다. 실제 기기 로그는 48,000Hz, 저지연 모드1, capacity3,840/활성384프레임이었다. [Android AudioTrack API](https://developer.android.com/reference/android/media/AudioTrack)의 활성 버퍼와 capacity 구분을 따른다.
- 첫 블록을 먼저 쓴 뒤 출력하고, 정지·후방 탐색 때는 큐와 native 버퍼를 비운다. 이전 쓰기 작업은 generation으로 차단한다. 준비 작업을 직렬화하고 해제 중 만들어진 자원은 publish하지 않는다. 쓰기 실패는 별도 실패 신호로 다음 타격 전에도 종료한다. native underrun 뒤에는 지난 PCM 구간을 건너뛰어 이후 타격까지 계속 늦추지 않는다.
- 모범 반주는 회색 표시의 0.9–1.1배 보정 시계를 사용하지 않는다. `native-combined-1`의 실제 타격 요청에도 첫507ms/이후379ms대 보정이 나타나 이 경로를 확인했다. 음원 위치를 측정한 TimeMark를 전달하고 정속 반주 anchor를 별도로 둔다. 작은 후행 보고는 같은 반주 세션에서 음원 위치를 되감지 않으며, 명시 탐색은 새 세션으로 시작한다.
- 120ms 미래 tick을 일괄 환산하는 안은 채택하지 않았다. 구간 빠르기와 반복을 새로 가정하는 공통 예약 API 없이 기존 실제 음원 시계를 유지한다. `positionSampledAt`과 비동기 `failed`는 기본값을 둬 다른 플랫폼 구현과 호환한다. iOS 실행은 여전히 미검증이다.

### 측정 범위와 검사

같은 Galaxy S24+에서 154 BPM·공개137·장단 단독을 12초씩 번갈아 재생한 유효 비교는 각2회다. 두 APK는 공개곡 진입점·화면 유지·버전 코드·캡처 조건이 같다.

| 항목 | SoundPool | PCM 초안(44.1kHz) |

| 검출 간격 전체 범위 | 277.333–490.667ms | 383.999–394.375ms |
| 실행별 간격 오차 절대최대 | 26.94–112.28ms | 5.24–5.61ms |

검출은 앞과 같은 파형 상관0.95 초과, 처음0.8초·끝0.5초 제외 조건이다. 검출 수를 누락률로 쓰지 않는다. 이후 native48kHz 구성의 동시 재생 녹음에서는 구음 순서를 맞춘 고신뢰11타의 **출력 간격과 호출 간격 차이**가 최대0.063ms였다. 이 값은 호출 이후 출력 변동을 보는 지표이며 음악과의 위상 오차나 최종 전체 재생 검증 수치가 아니다. 당시 모범 반주는 아직 화면용 시계를 사용했다.

PCM 혼합·분할 쓰기·초기화·출력 공백 후 시간표 보존, native률 변환의 길이·음높이, 타격 사이 비동기 실패 종료, UI 지연 전달·화면 보정 속도와 반주 시계의 분리 회귀를 실패 전·성공 후로 확인했다. 마지막 공통 코드 변경은 Android host·Android APK 및 JS/Wasm 컴파일을 통과했다. 이후 Android 전용 underrun 보정은 해당 host·APK로 확인한다.

5쌍 비교 계획 중 USB가 반복 단절되어 일부는 완료하지 못했다. 준비 중 사용자 앱 전환, 종료 시 잘못된 foreground 관찰자, USB 단절로 실패한 실행을 성공 비교에 넣지 않았다. 초기 모범 재생 시도는 장단이 꺼진 녹음이므로 동시 재생 확인에서 제외했다. 검증 도구는 매 프로세스 시작 후 실제 설정 UI에서 장단을 켜고 ‘소리 켜짐’을 확인하도록 고쳤다. 설정·계정 상태를 직접 주입하지 않았다.

최종 음원용 시계 분리 이후의 실기기 동시 재생·탐색·변속·배경 전환 재확인은 ADB 기기 부재로 대기 중이다. 최종 코드의 자동 검사와 앞선 PCM 출력 측정을 구분한다. 관련 파일은 `output/jangdan-sync-791/{capture_run.py,jitter_summary.py,analyze_combined.py,*-hits.txt,*-analysis.json}`에 보관했다. 임시 공개곡·기준음원 진입점과 타격 로그는 제품 소스에서 제거했다.

최종 제품 소스로 host 1,494건(실패0·제외4)과 Android APK를 확인하고 XML·빌드 로그를 `final-host-tests/`, `final-host-summary.json`, `final-product-check.log`에 보관했다. 그 전 전체 실행에서 변경하지 않은 `SheetAudioDeviceStoreTest.performanceSurvivesRestartOnlyWithItsVerifiedAudioAndVersion`이 한 번 실패했으며, 뒤의 전체 실행·해당 클래스4건·최종 전체 실행은 통과했다. 최초 실패의 상세 예외는 후속 보고서에 덮여 정확한 원인을 확정하지 못했다. 관련 구현이나 검사를 변경·제외하지 않았다.

### 디코더 시작과 첫 타격 보완

USB 기기 부재가 지속되어 기존 `Medium_Phone` API37.1 x86_64 에뮬레이터를 read-only·headless·포트5580으로 실행했다. 같은 실제 `PracticeRoute`와 Android 플레이어를 사용했다. virtual HAL의 underrun이 발생한 실행에서도 작업이 죽지 않고 논리 프레임을 건너뛰어 정지·재시작했다. 이 환경의 프레임·타격 지표를 Galaxy 성능으로 쓰지 않는다.

음원용 시계를 분리한 실행에서도 최초 Deong과 다음 Deok의 요청 사이가 1.28초인 경우가 있었다. `MediaPlayer.start()` 성공 직후의 `Playing` 알림을 실제 디코더 시계 진행으로 오인해 첫 타격을 먼저 냈기 때문이다. Android는 시작·재개 전 위치를 기준점으로 잡고 실제 위치가 증가하기 전까지 `positionClockRate=0`을 보낸다. 대기 중에는5ms로 위치만 확인하며 같은0 상태를 UI에 반복 발행하지 않는다. 진행 후에는 재생 배율과50ms 조회 주기로 돌아간다.

장단 세션의 `clockReady`는 이 대기 중 타격 커서를 건드리지 않는다. 실제 진행 후 첫 타격을 내므로 startAt·재개 중복 방지 기준도 보존한다. clockRate를 제공하지 않는 구현은 기존 동작을 유지한다. ‘100ms 동안 시계가0이면 타격0건, 실제 진행 후 다음5ms 조회 안에 Deong1건’ 회귀를 실패 전·성공 후로 확인했다. 양성 검사에서 다음 폴링까지 시간을 진행시키지 않은 테스트 설정1회는6ms 진행으로 바로잡았다.

보완한 에뮬레이터의 첫 타격 요청 간격은386.8ms, 다음은388.0ms였고 `덩–덕–궁–덕`이 이어졌다. 실제 UI를 통해 모범+장단 재생·일시정지 뒤 추가 타격 없음·재생 중 후방 탐색·정지 중 전방 탐색·재개·홈 이동 후 타격 중단·복귀 후 자원 재생성·속도 슬라이더80%(123 BPM) 선택 후 재생을 확인했다. `lifecycle-emulator-5580.json`과 로그가 증거다. 첫 도구 실행의 속도 실패는 화면을 문자 선택 버튼으로 오해한 것으로, 실제 Slider의 새 관찰 범위에서 조작하고123 BPM을 재확인했다. 접근성 null-root일 때 낡은 XML을 재사용하지 않도록 도구도 수정했다.

제품 소스의 host1,495건(실패0·제외4), Android APK, JS·Wasm 컴파일 통과. `decoder-host-summary.json`, `decoder-host-tests/`, `decoder-product.apk`에 보관했다. `build_probe.py`는 검증 APK를 만든 뒤 진입점과 로그 소스를 반드시 원복한다. 원래 QA 앱 서명과 개인 악보 원본 제약은 여전히 적용된다. 최종 Galaxy 재확인은 USB 재연결 대기이며, 에뮬레이터 결과로 대신 완료했다고 보고하지 않는다.
