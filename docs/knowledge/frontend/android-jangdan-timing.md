# Android 장단 타격 누락 조사

- 작업: [S15P31E102-791](https://ssafy.atlassian.net/browse/S15P31E102-791), Story S15P31E102-319
- 조사일: 2026-11-12
- 대상: `e0bd8235`, QA 앱 `qa-20261111.155700-e0bd8235`, Galaxy S24+ SM-S926N, Android 17
- 상태: 재생·표시 수정 구현, Android host 검사와 공개곡 장단 모드의 실기기 전후 비교 수행. 추가 실기기 조작 검증은 USB 연결 종료로 미완료.

## 확인한 현상

‘파자마 파티즈의 노래’에서 장단 타격이 불규칙하게 빠지는 현상을 실기기에서 확인했다. 화면 처리와 같은 스레드에서 장단을 조회하면서 30ms보다 늦은 타격을 버리는 경로가 유력한 원인이다. 타격 호출과 UI 정지 구간을 함께 추적하지 않았으므로 이 경로를 단독 원인으로 확정하지 않는다.

사용자 보고는 Android의 **내 악보 연습 화면**이다. 연결된 QA 계정의 개인 악보 목록에는 해당 제목이 없었다. 실제 재생 검증은 **제공 곡 소금 판본 137**에서 했으며, 개인 악보의 내용·장단·생성 음원이 같다고 가정하지 않는다.

## 입력과 데이터 검증

운영 공개 API의 단소 136·소금 137을 조회했다. 두 판본은 각각 음표 535개, 154 BPM, `QUARTER`, 장단 12 ‘4박 기본 반주’다. 악보는 한 박 2tick, 장단 주기 8tick에 `덩·덕·궁·덕`이 배치되어 있다.

각 연주 시간표의 표시 구간 1,104개는 1tick당 194.805ms로 일정했다. 154 BPM으로 직접 계산한 시간과의 차이는 마지막 구간 시작에서도 약 0.215ms였다. **조회한 공개 판본에서는** 구간별 빠르기와 시작 BPM의 불일치를 원인에서 제외할 수 있다. 이 결과를 확인하지 못한 개인 악보에 적용하지 않는다.

조회 경로:

- `/api/songs/{136,137}/score`
- `/api/songs/{136,137}/model-audio`
- `/api/songs/{136,137}/model-audio/performance`

## 실기기 재현과 관찰

1. 소금을 선택하고 제공 곡의 ‘파자마 파티즈의 노래’를 연다.
2. 연습 설정에서 장단 소리를 켜고 기본 빠르기로 모범 연주를 재생한다.
3. ‘장단으로 연습’도 같은 악보에서 재생한다.
4. `adb shell dumpsys gfxinfo com.ssafy.eolssu.qa`와 기기 재생 출력 녹음을 확인한다.

모범 연주 재생 중 얻은 프레임 통계는 총 2,049프레임 중 지연 1,487프레임(72.57%), 중앙값 57ms, 90백분위 109ms였다. 이 통계는 해당 화면의 재생 관찰 구간이며 앱 전체 성능이나 다른 곡의 수치가 아니다.

기기 재생 출력은 scrcpy 4.1의 `--audio-source=playback --audio-dup --no-video --no-window --no-control --audio-codec=flac`으로 기록했다. 마이크 입력은 사용하지 않았다. 모범 연주 녹음은 연결 종료로 10.24초만 확보했고, 장단 단독 녹음은 7초 제한으로 정상 종료하여 6.229초의 오디오를 확보했다. 잘린 녹음을 전체 곡 검증으로 보고하지 않는다.

장단 단독 녹음과 앱이 사용하는 원본 샘플을 48kHz 모노로 디코딩해 파형 상관을 비교했다. 녹음 기준 2.646146초의 ‘덩’, 3.478146초의 ‘궁’은 각각 상관계수 약 1.0으로 검출됐다. 두 타격 사이는 **832ms**다. 정상 패턴의 한 박은 약 **389.61ms**이며 그 사이에 있어야 할 ‘덕’이 빠진 현상과 부합한다. 샘플 뒷부분의 상관 피크가 중복 검출될 수 있어 단순 검출 개수를 누락률로 사용하지 않았다.

음원·기기 캐시·녹음 원본은 Git에 넣지 않는다. 재현 자료는 조사 worktree의 Git 제외 `output/jangdan-sync-791/`에 보관했다. `baseline-combined.flac`, `baseline-rhythm.flac`, `analyze_capture.py`와 장구 샘플 3개가 비교 입력이다. `python output/jangdan-sync-791/analyze_capture.py baseline-rhythm.flac`으로 관찰값을 다시 계산할 수 있다. 로컬 PyAV·NumPy가 필요하다.

## 코드와 원인 가설

- [PracticeViewModel](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/practice/PracticeViewModel.kt)은 `viewModelScope`에서 만든 계정 범위를 [JangdanSession](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/practice/JangdanSession.kt)에 넘긴다.
- `JangdanSession.start`는 그 범위에서 `launch`하고 5ms 간격으로 현재 tick을 확인한다. 재생 루프를 UI와 분리하는 dispatcher 지정이 없다.
- [JangdanCursor](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/core/audio/JangdanPlan.kt)의 기본 `lateMs`는 30ms다. 이전 조회 이후의 타격이라도 이 창보다 과거이면 버리므로, UI 처리로 조회가 늦어질 때 타격이 사라질 수 있다.

큰 악보에서 관찰된 UI 지연, 실제 불규칙한 타격 간격과 이 코드 경로는 서로 부합한다. 다만 프레임 통계는 개별 타격 시각의 직접 추적을 대신하지 않는다. 오디오 출력 지연과 시계 보정의 기여도도 분리 측정하지 않았다.

## 수정 시 검증할 조건

장단 조회·출력을 UI 작업으로부터 분리하는 방안을 우선 검토한다. 지연 허용치만 늘리면 늦은 타격이 몰려 나올 수 있으므로 근본 해결로 취급하지 않는다. 별도 실행 문맥을 도입하면 샘플 준비·출력·정지·해제의 동시 접근, 모드 전환·일시 정지·탐색·변속·화면 이탈·오디오 포커스를 함께 검증해야 한다.

수정 전후에 같은 기기·앱 입력·154 BPM으로 타격 간격과 누락을 비교하고, UI 작업을 지연시켜도 타격 시계가 계속 진행되는 회귀 검사를 둔다. 사용자 개인 악보 원본 재현과 수정 후 청취 검증은 별도로 남아 있다.

## 구현과 회귀 결과

제품 수정 기준은 최신 `origin/develop=51d111ba`다. [수정 스펙](../../specs/practice-playback-timing.md)에 따라 다음을 구현했다.

- Android 장단 조회·출력만 전용 오디오 우선순위 스레드로 옮겼다. 준비·포커스·UI 상태 전환은 기존 소유자에 둔다. 샘플·스트림의 공유 상태를 동기화하고 정지 후 출력을 차단하며, 새 재생 전에 취소 중인 이전 작업의 종료를 기다린다.
- 처음 `Playing/0ms`가 보고되면 디코더의 실제 진행을 기다린다. 연속 재생 중 크게 뒤처진 위치 보고는 화면을 되감는 대신 멈춰 기다린다. 명시적인 탐색·재시작은 새 기준점을 사용한다.
- 휴대폰 연습 보드는 보이는 묶음과 양옆 이웃만 구성한다. 화면 밖 너비는 각 칸과 간격의 픽셀 반올림까지 보존한다. 편집기 등 기존 호출자는 기본 표시 방식을 유지한다.

실패 전·성공 후 확인:

| 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| UI 스케줄러를 멈춘 1.5초 동안 4타 출력 | 1타 | 4타, 정지 뒤 추가 0타 |
| 첫 0 위치에서 400ms를 기다릴 때 화면 시계 | 먼저 400ms 진행 | 0ms 유지, 첫 실제 보고 뒤 진행 |
| 큰 후행 위치 보고 | 화면 기준점이 뒤로 이동 | 표시 위치 유지; 명시적 탐색은 뒤로 이동 가능 |
| 긴 악보의 표시 창 | 전체 묶음 반환으로 범위 검사 실패 | 처음·중간·끝·창 크기 변경 검사 통과 |

Android host 전체는 1,485건 중 실패 0건·조건부 제외 4건이다. Android debug APK, JS·Wasm 공통 코드 컴파일도 통과했다. Windows에서 iOS 컴파일·실행은 하지 않았다. 임시 검증 진입점을 추가하기 전 제품 코드로 실행한 결과다.

## 실기기 전후 비교

기존 QA 앱과 로컬 debug 키가 달라 갱신 설치가 거부됐다. 별도 `com.ssafy.eolssu.qa791` 앱의 간편 로그인도 기존 QA로 복귀했다. 기존 앱을 삭제하거나 로그인 정보·쿠키를 복사하지 않았다. 이후 두 APK에 **같은 임시 공개곡 진입점**을 넣어 실제 `PracticeRoute`, DI, Repository, Android 플레이어를 실행했다. 제품 인증·회원 흐름과 개인 악보 원본을 검증한 결과는 아니다. 임시 진입점 소스는 제품 변경에서 제거했다.

같은 Galaxy S24+·Android 17, 공개 소금137·154 BPM의 ‘장단으로 연습’을 재생 시작부터 약 8초씩 교대로 측정했다. 매 실행마다 앱을 새로 열고 `gfxinfo`를 초기화했다. 양쪽 모두 scrcpy 4.1의 FLAC 재생 출력 캡처를 사용했다. 프로파일러를 켠 수치는 아니다. ART 샘플링 파일은 비어 있어 개별 함수별 CPU 비중을 얻지 못했다. 아래 결과는 타격 실행 분리와 화면 구성 제한을 함께 적용한 변화다.

| 항목 | 기준 APK: 유효 4회 | 수정 APK: 유효 5회 |
| --- | --- | --- |
| 실행별 프레임 중앙값의 중앙값 | 65ms (65–73ms) | 10ms (10–10ms) |
| 실행별 프레임 90백분위의 중앙값 | 105ms (105–133ms) | 25ms (24–27ms) |
| 지연 프레임 비율 중앙값 | 74.71% (70.70–83.94%) | 17.25% (15.81–21.96%) |

초기 진입 준비 실패 1회와 USB 단절 3회는 유효 실행에 넣지 않았다. 원래 각 5회 비교를 계획했으나 마지막 기준 실행은 연결이 복구되지 않아 수행하지 못했다. 단일 기기·짧은 구간의 비교이며 전체 곡·모든 기기의 성능 수치가 아니다.

원본 장구 파형과 상관계수 0.95 초과인 타격만, 각 녹음의 처음 0.8초와 끝 0.5초를 제외해 비교했다. 수정본에서는 15–16타의 `덩–덕–궁–덕` 순서가 이어졌고, 기준본에서는 4–8타만 검출됐다. 이는 보수적인 파형 검출 수이며 누락률 자체가 아니다. 기준본의 실행별 최대 검출 간격은 1,557–3,157ms, 수정본은 427–512ms였다. 수정본 한 구간에는 512ms 다음 256ms 간격이 관찰돼 **출력 타이밍의 잔여 변동까지 없어졌다고 단정하지 않는다.** 실제 출력과 캡처 경로의 기여도는 분리하지 못했다.

재현 자료: 로컬 `output/jangdan-sync-791/comparison.json`, 실행별 `*-gfx.txt`·FLAC·캡처 로그, `capture_run.py`, `ProbePracticeApp.kt`, 두 비교 APK. Python 3·PyAV·NumPy·ADB·scrcpy로 같은 입력을 다시 분석할 수 있다. 녹음과 APK는 Git에 넣지 않는다.

남은 실기기 확인은 수정 후 모범 음원과 장단의 동시 재생, 최초 회색 표시·탐색·변속·확대·배경 전환의 직접 관찰, 잔여 출력 간격 변동, 사용자 개인 악보 원본이다. 관련 자동 회귀 통과와 이 실기기 확인을 구분한다. 기존 QA 앱에는 로컬 서명 문제로 이 변경을 설치하지 않았다.
