# 악보 파일 선택과 접수 경계

- 작업: S15P31E102-539. 기준: develop e99fc7de의 `SheetImportController`, `SheetImports`, `SheetImportFiles`, [내 악보 계약](../../specs/user-sheets.md).
- 사용자 결정(2026-11-06): 정간보 장단 선택을 인식 후에서 업로드 전으로 옮긴다. 오선보는 앞 화면에서 고른 황 음을 `Eb4` 같은 서버 문자열로 보낸다.

## 접수와 인식 완료 구분

`POST /api/users/me/sheets/imports`는 multipart `files`(같은 이름의 파트 여러 개)·JSON `metadata`와 `Idempotency-Key`를 받는다. 정간보 요청 예시는 다음과 같다.

```json
{"title":"연습 악보","notation":"JEONGGANBO","instrumentId":"카탈로그의 실제 ID","jangdanId":"사용자가 고른 실제 ID"}
```

악기·장단 ID는 활성 카탈로그에서 얻으며 순서로 만들지 않는다. BPM은 보내지 않아 서버 계약의 기본값·인식 결과를 따른다. PDF 쪽 수·암호·완전한 디코딩은 서버가 판단한다. 클라이언트는 기본 시그니처·빈 파일·개수·PDF와 이미지 혼합·합계 20MiB를 확인한다. Android는 ContentResolver 스트림을 남은 한도 + 1바이트까지만 읽는다. Web은 File 크기를 먼저 확인하고 Data URL을 원본 바이트로 복원한다. iOS는 선택 URL의 크기를 먼저 확인하고 scoped access를 반환한다.

실제 바이트와 제목·선택값이 준비된 뒤에만 제출한다. 202와 유효한 악보 ID를 확인하기 전 성공 표시하지 않는다. 접수 뒤에는 파일 바이트를 화면 상태에서 비우고 접수 완료·내 악보 목록 이동을 표시한다. 고정 42%/62% 진행률이나 예시 인식 결과를 이 흐름에서 사용하지 않는다. 기존 서버 악보 조회·초안·확정 저장은 그대로 둔다.

## 실패와 수명

- 같은 화면에서 입력을 바꾸지 않고 다시 제출하면 같은 키를 쓴다. 응답 유실 뒤 서버가 이미 접수했어도 같은 요청으로 재조회되는 SHT-07 멱등성 계약을 사용한다. 이는 **SHT-14 인식 재시도 구현이 아니다**.
- 파일·제목·악기·장단을 바꾸면 새 제출이다. 키와 파일은 기기 영구 저장소에 남기지 않는다. 앱 종료·화면 완전 이탈 뒤의 중복 방지는 이 키로 보장하지 않으므로 목록을 먼저 확인한다.
- 취소·읽기 실패·잘못된 선택은 앞서 유효하게 선택한 파일을 덮어쓰지 않는다. 업로드 중 입력과 중복 탭을 막는다.
- 로그인 세대가 바뀌면 파일·제목·작업을 폐기하고 이전 화면 콜백을 거절한다. Repository도 기존 `inSession` HTTP 경계를 사용한다.
- 파일명은 표시에는 원문을 쓰고 multipart에는 제어문자·따옴표·경로 구분자를 치환한다. 파일 경로·기기 권한은 전송하지 않는다.

## 의존성과 미확인 사항

BE S15P31E102-534는 시작 시 진행 중이며 원본 임시 처리·종료 후 삭제를 바꾼다. 이 FE는 원본 장기 보관·원본 조회·인식 재시도에 의존하지 않고 SHT-07 요청·202 접수만 사용한다. 병합 전 변경된 SHT-07 계약은 다시 대조해야 한다. 상태 조회(SHT-10), 완료 문서로 이동, 실패 후 재업로드·인식 재시도 화면은 후속 작업이다.

Notion MCP는 object_not_found, 현재 채팅에는 in-app browser가 없어 공개 API 원문 최신 재조회는 불가능했다. 저장소 명세와 실제 Controller·검증 코드를 근거로 삼았다. HTTP 대역 테스트는 실서버 접수·실제 OMR 성공의 증거가 아니다. 연결된 Android 기기 없음, iOS는 Windows에서 컴파일·실행할 수 없음, 웹 파일 선택 조작도 미검증이다. 명령·결과는 [539 계획](../../plans/S15P31E102-539.md)에 기록한다.
