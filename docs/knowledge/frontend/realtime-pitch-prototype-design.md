## 선택

AndroidAudioRecorder 클래스와 기존 AudioRecorder 제어 함수를 유지한다. Android 내부에서 마이크를 읽는 방법만 AudioRecord로 바꾸고, 같은 입력을 파일 저장과 음높이 분석에 사용한다. 기존 100ms 주기는 음량 확인에 유지한다. 음높이 결과는 기존 코루틴 Flow로 전달하고 ViewModel이 도착할 때 처리한다. Flow는 결과를 순서대로 받아 처리하는 통로이며 새 라이브러리를 추가하지 않는다.

새 모듈·Repository·UseCase·네트워크 API·별도 화면을 만들지 않는다. Android 플랫폼 등록도 기존 클래스를 사용하므로 바꿀 필요가 없다. 서버 점수와 결과 저장, 악보 이동은 기존 흐름을 따른다.

```text
기존 AndroidAudioRecorder
  AudioRecord 하나로 마이크 입력
    ├─ MediaCodec으로 AAC 압축 → MediaMuxer로 m4a 저장
    └─ 짧은 소리 구간 분석 → 시각이 붙은 불변 결과를 Flow로 전달

기존 PracticeViewModel
  watchRecording의 100ms 주기 → 기존 음량 확인
  녹음 중 분석 결과 수집 → 입력 구간의 기존 ScoreEvent 찾기
    → 현재 음과 직전 음의 안내만 잠깐 보관
    → 기존 연주 하단에 음표 이름과 음높이 안내 표시
```

이 화면은 연주 중 음높이 안내다. 음표별 최종 점수나 Perfect 등급은 만들지 않는다.

실시간에는 목표 음 대비 맞음·틀림과 판정 대기만 계산한다(2026-11-08 S15P31E102-566 전에는 높음·낮음·맞음). 소리를 시작한 박자, 음의 유지 길이, 연주 전체와 악보의 재정렬, 전체 조율 추정은 수행하지 않는다. 분석할 소리 구간의 시간과 이벤트 연결은 음높이를 엉뚱한 음과 비교하지 않기 위해 유지한다. 이것은 박자 점수를 매기는 처리가 아니다. 음높이만 비교하면 다른 판정을 추가하는 것보다 연산과 상태가 줄어들지만 CPU·배터리·표시 지연의 감소량은 아직 측정하지 않았다.

## 공통 연결은 선택 속성 두 개로 제한

`AudioRecorder.kt`에 음높이 결과 통로와 실제 녹음 경계 위치를 읽는 선택 속성을 추가한다. 기존 `start`, `pause`, `resume`, `stop`, `cancel`, `level`, `interrupted`의 의미와 반환값은 유지한다. 경계 위치는 화면과 파일의 중단 위치를 맞추기 위해 필요하며 음높이 분석 결과의 도착을 기다려 얻지 않는다.

호출 형태의 설계 예시는 다음과 같다. 실제 코드가 아니다.

```kotlin
val readings = recorder.pitchReadings  // Flow<PitchReading>?, 기본 null
val boundary = recorder.captureBoundary  // CaptureBoundary?, 기본 null
```

- `pitchReadings == null`: 실시간 안내를 지원하지 않는다. iOS와 기존 테스트 대역은 기본값으로 계속 동작한다. Android는 녹음 시작 전에 통로를 제공하고 ViewModel은 시작 전에 수집을 연결한다. 수집 자체는 마이크를 켜거나 파일을 만들지 않는다.
- 아직 음을 찾지 못했거나 무음이면 결과의 `frequencyHz`가 null이다. 분석 장애는 안내 사용 불가로 구분하고 파일 녹음은 유지한다.
- `PitchReading`에는 녹음 실행·재개 구간 식별자, 결과 순번, 구간의 시작·끝 샘플, 실제 샘플레이트, `frequencyHz`, 분석 품질 값, 결과 생성의 단조 시각을 둔다. 모든 결과는 읽기 전용이다.
- `CaptureBoundary`에는 녹음 실행·재개 구간 식별자, 파일 기준 누적 샘플 위치, 실제 샘플레이트, 경계의 단조 시각을 둔다. 시작·일시정지·재개 함수가 성공해 반환한 뒤 해당 함수가 확정한 위치를 즉시 읽을 수 있어야 한다. 분석 결과 통로보다 늦게 갱신하면 안 된다.
- 결과 객체와 분석 입력 배열은 서로 소유권을 나누지 않는다. ViewModel에 변경 가능한 PCM 배열이나 Android 타입을 넘기지 않는다.
- 통로는 결과 순서를 유지하고 최대 16개만 대기시킨다. 파일 저장 작업은 결과 수신을 기다리지 않는다. 초과 시 분석 누락을 알리고 이전 안내를 비우며 누락을 오답으로 바꾸지 않는다. 마지막 결과 하나로 조용히 덮어써 정상적인 음까지 빠뜨리는 방식은 사용하지 않는다.
- 음높이 추정 함수는 `core/audio` 안의 순수 계산으로 둔다. 악보 해석과 맞음·틀림 판단은 `feature/practice`에 둔다. 오디오 코드가 화면이나 곡 Repository를 참조하지 않는다.

## Android 내부 처리

파일은 현재와 같은 모노 AAC 128kbps m4a를 유지하고 샘플레이트는 우선 기존 44.1kHz를 요청한다. 입력 소스도 기존 VOICE_RECOGNITION을 유지한다. 지원되지 않는 설정을 조용히 다른 설정으로 바꾸지 않고 기존 녹음 시작 실패 경로로 알린다.

마이크 읽기·인코더·파일의 소유자는 녹음 실행별 작업 하나로 제한한다. 음높이 분석은 별도 작업에서 20ms 간격의 완성된 분석 구간을 처리한다. 분석 작업이 밀리면 안내 사용 불가를 알리고 최근 구간에서 다시 시작할 수 있지만 파일로 저장할 소리는 버리지 않는다. 입력 대기 공간은 고정 크기로 제한하며 파일 저장을 따라가지 못하면 녹음 실패로 처리한다. 메모리가 계속 늘어나거나 누락된 파일을 정상으로 제출하면 안 된다.

분석 작업이 실패하면 즉시 안내를 지우고 해당 녹음의 분석만 중지한다. 파일 저장은 정상인 한 계속한다. 마이크나 인코더가 실패하면 기존 `interrupted` 감시 또는 `stop()` 실패 결과로 녹음 실패를 알린다.

MediaCodec 출력 형식이 준비된 뒤 MediaMuxer에 트랙을 추가하고 파일 쓰기를 시작한다. 종료 시 입력 종료를 인코더에 알리고 남은 출력을 모두 저장한 다음 파일을 닫는다. 파일 마무리가 끝나기 전에는 RecordedAudio를 반환하지 않는다. 이 순서는 [MediaCodec 문서](https://developer.android.com/reference/android/media/MediaCodec)와 [MediaMuxer 문서](https://developer.android.com/reference/android/media/MediaMuxer)를 따른다.

파일 저장은 최대 10분 전체를 메모리에 쌓지 않는다. 이전 업로드 대기 파일의 보관·이동·재전송 정책은 바꾸지 않는다.

## 시작·중단·종료

| 동작 | 한 줄 설명 | 보장할 결과 |
| --- | --- | --- |
| 시작 | 이전 실행의 자원을 정리하고 새 입력을 연다 | 이전 실행 분석값이 새 실행에 들어오지 않는다 |
| 일시정지 | 새 소리의 파일 저장·분석 반영을 함께 멈춘다 | 안내와 분석 창을 지우고 멈춘 동안의 소리를 파일에 넣지 않는다 |
| 이어서 연주 | 새 구간 식별자로 분석을 다시 채운다 | 카운트다운과 일시정지 시간을 파일 시간에 더하지 않는다 |
| 정상 종료 | 파일 저장을 마무리한다 | 파일 준비가 끝난 뒤 기존 종료 팝업과 평가 이동을 허용한다 |
| 취소·화면 이탈 | 현재 실행을 폐기하고 자원을 정리한다 | 늦은 분석·파일 완료가 다른 실행의 상태나 파일을 건드리지 않는다 |

파일 마무리와 녹음 경계 확정을 UI 스레드에서 기다리지 않는다. ViewModel의 시작·일시정지·재개·종료 처리에 기존 코루틴을 사용하고 필요한 대기만 작업 스레드로 옮긴다. 제어 진행 중에는 중복 입력을 막는다. `PracticeUiState`에 `finalizingRecording` 상태를 추가해 그동안 재시작·평가 이동을 막고 저장 중을 표시한다. 파일이 없는 동안 `takeForEvaluation()`을 호출해 녹음 실패로 바뀌는 일을 방지한다.

시작 준비 전부터 녹음 실행 객체를 등록한다. Android 내부의 상태는 준비 중 → 녹음 중 → 일시정지 → 마무리 → 해제로 관리하고 취소 표시는 어느 단계에서도 되돌리지 않는다. 취소가 준비 중에 도착하면 준비가 나중에 성공해도 즉시 자기 마이크·인코더·파일을 정리하고 녹음 중으로 전환하지 않는다. 취소한 실행의 정리가 확인되기 전에는 다음 실행이 마이크를 열지 않는다.

ViewModel은 시작·일시정지·재개·종료 제어를 한 번에 하나씩 처리한다. 작업 스레드로 넘기기 전에 실행 식별자와 제어 진행 상태를 저장한다. 화면 이탈과 계정 변경은 식별자를 무효화하고 Android 실행의 취소 표시를 먼저 남긴다. 시작이 반환한 뒤에도 실행·계정·화면 상태를 다시 확인한 경우에만 `beginRecording()`과 `startStepping()`을 호출한다. 취소로 결과 반환이 생략되어도 Android 실행 객체가 스스로 정리하도록 하며 UI의 완료 콜백에 자원 해제를 맡기지 않는다.

취소된 코루틴이 네이티브 파일 처리를 자동으로 중지한다고 가정하지 않는다. Android 녹음 실행 객체가 종료와 폐기를 한 번만 수행한다. ViewModel은 시작 때의 녹음 키와 현재 계정을 다시 확인한 뒤에만 파일 완료를 상태에 반영한다. 오래된 완료가 도착하면 그 실행의 파일만 정리한다. 종료 중 새 녹음을 시작하지 않는다.

일시정지 제어와 입력 처리의 경계는 Android 내부에서 직렬화한다. 제어 변경 전후 소리가 섞인 분석 창은 버린다. 중단·해제 대기에는 상한을 두고 UI에서 기다리지 않는다. 상한 초과나 파일 마무리 실패는 정상 녹음으로 제출하지 않는다.

## 입력 시각과 기존 악보 연결

현재 `PracticeTimelineClock`과 `RecordingClock`의 구현은 교체하지 않는다. ViewModel에 녹음 구간별 기준점만 보관하고 기존 시계의 시작·재개 위치를 그 기준점으로 맞춘다. 결과가 도착한 순간의 `position`에 무조건 붙이지 않는다.

녹음 구간마다 기준점 `(실행 ID, 구간 ID, F0, P0, C0, sampleRate)`를 보관한다. F0는 구간 시작의 파일 누적 샘플 위치, P0는 해당 위치의 악보 경과 ms, C0는 그 경계의 단조 시각이다. 최초 구간은 P0=0으로 시작한다. 같은 구간의 파일 위치 F는 `P(F) = P0 + (F - F0) × 1000 / sampleRate`로 악보 시간에 대응한다. 분석 창의 양 끝에 이 식을 적용해 같은 이벤트 안에 있는지 확인한다. AAC 출력 시각은 파일 전체의 누적 샘플 수를 사용하며 일시정지 시간은 더하지 않는다.

일시정지를 누르면 화면 진행과 안내를 먼저 멈추고 중복 제어를 막는다. Android 작업이 파일에 받아들일 마지막 샘플 Fcut을 확정한 뒤 `pause()`가 반환한다. ViewModel은 `Pcut = P(Fcut)`으로 실제 저장 경계의 악보 위치를 계산하고 기존 화면의 보존 위치를 맞춘다. 재개할 때는 `F0=Fcut, P0=Pcut`인 새 구간을 만들고 Android 재개 경계가 확정된 뒤 기존 시계를 이어 간다. 클릭 시각이나 제어 함수 호출 전 화면 위치를 구간 기준점으로 계속 재사용하지 않는다. 일시정지 확인 중 발생한 화면 보정은 새 판정이나 박자 오류로 표시하지 않는다. RecordingClock은 기존 최대 길이·무입력 감시용으로 유지하고 음표 찾기에는 사용하지 않는다. 누적 시간을 새로 설정하는 함수를 RecordingClock에 추가하지 않는다.

입력 경계의 시각은 [AudioRecord.getTimestamp](https://developer.android.com/reference/android/media/AudioRecord)의 MONOTONIC 기준과 샘플 위치를 대응시켜 구한다. 단조 시각은 시스템 시계를 바꿔도 뒤로 가지 않는 경과 시간 기준이다. ViewModel은 같은 시간 기준으로 구간 경계 C0부터 화면 시계를 시작할 때까지의 경과를 보존 위치에 반영한다. 파일 시각·Android 단조 시각·Kotlin 시계의 단위를 혼용하지 않고 변환을 작은 함수에서 검증한다. 기존 시계 내부를 바꾸는 대신 시작·재개 시 carry 위치만 맞춘다.

`CaptureBoundary`는 시각 대응의 유효 여부도 표시한다. 장치 시각을 얻지 못했거나 입력 누락으로 시간 관계가 깨졌으면 녹음은 기존 방식으로 계속하고 음높이 안내는 시간 연결 대기로 둔다. 1초 안에 대응을 얻지 못하면 안내 사용 불가를 표시한다. 실제 장치 시각을 다시 얻으면 현재 구간의 기준점을 다시 확인한 뒤 안내를 재개한다. 읽기 함수가 반환된 시각을 실제 소리 입력 시각이라고 간주하지 않는다. 시각 변환 오차는 기기에서 확인하고 측정 없이 0ms라고 쓰지 않는다. 장치 시각이 계속 없는 기기는 파일 녹음 검증과 별개로 실시간 안내 미지원으로 기록한다.

`startTick`, `durationTick`, `ticksPerBeat`, 현재 녹음 시작 때의 BPM으로 이벤트 구간을 계산한다. 분석 창이 서로 다른 이벤트나 일시정지 경계에 걸치면 판정 대기로 둔다. 지난 이벤트 결과도 300ms 유효 기간 안이면 해당 eventId의 직전 음 안내로 전달한다. 현재 음의 결과인 것처럼 옮겨 표시하지 않는다.

ViewModel은 현재 음과 직전 음의 최근 유효 결과만 보관한다. 기존 화면 상태에 현재 목표 음과 직전 음의 이름을 함께 전달하므로 늦은 결과도 어느 음의 안내인지 구분한다. 같은 이벤트 안에서는 최신 결과로 갱신하고 이벤트가 넘어갈 때 직전 음으로 한 번 넘긴다. 두 이벤트보다 오래된 결과나 300ms가 지난 입력 결과는 지운다. 녹음 종료·중단·재시작·계정 변경 때 둘 다 지운다. 전체 곡의 실시간 결과 목록이나 점수 저장은 만들지 않는다.

이음은 원본 eventId를 유지한다. 쉼은 쉼 안내만 표시하고, 시김새가 있는 이벤트는 이번 시제품에서 음높이의 맞음·틀림을 확정하지 않는다. 샘플 악보처럼 기준 주파수나 원본 시간 정보가 없으면 실시간 안내만 숨기고 기존 녹음은 유지한다.

## 음높이 계산과 임시 기준

소리의 반복 주기를 찾는 [YIN 원 논문](https://pubmed.ncbi.nlm.nih.gov/12002874/)을 기준으로 작은 순수 계산 함수를 작성한다. 새 모델·외부 라이브러리·리샘플링 처리는 우선 추가하지 않는다. 분석 창은 2048샘플로 시작한다. 44.1kHz에서 약 46.4ms이며 두 주기 이상 담을 수 없는 낮은 음은 판정하지 않는다. 이 수치는 구현 시작 제안이고 성능 측정값이 아니다.

분석 창은 약 20ms마다 이동한다. 44.1kHz에서는 882샘플 간격이다. 낮은 주파수 한계를 창 길이로 정하고 높은 한계는 입력 샘플레이트의 절반보다 낮게 둔다. 실제 시제품은 단소·소금 악보에 필요한 범위와 옥타브 오류를 드러낼 범위를 먼저 확인해 제한한다. 현재 목표 음에 가까운 후보만 강제로 고르거나 옥타브 차이를 접어서 정답으로 처리하지 않는다.

최초 검증 범위는 100ms 이상 안정된 소리가 있는 단음이다. 약 46.4ms 창과 20ms 이동 간격이면 안정 구간 안에 분석 창이 들어갈 기회가 생긴다. 실제 소리의 시작과 끝, 처리 부하에 따른 성공은 별도 검증한다. 창보다 짧거나 안정 구간이 없는 음은 판정 대기로 두며 잘못 불었다고 처리하지 않는다. 100ms보다 짧은 음까지 모두 인식한다고 보장하지 않는다.

검사에서는 100ms와 기존 악보의 약 166.7ms 음에 대해 입력 시작 위치를 0~20ms 범위에서 옮겨도 정상 처리 부하에서 결과가 전달되는지 확인한다. ViewModel 수집·화면 반영이 100ms 늦어져도 해당 이벤트의 결과가 잠깐 보존되는지 확인한다. 긴 연속 연주에서 20ms마다 분석을 따라가지 못하면 주기를 임의로 늦추고 통과로 처리하지 않는다. 분석 범위를 줄이는 등 원인을 검토하고 미해결이면 안내 기능 검증 실패로 남긴다.

기준 주파수는 기존 `ScoreTiming.hwangHz`와 `ScoreNote.SourcePitch`에서 계산한다. 12율명의 순서에 따른 반음 수와 옥타브를 사용한다.

```text
목표 Hz = hwangHz × 2 ^ ((율명 반음 수 + 12 × octave) / 12)
음높이 차이 = 1200 × log2(인식 Hz / 목표 Hz)
```

차이 단위는 센트다. 100센트가 반음 하나다. 이 계산은 `data/src/playback/common_score.py`의 `target_hz` 식과 대조했다. 운지법 패널의 악기 선택을 바꿔도 악보의 기준 주파수를 임의로 바꾸지 않는다.

시제품은 악보 기준과의 차이를 표시하며 연주자의 조율을 자동 보정하지 않는다. ±50센트를 맞음 범위의 초기 제안으로 두고 화면에 최종 채점과 구분되는 음높이 안내를 표시한다. 첫 음을 틀리게 불었을 때 그것을 기준으로 맞춰 주는 동작을 피한다. 자동 조율 보정과 등급 규칙은 362의 별도 설계에서 검토한다.

무음·너무 작은 입력·주기 불명확·오래된 결과는 판정 대기다. 임시 시작값은 RMS -45dBFS와 YIN 정규화 차이 0.15 이하로 두고 실제 녹음으로 확인한다. RMS는 구간 전체의 소리 크기이고 기존 음량 배지의 최고 크기와 다르다. YIN 품질 값은 정답일 확률이 아니므로 85% 정확도 같은 표현으로 표시하지 않는다. 입력 구간 끝의 단조 시각에서 300ms가 지나면 결과를 지운다. 결과 생성·수신 시각으로 유효 시간을 다시 시작하지 않는다. 이 값들은 확정된 팀 정책이 아니다.

서버의 f/2f 보정을 무조건 복제하지 않는다. 두 배 주파수 오인이 실제 입력에서 발견되면 기존 검증 녹음으로 원인을 확인한 뒤 최소 수정으로 해결한다. 옥타브 오류 확인 없이 구현 완료로 처리하지 않는다.

2026-11-08 갱신(S15P31E102-556): 515 실기기 로그에서 중(415Hz) 안에 140Hz·84Hz(기본음 1/3·1/5)가 잡혀 2회 확인을 통과했다. YIN이 주기의 배수를 고른 오류다. `YinPitchEstimator.correctHarmonic`이 같은 창의 주파수 세기로 이를 고친다. 잡은 높이 f 자리 세기가 2f~5f 중 가장 센 자리의 0.1배보다 작으면, 소리가 있는 가장 낮은 배수로 올린다. 0.1은 서버 S15P31E102-251과 같다. 목표 음은 쓰지 않는다. 두 배로 잡는 쪽은 고치지 않는다. YIN은 기본음이 2배음의 0.25배 이하일 때만 그렇게 틀리고, 내려 고치면 진짜 역취를 숨길 수 있기 때문이다. 두 음이 창 가운데에서 바뀌는 경우처럼 경계 누설로 약수 자리 세기가 0.1배를 넘으면 고치지 못한다.

## 확인할 검사와 중단 조건

1. 기존 녹음 지원·권한·무입력·일시정지·계정 변경·종료 테스트가 유지된다. 기본 null 녹음기를 쓰는 iOS 경로와 테스트 대역이 실시간 안내 때문에 막히지 않는다.
2. 고정 파형으로 Hz 오차·반음 차이·옥타브 차이·무음·짧은 입력을 확인한다. 실제 단소·소금 검증 녹음의 정답 구간에서도 별도 비교한다.
3. 이벤트 전환 직전 입력의 늦은 도착·경계를 가로지르는 창·쉼·시김새·이어 연주·새 실행·입력 후 300ms 지난 결과를 작은 배열과 가상 시간으로 검사한다. 100ms·166.7ms 안정음의 분석 시작 위치와 수집 지연을 바꾸고 음표 ID가 유지되는지 확인한다.
4. 파일 준비 전 평가 클릭·중복 종료·종료 중 계정 변경·파일 실패·취소 후 늦은 완료를 확인한다. 시작 준비 중 화면 이탈·계정 변경·취소 직후 재시작에서도 이전 마이크가 남지 않아야 한다. 일시정지를 10회 반복해도 샘플 기반 파일 시간과 악보 위치의 대응 오차가 누적되지 않는지 확인한다. 한 녹음의 실패가 다음 파일을 삭제하지 않아야 한다.
5. `:shared:testAndroidHostTest`와 `:androidApp:assembleDebug`를 실행한다. 변경 범위에 맞게 웹 컴파일도 확인하며 Windows에서 iOS 실행 성공으로 확대하지 않는다.
6. 실제 Android에서 저장 파일 재생·기존 서버 제출, 중단 후 연결 부위, 최대 길이 파일의 크기·메모리·종료 시간을 확인한다. 기존 10분 녹음을 유지하므로 긴 녹음 확인은 병합 전 필요하다.
7. 실제 단소·소금에서 옥타브 오류와 안내 지연을 측정한다. 기기 입력부터 화면 표시까지의 측정과 함수 처리 시간을 구분한다. 분석이 밀려도 녹음 누락이 없음을 확인한다.

문제없이 동작한다는 결론은 위 검증 뒤에만 내린다. 녹음 누락·파일 손상·UI 멈춤·잘못된 이벤트 표시가 남으면 병합하지 않는다. 문제가 생기면 Android 내부 교체와 안내 연결을 함께 되돌려 기존 MediaRecorder 경로로 복구한다. 사용자 녹음이나 업로드 대기 파일을 삭제하는 방식으로 되돌리지 않는다.

## 이번 단계에서 확인한 것과 남은 것

현재 코드 호출부, 공통 악보의 주파수·시간 정보, 녹음 종료와 평가 이동의 연결, 기존 테스트 위치와 Android 공식 문서를 대조했다. 별도 분석 통신이나 새 모듈 없이 기존 경계에 연결할 수 있다는 설계다.

실제 Android에서 PCM 입력·AAC 인코딩·분석을 함께 실행하지 않았다. 정확도·표시 지연·기기별 시각 대응·최대 길이 안정성은 미검증이다. 분석값과 임시 기준은 검토 대상이며 제품 계약이나 측정 결과로 취급하지 않는다.

2026-11-05 설계 검토의 세 지적은 문서에 반영했다. 최신 결과 하나를 100ms마다 읽는 방식을 결과 통로와 두 음의 임시 보관으로 바꾸고, 분석 창·이동 간격·최초 검증 범위를 명시했다. 시작 준비 중 취소의 자원 소유권과 구간별 파일 샘플·악보 시간 기준점도 명시했다. 독립 재검토에서 세 지적의 문서상 해결을 확인했다. 구현 및 실행 검증으로 해결을 확인한 상태는 아니다.

## 구현에서 확인한 사항

검토한 단일 마이크 입력, 기존 클래스와 제어 함수, AAC 128kbps·44.1kHz·모노 m4a, 2048샘플 창과 882샘플 이동을 사용했다. Android 입력과 파일 처리는 실행별 작업 하나가 소유하고 YIN 계산은 별도 작업에서 처리한다. 새 모듈·라이브러리·서버 API와 iOS 녹음 변경은 없다.

선택 속성 두 개 안에서 `CaptureBoundary`에 경계를 조회한 단조 시각과 분석 사용 가능 여부도 전달한다. 조회 시각은 장치 입력 시각을 대신하지 않으며 결과 만료와 기존 화면 시계의 시작 위치 보정에만 사용한다. 파일의 누적 샘플 위치와 Android가 제공한 입력 시각은 각각 유지한다.

현재 음과 직전 음을 이름과 함께 표시한다. 두 줄의 최소 높이를 확보하고 무음·불확실한 소리·시김새는 맞음으로 표시하지 않는다. 파일 마무리 중에는 저장 안내를 표시하고 평가와 재시작을 막는다. 결과의 300ms 만료는 기존 100ms 음량 확인을 기다리지 않고 별도 작업으로 처리한다.

취소된 작업 스레드의 시작 호출이 반환되기 전에 다음 제어가 앞서가지 않도록 제어 순서를 잠근다. 화면 이탈은 취소 표시와 실행 번호 무효화를 먼저 수행하고, 늦게 돌아온 시작·파일 완료로 화면을 복원하지 않는다. Android 마이크 실행은 준비 작업 전에 등록하고 이전 실행이 자원을 해제한 뒤 새 입력을 연다.

자동 계산 검사와 가상 마이크를 연결한 실제 ViewModel 검사는 실제 마이크 검증과 구분한다. `AudioRecord` 입력 누락 감지, AAC 파일 마무리, 최대 10분 안정성과 입력 시각 대응의 기기별 정확성은 실기기로 확인해야 한다. 공식 API가 제공하는 시각·프레임 수를 사용했다는 사실만으로 녹음 품질이나 안내 지연을 입증한 것으로 보지 않는다. 실제 명령과 결과는 작업 계획 문서에 기록한다.


## 화면 표시 변경 철회

사용자 요청으로 추가한 음높이 안내 두 줄과 녹음 저장 중 문구, 버튼 잠금 표시를 기존 화면으로 되돌렸다. 녹음·분석·결과 만료와 저장 완료 전 평가를 막는 내부 제어는 유지한다. 현재 시제품은 화면에 실시간 음높이를 표시하지 않으므로 515의 화면 표시 완료 조건은 충족하지 않는다. 이전 코드 리뷰는 이 수정 전 기준이다.


## 사용자에게 보이는 동작 복원

사용자가 화면 모양뿐 아니라 동작도 기존대로 유지하도록 명시했다. PracticeViewModel과 PracticeUiState를 `aa334ff5` 기준으로 복원했다. 추가한 팝업 지연·뒤로 가기 차단·중복 제어 차단·악보 시각 보정·음높이의 화면 상태 전달을 제거했다. Android 녹음 내부의 단일 입력·AAC 저장·YIN 분석과 선택 오디오 속성, 독립적인 비교 계산은 유지한다. 화면 연동은 현재 없으며 기존 동기식 녹음 제어 계약을 사용한다. 철회한 화면 상태와 비동기 제어를 전제로 추가했던 테스트는 제거하고 기존 녹음 테스트를 원복했다. 실제 처리 시간과 기기 동작까지 동일하다는 측정 결과는 아니며 실기기 검증은 남아 있다.

## 2026-11-06 FE 결과 구독 연결

이 절이 현행 구현 기준이다. 위의 초기 화면·비동기 녹음 제어 설계는 이후 철회됐으며 다시 추가하지 않았다. 현재 변경은 `PracticeViewModel.pitchFeedback`만 새로 제공한다. 기존 `uiState`, 화면, 팝업, 버튼과 악보 진행 시계는 그대로다. Android 관측과 공통 악보의 시간·주파수 기준이 있을 때 녹음 모드에서 동작한다. 모범 연주·장단 연습·한 음씩 따라 불기의 자동 진행 판정이나 서버의 연주 후 채점으로 사용하지 않는다.

### 화면 담당자가 연결할 값

```kotlin
viewModel.pitchFeedback.collect { feedback ->
    val current = feedback.current
    val previous = feedback.previous
    // eventId로 악보 음에 연결하고 correct를 화면 표시로 변환한다.
}
```

| 값 | 한 줄 설명 |
| --- | --- |
| `current` | 현재 악보 이벤트에 속한 유효 결과다. 없으면 null이다. |
| `previous` | 직전 악보 이벤트에서 늦게 도착한 유효 결과다. 현재 음의 결과로 옮겨 쓰지 않는다. |
| `eventId` | 원본 악보 이벤트 식별자다. 화면 위치나 순번을 새로 추측하지 않는다. |
| `targetName` | 목표 음 이름 또는 쉼 기호다. |
| `heardHz` | 2회 확인을 통과한 음높이다. 없으면 null이다. |
| `correct` | 맞는 음을 불었는지다. true 맞음, false 틀림, null 판단 보류다(S15P31E102-566). 음정이 몇 센트 어긋났는지가 아니라 다른 음을 불었는지를 본다.<br>맞음: 곡에서 목표 바로 위·아래 음까지 거리의 절반 안이다. 각 쪽은 최대 100센트이고, 이웃이 없는 쪽도 100센트다. 이웃이 반음이면 그쪽은 50센트다.<br>보류: 곡의 가장 낮은 목표 음보다 200센트 넘게 낮은 값, 목표와 600센트 넘게 떨어졌으면서 1,200센트 ±100 밖인 값이다. 측정 오류일 수 있어 맞음·틀림으로 정하지 않는다.<br>틀림: 그 밖이다. 1,200센트 ±100 차이(역취·평취 같은 옥타브 실수)도 틀림이다.<br>조율 보정이 없어 연주 후 서버 결과(연주 전체 조율 차이를 뺀 뒤 ±50센트)와 다를 수 있다. 평소 음정보다 50~100센트 벗어난 음은 여기서 맞음, 서버 결과에서 틀림이 될 수 있다. 낮음·높음 방향은 주지 않는다. 보류를 화면에 어떻게 보일지는 FE가 정한다. |
| `rest` | 쉼 구간이면 true다. 쉼과 꾸밈음은 `correct`가 null이다. |
| `capturedEndNanos` | 입력 창 종료 시각이다. 다른 시계나 서버 시각과 직접 빼지 않는다. |

`current == null`과 `current.correct == null`을 맞음으로 표시하지 않는다. 원시값은 녹음기의 `PitchReading.rawFrequencyHz`에 보존하며 화면 안내는 확정값만 쓴다. 맞음 범위와 두 입력 간100센트 이내 확인은 서로 다른 기준이다. 최종 점수·리듬·길이 점수는 제공하지 않는다. 미지원 플랫폼이나 시간 기준 없는 악보에서는 현재·직전이 모두 null인 흐름을 유지한다.

### 시간 연결과 결과 수명

녹음 시작·재개 시 파일 샘플 기준점과 당시 악보 경과시간을 연결한다. 같은 구간에서 유효한 입력 시각이 늦게 확보돼도 악보 기준점을 현재 시각으로 옮기지 않는다. 구간을 넘는 분석 창·옛 녹음·순번 역전·300ms 이상 늦은 값은 유효 안내로 바꾸지 않는다. 일시정지 시간을 파일과 악보에 더하지 않는다.

악보 위치가 바뀌면 이벤트 ID를 따라 현재·직전을 다시 분류한다. 입력이 끊겨도 입력 종료 시각300ms 뒤에는 만료한다. 일시정지·종료·취소·재시작·화면 이탈·계정 변경 시 결과를 비우고 구독을 정리한다. 화면 담당자가 이를 별도로 구현할 필요는 없다. 만료·구간 연결의 자동 검사와 실제 기기·표시 지연 확인은 구분하며 실행 결과는 작업 계획을 따른다.
