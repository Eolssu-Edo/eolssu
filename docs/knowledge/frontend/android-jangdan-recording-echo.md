# Android 평가 녹음의 장단 누음 실측

S15P31E102-695에서 평가 중 스피커 장단을 유지하면서 녹음 속 장단을 줄이는 방법을 비교했다. Galaxy S24+ (SM-S926N, Android 17/API 37)의 내장 스피커와 마이크를 사용했다. 임시 APK는 Android 앱과 동일한 `VOICE_RECOGNITION` 44.1kHz 모노 PCM 입력 및 `USAGE_MEDIA`/`CONTENT_TYPE_MUSIC` SoundPool 출력을 사용했다. 타격음은 170ms 감쇠 멀티톤으로 생성했다.

## 기기 에코 제거

녹음 세션에서 AEC가 활성화되었는지 API 응답으로 확인하고, 타격음과 상관이 높은 마이크 입력 성분의 크기를 비교했다. 같은 시스템 볼륨에서 인접한 AEC 끔·켬 구간을 비교했다.

| 녹음 소스 | 시스템 미디어 볼륨 | AEC 끔 | AEC 켬 | 감소량 |
| --- | --- | --- | --- | --- |
| `VOICE_RECOGNITION` | 10/15 | −32.26dBFS | −32.64dBFS | 0.38dB |
| `VOICE_RECOGNITION` | 11/15 | −31.14dBFS | −31.43dBFS | 0.29dB |
| `VOICE_COMMUNICATION` | 11/15 | −57.69dBFS | −57.79dBFS | 0.10dB |

기존 녹음 경로에서 AEC를 켰을 때 누음 감소는 반복 간 편차보다 작았다. `VOICE_COMMUNICATION`에서는 AEC를 끈 상태에서도 입력 크기가 크게 달랐다. 실제 악기 음높이, 약한 음과 시작점의 보존, 채점 점수는 이 측정에서 비교하지 않았다. 임시 APK를 제거했고 마이크 입력 파일은 저장하지 않았다.

통화용 출력과 입력을 모두 선택한 후 한 녹음 세션에서 AEC 끔·켬을 교차 비교했을 때 타격 누음은 크게 줄었다. 켠 구간에서 마이크 입력이 0이 된 구간도 관찰했다. 이 경로에서 실제 악기 소리가 보존되는지 확인되지 않아 채점에 적용하지 않았다.

## 재생 참조로 장단 성분 빼기

모의 실험은 앱 장단 자산 ‘덩’·‘쿵’·‘덕’의 M4A를 [배포 명세](../../../frontend/shared/src/commonMain/composeResources/files/jangdan/manifest.json) SHA-256과 대조하고 FFmpeg에서 44.1kHz 모노 PCM16으로 디코딩했다. 캘리브레이션의 장단만으로 지연과 스피커 응답을 추정하고, 다른 순서와 세기의 타격에 응답을 고정해 적용했다. 평가 타격에는 523.25Hz 합성음을 일부러 겹쳤다.

- 모의 입력에서 장단과 바닥 잡음의 합은 29.27dB 줄었다. 합성음의 알려진 구간에서 스펙트럼 피크는 전후 523.19Hz, RMS 문턱으로 잰 시작점은 전후 434.01ms였다.
- 스피커 응답이 그대로여도 보정하지 않은 시간 차이가 32샘플(약 0.73ms) 생기면 감소량은 0.27dB로 떨어졌다.

```powershell
# 앱의 manifest와 일치하는 세 M4A의 경로를 사용한다.
foreach ($sample in @('deong','kung','deok')) {
    ffmpeg -i "path/to/m4a/$sample.m4a" -ac 1 -ar 44100 -c:a pcm_s16le "path/to/pcm/$sample.wav"
}
python frontend/tools/probe_jangdan_echo_reference.py "path/to/pcm"
```

Galaxy에서는 8회 타격의 녹음으로 에코 파형을 만들고, 별도의 8회 타격에 적용했다. `VOICE_RECOGNITION`과 일반 미디어 출력을 유지하고, 타격마다 재생 참조와 녹음의 파형을 맞춘 뒤 고정한 에코 파형을 뺐다.

| 재생 입력 | 시험한 정렬 | 장단 누음 변화 |
| --- | --- | --- |
| 170ms 합성 타격음 | 타격별 파형 정렬 | 중앙값 14.90dB 감소, 최소 12.13dB 감소 |
| 앱의 ‘덩’ PCM | 타격별 파형 정렬 | 중앙값 9.34dB 감소. 8회 중 7회 8.60~11.92dB 감소, 1회 3.17dB 증가 |
| 앱의 ‘덩’ PCM | 고정 지연 / 녹음 타임스탬프만 사용 | 중앙값 각각 1.27dB / 0.52dB 증가 |

‘덩’ 시험은 미디어 볼륨 11/15와 SoundPool 이득 0.35에서 진행했다. 누음 지표는 재생 PCM의 앞 72.6ms를 기준으로, 약 49.9~147.4ms 지연 범위에서 가장 유사한 마이크 입력 성분을 잰 값이다. 첫 시험에서 관찰한 지연은 주로 84.54ms 또는 144.58ms였다.

반복 시험에서 캘리브레이션으로 얻은 마이크 파형에 직접 맞추면 감소 중앙값은 2.08dB였다. 재생 PCM과 일치하는 성분이 3dB 이상 줄어든 타격에만 적용하면 8타 중 3타에서 3.17~3.79dB 줄었고, 5타는 원본을 썼다. 보정을 적용한 타격 중 지표가 악화된 경우는 없었다. 반복 시험의 정렬 방식과 측정 시점이 달라 감소량 차이의 원인을 분리하지 못했다.

두 시험에서 녹음 후 디지털로 더한 523Hz 음의 크기 오차는 각각 최대 0.36dB와 0.63dB였다. 실제 악기와 장단을 같은 마이크로 녹음했을 때의 음높이·시작점·점수는 검증 범위에 포함되지 않았다.

제품 검증에서는 출력 PCM과 마이크 샘플을 같은 시간축에 맞추고, 정렬 후보가 모호하면 그 구간은 보정을 건너뛰는 방법을 비교한다. 스피커 볼륨과 기기 위치가 달라질 때도 악기 입력과 채점이 보존되는지 실기기에서 확인한다.

- [Android 세션 단위 AEC](https://developer.android.com/reference/android/media/audiofx/AcousticEchoCanceler)
- [Android 녹음 전처리와 소스별 설정](https://source.android.com/docs/core/audio/implement-pre-processing)
- [WebRTC 재생 참조 및 녹음 프레임 처리 API](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h)

## 연속 PCM 참조와 음악 보존 비교 — 2026-11-10

사용자는 스피커 장단과 휴대폰 내장 마이크를 모두 유지하기로 했다. 이어폰이나 외장 마이크를 전제로 하지 않는다. 기본 AEC 설정 변경만으로는 해결되지 않아, 별도 임시 APK에서 연속 `AudioTrack`으로 장단을 재생하고 정확히 같은 PCM과 마이크 입력을 비교했다. 제품 앱의 SoundPool·녹음·채점 코드는 아직 변경하지 않았다.

### 입력과 시각 기준

- 같은 Galaxy S24+의 `VOICE_RECOGNITION`, 일반 모드, `USAGE_MEDIA`/`CONTENT_TYPE_MUSIC`, 44.1kHz 모노 PCM16을 사용했다. 정확히 렌더한 PCM 882,000샘플과 마이크 935,802샘플을 보관했다. 앞쪽에 장단별 4회, 총 12회 보정 타격을 두고 뒤쪽 16회는 다른 순서와 이득으로 재생했다. AEC3는 뒤쪽에서도 온라인 적응을 계속한다. 고정 파형 방식만 보정 타격으로 만든 파형을 이후 고정한다.
- 세 녹음의 미디어 볼륨은 4/15, 8/15, 8/15였다. 입력·출력은 각각 내장 마이크·스피커였고 재생 언더런은 모두 0회였다. 세 번째 녹음 중 확인한 AudioFlinger 효과 체인은 입출력 모두 0개였다. 이것이 제조사 HAL 내부 처리의 부재를 증명하지는 않는다. `UNPROCESSED` 지원은 기기 설정에서 false였다.
- 재생 PCM SHA-256: `eb475653e0d1ac56d4b115a973645882f06b1dc0df0efe01d2d8be30de37df04`. 마이크 원본은 아래 표의 SHA-256으로 확인했다. 마이크 파일과 모델 바이너리는 Git에 넣지 않는다.

| 입력 | 시각 식별자 | 마이크 SHA-256 |
| --- | --- | --- |
| take1 | `20261110-162526` | `0d805ece50056415b6f625f6443bd10ffe7598476b43302cee362097c7011d01` |
| take2 | `20261110-162906` | `cf2e062ad3773e905634120ff6e4f00cce8a44b2f91d58a7053c0ab0f72d3867` |
| take3 | `20261110-163648` | `b4cea51c73b2cde673a3d912489506af8692f7e0c5c198d30b6e213f605f4e62` |

두 스트림의 하드웨어 프레임 시각을 같은 MONOTONIC 시계에 맞추면 참조 시작점은 마이크 파일의 22,373 / 22,152 / 21,760샘플이다. 파일 샘플 0이 녹음 트랙 프레임 0이고 중간 누락이 없다는 전제다. `hw_frame − client_frames`는 앱이 아직 읽지 않은 양일 수 있으므로 이를 누락 샘플로 단정해 빼지 않는다. 20초 동안 두 클록의 상대 차이는 약 2.5샘플 이하였다. [Android AudioRecord 타임스탬프](https://developer.android.com/reference/android/media/AudioRecord#getTimestamp(android.media.AudioTimestamp,%20int))

원본 파형의 상관 최대값은 이보다 약 40~50ms 늦은 위치를 선택했다. 이를 그대로 참조 정렬이나 평가 구간 시작에 쓰면 초기 타격을 놓쳤다. 최종 RMS 비교 구간은 각 재생 이벤트의 하드웨어 시각 10ms 전부터 원본 클립 길이 + 120ms까지다. 모든 방식에 같은 구간을 썼다. 마이크 RMS에는 배경 소음도 포함되므로 아래 수치는 장단 성분만 분리한 ERLE가 아니다.

### 실제 장단 녹음의 감소량

| 처리 | take1 중앙값 / 최저 | take2 중앙값 / 최저 | take3 중앙값 / 최저 |
| --- | --- | --- | --- |
| WebRTC AEC3 기본 후단 억제 | 1.39 / 0.37dB | 14.27 / 1.02dB | 21.42 / 4.61dB |

| AEC3 선형 결과만 사용한 실험 빌드 | — | — | 2.68 / 1.74dB |
| AEC3 후단 억제 30% | — | — | 5.70 / 3.01dB |

양수는 감소, 음수는 증가다. 첫 두 행은 저장소 재현 도구로 원본 PCM에서 다시 실행한 값이다. take2의 이전 변환 WAV에는 양의 최대 PCM 값이 한 단계 낮아지는 변환이 있어, 그 파일의 AEC3 중앙값 14.74dB를 최종값으로 쓰지 않았다. take3에도 일부 PCM 최대·최소 샘플이 있으므로 무클리핑 녹음으로 표현하지 않는다.

take1은 재생 전·중간·후 배경 소음의 변동이 컸고 보정 타격 RMS가 평균 배경보다 약 0.94dB 높았다. take2는 약 9.30dB 높았다. 조용한 볼륨의 작은 감소량은 약한 참조와 배경 소음의 영향을 함께 받았으며, 모든 타격의 에코가 배경보다 작았다는 뜻은 아니다.

### 연주음 보존과 채점 입력

장단만 줄이는 결과와 연주음을 보존하는 결과를 나눠 확인했다. 국립국악원 산조대금 단음 파일의 약 262·522·627Hz 구간을 사용해 실제 마이크 녹음에 디지털로 더했다. 마이크·스피커·악기를 함께 거친 아날로그 혼합은 아니다. 원본은 `sanjo_deageum_scale_sus_04.wav`, SHA-256 `6EEBBA16C05B3AD9792A5960C8C46F310394894EBC1ACF092E62C32ABAB87332`이며, 48kHz의 `[34560:92160]`, `[2157120:2214720]`, `[2554560:2612160]`을 모노로 평균해 44.1kHz로 변환했다. 마지막 20ms에는 인공 페이드를 적용했으므로 실제 연주 종료·길이 검증에는 쓰지 않는다.

- 기본 AEC3는 장단과 겹친 일부 대금 구간도 낮췄다. `처리(장단+대금) − 처리(장단)`을 같은 이득·이력으로 비교하면, take3의 0dB 혼합에서 음높이 주변 대역 이득의 하위 10%가 일부 사례에서 −24~−26dB였다. 많은 프레임은 약 −0.4dB로 보존됐다. 따라서 대금 전체가 사라진다는 결론도 적절하지 않다.
- AEC3의 합성 대조 입력에서 관찰한 처리 지연은 427샘플, 약 9.68ms다. 보정하지 않은 627Hz 단독 입력의 옥타브 오류는 이 지연을 맞추면 사라졌다. 동일한 샘플 수가 동일한 음 시작 시각을 보장하지 않는다.
- 후단 억제를 없애거나 약하게 하면 연주음 손상은 줄지만 장단 잔여음이 커졌다. 고정 파형 빼기는 같은 보정 파형을 쓰는 한 `처리(장단+대금) − 처리(장단) = 대금`을 수치 오차 범위에서 보존했다. 그래도 잔여 ‘쿵’ 때문에 음높이 누락과 늦은 시작점이 남았다.
- 동일한 take3 혼합 18건의 비교용 YIN 검사에서 고정 파형은 8건, 고정 파형 + 약한 AEC3는 7건이 실험 문턱을 통과했다. 문턱은 유성 프레임 재현율 ≥95%, 짝지어진 프레임의 p95 음높이 오차 ≤25센트, 시작 오차 ≤20ms, 600센트 초과 오류 없음이다. 팀의 확정 합격 기준이나 Android Kotlin YIN 실행 결과가 아니다. 혼합 비율을 정하는 구간이 다른 앞선 시험의 14/18과 직접 비교하지 않는다.
- 서버 구현의 `decode_recording → pyin_f0 → frame_rms`도 첫 ‘쿵’에 겹친 3음 × 0/+6dB의 6건에서 실행했다. 원본 유성 프레임 재현율 중앙값은 72.3%, 고정 파형 + 약한 AEC3는 87.3%였지만 위 실험 문턱은 둘 다 0/6이었다. 서로 다른 추정기의 유성 프레임 분모는 같지 않다. 짧은 PCM 입력을 쓴 음높이 비교이며 AAC, 전체 곡 문맥, DTW, 최종 점수, 실시간 Android 분석을 검증한 것은 아니다.

단순 HPSS와 200Hz 고역통과 필터도 채점 입력의 보존을 일관되게 개선하지 못했다. 다른 녹음에서 만든 고정 파형을 재사용하면 오히려 누음이 커졌다. 따라서 같은 녹음의 보정 구간, 볼륨·출력 경로 변화 감지, 처리 지연 보정, 실제 악기 혼합에서의 검증이 필요하다.

### 재현

[재현 도구](../../../frontend/tools/probe_jangdan_aec3.py)는 외부 업로드 없이 로컬 PCM과 타임스탬프를 읽고 float32 WAV와 JSON을 출력한다. Python 3.12, NumPy 2.5.4, SciPy 1.16.3, `pywebrtc-audio==0.2.0`으로 AEC3를 실행했다. 고정 파형은 NumPy/SciPy만 필요하다. 원본 `timeline.json`의 참조 SHA-256과 44.1kHz 모노 규격을 검사한다.

```powershell
$probeData = Join-Path $env:TEMP 'eolssu-stream-reference-695'
python frontend/tools/probe_jangdan_aec3.py `
    "$probeData/take-20261110-163648" "$probeData/reference.s16le" `
    "$probeData/timeline.json" "path/to/aec3-result"
python frontend/tools/probe_jangdan_aec3.py `
    "$probeData/take-20261110-163648" "$probeData/reference.s16le" `
    "$probeData/timeline.json" "path/to/template-result" --method frozen-template
```

녹음 폴더에는 `mic.s16le`, `capture-timestamps.csv`, `playback-timestamps.csv`가 필요하다. CSV에는 `hw_frame`, `hw_nanos`, `status`가 있어야 한다. 프레임 1초~18초의 유효 타임스탬프로 시계를 맞추는 이 20초 시험 전용 도구다. 고정 파형의 보정 영역에는 장단별 최소 3회가 필요하며, 보정 이후의 입력을 파형 생성에 쓰지 않는다. AEC3 기본 패키지는 AEC를 켜면 고역통과 처리를 강제하므로 `high_pass_filter=False`가 완전한 필터 우회를 뜻하지 않는다. [버전 고정 래퍼 구현](https://github.com/strands-labs/pywebrtc-audio/blob/v0.2.0/bindings/webrtc_audio_bindings.cpp)

후단 억제 강도 비교는 별도의 임시 소스 빌드다. 선형 필터 잔차가 유효한 경우 이를 선택한 뒤 `SuppressionFilter::ApplyGain` 직전 이득을 `1 − mix × (1 − gain)`으로 조절했다. 합성 대조에서 `mix=0`도 에코를 줄였고 처리 지연을 유지했다. 공개 0.2.0의 옵션이 아니며, 제품 의존성에 추가하지 않았다. Android 도입에는 별도 네이티브 빌드·수명주기·성능 검증이 필요하다.

### 추가 대안 비교

- **재생 속성:** 같은 참조 PCM·볼륨 8/15에서 `CONTENT_TYPE_MUSIC`만 `CONTENT_TYPE_SPEECH`로 바꿨다. 둘 다 `USAGE_MEDIA`와 STREAM_MUSIC, 내장 스피커·마이크, 언더런 0회를 확인했다. `20261110-165222` 녹음 SHA-256은 `65e75c81586bc5a76b3f72b6b0b1325d3afd83baa864cdcdb93f731de1ef3804`다. AEC3 감소 중앙값/최저는 13.60/1.27dB, 고정 파형은 5.92/−0.65dB였다. 앞선 MUSIC 반복보다 개선되지 않았다. 녹음 시점의 차이가 있으므로 음성 속성이 악화의 원인이라고 단정하지 않는다.
- **파형 이득 추정:** 고정 파형의 전체 대역에서 타격 구간별 이득을 추정하고 예상 이득의 0.25~1.5배로 제한하면 take2의 감소 중앙값/최저는 10.14/0.13dB, take3은 13.56/2.01dB였다. 동일한 18건의 혼합 문턱 통과는 각각 9/18, 10/18이었다. 정답 음높이를 쓰지 않았지만 입력에서 이득을 다시 맞추므로 연주음 보존이 수학적으로 보장되지는 않는다. 세 대역을 따로 맞추는 방식은 take2의 기존 통과 두 건을 잃었다.
- **시간·주파수별 감쇠:** 보정 타격의 STFT 에너지 중앙값을 예상 장단 에너지로 사용했다. 최소 진폭 10%의 마스크는 take3에서 16.12/2.28dB 감소했으나 대금 혼합은 6/18만 통과했다. 파형 이득 추정보다 연주음 보존이 낫지 않았다.
- **음악 분리 모델:** Demucs 4.1.0 패키지의 공식 HTDemucs 체크포인트 `955717e8.safetensors`(84,025,440바이트)를 내려받아 로컬 RTX 4070 Laptop에서 실행했다. 21.22초 입력의 첫 추론은 7.07초, 이후 0.60~0.63초였으며 이 시간을 휴대폰 성능으로 해석하지 않는다. 입력에서 추정 드럼을 빼면 take3 장단 감소 중앙값은 6.52dB였지만 최악은 8.43dB 증가했다. 서버 pYIN의 첫 ‘쿵’ 혼합 6건도 문턱 통과 0/6이었다. 같은 음량의 627Hz 혼합에서는 대금 대역 중앙값이 6.57dB 감소했으므로 채점용 대안으로 채택하지 않았다. 녹음은 외부로 전송하지 않았다. [Demucs 원본](https://github.com/adefossez/demucs), [공식 모델 파일](https://huggingface.co/adefossez/HTDemucs/blob/main/955717e8.safetensors)

### 장단 볼륨과 연주 입력 크기

단일 타격 직후 250ms로 정한 혼합 비율은 그 뒤의 더 큰 장단 유입을 반영하지 못했다. 볼륨 조절의 출발점을 확인하기 위해 각 1.2초 대금 구간에서 가장 큰 장단·잡음의 250ms 창을 찾고, 같은 창의 대금 RMS가 그보다 +12/+18/+24dB가 되도록 디지털 혼합 9건을 다시 만들었다. 전체 혼합에 같은 이득을 적용해 새 클리핑을 막았다. 마이크에 이미 있던 클리핑은 복원하지 않았다.

가장 낮게 시험한 +12dB에서 3개 음 모두 원본과 고정 파형 처리의 실험 문턱을 통과했다. 서버 pYIN의 기준 음높이 ±50센트 안 프레임 재현율은 99~100%, 시작점 차이는 0~10ms, 옥타브 오류는 없었다. +18/+24dB에서도 모두 통과했다. 이 결과는 **약한 연주를 훼손하는 제거를 더 세게 거는 것보다, 마이크에 들어오는 연주/장단 비율을 확보하는 경로**를 뒷받침한다.

+12dB는 통과가 관찰된 최저 시험점이며, 최소 필요 비율이나 앱 볼륨 단계의 확정값은 아니다. 사람에게 장단이 충분히 들리는지, 실제 연주와 장단이 동시에 마이크에 들어올 때도 같은 결과인지, 전체 곡 점수에 영향을 주는지는 별도 확인해야 한다. 이 실험에서 낮은 비율의 결과를 높은 비율로 일반화하지 않는다.

## 사용자 소금 실연

같은 날 사용자가 임시 앱의 시작 버튼을 눌러 두 번 연주했다. 사용 악기는 사용자가 소금으로 확인했다. 내장 스피커·마이크와 볼륨 8/15, 동일 참조 PCM을 사용했다. 첫 약 11초는 보정 구간이며 이후 같은 음을 길게 연주하도록 안내했다. 두 번 모두 935,802샘플, 언더런 0회였고 기기 원본과 전송본의 해시를 확인했다. 실험 후 임시 APK를 제거하고 원래 볼륨을 복구했다.

| 입력 | 마이크 SHA-256 | 관찰 |
| --- | --- | --- |
| `20261110-170050` | `5a1d059aadfa2794afe00d591fb61f4c2e8271c6a5bfeea21c9de06603b7a410` | 보정 전·중에 연주와 같은 약 467Hz의 강한 성분이 있었음. 클리핑 0샘플 |
| `20261110-170621` | `d1dbbb09f08b7fb0872998add5d87cc740c2a13356a5554533fcf37a0fedae16` | 보정 전·중에 연주 기준 음높이 검출 없음. PCM 최대·최소 6샘플(보정 1, 연주 중 5) |

첫 실연에서는 고정 파형 보정이 오히려 실제 원본에 약했던 470Hz 성분을 만들었다. 녹음 12.0~12.5초의 450~490Hz RMS가 원본 −56.66dBFS에서 보정 후 −30.58dBFS로 올라갔고, 그 성분은 차감한 파형과 상관 0.999였다. 소금과 같은 음의 첫 검출도 원본보다 약 3초 빨랐다. **연주음이 보정 구간에 들어가면 음표를 보존하는 것이 아니라 없는 음표를 만들 수 있다.** 이 보정은 유효한 보정으로 취급하지 않는다.

두 번째 실연은 안내를 강화하고 장단이 끝난 뒤에도 완료 표시까지 연주하도록 했다. 장단이 없는 20.07~20.97초의 90프레임 모두 약 464.8Hz로 검출됐다. 장단이 겹친 비교 구간 798프레임에서 이 음의 ±50센트 안에 든 프레임은 원본 628, 고정 파형 676, AEC3 661개였다. 기준에 맞던 원본 프레임의 유지율은 고정 파형 99.84%, AEC3 99.20%였다. 실제 소리 시작 시각·정답 음표를 따로 기록하지 않았으므로 이 수치를 시작점 정확도나 최종 점수 개선으로 표현하지 않는다. 같은 음높이의 조기 주입 현상은 두 번째 실연에서 나타나지 않았다.

안정적인 연주 구간 13~18초를 대역별로 비교했다. AEC3의 427샘플 지연을 맞춘 뒤 같은 대역 필터를 적용했다.

| 대역 | 원본 RMS | 고정 파형 변화 | AEC3 변화 |
| --- | --- | --- | --- |
| 100~250Hz, 장단 저음이 포함된 혼합 대역 | −49.47dBFS | 4.26dB 감소 | 6.69dB 감소 |
| 450~490Hz, 소금 기본음 대역 | −27.52dBFS | 0.006dB 감소 | 0.48dB 감소 |

저음 대역에도 장단 외의 소리가 있으므로 그 감소량은 순수한 장단 제거량이 아니다. 장단이 없는 마지막 구간에서 소금 대역은 고정 파형 변화가 없고 AEC3가 0.34dB 낮았다. **이 소금 한 음의 실연에서는 연주음 보존과 저음 감소를 확인했다.** 약한 음, 다른 음역·악기, 위치·볼륨 변경, 곡 전체 채점까지 검증한 결과는 아니다.

별도 장단 단독 녹음에서 서버 pYIN의 유성 오검출은 원본 282/850프레임, 고정 파형 134/850, AEC3 125/850이었다. 대부분 약 108~110Hz였다. pYIN 탐색 하한을 180/200Hz로 높이면 일부 장단이 약 330Hz로 다시 검출돼 단순 하한 변경도 채택하지 않았다. 카탈로그 음역은 채점용 물리 하한의 승인이 아니며, 기존 잘못된 음의 `PITCH` 판정을 `MISSED`로 바꿀 수 있다.

제품 반영 전 필요한 조건은 다음과 같다. 첫 실연의 실패 때문에 조용한 보정을 화면 안내만으로 보장된 것으로 취급하지 않는다.

1. 재생 PCM·녹음 시각을 같은 경로로 확보하고 중단·재시작·볼륨·출력 경로 변경을 처리한다.
2. 보정 중 연주나 다른 음이 감지되면 보정 파형을 적용하지 않고 다시 측정한다. 보정 품질이 낮거나 경로가 바뀌어도 같은 처리가 필요하다.
3. 자동으로 더 강하게 억제하기보다 연주 입력과 장단 유입의 비율을 확인해 재생 볼륨을 조절한다. 장단의 실제 청취 가능성도 검증한다.
4. 처리 지연을 보정하고 연속 음표·쉼표·잘못된 음·짧은 음을 포함한 실제 녹음에서 Android 안내와 서버 최종 채점을 확인한다.

이 실험 단계에서는 제품 녹음 경로나 채점 기본값을 바꾸지 않았다. 이후 사용자의 자동 차단·앱 적용 요청에 따라 아래 구현을 진행했다.

## 자동 차단을 포함한 Android 구현

구현 기준은 `96797e25`와 [스펙](../../specs/android-recording-echo.md)이다. 장단을 켠 평가 시작 전에 사용할 실제 클립을 네 번씩 재생한다. 무재생 구간의 지속음·소음, 반복 타격의 일치도와 저역·전체 응답의 잔차를 확인한다. 통과한 경우에만 3초 카운트다운 뒤 녹음하며, 실패하면 재측정·보정 없이 연주·취소를 선택한다.

연속 AudioTrack의 실제 출력 프레임과 AudioRecord의 하드웨어 시각으로 재생 위치를 연결한다. 보정부터 평가 시작까지 마이크를 재시작하지 않지만, 보정 PCM은 AAC·음높이 분석에 넣지 않는다. 20ms 입력 블록에서 예상 장단과 실제 입력이 충분히 일치할 때만 제한된 감산을 하고, 같은 처리 PCM을 저장과 분석에 전달한다. 별도 버퍼 지연이나 샘플 삭제는 없다. 볼륨·기기·출력 epoch·언더런·클리핑·시각 유효성이 바뀌면 보정을 끄고 원본 녹음을 계속한다. 일시정지는 마이크를 정지하고 보정을 폐기한다.

독립 검토에서 타격 순간에만 더한 467Hz가 고역 일치 검사만 통과해 없는 음을 만드는 사례를 재현했다. 짧은 타격에도 응답 전체와 120ms 꼬리의 반복 잔차 검사를 추가했다. 90–700Hz와 90–10000Hz 각각에서 조용한 구간의 잡음 전력 두 배를 제외한 잔차/중앙 파형 전력이 `.15`를 넘으면 거부한다. 이 문턱은 아래 입력에서 검증한 공학적 기준이며 모든 악기·환경의 판별 보장이 아니다. 동일한 위상·이득으로 매번 반복되는 외부음이나 문턱보다 약한 오염은 구별하지 못할 수 있다.

### 자동 검사 결과

실제 Galaxy 소금 원본 두 개를 Kotlin 제품 알고리즘으로 다시 실행했다. 원본 SHA-256은 위 실연 표와 대조했다.

| 입력/검사 | 결과 |
| --- | --- |
| `170050` 보정 중 소금 | `NotQuiet`로 거부 |
| `170621` 조용한 보정 | 통과, 최소 반복 일치도 `.661266`, 최대 응답 잔차 `.02083424` |
| 깨끗한 보정의 holdout | 42개 블록에 실제 적용, 전체 혼합 RMS 1.2494dB 감소 |
| 같은 실연의 13–18초 | 100–250Hz 1.84675dB 감소, 소금 450–490Hz 0.00489dB 감소 |
| 타격 중에만 더한 467Hz, 회차별 위상 변화 | 수정 전 통과를 재현한 뒤 `Unreliable` 거부 |
| 무음·연주 우세·일치하지 않는 입력 | 해당 블록 원본 보존 |

두 PCM의 길이는 모두 935,802샘플이다. 혼합 저역 감소를 순수 장단 제거량이나 전체 곡 점수 개선으로 해석하지 않는다. 이 보수적인 필터는 앞선 무조건 감산보다 처리 구간이 적다.

이 Kotlin 출력에 실제 서버의 `decode_recording`·pYIN을 적용한 별도 비교에서도, 같은 장단 활성 798프레임의 기준음 464.818Hz ±50센트 검출은 원본 628개에서 670개로 늘었다. 원본에서 맞던 628개는 모두 유지됐고 공통 프레임의 음높이 차이 95백분위는 0센트였다. 연주 안내 전 PCM과 장단 종료 뒤 PCM은 원본과 동일했다. 첫 연속 검출은 12.19초에서 12.17초로 20ms 빨라졌지만 실제 연주 시작의 정답은 없으므로 시작점 개선으로 해석하지 않는다. 출력 SHA-256은 `5b32a16c0cdeff40a5c90527a1a3e04125ff86def9817a8042a9d1e00d22a28a`다. 이 비교는 실연 한 건의 PCM이며 앱 AAC·곡 전체 점수 검증을 대신하지 않는다.

재현은 `EOLSSU_ECHO_FIXTURES`를 로컬 `eolssu-stream-manual-695` 폴더로 지정하고 `frontend`에서 `gradlew.bat :shared:testAndroidHostTest --tests '*RecordingEchoReplayTest' --max-workers=2`를 실행한다. 원본 음성은 Git에 포함하지 않는다. `EOLSSU_ECHO_REPLAY_OUTPUT`을 지정하면 처리 PCM을 로컬에 저장한다.

통합 Android host 검사는 1,310건 중 1,306건 통과, 4건은 별도 서버/코퍼스/운영 QA 설정이 필요한 선택 검사로 건너뛰었다. 실측 replay는 설정을 제공해 실제 실행했다. 이후 취소 경쟁 수정에 영향을 받는 보정 UI·출력 검사 15건도 통과했다. 준비 취소의 늦은 완료, 백그라운드 복귀 후 player 재사용, 출력 자원 해제, 취소와 모델 게시의 경쟁을 독립 검토 후 수정했다. iOS 실행·컴파일은 Windows에서 확인하지 않았다.

### 설치와 남은 실기기 검증

Android APK와 공유 JS/Wasm 컴파일을 통과했다. Galaxy S24+(SM-S926N, Android 17/API 37)의 기존 `com.ssafy.eolssu.qa`에 `qa-local-695-96797e25`(versionCode `1794300497`)를 데이터 삭제 없이 설치했다. 기존 QA 인증서로 서명했으며 서명 항목을 제외한 638개 APK 내용이 원본 빌드와 동일함을 확인했다. 서명 APK SHA-256은 `8ebb55cedd116990a29247eef370b0f34631422afad0687a23e3c8694a1579c9`다. 로그인과 마이크 권한은 유지됐다.

실제 화면에서 홈 → AI 연주 평가 시작 → 꿩꿩장서방(자진모리, 162 BPM) → 연습 화면으로 진입했다. 원래 꺼져 있던 장단을 시험 동안 켜고 미디어 볼륨 5/15에서 보정 안내를 확인했다. 첫 시도는 `17:53:35 NotQuiet`, 한 번의 재시도는 `17:55:16 Unreliable`로 차단됐다. 두 번 모두 평가 녹음을 시작하지 않았으며 새 AAC도 만들지 않았다. 실패 보정을 차단하는 제품 경로는 관찰했지만, **실기기에서 정상 보정 적용·AAC 반영·볼륨 변경 우회는 아직 확인하지 못했다.** 연결 중단과 주변 소리, 반복 일치도 등 어느 조건이 원인인지는 현재 집계 로그만으로 확정할 수 없다.

사용자가 다음 날 재개하겠다고 요청해 시험을 중단했다. 다음 작업은 원본 음성을 로그로 남기지 않는 보정 거부 단계·클립·집계 수치 진단을 추가하고, 정상 통과와 실제 AAC를 확인하는 것이다. 통과를 얻기 위해 문턱을 느슨하게 바꾸지 않는다. 전체 곡 채점, 다른 음역·악기·환경과 iOS는 별도 미검증으로 남긴다.
