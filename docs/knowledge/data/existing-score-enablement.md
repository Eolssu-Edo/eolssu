# 기존 파일로 채점할 수 있는 36곡의 활성화 근거

S15P31E102-704. 2026-11-10 사용자가 기존 파일을 유지할 수 있는 곡을 S15P31E102-699의 악보 교정과 분리하도록 요청했다. [작업 계획](../../plans/S15P31E102-704.md)과 [활성화 스펙](../../specs/existing-score-enablement.md)을 따른다.

## 대상과 원본 대조

단소 36, 정악대금 51–78 중 62·63·65 제외, 산조대금 79–88의 36곡이다. 699의 `data/processed/scoring-audit-699/comparison.json` 및 곡별 공개 상세 스냅샷에서 동일 JGB 재변환 결과의 이벤트·시간축·곡 정보 일치를 확인한 항목이다. 해당 스냅샷의 공통 악보를 정렬된 JSON 키, UTF-8, 공백 없는 JSON으로 정규화한 SHA-256을 [적용 계획](../../../infra/catalog/scoring-plans/existing-704.json)에 고정했다. 이는 악보 원보 전체를 새로 사람 검수했거나 연주 정확도를 승인했다는 뜻이 아니다.

699에서 고치는 10곡 `19,32,37,45,50,62,63,65,104,109`는 대상에 없다. 기존 숨표·시김새·`provenance.review`도 그대로 보존한다. 따라서 기존 `enable_scoring.patch()`의 `reviewed` 승격을 사용하지 않고 `enable_existing_scores.py`에서 `is_scorable`만 바꾼다.

## 실제 AI 입력 계약과 길이

기준 소스는 `origin/develop`의 `1381bbf9`이며, `ScoreJsonNotes.kt`와 `ai/src/ai_service/api.py`를 대조했다. 공통 악보의 NOTE만 순서대로 번호를 매기고 `startTick/ticksPerBeat`, `durationTick/ticksPerBeat`를 AI의 `startBeat`, `beats`로 보낸다. 율명 반음 오프셋과 `12×octave`를 사용하며 시김새 배열의 유무를 bool로 보낸다.

로컬 Python의 Pydantic 2.11.10에서 실제 소스의 `_Camel`, `NoteIn`, `AnalysisIn` 클래스 AST를 그대로 불러 36곡의 1,838개 NOTE 전체를 검증했다. `schemaVersion=1`, NOTE/REST 종류, 음표 수, 양의 틱 단위·길이, 음 시작 순서·비중첩과 허용 BPM 단위를 통과했다. 이 검사는 입력 계약만 확인하며 pYIN 추론을 실행하지 않았다. 운영 pitches 행의 실제 연결은 공개 악보 API와 통합 검증에서 따로 확인한다.

AI 소스는 `HOP_S=0.01`, 셀당 24byte, `MAX_DTW_BYTES=4GiB`이다. 기본 BPM에서 첫 NOTE~마지막 NOTE 끝은 최대 95.25초, REST까지 포함한 곡 끝은 최대 97초다. 전체 길이와 같은 녹음으로 계산해도 36곡 모두 메모리 거절 경계 안에 있다.

| 곡 | 기대 음표 구간 | REST 포함 곡 끝 | 예상 DTW byte |
| --- | ---: | ---: | ---: |
| 67 인연 | 95.25초 | 97초 | 2,217,420,000 |
| 54 뱃노래(기본음) | 83초 | 84초 | 1,673,280,000 |
| 55 뱃노래(장식음) | 83초 | 84초 | 1,673,280,000 |

계산은 `기대 음표 초 × 녹음 초 ÷ 0.01² × 24`다. 느린 BPM이나 길어진 녹음까지 성공을 보장하지 않으며, 기존 서비스의 녹음 길이 정책을 바꾸지 않는다. 운영 AI 코드가 이 버전인지와 실제 추론 결과는 운영 담당자가 확인한다.

## 실행 검증과 실제 추론 절차

격리된 로컬 Docker MySQL 8.4에서 채점 UPDATE가 없는 상태로 활성화·충돌 검증 3개가 실패하는 것을 먼저 확인했다. 이후 한 트랜잭션의 행 잠금·스냅샷 비교·조건부 UPDATE를 구현했다. 악보 및 검수 정보, songs의 나머지 열과 현재/과거 판본 모범 음원 행의 해시를 읽어 적용 전후로 비교한다. 이미 켜진 곡의 `updated_at`도 변하지 않는다. 마지막 88번 곡의 충돌이면 앞 곡의 변경도 롤백한다. 표준 실행·테스트 명령은 [catalog README](../../../infra/catalog/README.md#기존-악보를-유지한-36곡-채점-켜기)에 있다.

실제 AI 확인은 운영 담당자가 배포 버전과 메모리 여유를 확인한 뒤 직렬로 수행한다. 각 곡의 실제 전체 NOTE 입력을 입력 모델로 검증하고, 선택한 짧은 구간에 해당하는 통제 오디오를 내부 HTTP 주소로 제공한다. `/v1/analyses`에 해당 구간의 원래 NOTE idx·BPM·단위로 요청해 HTTP 200, `status=DONE`, NOTE idx 보존과 결과 개수를 확인한다. 실패하면 HTTP 상태·실패 코드·곡 ID·구간·모델 버전만 기록하고 서명 URL은 출력하지 않는다. 구간 샘플 성공을 전곡 전체 연주 성공이나 사람 연주의 정확도 검증으로 보고하지 않는다. 전곡 추론은 36곡을 한꺼번에 실행하지 않고 CPU·메모리·백엔드 제한 시간을 확인한 뒤 대표 악기·최장 곡부터 진행한다.

운영 활성화와 추론 결과는 실행 담당자가 [704 계획](../../plans/S15P31E102-704.md)에 기록한다. 본 구현 작업자는 운영 쓰기를 하지 않았다.

2026-11-10 후속 운영 검증에서 36곡 모두 활성화됐고, 실제 pyin-5 API에 곡별 짧은 합성 연주를 입력해 36/36 DONE 응답을 확인했다. 전체 1,838개 음표는 운영 pitches로 변환해 입력 모델을 통과했다. 56은 적용 전에 이미 활성화돼 실제 UPDATE는 35곡이며 악보·검수 표시·음원 행은 보존됐다. 전곡 전체 길이 연주와 사람 연주 정확도는 검증하지 않았다. [실행·백업 기록](../../plans/S15P31E102-704.md#운영-완료-기록)을 참조한다.
