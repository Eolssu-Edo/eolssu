## 정악대금까지 포함한 네 악기 청취본

같은 날 사용자가 정악대금도 포함하도록 확인했다. 네 번째 입력은 공개 56의 악보를 내려받아 `music.ticksPerBeat`만 4→6, `score.scoreVersion`만 1→2로 바꾼 검토 판본이다. 이벤트 26개(25음·1쉼)와 모든 ID·시작/길이 tick·음높이·운지·숨표·8각 32정간을 그대로 보존했다. 숨표를 포함한 표시 슬롯은 35개다. 기존 56의 수업 원보는 정간보만 있으며 박자표·전통 장단명·BPM 수치는 인쇄돼 있지 않다. PDF SHA-256은 `e30b89dee0e9d81979b576e124242ca59648b6dc99b32b108de081e5bf100c1f`다. 4정간 구절과 수업 시범의 한배를 맞춰 정간당 4분음표 1박으로 해석한 연습 편곡이다.

기존 비율을 유지한 채 77 BPM만 넣으면 음악 길이는 37.403초, 실제 한 정간은 1.5박이 된다. 정확한 77 BPM 편곡에서는 32박 24.935065초이며, 단모리 한 주기는 24tick·8소박·3.116883초다. v1 JSON을 같은 판본명으로 덮어쓰지 않았다.

최종 생성 기준은 `develop dfe78ebd`다. `preview-four-instruments/`에 네 CAT 모범 음원·MIDI·수행 시간표와 단모리 혼합 청취본을 모두 만들었다. 정악대금 검토 악보 SHA-256은 `750ad93ee1ea2da738a4891e56fa62b17b5cae49c77c62ad5eb7d2f8338d2add`, CAT M4A는 `3cee9f208a1725af045a04e6054ae8915e2114832f2e130f9077f62851844118`, 혼합 청취본은 `2f93820f1258e50076460d8f82f1596d0db8b72d795e32b2449f886d0896d110`다. 네 혼합 파일은 모두 25.485079초이며 실제 디코딩에서 클리핑이 없었다.

운영 정악대금 56은 기존 v1·90 BPM을 유지한다. 처음 점검했을 때 `ApiEvaluationRepository`와 `ResultViewModel`은 저장 결과의 판본과 현재 공개곡 판본이 다르면 결과 화면의 악보 연결을 실패 처리했다. 서버의 취약 구간·구간 비교도 `ScoreChanged`를 반환하고 진행 중 분석은 판본 변경을 거부했다. 저장된 점수·음표 결과 API는 조회되지만, 구판 음원 행을 남기는 것만으로 이전 결과 화면까지 보존되지는 않았다. 이에 아래 후속 구현에서 구판 보관·정확한 판본 조회와 제출 판본 검사를 추가했다. 운영 교체는 해당 코드와 새 앱의 게시 후 수행한다.

서버의 보충 장단 매핑은 기존 세 v1과 정악대금 v2를 각각 명시적으로 허용한다. sourceId·악기·JGB 해시·판본이 맞아야 하며 56 v1에 v2 반주를 잘못 붙이지 않는다. 최종 관련 서버 단위 검사 21건과 격리 MySQL HTTP API 13건이 통과했다. 실제 API 경로에서 네 판본의 보충 단모리·BPM·악보 원문·판본·NULL FK를 확인했다. 앱 시간 예약과 기존 응답 계약 검사 12건도 통과했다. 세 판본 단계의 서버 전체 빌드는 704건 통과·opt-in 스냅샷 1건 건너뜀이었으며, 정악대금 추가 후에는 영향받은 검사만 다시 실행했다.

정악대금 v2 CAT77은 최신 `ai/src`를 읽기 전용으로 넣은 네트워크 격리 컨테이너에서 실제 `/v1/analyses`·FFmpeg·pYIN·DTW를 통과했다. 정상 입력은 총점·음정·박자·길이 모두 100점, 25개 음표 모두 CORRECT였다. 같은 음원에 정답만 4반음 올린 대조는 총점 4점·음정 4점(24 PITCH·1 CORRECT), 무음은 FAILED/NO_SOUND였다. 정상·대조 모두 v2와 25개 음표 ID를 보존했다. 모델은 `pyin-5`, 채점은 `note-mean-1`이다. 파일 fetch만 검증한 로컬 CAT 바이트로 대체했으므로 공개 업로드·로그인 세션·실제 악기 녹음 검사로 확대하지 않는다. 증적은 `grading56/results.json`에 보관했고 컨테이너는 종료·삭제했다.
