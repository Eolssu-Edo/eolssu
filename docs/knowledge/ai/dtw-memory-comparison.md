## 경로·비용·판정

실제 `score`를 호출하고 그 안의 librosa DTW 호출을 잠시 관찰한다. 판정 로직은 복제하지 않았다. 반환 경로는 마지막 프레임 쌍에서 첫 프레임 쌍으로 거슬러 가며 양 끝을 포함한다. float64 비용을 사용한다.

| 사례 | 확인한 결과 |
| --- | --- |
| 단일 프레임 | 경로 `[[0,0]]`, 비용 0, DONE·100점 |
| 쉼 포함 4프레임 | 양쪽 무성은 0, 한쪽 무성은 300. 대각 경로·비용 0, 요청 음 ID 7·9 보존 |
| 같은 음 3개 | 세 음 모두 CORRECT. 같은 높이의 프레임 정렬과 실제 재발음 검출을 혼동하지 않는다 |
| 정답 3·녹음 2프레임 | 경로 `[[2,1],[1,0],[0,0]]`, 비용 50. 대각·수직 후보가 동점일 때 대각 우선 |
| 전부 무음 | FAILED·NO_SOUND, DTW 호출 없음, 음별 결과 없음. MISSED 결과를 만들어 넣지 않음 |
| 일정한 f0 2·4·8초 | 각 200·400·800프레임. 대각 경로·비용 0, DONE·100점 |

동점 순서는 대각 `[1,1]` → 수평 `[0,1]` → 수직 `[1,0]`이다. 설치된 librosa 1.0.0의 `__dtw_calc_accu_cost`는 순서대로 순회하며 더 작을 때만 갱신한다. 대각 이동의 추가 비용은 0, 나머지는 50이다.

대각 후보가 최솟값이 아닌 동점도 별도로 확인했다. 비용 표 `[[0,0,0],[0,200,0],[0,0,100]]`의 최종 비용은 200이며 경로는 `[[2,2],[2,1],[1,0],[0,0]]`다. 수평과 수직이 동점인 마지막 칸에서 수평이 선택된다. 이 표는 우선순위 검사용이며 녹음 품질 사례가 아니다.

8개 사례를 독립 프로세스에서 각각 3회 실행했다. 입력 해시·경로·비용·전체 채점 결과를 포함한 snapshot은 사례별로 3회 모두 같았다. 시간과 메모리는 비교에서 분리했다. 6000 BPM의 1프레임 사례는 경계 검사만을 위한 값이며 제품 지원 BPM이 아니다.

## 작은 입력 측정

환경: Windows 11 `10.0.26200`, AMD64, 논리 CPU 20개, Python 3.12.10, numpy 2.5.4, librosa 1.0.0. OPENBLAS_NUM_THREADS와 OMP_NUM_THREADS는 1로 지정했다. NUMBA_NUM_THREADS는 별도 지정하지 않았다. 잠금 파일 해시는 `5fc91fbbd72adf4a6b2f45f084584a8309068256874a610ee1f652732a352818`이다.

각 프로세스에서 단일 프레임으로 준비한 뒤 score 관찰 구간을 측정했다. 아래 시간에는 관찰·결과 변환의 작은 비용도 포함한다. tracemalloc은 해당 구간의 Python 추적 할당이며 전체 프로세스 메모리와 다르다.

| 양쪽 길이 | 반복 | 시간 중앙값 ms | tracemalloc 최대 bytes 범위 | 프로세스 최대 RSS bytes |
| --- | --- | --- | --- | --- |
| 2초 | 3 | 13.973 | 979633~979633 | 123219968 |
| 4초 | 3 | 18.737 | 3874233~3874353 | 125743104 |
| 8초 | 3 | 40.971 | 15423433~15423433 | 138031104 |

프로세스 최대 RSS는 Windows GetProcessMemoryInfo의 PeakWorkingSetSize다. 모듈 읽기와 JIT 준비를 포함한 프로세스 생애 최댓값이며 score 구간만의 증가량이 아니다. U1은 RSS 1GiB의 강제 제한을 구현하지 않았고, 최대 800×800인 고정 사례만 받는다. 자식 프로세스당 60초 제한은 준비도 포함한다. U4에서 계획한 준비 제외 시간 제한과 구분한다.

이 환경의 tracemalloc 값은 칸당 약 24.1~24.5바이트다. 기존 macOS 측정의 약 20바이트와 같다고 쓰지 않는다. 관찰을 제외한 plain score도 같은 입력에서 975385·3868369·15414369바이트로 약 24.1~24.4바이트였다. 따라서 차이를 관찰 도구의 영향으로만 설명할 수 없다. 배열의 임시 할당·라이브러리·실행 환경 차이의 원인은 아직 분리하지 않았다.

예산 검사의 `24×N×M`은 기존 API와 같은 근사치이며 실제 peak의 엄밀한 상한이 아니다. 향후 긴 입력의 자원 제한에는 추가 메모리와 강제 종료 수단이 필요하다. 이 결과로 긴 녹음의 안전성·운영 처리 시간·동시 요청 수를 보장하지 않는다.

## 리뷰 후 예상 메모리 계산 수정

첫 기록의 반복음 사례는 마지막 음 길이만 사용해 3×3 비용 표의 예상치를 216바이트가 아닌 72바이트로 계산했다. 시작 박이 없으면 전체 음 길이를 합산하고, 시작 박이 있으면 마지막 음 끝에서 첫 음 시작을 뺀다. 따라서 중간 구간 이전의 시간도 계산에서 제외한다. 서비스 채점 코드는 바꾸지 않았다.

예산 100바이트에서 반복음 실행을 거절하는 사례와 첫 시작 박이 10인 사례가 수정 전에 실패했고 수정 뒤 통과했다. 쉼을 포함한 길이도 검사한다. 관련 테스트는 11개다. 수정된 도구로 24회를 다시 실행해 모든 입력 해시·경로·비용·판정 snapshot이 기존과 같고 반복음 예상치가 3회 모두 216바이트임을 확인했다. 위 측정 표도 이 재실행 결과다. 예전 `u1-baseline.json`은 잘못된 예상치를 포함하므로 이후 후보 비교의 기준 기록으로 사용하지 않는다.

## C0에서 승인한 연결 방식

- 이 도구는 기준 관찰용이다. `score`가 DTW 호출 전에 전체 C를 만들기 때문에 DTW 호출만 후보로 교체하면 비용 행렬 할당이 남는다.
- 사용자 승인 뒤 U2에서 전체 C를 만들기 전의 `expected·detected → path` 부분을 `_align`으로 분리했다. 기본 함수는 원래의 전체 DTW를 호출한다. 공개 score 입력·결과·API·모델 버전은 그대로이며 판정 코드를 복제하지 않았다. U1 당시에는 서비스 코드를 수정하지 않았다.
- 후보는 단독 평가 프로세스의 문맥 안에서만 `_align`을 잠시 교체한다. 정상 반환과 경로 없음 예외 모두 원래 함수로 복구하는 테스트를 뒀다. 서비스에서는 후보를 사용하지 않으며 다중 스레드에서 이 교체 도구를 사용하지 않는다.
- U4의 큰 입력에 앞서 OS별 강제 메모리 제한 가능 여부와 추가 할당 예산을 확인해야 한다. 현재 RSS는 관측값일 뿐 메모리 제한 장치가 아니다.

## U2 후보 구현과 작은 입력 검증

코드: [후보 A·B](../../../ai/evaluation/dtw_candidates.py), [실제 score 연결 CLI](../../../ai/evaluation/dtw_candidate_check.py), [테스트](../../../ai/tests/unit/test_dtw_candidates.py). numba는 기존 librosa의 잠긴 의존성을 사용하며 새 패키지나 모델을 추가하지 않았다. 측정 환경의 numba는 0.68.0이고 JIT는 활성 상태였다.

| 후보 | 구현한 저장 방식 | 보존·실패 규칙 |
| --- | --- | --- |
| A | float64 두 행으로 진행하고 중간 행만 보관한다. 역추적할 블록의 uint8 방향 표만 재계산하며 이전 표는 다음 블록 전에 해제한다. 초기 K는 min(N, ceil(sqrt(8N)))이다 | 비용 계산 순서와 동점의 대각→수평→수직 순서를 유지한다. 전체 C·D는 만들지 않는다. 작은 N이나 시험용 K에서는 한 블록이 전체 행을 포함할 수 있다 |
| B | 중심선 주변의 허용 칸만 평탄한 uint8 방향 배열로 저장한다. 누적 비용도 최대 band 폭의 두 행만 사용한다 | 폭은 0.5·1·2초로 별도 실행한다. 무경로는 NO_PATH로 따로 반환하고 전체 DTW로 자동 전환하거나 MISSED 판정을 만들지 않는다 |

후보 A는 20개 입력 모양에 K의 기본값·1·2·3·4를 적용한 100개 비교 조건에서 기존 경로와 일치했다. 쉼·반복음·동점·서로 다른 길이·단일 행/열·소수 센트 사례를 포함한다. B는 전체 폭에서 기존 DTW와 비교하고, 좁은 폭에서는 같은 허용 칸을 가진 비용 표를 기존 DTW에 넣어 별도로 비교했다. 이를 위해 테스트에서만 작은 전체 표를 사용하며 후보 자체는 전체 비용 표를 만들지 않는다.

기존 U1 기록 8개의 입력 해시·경로·비용·전체 판정이 함수 분리 뒤에도 같았다. CLI에서 A와 B의 0.5·1·2초 폭을 각각 8사례 실행했다. 각 방식에서 7개는 DONE, 전부 무음인 1개는 FAILED·NO_SOUND이며 U1의 판정과 경로·비용이 일치했다. 초단 경계 입력에서는 band가 전체 폭을 포함하고 긴 일정음에서는 대각 경로가 정답이므로, 이 결과를 템포 변화·실제 연주 품질의 근거로 확대하지 않는다.

### 자체 확인에서 수정한 band 경계

실수 중심선 계산은 201×117 입력의 100행에서 중심 58을 57.999…로 만들 수 있었다. 폭 1일 때 포함해야 할 오른쪽 59열이 빠져 기준 경로와 달라지는 테스트가 실패했다. 경계는 `|j×(N−1) − i×(M−1)| ≤ 폭×(N−1)`을 만족하는 정수 칸으로 계산하도록 수정했다. 같은 중심선·폭을 정확하게 구현한 것이며 폭을 넓히거나 품질 허용값을 바꾼 것은 아니다.

### 800×800 할당 점검

이 표는 각 방식별 독립 프로세스에서 한 번 실행한 정렬 단독 점검이다. U1과 달리 score 전체가 아니며 2프레임으로 해당 정렬을 준비한 뒤 측정했다. 입력은 양쪽 모두 800개의 0센트이고 B의 반폭은 50프레임이다. 세 방식 모두 같은 대각 경로를 반환했다.

| 방식 | tracemalloc 최대 bytes | 준비를 포함한 프로세스 최대 RSS bytes |
| --- | --- | --- |
| 기존 전체 DTW | 15386928 | 138276864 |
| A | 224960 | 131592192 |
| B | 206317 | 141029376 |

추적 할당은 감소했지만 B의 프로세스 최대 RSS는 이 1회 측정에서 오히려 컸다. 모듈·JIT 준비까지 포함한 생애 최대 RSS이므로 정렬 배열의 크기와 같은 값이 아니다. 이 표로 운영 메모리 절감률·속도 우열·장시간 지원을 확정하지 않는다. U4에서 조건별 반복과 전체 처리 측정을 해야 한다.

원시 결과 `data/processed/dtw-286/u2-small-memory.json`에는 실행한 자식 프로세스 코드인 probeSource와 소스·잠금 해시를 함께 남겼다. 이 측정 코드는 저장소에 없어 위 표는 명령으로 다시 만들 수 없다. U4의 측정 도구를 저장소에 둔 뒤 같은 조건을 다시 잰다. Python·numpy·librosa와 스레드 설정은 U1과 같으며 서로 다른 실행 구간의 시간·메모리를 직접 전후 개선율로 계산하지 않는다.

### 후보 CLI 재현

결과 JSON의 `computedCells`는 비용을 계산한 칸 수다. 기준·A는 N×M이고, B는 band 안의 칸 수이며 칸마다 uint8 방향 하나를 저장한다. 8초 정상 사례(800×800)에서 기준·A는 640,000칸, B의 반폭 0.5·1·2초는 각각 78,250·150,700·280,600칸이었다.

U1의 잠금 환경·짧은 Numba 캐시를 준비한 뒤 ai 폴더에서 실행한다. 임의 길이의 외부 입력을 받지 않고 U1의 작은 고정 사례만 사용한다.

