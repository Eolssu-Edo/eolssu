## U4 곡별 시간·메모리 측정

현행과 A, B 세 폭을 비교한다. 네 곡에 BPM 40·중간·기본을 적용하고, 각 방식과 입력을 별도 프로세스로 다섯 번 실행한다. 정렬 시간은 음높이 배열을 만든 뒤 정렬 함수만 잰다. m4a 전체 시간은 디코딩·pYIN 음높이 추정·음량 계산·채점을 포함한다. 앱과 네트워크 시간은 포함하지 않는다. 입력 m4a는 검수된 악보와 사인파·배음으로 별도 생성하며 실제 연주나 팀원이 제공한 음원은 아니다. 악보 마지막 쉼까지 녹음에 포함하며, 채점 기준 프레임은 서비스와 같이 마지막 음 끝까지다.

기준 방식의 전체 행렬은 `24 × 정답 프레임 × 녹음 프레임`으로, 후보는 필요한 저장 공간과 여유를 더해 사전 추정한다. 512MiB를 넘는 정렬은 실행하지 않는다. 추정에 모듈 준비와 pYIN의 사용량은 포함되지 않는다. 모든 프로세스와 자식 프로세스의 커밋 메모리는 작업 개체로 1GiB까지 제한한다. 측정 프로세스의 상주 메모리는 계획의 1GiB보다 여유를 두어 768MiB로 강제 설정한다. 상한 근처의 RSS 수치는 제한 영향이 있을 수 있다. RSS는 준비를 포함한 프로세스 생애 최대이며 ffmpeg 자식의 RSS는 별도로 측정하지 않는다.

실행 전에 작은 프로세스로 커밋 메모리 제한과 시간 초과 종료를 확인한다. 상주 메모리 강제 설정과 실제 할당도 확인한다. 32MiB 상한 시험에서는 최대치가 설정값보다 12KiB 높게 나타났으므로 1GiB에 바로 맞추지 않았다. Windows의 강제 상한 설정과 커밋 메모리 제한은 서로 다른 기능이다. [Windows 상주 메모리 설정](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex) · [Windows 작업 개체 메모리 제한](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)

시간 제한은 실제 자식 PID를 남기고 4초간 대기하는 작은 프로세스에도 적용해 확인했다. 0.7초 제한에서 약 0.73초에 돌아왔고 기록된 자식 프로세스가 종료된 것을 확인했다. 이는 현 PC에서의 종료 확인이며 외부 서버의 제한 확인은 아니다.

시간 제한은 준비가 끝난 뒤 60초가 아니라 **준비를 포함해 60초**로 두었다. 계획보다 일찍 종료될 수 있으므로 그 경우 성공이 아니라 시간 초과로 기록한다. 어떤 방식이 실패하면 같은 입력 방식·후보의 남은 반복과 그보다 긴 입력을 실행하지 않는다. 미완료와 예산 거절은 성공한 측정값에 합치지 않는다. 측정 결과는 `data/processed/dtw-286/u4-full-rest.json`에 기록하며 Git에 올리지 않는다.

첫 시도 `u4-full.json`은 곡 끝 쉼을 빠뜨린 것을 발견해 중간에 중단했다. 이 결과는 전체 곡 성능 근거에서 제외하고, 마지막 쉼을 반영한 입력으로 다시 측정한다.

측정 환경은 Windows 11 `10.0.26200`, Intel Core i7-13700H, Python 3.12.10, NumPy 2.5.4, librosa 1.0.0, Numba 0.68.0, SciPy 1.18.1, FFmpeg 9.0.2다. `OPENBLAS_NUM_THREADS`와 `OMP_NUM_THREADS`는 1이다. 기준 코드 커밋은 `68990e1`이며, 측정 도구 SHA-256은 `95f3a38c7f57a553b58a3dd0d8d587e7df17e78e0eaf103d1238de566ac607cd`다. 후보 코드는 `94c7c6454f85d4bcd1c5634a49f8a99f037ca4976274b4c59489abd70e39f202`, 서비스 채점 코드는 `31a1de1c9889d8279733d958677e5c060421129fdde212d1c379bb612b50f875`, 잠금 파일은 `5fc91fbbd72adf4a6b2f45f084584a8309068256874a610ee1f652732a352818`이다. 각 녹음과 추정한 음높이·음량의 해시는 결과 파일에 남긴다.

### 측정 결과

600회 중 550회가 성공했고, 나머지 50회는 현행 행렬의 사전 추정이 512MiB를 넘어 건너뛰었다. 모든 곡·BPM·입력 방식·후보 조합의 시도 횟수는 다섯 번이다. 오류·시간 초과는 없었고 상주 메모리 상한 근처로 표시된 측정도 없었다. 같은 곡·BPM·입력 방식 안에서는 음높이와 음량 해시가 모든 성공 실행에서 같았다.

이번 곡 기반 측정은 저장소에 검수된 정답이 있는 단소 네 곡이다. 다른 지원 악기와 곡의 측정 자료는 확인하지 못했으므로 서비스 전체 범위의 BPM 40 지원 여부는 미확정이다.

모든 조건의 반복별 시간·최대 RSS·점수·경로 해시는 [U4 결과 표](dtw-u4-results.csv)에 있다. `seconds_1`~`seconds_5`는 반복별 측정, `peak_rss_bytes_1`~`peak_rss_bytes_5`는 각 프로세스의 생애 최대 RSS다. 중앙값과 범위는 성공한 반복만으로 계산한다. 빈 칸은 측정하지 않은 값이다. 결과 표 SHA-256은 `b05d548fa764eb61254944ba48fd8bda8341f80e0ffc94daef9928fef1da3c7e`, Git에서 제외한 원본 JSON의 SHA-256은 `e2363809530730e8c9547e92f9bc955c698440ec4894d3f6cb8ebc3bbb82a915`다.

가장 긴 도라지타령 BPM 40의 합성 m4a는 악보 끝 쉼까지 126초다. 기준 음표는 마지막 음 끝까지 124.5초이고, 디코딩 후 추정 음높이는 126.01초다. 현행의 정렬 메모리는 약 3.5GiB로 추정돼 실행하지 않았다. 아래 시간은 다섯 번의 중앙값, RSS는 다섯 프로세스의 최대값이다.

별도로 디코딩한 PCM은 126.00초이며 마지막 0.5초의 표본 최대 진폭은 0이다. 126.01초는 음높이 추정 프레임 수에 0.01초를 곱한 값이다.

| 방식 | 정렬만 시간 · 최대 RSS | m4a 전체 시간 · 최대 RSS | m4a 총점 |
| --- | --- | --- | ---: |
| 현행 | 예산 초과 | 예산 초과 | 미측정 |
| A | 1.167초 · 140.5MiB | 5.013초 · 606.6MiB | 100 |
| B 반폭 0.5초 | 0.010초 · 135.2MiB | 3.977초 · 606.9MiB | 69 |
| B 반폭 1초 | 0.014초 · 136.0MiB | 3.801초 · 606.8MiB | 87 |
| B 반폭 2초 | 0.020초 · 138.2MiB | 4.323초 · 607.5MiB | 100 |

이 입력은 현행 결과가 없어 A를 정답으로 확정하거나 B의 점수 차이를 실제 연주 정확도로 해석할 수 없다. 실제로 현행과 비교된 7개 곡·BPM 조건의 두 입력 방식에서는 A의 경로 해시와 총점이 모두 현행과 같았다. B 반폭 0.5초는 그중 다섯 조건에서 경로가 달랐고, B 반폭 1·2초는 관측된 경로 차이가 없었다. 예산 때문에 현행을 실행하지 못한 다섯 조건의 경로 일치는 미검증이다.

최대 RSS는 607.5MiB였다. 같은 곡의 m4a 전체 처리에서는 정렬 폭이 달라도 최대 RSS가 약 607MiB로 비슷해, 이번 입력에서는 음높이 추정과 준비 등 정렬 밖의 메모리 비중도 크다는 관찰과 부합한다. 각 방식은 순서대로 다섯 번 측정했으며 OS 부하와 CPU 온도를 통제하지 않았다. 이 결과만으로 운영 서버의 처리 시간이나 동시 요청 수를 보장하지 않는다.

### 마지막 쉼을 포함했을 때의 아리랑 판정

기본 BPM의 고정 음높이 입력에서 마지막 음 뒤 0.62초 무음을 추가하면 현행 총점이 100점에서 98점으로 바뀐다. 마지막 음 ID 60은 정상에서 박자 오류로 바뀌며 시작 오차가 15ms에서 625ms가 됐다. 바로 앞 ID 59의 길이 오차는 5ms에서 625ms로 바뀐다. 두 음은 같은 높이이며, 관찰된 정렬에서 ID 60에 대응한 녹음 프레임의 시작이 2813에서 2875로 이동했다. 마지막 쉼과 같은 높이 연속 음의 정렬이 상호작용한 것으로 보이지만, 사람의 실제 연주에서도 같은 문제가 생기는지는 미검증이다. 이 작업은 서비스 채점 코드를 바꾸지 않았다.

## 경로·비용·판정

실제 `score`를 호출하고 그 안의 librosa DTW 호출을 잠시 관찰한다. 판정 로직은 복제하지 않았다. 반환 경로는 마지막 프레임 쌍에서 첫 프레임 쌍으로 거슬러 가며 양 끝을 포함한다. float64 비용을 사용한다.

| 사례 | 확인한 결과 |
| --- | --- |
| 단일 프레임 | 경로 `[[0,0]]`, 비용 0, DONE·100점 |
| 쉼 포함 4프레임 | 양쪽 무성은 0, 한쪽 무성은 300. 대각 경로·비용 0, 요청 음 ID 7·9 보존 |
| 같은 음 3개 | 세 음 모두 CORRECT. 같은 높이의 프레임 정렬과 실제 재발음 검출을 혼동하지 않는다 |
| 정답 3·녹음 2프레임 | 경로 `[[2,1],[1,0],[0,0]]`, 비용 50. 대각·수직 후보가 동점일 때 대각 우선 |

| 일정한 f0 2·4·8초 | 각 200·400·800프레임. 대각 경로·비용 0, DONE·100점 |

동점 순서는 대각 `[1,1]` → 수평 `[0,1]` → 수직 `[1,0]`이다. 설치된 librosa 1.0.0의 `__dtw_calc_accu_cost`는 순서대로 순회하며 더 작을 때만 갱신한다. 대각 이동의 추가 비용은 0, 나머지는 50이다.

대각 후보가 최솟값이 아닌 동점도 별도로 확인했다. 비용 표 `[[0,0,0],[0,200,0],[0,0,100]]`의 최종 비용은 200이며 경로는 `[[2,2],[2,1],[1,0],[0,0]]`다. 수평과 수직이 동점인 마지막 칸에서 수평이 선택된다. 이 표는 우선순위 검사용이며 녹음 품질 사례가 아니다.

8개 사례를 독립 프로세스에서 각각 3회 실행했다. 입력 해시·경로·비용·전체 채점 결과를 포함한 snapshot은 사례별로 3회 모두 같았다. 시간과 메모리는 비교에서 분리했다. 6000 BPM의 1프레임 사례는 경계 검사만을 위한 값이며 제품 지원 BPM이 아니다.

## 작은 입력 측정

환경: Windows 11 `10.0.26200`, AMD64, 논리 CPU 20개, Python 3.12.10, numpy 2.5.4, librosa 1.0.0. OPENBLAS_NUM_THREADS와 OMP_NUM_THREADS는 1로 지정했다. NUMBA_NUM_THREADS는 별도 지정하지 않았다. 잠금 파일 해시는 `5fc91fbbd72adf4a6b2f45f084584a8309068256874a610ee1f652732a352818`이다.

프로세스 최대 RSS는 Windows GetProcessMemoryInfo의 PeakWorkingSetSize다. 모듈 읽기와 JIT 준비를 포함한 프로세스 생애 최댓값이며 score 구간만의 증가량이 아니다. U1은 RSS 1GiB의 강제 제한을 구현하지 않았고, 최대 800×800인 고정 사례만 받는다. 자식 프로세스당 60초 제한은 준비도 포함한다. U4에서 계획한 준비 제외 시간 제한과 구분한다.

이 환경의 tracemalloc 값은 칸당 약 24.1~24.5바이트다. 기존 macOS 측정의 약 20바이트와 같다고 쓰지 않는다. 관찰을 제외한 plain score도 같은 입력에서 975385·3868369·15414369바이트로 약 24.1~24.4바이트였다. 따라서 차이를 관찰 도구의 영향으로만 설명할 수 없다. 배열의 임시 할당·라이브러리·실행 환경 차이의 원인은 아직 분리하지 않았다.

예산 검사의 `24×N×M`은 기존 API와 같은 근사치이며 실제 peak의 엄밀한 상한이 아니다. 향후 긴 입력의 자원 제한에는 추가 메모리와 강제 종료 수단이 필요하다. 이 결과로 긴 녹음의 안전성·운영 처리 시간·동시 요청 수를 보장하지 않는다.

## 리뷰 후 예상 메모리 계산 수정

첫 기록의 반복음 사례는 마지막 음 길이만 사용해 3×3 비용 표의 예상치를 216바이트가 아닌 72바이트로 계산했다. 시작 박이 없으면 전체 음 길이를 합산하고, 시작 박이 있으면 마지막 음 끝에서 첫 음 시작을 뺀다. 따라서 중간 구간 이전의 시간도 계산에서 제외한다. 서비스 채점 코드는 바꾸지 않았다.

예산 100바이트에서 반복음 실행을 거절하는 사례와 첫 시작 박이 10인 사례가 수정 전에 실패했고 수정 뒤 통과했다. 쉼을 포함한 길이도 검사한다. 관련 테스트는 11개다. 수정된 도구로 24회를 다시 실행해 모든 입력 해시·경로·비용·판정 snapshot이 기존과 같고 반복음 예상치가 3회 모두 216바이트임을 확인했다. 위 측정 표도 이 재실행 결과다. 예전 `u1-baseline.json`은 잘못된 예상치를 포함하므로 이후 후보 비교의 기준 기록으로 사용하지 않는다.

## C0에서 승인한 연결 방식

- 이 도구는 기준 관찰용이다. `score`가 DTW 호출 전에 전체 C를 만들기 때문에 DTW 호출만 후보로 교체하면 비용 행렬 할당이 남는다.
- 사용자 승인 뒤 U2에서 전체 C를 만들기 전의 `expected·detected → path` 부분을 `_align`으로 분리했다. 기본 함수는 원래의 전체 DTW를 호출한다. 공개 score 입력·결과·API·모델 버전은 그대로이며 판정 코드를 복제하지 않았다. U1 당시에는 서비스 코드를 수정하지 않았다.
- 후보는 단독 평가 프로세스의 문맥 안에서만 `_align`을 잠시 교체한다. 정상 반환과 경로 없음 예외 모두 원래 함수로 복구하는 테스트를 뒀다. 서비스에서는 후보를 사용하지 않으며 다중 스레드에서 이 교체 도구를 사용하지 않는다.
- U4의 큰 입력에 앞서 OS별 강제 메모리 제한 가능 여부와 추가 할당 예산을 확인해야 한다. 현재 RSS는 관측값일 뿐 메모리 제한 장치가 아니다.

## U2 후보 구현과 작은 입력 검증

코드: [후보 A·B](../../../ai/evaluation/dtw_candidates.py), [실제 score 연결 CLI](../../../ai/evaluation/dtw_candidate_check.py), [테스트](../../../ai/tests/unit/test_dtw_candidates.py). numba는 기존 librosa의 잠긴 의존성을 사용하며 새 패키지나 모델을 추가하지 않았다. 측정 환경의 numba는 0.68.0이고 JIT는 활성 상태였다.

| 후보 | 구현한 저장 방식 | 보존·실패 규칙 |
| --- | --- | --- |
| A | float64 두 행으로 진행하고 중간 행만 보관한다. 역추적할 블록의 uint8 방향 표만 재계산하며 이전 표는 다음 블록 전에 해제한다. 초기 K는 min(N, ceil(sqrt(8N)))이다 | 비용 계산 순서와 동점의 대각→수평→수직 순서를 유지한다. 전체 C·D는 만들지 않는다. 작은 N이나 시험용 K에서는 한 블록이 전체 행을 포함할 수 있다 |
| B | 중심선 주변의 허용 칸만 평탄한 uint8 방향 배열로 저장한다. 누적 비용도 최대 band 폭의 두 행만 사용한다 | 폭은 0.5·1·2초로 별도 실행한다. 무경로는 NO_PATH로 따로 반환하고 전체 DTW로 자동 전환하거나 MISSED 판정을 만들지 않는다 |

후보 A는 20개 입력 모양에 K의 기본값·1·2·3·4를 적용한 100개 비교 조건에서 기존 경로와 일치했다. 쉼·반복음·동점·서로 다른 길이·단일 행/열·소수 센트 사례를 포함한다. B는 전체 폭에서 기존 DTW와 비교하고, 좁은 폭에서는 같은 허용 칸을 가진 비용 표를 기존 DTW에 넣어 별도로 비교했다. 이를 위해 테스트에서만 작은 전체 표를 사용하며 후보 자체는 전체 비용 표를 만들지 않는다.

기존 U1 기록 8개의 입력 해시·경로·비용·전체 판정이 함수 분리 뒤에도 같았다. CLI에서 A와 B의 0.5·1·2초 폭을 각각 8사례 실행했다. 각 방식에서 7개는 DONE, 전부 무음인 1개는 FAILED·NO_SOUND이며 U1의 판정과 경로·비용이 일치했다. 초단 경계 입력에서는 band가 전체 폭을 포함하고 긴 일정음에서는 대각 경로가 정답이므로, 이 결과를 템포 변화·실제 연주 품질의 근거로 확대하지 않는다.

### 자체 확인에서 수정한 band 경계

실수 중심선 계산은 201×117 입력의 100행에서 중심 58을 57.999…로 만들 수 있었다. 폭 1일 때 포함해야 할 오른쪽 59열이 빠져 기준 경로와 달라지는 테스트가 실패했다. 경계는 `|j×(N−1) − i×(M−1)| ≤ 폭×(N−1)`을 만족하는 정수 칸으로 계산하도록 수정했다. 같은 중심선·폭을 정확하게 구현한 것이며 폭을 넓히거나 품질 허용값을 바꾼 것은 아니다.

### 800×800 할당 점검

이 표는 각 방식별 독립 프로세스에서 한 번 실행한 정렬 단독 점검이다. U1과 달리 score 전체가 아니며 2프레임으로 해당 정렬을 준비한 뒤 측정했다. 입력은 양쪽 모두 800개의 0센트이고 B의 반폭은 50프레임이다. 세 방식 모두 같은 대각 경로를 반환했다.

| 방식 | tracemalloc 최대 bytes | 준비를 포함한 프로세스 최대 RSS bytes |
| --- | --- | --- |
| 기존 전체 DTW | 15386928 | 138276864 |
| A | 224960 | 131592192 |
| B | 206317 | 141029376 |

추적 할당은 감소했지만 B의 프로세스 최대 RSS는 이 1회 측정에서 오히려 컸다. 모듈·JIT 준비까지 포함한 생애 최대 RSS이므로 정렬 배열의 크기와 같은 값이 아니다. 이 표로 운영 메모리 절감률·속도 우열·장시간 지원을 확정하지 않는다. U4에서 조건별 반복과 전체 처리 측정을 해야 한다.

원시 결과 `data/processed/dtw-286/u2-small-memory.json`에는 실행한 자식 프로세스 코드인 probeSource와 소스·잠금 해시를 함께 남겼다. 이 측정 코드는 저장소에 없어 위 표는 명령으로 다시 만들 수 없다. U4의 측정 도구를 저장소에 둔 뒤 같은 조건을 다시 잰다. Python·numpy·librosa와 스레드 설정은 U1과 같으며 서로 다른 실행 구간의 시간·메모리를 직접 전후 개선율로 계산하지 않는다.

### 후보 CLI 재현

결과 JSON의 `computedCells`는 누적 비용을 계산한 칸 수다. A는 순방향 N×M에 경로 복원을 위한 블록 재계산 칸을 더한다. B는 실제 계산한 band 칸 수다. 한 행이나 한 열의 유일한 경로와 빈 행으로 인한 조기 실패는 계산하지 않으므로 0이다. 결과의 경로 비용을 따로 확인하는 반복은 이 숫자에 포함하지 않는다. 8초 정상 사례에서 기준은 640,000칸, A는 1,280,000칸이다. B의 반폭 0.5·1·2초는 각각 78,250·150,700·280,600칸이다.

U1의 잠금 환경·짧은 Numba 캐시를 준비한 뒤 ai 폴더에서 실행한다. 임의 길이의 외부 입력을 받지 않고 U1의 작은 고정 사례만 사용한다.

```powershell
uv run python -m evaluation.dtw_candidate_check --method A --out ../data/processed/dtw-286/u2-A.json
uv run python -m evaluation.dtw_candidate_check --method B --half-width-seconds 0.5 --out ../data/processed/dtw-286/u2-B.json
uv run python -m evaluation.dtw_candidate_check --method B --half-width-seconds 1 --out ../data/processed/dtw-286/u2-B-1s.json
uv run python -m evaluation.dtw_candidate_check --method B --half-width-seconds 2 --out ../data/processed/dtw-286/u2-B-2s.json
uv run pytest tests/unit/test_dtw_candidates.py tests/unit/test_dtw_baseline.py
```

CLI JSON에는 후보·폭·상태·경로·비용·전체 판정과 후보·판정·입력 정의 코드·잠금 파일 해시를 저장한다. U2 구현의 정식 리뷰, U3의 곡·오류별 품질 비교와 U4의 길이·BPM별 측정은 아직 진행하지 않았다.
