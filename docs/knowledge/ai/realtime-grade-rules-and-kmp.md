## 서버 기준과 실시간 처리의 차이

서버는 연주 후 전체 녹음과 악보를 DTW로 맞춘다. DTW는 길이가 다른 두 시간 흐름의 대응 위치를 찾는 계산이다. 실시간 앱은 앞으로 연주할 소리를 알 수 없어 같은 결과를 즉시 보장할 수 없다.

| 항목 | 서버 구현 | 실시간에서 필요한 선택 |
| --- | --- | --- |
| 음높이 | pYIN 추정과 배음 보정 후, 정렬된 유성 구간의 가운데 60%에서 중앙값을 쓴다. | YIN의 짧은 창을 어떻게 음 하나로 모을지 정해야 한다. |
| 조율 | 꾸밈음이 아닌 음들의 오차를 연주 전체에서 모아 중앙값으로 보정한다. | 이미 끝난 신뢰 가능한 음만 사용하거나 시작 전 기준음을 받는 방법을 비교한다. |
| 빠르기 | 이웃 음 시작 오차의 기울기 중앙값으로 연주 전체의 빠르기 차이를 뺀다. | 과거 음만으로 추정하면 초기·변속 구간에서 다른 값이 나온다. |
| 박자 이웃 | 유효 음 기준 앞뒤 최대 3음을 비교한다. | 과거 최대 3음만 쓰거나 뒤의 3음을 기다려야 한다. 두 방법의 지연·오류를 비교한다. |
| 흔들림 | 유효 음 12개 이상에서 이웃 시작 오차 차이의 MAD를 사용한다. | 12개는 서버의 통계 사용 조건이다. 앱의 초기 학습 음 수로 자동 채택하지 않는다. |
| 길이 | 음 시작부터 마지막 유성 프레임까지를 정렬 뒤 계산한다. | 연주 중인 음의 최종 길이는 아직 알 수 없다. 종료 전에는 길이 등급을 확정하지 않는다. |
| 놓친 음 | 정렬된 유성 프레임이 목표 길이의 30%보다 적으면 MISSED 후보가 된다. | 분석 누락·아직 시작 전·진짜 누락을 나눠야 한다. 같은 비율을 바로 적용하지 않는다. |

서버의 판정은 CORRECT·PITCH·TIMING·MISSED이며, 연주 전체 무음·짧은 입력은 별도 실패다. 길이 오차는 부분 점수에 영향을 주지만 별도의 DURATION 판정은 없다. 이 값을 앱의 네 등급으로 이름만 바꿔 대응시키지 않는다.

## 음높이와 조율

목표 주파수는 악보의 황종 주파수와 율명·옥타브에서 계산한다. 주파수 비율을 반음보다 세밀한 단위로 나타내는 센트를 사용하며 100센트가 반음이다.

```text
목표 Hz = 악보 hwangHz × 2^(목표 반음 번호 / 12)
오차 cent = 1200 × log2(검출 Hz / 목표 Hz)
조율 보정 후 오차 = 오차 cent - 적용한 조율 보정값
```

515의 `comparePitch`는 조율 보정 없이 ±50센트 양끝을 포함해 Match로 본다. 이는 종합 등급 Great의 확정 기준이 아니다. `PitchConfirmation`의 두 입력 간 100센트 확인은 순간적인 흔들림을 거르는 별개의 규칙이다. 통과했다고 목표 음에 맞았다는 뜻도 아니다.

서버 조율 보정 상한은 기본 100센트와 곡 내 최소 음 간격에서 음정 허용값과 여유 10센트를 뺀 값 중 작은 값이다. 최소 간격이 100센트이고 음정 허용이 50센트면 상한은 40센트다. 추정 보정량이 상한을 넘으면 서버는 보정하지 않고 `tuning_out_of_range`를 남긴다. 상한·여유값은 코드 기준이며 모든 악기에 검증된 제품 규칙으로 일반화하지 않는다.

실시간 제안은 기준음 사전 측정과 과거 완료 음의 중앙값 추정을 비교하는 것이다. 중앙값 추정에는 목표가 확실한 음만 넣고, 무음·꾸밈음·분석 불가·옥타브 의심 구간은 제외하는 안을 검토한다. 업데이트 주기와 최소 음 수, 보정값 변경 시 과거 안내를 다시 평가할지는 미정이다. 실제 잘못 분 음을 조율 차이로 흡수하지 않는지 별도로 검사한다.

### 옥타브 처리

서버 `_undo_subharmonic`은 추정 f의 주파수 성분이 2f 성분의 0.1배보다 작으면 추정을 2f로 올린다. 이는 모든 옥타브 오류를 고치는 규칙이 아니며 앱에는 아직 없다. 515의 강한 두 번째 배음 합성음에서는 반대로 한 옥타브 높게 잡는 약점이 관찰됐다. 따라서 서버의 보정을 그대로 옮기거나 모든 검출값을 절반으로 낮추지 않는다.

후속 구현 후보는 같은 시간 구간의 f/2·f·2f 성분과 주기 정보를 함께 비교하되, 기준 음과 같아지는 방향으로 강제 보정하지 않는 것이다. 옥타브를 실제로 틀리게 분 입력과 도구가 잘못 잡은 입력을 구별할 자료가 먼저 필요하다. 이 Task에서는 알고리즘이나 임계값을 채택하지 않는다.

## 박자와 길이

서버의 시작 허용값은 `max(0.125 × 한 박의 초 길이, 4 × 흔들림)`이다. 흔들림은 이웃 음 사이의 시작 오차 차이에서 전체 빠르기 차이의 영향을 먼저 제거한 뒤 계산한다. 제거한 값들의 중앙값으로부터 절대 편차의 중앙값을 구하고 1.4826/√2를 곱한다. 12개 미만의 유효 음에서는 흔들림을 0으로 둔다. BPM 96이면 한 박 625ms, 최소 시작 허용은 78.125ms다. 박은 악보의 BPM 단위에 맞추며 정간 수와 혼동하지 않는다.

계산 순서는 다음과 같다. 시작 오차와 목표 시작 시각의 단위는 초다.

```text
drift = median(이웃 시작 오차 차이 / 이웃 목표 시작 시각 차이)
steps = 이웃 시작 오차 차이 - drift × 이웃 목표 시작 시각 차이
spread = 1.4826 / √2 × median(abs(steps - median(steps)))
```

마지막 식은 유효 음이 12개 이상일 때 적용한다. 예를 들어 전체 빠르기 차이만으로 이웃 시작 오차 차이가 50ms와 100ms를 번갈아 보인다면, 보정 전 중앙 절대 편차는 25ms다. 이를 그대로 사용하면 BPM 96에서 허용값이 약 104.84ms로 넓어진다. 빠르기 영향을 정확히 제거해 steps가 모두 0이면 최소 허용값 78.125ms가 유지된다. 이는 계산 순서를 설명하는 예시이며 실제 녹음 측정값이 아니다.

서버는 각 음의 전체 기준 시작 오차와 앞뒤 이웃 기준 오차 중 절대값이 작은 쪽을 판정에 쓴다. 이웃 기준에는 전체 빠르기 차이 제거도 포함된다. 실시간 제안에서 사용할 오차를 이 계산과 같은 값이라고 부르면 안 된다.

| 실시간 후보 | 장점 | 손실·미정 사항 |
| --- | --- | --- |
| 과거 완료 음 최대 3개로 예상 시작을 계산 | 미래 입력을 기다리지 않는다. | 처음 몇 음·갑작스러운 변속에서 통계가 불안정하다. 추정식과 부족할 때의 대체 규칙은 미정이다. |
| 뒤의 3음까지 기다려 완료 결과 계산 | 서버의 국소 이웃 조건에 더 가깝다. | 뒤 3음의 길이만큼 기다린다. 전체 통계 차이까지 없어지지는 않는다. |
| 연주 중에는 음높이만 안내하고 박자·길이는 종료 후 제공 | 검증되지 않은 실시간 종합 등급을 피한다. | 즉시 네 등급을 보여 주려는 요구를 충족하지 못한다. |

시작을 아는 방법도 별도로 검증한다. 높이가 다른 음은 목표 변화로 찾을 수 있지만 같은 음 반복은 높이만으로 경계가 나뉘지 않는다. 서버는 RMS 감소와 상승을 사용하며, 끊지 않은 동음은 구별하기 어렵다는 한계가 있다. 앱은 동음·숨소리·쉬는 박·연속음을 포함한 기준 녹음으로 경계 검출부터 확인해야 한다.

길이의 서버 기본 허용은 목표 길이의 25%다. 예를 들어 목표 400ms이면 100ms다. 이는 서버 `_credit` 부분 점수의 허용값이며 앱의 네 등급 경계가 아니다. 음 종료 시점의 확정 방법과 늦게 도착한 창을 기다리는 시간도 미정이다.

## 네 등급과 보류 상태의 초안

다음은 역할 제안이다. 숫자와 합성 규칙은 채점 기준 담당자·FE 담당자가 실제 입력 비교 후 결정한다. 승인 전에는 화면 문구나 API 계약으로 사용하지 않는다.

| 상태 | 제안한 의미 | 아직 결정할 사항 |
| --- | --- | --- |
| Perfect | 확정된 비교 항목이 엄격한 범위 안이다. | 음높이·박자·길이 각각의 엄격한 범위 |
| Great | 확정된 항목이 기본 허용 범위 안이다. | 서버 기본값 채택 여부, 항목 간 합성 |
| Good | 기본 범위를 벗어났지만 안내할 수 있는 근접 연주다. | 바깥 경계, 등호 처리, 한 항목만 벗어난 경우 |
| Bad | 근거가 충분한 완료 음이 Good 범위 밖이거나 놓친 음으로 확정됐다. | 확정 조건과 누락 유예시간 |
| 보류 | 입력 없음·분석 불가·2회 확인 대기·조율 준비·음이 아직 진행 중인 상태다. | 사용자에게 표시할 방법과 잠정 결과 수정 정책 |

미검출을 바로 Bad로 표시하지 않는다. 아직 확보하지 않은 박자·길이를 0점으로 넣어 네 등급을 만들지도 않는다. 꾸밈음은 515처럼 일반 음높이 정답 판정에서 제외하고, 제외 항목을 만점 처리할지 종합 등급을 보류할지 결정해야 한다. 서양식 반음 근접만으로 국악 표현을 모두 채점할 수 있다고 설명하지 않는다.

검토할 합성 방식은 가장 나쁜 항목을 따르는 방식과 항목별 점수 가중합이다. 전자는 한 항목의 분석 실패에 민감하고 후자는 잘못 분 음을 다른 항목이 상쇄할 수 있다. 서버는 음높이 오류면 박자·길이 부분 점수도 0으로 만들지만, 이를 앱에 그대로 채택할지는 미정이다. 서버의 점수 합산 버전 `note-mean-1`과 네 등급 기준은 별도로 관리해야 한다.

## KMP 역할과 시간 연결

KMP는 Kotlin 공통 코드를 Android·iOS에서 함께 쓰는 구성이다. 공통 계산과 기기별 마이크 처리를 나누되 기존 구조를 사용한다. 새 모듈·네트워크 API는 이 초안에서 요구하지 않는다.

| 위치 | 구현된 역할 | 후속 제안 |
| --- | --- | --- |

[515 연결 구현](../../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/practice/PracticePitchSession.kt)은 녹음 시작·재개 시 파일 샘플 위치와 악보 경과시간을 연결한다. 일시정지한 실제 시간을 악보 시간에 더하지 않는다. 이벤트를 넘는 창·옛 녹음·늦은 입력을 현재 음에 억지로 붙이지 않는다. 현재와 직전 결과는 원본 이벤트 ID를 유지하며 입력 시각 기준 300ms 뒤 만료한다. 입력이 없어도 만료 작업이 동작한다.

기기 단조 시각은 서버 시각과 직접 빼지 않는다. 지연은 창 길이, 2회 확인의 대기, 작업 대기, 화면 반영을 나눠 측정한다. 창 안에 이미 들어 있는 시간과 추가 대기를 중복 합산하지 않는다. 515의 2048샘플/44,100Hz는 약 46.44ms 창이며 이동은 882샘플로 20ms다. 2회 확인은 보통 20ms를 추가하지만 음 시작부터 화면 표시까지 20ms라는 뜻이 아니다.

새 등급 결과 모델을 만들 때는 이벤트 ID·녹음/구간 ID·입력 시각·잠정/완료 여부·보류 사유·적용한 조율값·규칙 버전을 보존하는 안을 검토한다. 기존 PitchFeedback에 이 필드가 모두 있다는 뜻은 아니다. 내부 모델 제안이며 서버 요청·응답 필드 추가가 아니다.

## 비교 검증 계획

다음은 미실행 계획이다. 362 작성만으로 자동 검사나 기기 검증을 완료 처리하지 않는다. 등급 수치를 정하기 전에는 정확도 합격선을 임의로 만들지 않는다.

| 검증 | 입력·방법 | 비교할 결과 |
| --- | --- | --- |
| 계산 규칙 | 기준 주파수·정확한 시작/길이를 갖는 고정 입력, 각 경계의 바로 아래·같음·바로 위 | 음높이/박자/길이의 단위와 등호, 보류 사유, 합성 결과 |
| 조율·빠르기 | 고정 조율 이동, 전체 속도 차이, 실제로 틀린 한 음, 중간 변속 | 보정 전후 오차, 정상 음 오탐, 틀린 음의 잘못된 보정 |
| 초기 구간 | 유효 음 0·1·11·12·13개, 중간 미검출과 꾸밈음 | 초기 보류와 통계 사용 조건, 과거 결과 수정 여부 |
| 동음·옥타브 | 반복 동음, 끊지 않은 음, f와2f 성분을 바꾼 신호, 실제 악기 녹음 | 경계 누락, 옥타브 오류, 근거 없는 강제 보정 여부 |
| 짧은 음 | 40·60·100·160ms와 여러 시작 위치, 꾸밈음 | 검출 누락과 음이 끝난 뒤 확정되는 비율, 확인 지연 |
| 같은 녹음 비교 | 같은 파일·악보·버전을 서버와 앱 오프라인 분석에 사용 | 이벤트별 음높이/시작/길이 차이, 보류·오류 분포. 서버 결과는 음높이 정답으로 단정하지 않는다. |
| 미래 입력 차단 | PCM 창을 입력 시각 순서대로 공급하고, 해당 시각 이후의 샘플·음·통계에 접근하지 못하게 한다. | 같은 앞부분을 가진 두 입력에서 뒤쪽만 바꿔도 이미 제공한 잠정 결과가 동일한지 확인한다. |
| 실제 기기 | Android와 iOS를 각각 확인. 중단·재개·재시작·화면 이탈 포함 | 입력 시각 대응, 처리 대기, 파일 무결성, 화면 반영 지연 |

실시간 비교에서는 서버의 전체 파일 분석과 앱의 순차 입력 분석을 별도로 실행한다. 샘플레이트·창 길이·이동 간격·사용 가능한 마지막 샘플 위치를 기록하고, 각 결과에 입력 시각과 판단 시각을 남긴다. 비교 도구가 파일 전체를 보유하더라도 실시간 계산부에는 그 시점까지 도착한 창만 전달한다. 조율·빠르기·흔들림 추정에도 아직 도착하지 않은 음을 넣지 않는다.

같은 앞부분을 가진 두 입력의 뒤쪽만 바꾸는 검사를 추가한다. 공유한 입력 구간에서 그때 출력한 잠정 결과는 같아야 한다. 미래의 3음을 기다리는 후보는 기다린 뒤의 판단 시각을 기록하며 즉시 결과로 집계하지 않는다. 과거 결과를 수정하는 정책을 채택한다면 원래 출력은 보존하고 수정 시각·사용한 입력 범위·수정 이유를 따로 비교한다. 서버와 최종 결과가 비슷하다는 사실만으로 실시간 처리가 검증됐다고 판정하지 않는다.

JVM 비교 검사는 공통 Kotlin 계산을 실제 녹음의 PCM에 적용하는 후속 후보이며 아직 만들지 않았다. 테스트 입력의 정답 음높이를 독립적으로 확인해야 앱의 정확도를 판단할 수 있다. 디코딩 후 오프라인 재분석으로는 녹음 당시 원시 마이크 입력·실시간 누락을 증명하지 못한다. 실제 녹음은 소유자가 지정한 파일만 사용하고 개인 파일과 진단 로그는 Git에 넣지 않는다.

515에서 기록한 실제 마이크 5,238개 대조의 불일치 0건은 2회 확인 규칙 일치의 증거다. 실시간 종합 등급·음높이 정답 정확도·새 결과 연결의 기기 시간 대응까지 검증한 것은 아니다. 10분·가장 긴 곡 검증을 362에서 자동으로 다시 필수화하지 않는다.

## 검토 완료 조건과 근거

1. 채점 기준 담당자와 FE 담당자가 네 등급 경계·보류·잠정 결과 수정·합성 방식을 결정한다.
2. 과거 음만 쓰는 박자와 미래 음을 기다리는 박자 중 제품에 사용할 방식을 정한다.
3. 조율·초기 유효 음 수·음 종료·동음·배음의 미정 항목을 합의하거나 명시적으로 보류한다.
4. Android·iOS 담당자가 입력·저장·분석의 책임과 기기별 검증 범위를 확인한다.

이 문서는 위 결정을 위한 자료다. 모든 항목을 구현해야 362 문서 작성이 끝난다는 뜻은 아니다. 문서에는 미정 항목을 그대로 남길 수 있으나 후속 제품 구현은 필요한 결정을 먼저 받아야 한다.

코드와 기존 기록을 정적으로 대조해 작성했다. 이 초안 작성에서 모델 추론·모바일 빌드·실기기·새 등급 비교 실험은 실행하지 않았다.
