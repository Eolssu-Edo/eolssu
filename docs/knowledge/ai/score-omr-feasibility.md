## 1. 정간보 → 공통 악보

- 저장소: PDF → `jeongganbo_omr.py`(MALerLab 모델) → JG-like 텍스트 → `.jgb.json` → 사람 검수 → `score_data.py`. 결과는 [정간보 OMR](../data/jeongganbo-omr.md), [정확도](../data/jeongganbo-omr-accuracy.md).
  - 단소 아리랑: 정간 39/48개를 깨끗하게 잘랐고 그 칸의 율명은 모두 맞음. 대금 3차시(가는 글꼴)는 12/28칸만 잘림.
  - 실기교재 5곡 율명 63%, 음역 제한·중청 재판정으로 80%. 시김새는 곡마다 0~5개만 맞음. 모델 어휘에 중청태가 없음.
  - 칸 자르기가 한 번 틀리면 뒤 각이 모두 밀린다. 칸 상자는 `grid_boxes.py`가 소금 15곡에서 모두 찾았다([소금 검토](../data/sogeum-scores-review.md)).
- 공개 연구: 서강대 MALerLab [jeongganbo-omr](https://github.com/MALerLab/jeongganbo-omr)(README에 MIT, LICENSE 파일 없음, 정확도 89% 표기), 합성 데이터 학습 논문 [JOCCH 2025](https://scholarworks.sogang.ac.kr/item/5470e001-7b87-4e31-97ec-308667b4d025). 국립국악원 PDF를 정간 단위로 자르는 흐름이라 **다른 판형·폰 사진은 칸 검출부터 새로 만들어야 할 가능성이 높다**(추론).
- 105의 사진 정간보: OpenCV로 칸을 나누고 기호마다 `qwen3-vl:4b`(Ollama)로 분류. 새야새야 처음 독립 평가 22/32음, 같은 자료로 고친 뒤 32/32. 실제 촬영 2장 47/58음(81%). **홀드아웃 아님, GPU(RTX 4060 Ti) 측정**이다.

## 3. 공통 악보 → 오선보 파일

- FE 336의 `StaffProjection.kt`(336 브랜치 `6a7f220b`, **develop 미병합**)가 율명 → E♭ 기준 음이름, 2진 음가·점·붙임줄·3:2 분할을 한다. QUARTER·DOTTED_QUARTER와 황 311.13만 지원하고 박자표·마디선은 추정하지 않는다(같은 브랜치의 `docs/specs/generated-staff-notation.md`).
- MIDI는 지금 가능. MusicXML은 이 로직을 Python으로 옮겨 직접 쓰면 새 의존성이 필요 없다(music21은 의존성에 없음). PDF는 렌더러가 필요하다.
- 잃는 정보: 시김새(텍스트나 장식 기호로만), 장단(마디 묶음 정책 필요), JEONGGAN·JANGDAN_BEAT 단위 곡.

## 4. 서버 운영 조건

- 서버는 CPU만 있고 AI 컨테이너가 약 6GiB를 나눠 쓴다. **Audiveris JVM 메모리와 CPU 처리 시간은 공식 문서에 없어 실측이 필요하다.** 105 수치는 GPU PC 측정이다.
- Qwen3-VL 4B(105 정간보·오선보 보정)는 CPU에서 느리고 메모리를 많이 쓸 가능성이 높다(추론). 서버용으로는 VLM 없이 가는 경로를 먼저 본다.
- AGPL: 수정하지 않고 별도 프로세스·컨테이너로 실행하면 우리 앱과 묶인 하나의 프로그램으로 보지 않는 해석이 일반적이다([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#MereAggregation), 추론). 최종 판단은 팀이 한다. homr 가중치의 비상업 학습 데이터는 별도 위험이다.
- 105 서비스는 loopback 전용·인증 없음·Windows 프로세스 종료 방식이라 서버용으로 다시 만들어야 한다.

## 5. 실측: 표준악보집 오선보 (2026-11-03)

- 조건: Docker 안 Ubuntu 24.04·Python 3.12, CPU만, 메모리 상한 6GiB(`--memory 6g`), 이 PC(Windows Docker Desktop). 입력은 표준악보집 PDF 쪽을 300DPI PNG로 바꾸고 오선보가 있는 오른쪽 반만 자른 것.
- 정답: 같은 곡의 검수된 정간보(단소 오나라·북천이맑다커늘 단소1·어이얼어자리 단소1, 소금 오나라). 조 옮김과 무관하게 **이웃 음 사이 간격**을 맞춰 비교하고, 맞은 구간에서 길이 비율을 본다. 청성곡은 정답 없이 시간만 잼.
- 엔진: Audiveris 5.11.0(ubuntu24.04 deb), homr 0.7.0(`homr[cpu]`, 첫 실행에 모델 자동 내려받음).

| 곡 | 정답 음 | Audiveris 간격 일치 | Audiveris 길이 | homr 간격 일치 | homr 길이 |
| --- | ---: | --- | --- | --- | --- |
| 단소 오나라(단선율) | 62 | 59/61 | 61/61 | **61/61** | 62/62 |
| 소금 오나라(단선율) | 62 | 53/61 | 51/55 | **61/61** | 62/62 |

| 엔진 | 쪽당 시간 | 최대 메모리 | 메모 |
| --- | --- | --- | --- |
| Audiveris | 7.1~10.7초 | 0.73~0.92GB | 화면 없는 일괄 실행에도 GTK 라이브러리(`libgtk-3-0`)가 필요. deb의 데스크톱 메뉴 등록 스크립트는 컨테이너에서 실패해 빼고 설치 |

- **단선율은 homr, 2성부는 Audiveris가 나았다.** 2성부에서 homr 결과는 두 성부가 섞여 선율을 고르기 어려웠다(성부 고르기는 이번 비교 스크립트의 단순 규칙: 음이 가장 많은 파트의 1성부).
- **조 옮김은 자동으로 맞출 수 있다.** 표준악보집 오선보는 정간보 율명보다 6~15반음 다른 조로 적혀 있다. 인식된 음을 반음씩 옮겨 가며 악기 율명 표(단소 11음, 소금 곡 다섯 율 음역)에 가장 많이 들어가는 양을 고르니 8건 모두 실제 차이와 같았다(homr 어이얼어자리 1건은 정렬 오류로 잘못 잰 차이를 바로잡음).
- 두 엔진 모두 6GiB 상한에서 1.4GB 이하, 쪽당 15초 이하로 서버 조건 안이다. 서버는 CPU 코어 수가 달라 시간은 다시 잰다.
- 이 4곡은 개발에 쓰지 않은 자료지만 모두 같은 판형(표준악보집 인쇄 PDF)이다. **폰 사진과 다른 판형은 재지 않았다.**

## 한계와 다음 확인

- 오선보 폰 사진·다른 판형, 정간보 사진은 재지 않았다. 다음 가장 싼 확인은 같은 4곡을 폰으로 찍은 사진으로 같은 비교를 돌리는 것이다.
- MALerLab 모델 체크포인트의 릴리스 포함 여부와 LICENSE 파일 부재는 확인하지 못했다.
