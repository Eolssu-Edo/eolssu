# Notion 테스트 시나리오 작성 프롬프트

새 API나 앱 화면이 생겨 [Notion 테스트 문서](https://app.notion.com/p/40ca0252aa4580078930ccb1597aadc9)에 시나리오 행을 추가하거나 기존 행을 고칠 때 쓰는 프롬프트다. Notion MCP와 이 저장소를 읽을 수 있는 AI 에이전트에 아래 `프롬프트` 전체를 붙여 넣고, 맨 아래 `입력`만 채운다.

이 프롬프트는 2026-11-03에 47개 행을 정리할 때 쓴 규칙을 그대로 옮긴 것이다. 루트 `AGENTS.md`의 '검증과 지식 기록'은 같은 규칙의 요약이다.

## 프롬프트

````text
너는 Notion 테스트 문서 '테스트 시나리오 / 결과 기록'의 시나리오 행을 작성·갱신한다.
목표는 테스터가 완료 조건 번호만 보고 같은 번호의 가이드 단계를 따라 하면 그 조건의 통과·실패를 바로 판정할 수 있게 하는 것이다.
아래 규칙을 순서대로 지키고, 규칙에 없는 판단은 하지 말고 '먼저 정할 것'으로 보고한다.

# 0. 대상과 도구
- 테스트 DB data source: collection://49a5cbb2-1ca1-47a4-a463-1982fa5ec177
- 테스트 DB 전체 보기 view: view://444de345-a672-49a1-88c7-7c99835b4132
- 상단 가이드 페이지: 40ca0252aa4580078930ccb1597aadc9
- API 명세 DB data source: collection://80da0252-aa45-82ff-bd4d-87829106fa20 (보기 view://f5ba0252-aa45-8300-a340-086e8b8d2aae)
- 저장소: S15P31E102. 코드는 `git fetch origin develop` 뒤 `git show "origin/develop:<경로>"`, `git grep -n <패턴> origin/develop -- <경로>`로만 읽는다. 체크아웃·수정·커밋하지 않는다.
  - zsh에서 `$D:경로`처럼 변수 뒤에 바로 `:`를 붙이면 수식어로 해석된다. `"${D}:경로"`로 쓴다.

- 쓰기는 `notion-update-page`의 `update_properties`로 한 페이지씩, 바꾸는 컬럼만 보낸다. 새 행은 `notion-create-pages`로 위 data source에 만든다.

# 1. 먼저 읽을 것
1. 저장소 루트 `AGENTS.md`의 '검증과 지식 기록' 절. 이 프롬프트와 다르면 이 프롬프트를 따르고 차이를 보고한다.
2. 상단 가이드 페이지(1-1 표, 1-2 진행 순서, 1-3 칸 설명).
3. 대상 행과 같은 '시나리오 구분 (흐름)'의 기존 행 2개 이상. 형식은 기존 행을 기준으로 맞춘다.
4. 대상 API의 Notion API 명세 페이지 본문(Request·Response·Exceptions·동작·검증 규칙). 행의 '관련 API' relation에서 페이지를 찾는다.
5. 저장소의 계약·구현: `docs/specs/*.md`(상태 줄에 '사용자 승인'이 있는지 본다), 컨트롤러·서비스·도메인 코드, 테스트 코드, 앱 코드와 `frontend/shared/src/commonMain/composeResources/values/strings.xml`.

# 2. 근거의 우선순위
- 사용자 승인 계약(docs/specs의 승인 상태) > origin/develop 구현 코드 > Notion API 명세 > Notion 초안·메모.
- 기대값(HTTP 상태, errorCode, 필드, 한도, 앱 문구)은 위 근거에서 확인한 것만 쓴다. 앱 문구는 strings.xml의 값을 글자 그대로 쓴다.
- 근거끼리 다르거나(예: 명세는 A, 코드는 B), 조건을 고칠지 앱을 고칠지 정해야 하면 임의로 쓰지 말고 '먼저 정할 것'에 근거(경로:줄)와 선택지를 적어 보고한다.
- 애매한 항목은 추측하지 말고 코드·테스트·명세를 먼저 찾아본다. 그래도 답이 없으면 '확인 필요'로 보고한다.

# 3. 행 단위 컬럼 (새 행일 때 채우고, 기존 행은 바꿀 이유가 있을 때만 고친다)
- `테스트 시나리오`(제목): '대상 + 확인할 일'을 "~를 확인한다."로 쓴다. 개발 전이면 앞에 `\[개발 전\] `, 앱 연결 확인이 남았으면 `\[연결 확인\] `, 보류면 `\[보류\] `를 붙인다.
- `구분`: API 명세의 요구사항 코드(예: SHT-10). 여러 개면 `SHT-04·11`처럼 가운뎃점으로 잇는다.
- `시나리오 구분 (흐름) `: 회원·인증 / 곡·악보 / 연습·녹음 / 분석·결과 / 연습 기록 / 성장·학습 / 마이페이지 / 내 악보 중 하나. 이름 끝에 공백이 있다.
- `종류`: API / E2E / 자동 / 채점 정확도 / 보안 중 하나. 같은 영역의 기존 행을 따른다.
- `검증 범위`: 필요한 검증 종류(API·E2E·자동). 실행 여부와 무관하다.
- `관련 API`: API 명세 DB 페이지 URL 배열.
- `API 테스터`: 비어 있으면 오은서 `user://c60009e2-c3d2-48fc-970a-ce616a6e7703`. `E2E 검증 테스터`: 비어 있으면 권영민 `user://344d872b-594c-81cb-b824-0002851cd418`. 기존 담당자는 유지하고 한 명만 둔다.
- 건드리지 않는 컬럼: `자동 테스트 확인자`, `API 판정 결과`, `E2E 판정 결과`, `API 테스트 수행일`, `E2E 테스트 수행일`. 실제로 실행하지 않았으면 판정·수행일을 만들지 않는다.
- 자동 테스트 칸(`자동 Test 기대 동작`·`자동 Test 결과 <다르면 직접 수정>`·`자동 테스트 수행일`·`자동 판정`)은 아래 '8-1. 자동 테스트'를 따르고, 테스트를 실제로 실행했을 때만 결과·수행일·판정을 쓴다.

# 4. `/api/`와 `ui`
- `/api/`: 이 행이 부르는 API마다 한 블록. 블록 사이는 `<br /><br />`.
  - 첫 줄 `<b>METHOD 경로</b>`. 경로는 API 명세 URL 그대로(`/api` 접두사 없이, 예 `/users/me/sheets/\{sheetId\}/score`).
  - 둘째 줄 공백 4칸 + API 명세 '요구사항'에서 앞의 코드를 뺀 설명.
  - `/v1/`로 시작하는 내부 API는 셋째 줄에 공백 4칸 + `AI 서버 내부 호출 · 앱에서 직접 부르지 않음`.
  - API 명세에서 '작업 취소'인 경로는 넣지 않는다.
- `ui`: 테스터가 볼 앱 화면마다 한 블록.
  - `<b>화면 이름</b><br />    가는 길<br />    볼 요소`. 가는 길은 `홈 › 연습곡 선택하기 › 악보 추가하기`처럼 ` › `로 잇는다.
  - 앱에 아직 없는 화면은 가는 길 끝에 ` (앱 화면 개발 전)`을 붙인다.
  - 이름이 비슷하지만 다른 화면은 마지막에 `<b>참고</b><br />    화면 이름<br />    다른 점` 블록으로 적는다.
  - 화면 이름·버튼은 strings.xml 문구와 같게 쓴다.

# 5. 완료 조건 (`API 테스트 완료 필수 조건`, `E2E 테스트 완료 조건`)
- 한 줄에 조건 하나, 줄 앞에 동그라미 숫자 `① ② ③ … ⑳`를 붙이고 공백 하나 뒤에 문장을 쓴다. 줄 사이는 `<br />`.
- 조건은 관찰 결과로 통과·실패를 판정할 수 있어야 한다: HTTP 상태와 errorCode, 응답 필드 값, DB 행 상태, 화면 문구·상태.
- 조건이 될 수 없는 문장은 가이드의 `참고`로 보낸다: '판정하지 않는다', '보류한다', '따로 기록한다', '~후 실행한다', '확정 전', '초안이다', '적절히', '확인한다'만 있고 기대 결과가 없는 문장.
- 소제목이 필요하면 번호 없는 줄 `<b>자동 저장(SHT-11)</b>`을 쓰고, 번호는 소제목을 넘어 이어서 매긴다.
- 기존 행: 결과·결함이 번호로 기록되므로 번호를 다시 매기지 않는다. 새 조건은 마지막 번호 뒤에 붙인다. 틀린 조건은 같은 번호에서 문장만 바꾼다.
- E2E 조건은 화면에서 보이는 것만 쓴다. API 조건에 있고 앱 화면에도 보이는 동작(ui 컬럼·strings.xml 근거)은 E2E 조건에도 둔다.
- 테스트 데이터에 경계값·변형(500자/501자, 잘못된 ID, 만료 등)이 있으면 각각의 기대 결과를 조건에 둔다.

# 6. 수행 과정 가이드
## 공통
- 구획 제목은 굵게(`<b>수행 순서</b>`), 구획 사이는 `<br /><br />`, 줄 사이는 `<br />`.
- `수행 순서`의 단계 수는 같은 검증의 완료 조건 수와 같다. 단계 ⓝ은 조건 ⓝ을 확인하는 방법만 쓴다.
- 단계에는 행동·요청·입력·볼 위치만 쓴다. 기대값·`확인:` 줄·조건 문장을 반복하지 않는다.
- 한 단계에 행동이 여러 개면 같은 단계 아래 `<br />    - …`(공백 4칸 + 하이픈) 줄로 쓴다.
- 앞 단계 결과를 쓰면 '①의 응답에서', '②에서 이어서'처럼 번호로 가리킨다. 실제 실행 순서가 번호 순서와 다르면 단계는 조건 번호 순서대로 쓰고 순서는 `참고`에 '②·③·④는 ⑤보다 먼저 한다'처럼 적는다.
- 엔드포인트·버튼·화면 이름은 이 행의 /api/·ui·명세·strings.xml에 있는 것만 쓰고 새로 만들지 않는다.
## API 가이드
- 구획: `수행 순서` → `참고` → (있으면) `이전 수행 방식`.
- 로그인·ID 얻기 같은 준비는 별도 단계를 만들지 않고 해당 단계 안에 쓴다('GET /api/songs에서 얻은 songId로').
- 격리 환경·특수 상태가 필요하면 'API 담당자가 준비한 격리 QA DB에서 …'라고 쓴다.
## E2E 가이드
- 구획: `시작 상태` → `수행 순서` → `참고` → (있으면) `기기별 참고` → `남길 증거`.
- `시작 상태`는 `• ` 불릿으로 빌드·계정·기기·API 담당자가 준비할 데이터를 적는다. 조건과 무관한 준비(로그인, 화면 열기)는 단계가 아니라 여기에 둔다.
- 버튼·화면 이름은 작은따옴표로 앱 문구 그대로 쓴다('동의하고 시작하기').
- 앱에서 볼 수 없는 서버 값은 'API 담당자가 확인한 값과 화면 값을 비교한다'로 쓴다.
- 기기 공통으로 쓰고 기기마다 다른 점만 `기기별 참고`에 적는다.

# 7. 테스트 데이터
- `API 테스트 데이터 …`: 실제 요청 모양을 `<code>…</code>` 안에 실제 개행으로 쓴다. 주석은 `//` 또는 `#`. 예시 ID는 '실제 ID로 교체한다' 주석을 단다. 비밀번호·토큰·서명 URL 원문은 쓰지 않는다. 코드 블록 뒤 준비 사항은 `<br /><br />• 준비: …` 불릿으로 쓴다.
- 계약이 정한 필수 파라미터를 빠뜨리지 않는다(예: GET /api/lessons의 track). 시간 창이 있는 API는 검증 규칙을 통과하는 시각을 쓴다(예: visibleSeconds 900이면 startedAt·endedAt이 15분 넘게 떨어져야 한다).
- `E2E 테스트 데이터 …`: 입력값만 쉼표로 짧게 쓴다. 준비는 E2E 가이드의 `시작 상태`에 둔다.
- 취소된 기능(API 명세 '작업 취소', 스펙의 '작업 취소')의 데이터는 넣지 않는다.

# 8. 결과·결함·비고 칸의 번호 자리
조건 수가 정해지면 다음 칸에 내용 없이 동그라미 숫자만 줄마다 적는다. 테스터는 해당 번호에 결과·결함이 있으면 그 줄에 직접 쓰고, 없으면 비워 둔다.
- `API 테스트 수행 결과 < 직접 기록 >`, `API 발견된 결함 < 직접 기록 >`: `①<br />②<br />…`(API 조건 수만큼).
- `E2E 테스트 수행 결과 < 직접 기록 >`, `E2E 발견된 결함 < 직접 기록 >`: 기기 구획마다 같은 번호 자리를 둔다.
  `<b>안드로이드폰</b><br />①<br />②<br /><br />────────────────<br /><br /><b>태블릿</b><br />①<br />②<br /><br />────────────────<br /><br /><b>iOS</b><br />①<br />②`
- `비고, 메모`: `<b>API</b><br />①<br />②<br /><br /><b>E2E</b><br />①<br />②<br /><br /><b>자동</b><br />①<br />②`(자동은 8-1의 함수 수만큼)
- 해당 검증의 조건(자동은 함수)이 0개면 그 블록이나 칸은 만들지 않는다.
- 번호 밖(셀 맨 위·아래, 별도 제목·문단, `기존 기록` 같은 묶음)에는 아무것도 쓰지 않는다.
  - 한 번호에 여러 줄이면 첫 줄은 `ⓝ 내용`, 다음 줄부터는 그 번호 아래 `    - 내용`(공백 4칸 + 하이픈)으로 잇는다.
  - 날짜·기기·빌드처럼 여러 번호에 걸친 실행 정보는 그 실행으로 기록한 첫 번호 줄 아래에 한 번만 적는다. 실행이 여러 번이면 줄 앞에 `11-03 V19:`·`이전:`처럼 짧은 표시를 붙인다.
  - 결과가 아닌 메모(구현 전 정할 일, 판정 메모, 근거 링크)는 결과 칸이 아니라 `비고, 메모`의 같은 번호 줄에 쓴다.
  - 어느 조건에도 맞지 않는 결과는 가장 가까운 번호에 적고, 보고에 '조건 추가 후보'로 올린다.
- 칸에 이미 테스터가 쓴 기록이 있으면 지우지 않고 위 규칙대로 번호 줄로 옮긴다.
  - `1.`·`3`처럼 조건 번호가 붙은 기록은 같은 동그라미 번호 줄로 옮긴다(`5. 확인해야됨` → `⑤ 확인해야됨`).
  - 번호가 없는 기록은 내용이 확인하는 조건의 번호 줄로 옮긴다. 한 줄이 여러 조건을 다루면 조건별로 나눈다.
  - 내용 없는 기본 문구(`• 미실행.`, `• 실행 후 HTTP 상태·응답·저장 상태를 기록한다.`, `• 미실행; 결함 유무 미확인.`, `• 없음.`)와 완료 조건·참고 문장을 되풀이한 줄은 지운다. 빈 번호 줄이 같은 뜻이다.
- 조건을 나중에 추가하면 번호 자리도 마지막 번호 뒤에 같은 수만큼 붙인다. 기존 줄의 내용은 그대로 둔다.

# 8-1. 자동 테스트
- `자동 Test 기대 동작`: 이 행의 완료 조건을 실제로 검사하는 자동 테스트만 고른다.
  - 테스트 소스를 열어 그 동작을 assert하는지 확인한 것만 넣는다. 이름만 보고 넣지 않는다.
  - 같은 조건을 거의 같게 검사하는 테스트는 가장 직접적인 1~2개만 남긴다. 다른 행이 더 정확히 다루는 테스트는 그 행에 둔다.
  - 순서는 API 조건 번호 순 → E2E 조건 번호 순, 같은 조건이면 백엔드 → 앱 → AI.
  - 형식: `<b>① 클래스 › 함수</b><br />    API ③ · 기대 동작 한 문장.` 함수 이름은 점 대신 ` › `로 이어 Notion 자동 링크를 피한다.
  - 자동 테스트가 없는 조건과 실행 조건(폐기용 MySQL 등)만 맨 아래 `<b>참고</b>`에 0~3줄로 적는다. 파일 경로·판정 범위 같은 일반론은 쓰지 않는다.
- `자동 Test 결과`: 실제로 실행한 결과만 같은 번호 줄에 `통과`·`실패: 사유`·`미실행: 사유`로 쓴다. 실행 날짜·커밋·명령은 ① 아래 `    - `로 한 번만 적는다.
  - 실행 명령(이 Mac 기준): 백엔드 `./gradlew test databaseTest`(JDK 21, `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<실경로>`, 임시 MySQL 8.4), 앱 `./gradlew :shared:iosSimulatorArm64Test`(Android SDK가 없으면 공용 테스트를 iOS 시뮬레이터로 실행), AI `uv run pytest`. JUnit·pytest 결과 파일에서 함수별 상태를 읽는다.
- `자동 테스트 수행일`은 실행한 날짜, `자동 판정`은 고른 함수가 모두 통과면 `자동통과`, 하나라도 실패면 `자동실패`, 일부 미실행이면 비워 둔다.

# 9. Notion 서식
- 줄바꿈은 `<br />`, 굵게는 `<b>…</b>`. `**`와 실제 개행 문자는 `<code>` 밖에서 쓰지 않는다.
- `<code>` 밖에서는 `\_ \{ \} \[ \] \~`처럼 백슬래시를 붙여 쓴다(기존 셀 표기와 같게).
- `test_scoring.py`·`-Djava.io.tmpdir`처럼 도메인으로 보이는 문자열은 Notion이 링크로 바꾸므로 `<code>`로 감싼다.
- 문장은 '~한다.' 체, 한 줄 160자 이하.
- 한글은 그대로 쓴다. `\uXXXX` 같은 유니코드 이스케이프로 손으로 옮기지 않는다. 그렇게 옮기다 '늴리리야'가 '뉴리리야'로 저장된 적이 있다.

# 10. 쓰기 절차
1. 전체 보기를 view 모드로 읽어 스냅샷 파일로 저장한다.
2. 바꿀 셀 값을 스크립트로 만든다. 기존 셀을 고칠 때는 '바꿀 문자열이 정확히 한 번 나오는지' 확인하는 치환으로 만들고, 실패하면 멈춘다.
3. 행마다 `update_properties`로 바꾸는 컬럼만 보낸다.
4. 전체 보기를 다시 읽어 모든 행·모든 컬럼을 기대값과 비교한다. 비교 전에 `\` 뒤 `._~[]{}<>` 표기 차이는 같은 것으로 본다.
   - 한 글자라도 다르면 그 셀을 다시 쓰고 다시 비교한다. 에이전트가 값을 옮겨 적다 생긴 한 글자 오타가 여러 번 있었다.
   - 내가 바꾸지 않은 컬럼이 스냅샷과 다르면 다른 사람이 고친 것이다. 되돌리지 말고 보고한다.
5. 다른 세션·팀원이 같은 행을 고치고 있을 수 있다. 쓰기 직전에 다시 읽고, 스냅샷 이후 바뀐 셀은 그 값을 기준으로 다시 만든다.

# 11. 마치기 전 점검
행마다 아래를 확인하고 걸리는 것은 고치거나 보고한다.
- 조건 번호마다 같은 번호의 가이드 단계가 있고, 단계가 조건과 다른 것을 확인하지 않는다.
- 옛 가이드·참고에 있던 확인이 어느 조건에도 대응하지 않으면 '조건 추가'(근거가 있을 때) 또는 '가이드에서 제외'(근거가 없을 때)로 판단한다. 다른 행이 다루면 그 행 구분을 적는다.
- 테스트 데이터의 경계값마다 기대 결과 조건이 있다.
- API 조건에 있고 화면에서도 보이는 동작이 E2E 조건에 있다.
- 판정할 수 없는 조건이 없다.
- 기대값은 모두 근거(경로:줄)를 댈 수 있다.
- 결과·결함·비고 칸의 번호 자리 수가 조건 수와 같다.
- 결과·결함·비고 칸에 번호 밖의 줄(제목, `기존 기록`, 셀 맨 위·아래 문단)이 없다.

# 12. 보고
- 행마다 한 줄: `구분 · 바꾼 컬럼 · 조건 수(API/E2E)`.
- '먼저 정할 것': 구분, 무엇이 서로 다른지, 근거(경로:줄), 선택지와 권장안.
- 기존 기록을 옮겼다면: 담당자별 행 목록, 옮긴 위치, 지운 줄과 이유, 조건에 맞지 않아 가장 가까운 번호에 넣은 결과(조건 추가 후보).
- 다시 읽어 비교한 결과(불일치 0건인지), 다른 사람이 바꾼 셀.
````
