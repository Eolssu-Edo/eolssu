# 내 악보 음원 생성·보관 (S15P31E102-481)

## 기준과 범위

- 기준: Notion SHT-12·13, 2026-11-05 사용자 승인(내부 playback HTTP 서버 포함).
- POST `/api/users/me/sheets/{sheetId}/audio`: 현재 저장한 EVALUABLE 악보와 설정을 스냅샷으로 접수(202). 같은 버전·설정의 완료 파일은 200으로 재사용한다.
- GET 같은 경로: 생성 상태, 현재/생성 버전, outdated, 기존 파일 및 15분 서명 URL을 반환한다. 응답은 no-store다.
- 회원당 QUEUED/RUNNING 1건, 전역 생성기 호출 1건. 길이 600초(꼬리 포함), M4A 15MiB. 요청 제한 회원당 분당 10회.
- 새 파일 묶음이 완전히 저장된 뒤 이전 파일을 교체한다. 생성·저장 실패 시 이전 완료 파일은 유지한다. 악보 삭제·탈퇴는 생성과 경합하지 않도록 취소하고 파일을 정리한다.
- `outdated`는 보관 파일이 있으면 그 파일의 악보 버전으로 계산한다. 새 생성이 진행 중이거나 실패해도 파일이 옛 버전이면 true다. `scoreVersion`은 최근 요청의 버전이라 보관 파일의 버전과 다를 수 있다. 앱은 최신 여부를 `outdated`로 판단한다.
- 악보 삭제가 끝나지 못하면(503, 500, 삭제 중 재시작) 음원 파일 연결은 끊고 악보는 남긴다. `audio`·`midi`는 null, `status`는 FAILED, `failureCode`는 SERVER_ERROR다. 음원을 다시 요청하거나 삭제를 다시 시도할 수 있다.
- 한 backend 인스턴스에서 악보 삭제 전체 구간(음원·원본 정리와 DB 삭제)을 악보별로 보호한다. 음원을 요청한 적 없는 악보도 이 구간에서는 첫 생성이 409 STATE_CONFLICT다. 같은 악보의 다른 삭제 요청은 503이며, 먼저 시작한 삭제의 보호 상태를 풀지 않는다. 보호 상태는 소유한 요청만 종료·실패 시 해제한다.
- 공통 악보 생성 알고리즘은 DATA 코드를 재사용한다. 악기·BPM·educational-preview/v1을 적용하며 장단 포함은 기존 장단 계획/녹음 자산을 재사용한다.
- 2026-11-05 사용자 확정: 다른 악기를 선택해도 원래 음높이를 유지하고 소리만 바꾼다. 자동 이조하지 않는다. 저장 악보를 변경하지 않고 생성 입력 사본에 선택 악기를 적용한다.

## 내부 계약 초안

외부 앱 계약은 Notion을 유지한다. 내부 HTTP 포장 형식은 이 작업에서 양쪽을 함께 구현한다.

- 내부 `playback:8000`, 호스트 포트 없음. JSON 요청(공통 악보·악기 code·BPM·장단 설정), 결과는 ZIP(M4A·MIDI·길이 메타데이터).
- 입력 경로·실행 명령을 요청에서 받지 않는다. 임시 디렉터리만 쓰고 종료 시 정리한다. 생성은 자식 프로세스에서 실행해 시간 초과 시 종료할 수 있어야 한다.
- 생성기 시간 제한 90초, 백엔드 전체 수신 제한 100초, 길이 계산 대기 5초·실행 10초(백엔드 수신 15초)로 확정한다. 근거는 아래 실측이다.
- 길이 계산은 MIDI를 쓰지 않고 tick으로 구한다. 생성기 호출은 DB 트랜잭션 밖에서 하고, 접수 전 같은 잠금 안에서 악보 스냅샷을 다시 대조해 달라졌으면 409로 거절한다.
- 동시 길이 계산은 차례로 처리한다. 5초 안에 차례가 오지 않으면 503이다. 생성은 전역 1건이다.
- 생성기가 이미 렌더 중이면(백엔드 재시작 직후) 작업을 QUEUED로 되돌려 다시 시도한다. 같은 작업이 시간 제한 + 5분 동안 계속 대기하면 SERVER_ERROR로 끝낸다. 시작 후 시간 제한 + 5분이 지나도 RUNNING인 행도 SERVER_ERROR로 끝내 전역 슬롯을 푼다.
- 주기 작업 스레드는 4개다. 음원·악보 변환 작업자가 짧은 정리 작업을 막지 않게 한다.
- 운영 메모리는 `mem_limit: 1g`, `memswap_limit: 1g`로 스왑 없이 고정한다.

## 실측 (2026-11-05, 로컬 Docker, 1 CPU·1GiB·스왑 0)

입력은 실제 CAT 4악기, 장단 포함이다. 대상 코드는 481 브랜치이고, 운영 서버 측정은 아니다.

| 악보 | 길이 | 길이 계산 | 생성 | M4A |
| --- | --- | --- | --- | --- |
| 단소, 599박, 60 BPM | 599.55초 | 3.5초 | 21.4초 | 14.72MB |
| 소금, 599박, 60 BPM | 599.55초 | 3.4초 | 25.4초 | 12.83MB |
| 정악대금, 599박, 60 BPM | 599.55초 | 3.5초 | 23.7초 | 13.18MB |
| 산조대금, 599박, 60 BPM | 599.55초 | 3.3초 | 22.2초 | 13.18MB |
| 단소, 1590박, 160 BPM | 596.80초 | 3.7초 | 22.2초 | 15.56MB |

- 5건을 이어서 돌린 컨테이너의 메모리 정점은 700MiB, `memory.events`의 max·oom은 0이다.
- 최악 경우로 단소 599박 생성 1건과 같은 악보 길이 계산을 쉬지 않고 동시에 돌렸다. 메모리 정점은 923MiB, max·oom은 0, 생성 43.1초, 길이 계산 4.3~7.8초다. 여유가 약 100MiB이고 길이 계산 실행 제한 10초에 가까우므로 운영 서버에서 다시 재야 한다.
- 개선 전에는 스왑 없는 1GiB에서 최대 길이 생성이 OOM으로 종료됐다. 스왑을 허용한 측정은 스왑을 최대 약 450MiB 써서 통과한 것이었다.
- 메모리 수정 전후 CAT 합성 PCM은 단소·산조대금 40박 97 BPM에서 SHA-256이 같다.
- 빽빽한 악보는 M4A가 커지므로 15MiB(15,728,640바이트)를 넘으면 FAILED(TOO_LARGE)가 될 수 있다. 위 1590박 악보는 상한의 99%다.
- 설정/자산이 없으면 가용으로 보고하지 않는다. 실제 CAT/R2 검증을 합성/대역 테스트와 구분한다.
