# Jenkins 단계와 배포 순서

- 작업: S15P31E102-262, Story S15P31E102-40
- 요청: 2026-10-29 사용자 승인. 시작한 develop SHA로 끝까지 배포하고 이미 배포된 버전보다 이전인 경우만 순서상 차단한다. 모든 Jenkins 잡의 실패 위치를 stage로 세분화한다.
- 변경 전: 원격 develop HEAD와 정확히 같아야 배포했다. 변경 후: develop 이력에 속하는 후보를 허용하고 서비스별 현재 활성 릴리스 SHA와 Git 조상 관계를 비교한다. 커밋 시각·빌드 번호는 순서 기준으로 쓰지 않는다.
- 공유 배포 lock을 유지한 채 복구 후 현재 활성 릴리스를 읽는다. 실패한 후보 journal SHA는 배포 기준으로 사용하지 않는다. 같은 SHA 재실행·불변 산출물·이미지 label·건강 검사·자동 롤백은 보존한다. 초기 비 SHA 릴리스에는 비교 기준이 없으며 첫 관리 배포를 허용한다. 이력 확인 실패·분기된 이력은 순서를 증명할 수 없으므로 명시적으로 실패한다.
- 운영 잡: backend, frontend, blog. Gradle 준비·컴파일·타깃별 테스트·최적화·번들·구성 검사·이미지·보관·후속 잡 예약을 각각 표시한다. 배포 트랜잭션은 lock과 복구의 일관성을 위해 한 프로세스로 유지한다. 구조화 진행 이벤트를 별도 Pipeline 분기에서 관찰하여 내부 세부 단계도 실시간 하위 stage로 표시하고 최초 실패 단계는 빌드 설명에 남긴다.
- 검증: 임시 Git 원격·실제 조상 비교로 develop 전진/역순/동일/실패 복구 기준을 검사한다. Jenkins 선언 문법은 실제 컨트롤러 linter로 검증한다. 운영 잡 설정 변경 전 백업하고 변경 후 정의를 재조회한다. 앱 배포·Git push·MR 생성은 별도 요청 전 수행하지 않는다.
