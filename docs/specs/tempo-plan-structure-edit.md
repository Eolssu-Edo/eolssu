# 구간 빠르기가 있는 악보의 구조 편집 재매핑

상태: 1단계는 [S15P31E102-1091](../plans/S15P31E102-1091.md), 2단계는 [S15P31E102-1095](../plans/S15P31E102-1095.md)에서 구현했다. 2단계의 서버 저장 계약은 공유 계약의 의미 변경이라 MR에서 BE 리뷰를 요청한다.

S15P31E102-1088, Story S15P31E102-319. 2026-11-17 사용자가 1·2단계 규칙의 명세를 요청했다. 초안 v2는 독립 리뷰 세션이 `origin/develop` 코드와 대조해 검토했다. 그 지적 가운데 코드로 확인한 것을 반영했다. 기준 develop은 `1ef906e86`이다.

## 배경

구간 빠르기나 반복이 있으면 편집기는 정간 나누기·합치기, 각 추가·삭제를 막는다. 장단은 시간값을 유지하는 변경(772)만 고를 수 있고, 인식 정간보의 재시간 보정(822) 후보는 숨긴다. 잠금 조건은 `tempos` 또는 `repeats`에 항목이 있는지다(1080, [정간 잠금](../knowledge/frontend/sheet-editor-playback-guard.md#구간-빠르기와-정간-잠금)). 서버도 위치가 바뀌면 `PLAN_POSITIONS_CHANGED`로 거절한다([user-sheets](user-sheets.md), 790).

이 잠금은 계획을 다른 선율 위치에 추측해서 다시 붙이지 않으려는 안전장치다. 이 문서는 결과가 하나로 정해지는 편집부터 잠금을 푸는 규칙을 정한다.

## 현재 데이터와 동작

- `performancePlan.tempos[]`는 `gak`·`cell`(1부터)과 `bpm`(정간/분, 전체 배율 적용 전)을 가진다. 선택 필드는 `end_gak`/`end_cell`과 `start_bpm`이다. 끝 위치는 그 칸의 시작 시점, 즉 **배타**다. 악보 끝 `(gaks+1, 1)`도 허용한다. `repeats[]`는 각 단위의 `start_gak`·`end_gak`·`times`다. (`data/src/playback/tempo_repeat.py` `apply_tempo_repeat`)
- 한배 기호는 `expressions.placements`에 칸 ID(`cellId`)로 붙는다. 편집기는 기호를 `sourceCellIds`의 index로 읽고(`SheetTempoEditing.kt` `tempoMarks`), 저장할 때 새 칸 ID로 다시 쓴다(`orderedPlacements`). 각 구조가 바뀌면 칸 ID가 `c{각}-j{정간}`으로 다시 매겨진다.
- 사용자 악보 생성 경로(`common_preview.py`)는 숫자 계획이 있을 때 기호와 숫자가 같은 자리인지 검사하지 않는다. 그 검사는 JGB 경로(`tempo_repeat.py`)에만 있다.
- 편집기의 숫자 BPM은 기준 BPM 기준이다. 서버 `SheetExpressions.prepare`가 기본 BPM 변경분 `newBpm/oldBpm`을 `bpm`·`start_bpm`에 곱한다. 서버가 비교하는 "원본"은 마지막 확정본 `sheet.scoreJson`이다.
- 서버 `positions()`는 `bpmUnit`·`ticksPerBeat`·`ticksPerJeonggan`, 칸 ID·index·unit(row/col/eventId), 이벤트 id·cellId·startTick·durationTick이 모두 같아야 통과한다.
- 822 재시간 보정은 칸 수·row/col·칸 ID를 유지하고 tick만 정수 배율로 바꾼다(`SheetJangdanCorrection.kt` `withJangdan`). 다만 이 경로는 새 draft에 `tempoExpressions`를 넘기지 않는다.
- 편집기의 전체·구간 목표 빠르기 입력 범위는 40~200이다([1018](../knowledge/frontend/sheet-tempo-range.md)).

## 원칙

1. 결과가 하나로 정해질 때만 자동으로 옮긴다. 아니면 지금처럼 막고, 막는 이유와 걸린 구간(시작~끝 각·정간)을 보여 준다.
2. 계획을 조용히 버리지 않는다. 숫자 계획과 한배 기호는 항상 같은 자리로 함께 옮긴다.
3. 재매핑은 편집기의 구간 모델(끝은 배타)에 적용한다. 1082의 복귀 항목은 1089부터 쓰지 않고, 기본으로 바로 돌아가는 변경으로 읽는다. 저장된 원시 `tempos` 항목을 직접 옮기지 않는다.
4. 구조 편집과 재매핑은 하나의 commit이다. 실행 취소 한 번으로 둘 다 돌아간다.
5. 환산은 실수로 하고 반올림하지 않는다. 표시만 반올림한다. 같은 값 비교(`본래 속도로` 검사 등)는 허용 오차로 바꾼다.

## 1단계: 좌표가 바뀌지 않는 편집

대상은 정간 나누기·합치기와 822 장단 재시간 보정이다. 해시 결합 계약은 바꾸지 않는다.

### 서버 위치 검사 완화

`positions()`를 "각 수, 각별 정간 수, 칸 ID"의 비교로 줄인다. `bpmUnit`·tick 비율, 이벤트 tick, unit 비교는 뺀다. 칸 경계가 같으면 (각, 정간) 좌표와 기호의 `cellId`가 그대로 유효하기 때문이다. 각 수나 정간 수가 바뀌면 지금처럼 `PLAN_POSITIONS_CHANGED`로 거절한다.

### 정간 나누기·합치기

- 계획과 기호를 그대로 둔다. 빠르기는 정간 시작부터 적용되므로 칸 안의 음 배치와 무관하다.
- 합치기로 기호가 붙은 unit이 사라지면 기호를 같은 칸의 남은 첫 unit으로 옮긴다. 옮길 unit이 없으면 막는다. 자동 저장에서 기호가 조용히 사라지지 않게 하기 위해서다.

### 822 장단 재시간 보정

- 계획이 있어도 재시간 보정 후보를 보인다.
- 기본 BPM은 1054대로 고른 장단의 기본값을 따른다.
- 편집기는 모든 구간 `bpm`·`start_bpm`에 `f_new / f_old`만 곱한다. 여기서 `f = ticksPerBeat / ticksPerJeonggan`이다. 기본 BPM 변화분은 저장 때 서버가 `newBpm/oldBpm`으로 곱하므로 편집기에서 다시 곱하지 않는다. 결과적으로 구간은 기본 빠르기 대비 배율을 유지한다.
  - 예: 기본 대비 2배 구간은 보정 뒤에도 2배다.
  - 절대값을 유지하지 않는 이유: 822는 처음 고른 장단이 틀린 것을 바로잡는 작업이라 기존 절대 속도를 기준으로 신뢰할 수 없다. 기본 BPM을 바꾸면 구간도 비례 조정하는 기존 규칙과 같은 의미다.
- 사전 안내에 구간별 바뀌기 전→후 숫자를 보이고 확인받는다. 인식으로 들어온 절대값을 사용자가 지키고 싶을 수 있기 때문이다.
- 환산 결과가 편집기 범위 40~200을 벗어나면 보정을 막고 해당 구간을 보여 준다. 범위에 맞춰 자르면 배율이 바뀌므로 자르지 않는다.
- `withJangdan` 재시간 경로는 `tempoExpressions`를 새 draft에 보존해야 한다.
- 772의 시간값 유지 장단 변경은 지금처럼 기본 BPM을 유지한다.
- 표현할 수 없는 빠르기나 600초 초과는 기존 사전검사 오류(`TEMPO_UNRENDERABLE`/`EXPORT_TOO_LONG`)로 처리한다.

## 2단계: 각 추가·삭제

[S15P31E102-1095](../plans/S15P31E102-1095.md)에서 구현했다. 2026-11-17 사용자가 아래처럼 단순화하기로 결정했다. 처음 초안의 "지운 각의 구간 끝을 줄이기"는 쓰지 않는다.

### 좌표 이동 (각 k, 1부터)

각 추가(각 k 뒤에 새 각):
- k+1 이상인 모든 각 번호(구간 시작·끝, 복귀 항목, 반복, `gakContinuations`)에 1을 더한다. 새 각은 각 k 끝의 빠르기를 잇는다.
- 그래서 구간의 배타 끝이 (k+1, 1)이면 새 각도 그 구간에 든다. 점점 구간은 더 긴 거리에 걸쳐 변한다.
- 반복은 끝 각을 포함하므로, 끝 각 바로 뒤에 넣은 새 각은 반복 밖이다.
- 각 k에서 k+1로 이어지던 `gakContinuations`는 사이에 빈 각이 생겨 버린다.

각 삭제(각 k):
- 막는 경우: 빠르기 변경(목표가 없는 한배 기호 포함)이 각 k에서 시작함, 끝이 있는 구간(조금·점점·숫자 점진)이 각 k에 걸침, 반복 범위가 각 k를 포함함.
- '바로' 변경은 끝이 없어 다음 변경이나 악보 끝까지 이어지지만, 그 이어지는 각은 지울 수 있다. 막으면 뒤쪽 각을 거의 지울 수 없기 때문이다.
- 지울 수 있으면 k보다 뒤의 각 번호에서 1을 뺀다.
- 각 k 첫 정간에 있던 `조금` 구간의 복귀 항목은 삭제 뒤 같은 좌표, 곧 다음 각 첫 정간에 남는다. 그 자리에 다른 변경이 오거나 각 k가 마지막 각이면 버린다.
- 1089부터 기본으로 돌아가는 곳도 바로 바뀌는 곳(본래 속도로)으로 읽으므로 그 각은 위 막는 경우에 든다. 바로 위 규칙은 지울 수 있는 각에 남은 복귀 항목이 없어 사실상 쓰이지 않는다.
- 각 k로 들어오거나 각 k에서 나가던 `gakContinuations`는 버린다.

### 칸·이벤트 ID

- 각을 넣거나 지우면 보낼 악보의 칸 ID가 `c{각}-j{정간}`으로 다시 매겨진다.
- 편집 중 companion은 불러온 악보 기준 ID를 유지한다. 저장할 때 같은 정간 순서의 새 칸·이벤트 ID로 옮긴다. 대상은 `placements`(한배 기호 포함), `sourceSlots`, `slurGroups`다.
- 지운 칸의 항목은 버린다. 옮길 수 없는 `slurGroups`도 버린다.
- 새로 넣은 각은 아직 불러온 악보에 대응하는 칸이 없다. 그래서 한배 기호는 저장한 뒤에 넣을 수 있고, 숫자 빠르기는 바로 넣을 수 있다.

### 저장 계약

1. 앱은 companion이 있으면 상위 `sourceSha256`과 계획의 `input_sha256`을 **보낼 악보(`score`)의 정규화 SHA**에 결합한다. 정규화는 `commonSourceSha256`과 서버 `SheetExpressions.hash`의 키 재귀 정렬이다.
2. 서버 `SheetExpressions.prepare`는 확정본 해시와 요청 악보 해시를 모두 받는다.
   - 확정본 해시에 결합된 경우: 지금처럼 1단계 격자 비교를 한다. 옛 앱이 이 경로를 쓴다.
   - 요청 악보 해시에 결합된 경우: 격자 비교 대신 좌표 유효성을 검사한다. 모든 `tempos` 좌표가 실제 (각, 정간)이어야 하고 끝은 악보 끝도 허용한다. `repeats`는 1 ≤ 시작 ≤ 끝 ≤ 각 수여야 한다. 어긋나면 `PLAN_POSITIONS_CHANGED`다.
   - 둘 다 아니면 400 `INVALID_REQUEST`다.
3. 통과하면 지금처럼 준비된 악보 해시로 다시 결합한다. 새 필드는 만들지 않는다.
4. 의미 변경: 새 앱의 계획은 "마지막 확정본의 좌표"가 아니라 "함께 보낸 악보의 좌표"다. 이미 저장된 데이터는 바뀌지 않는다. 서버를 먼저 배포해야 새 앱의 저장이 통과한다.

처음 초안과 다른 점:
- 한배 기호와 숫자 계획의 자리 일치 검사(BE·`common_preview.py`)는 넣지 않았다. 앱이 기호와 계획을 같은 칸 순서로 함께 옮기기 때문이다.
- 해시 정규화 일치를 확인하는 앱·서버 공통 고정 테스트는 두지 않았다. 기존 `sourceSha256` 결합이 이미 같은 정규화에 기대고 있다.

## 검증

1단계:
- 나누기·합치기 뒤 계획·기호 보존, 합치기의 기호 이동과 막음
- 822 중모리↔굿거리에서 기본 대비 배율 보존: 편집기 환산과 서버 비례 조정을 함께 거친 end-to-end
- `start_bpm`, 복귀 항목, `본래 속도로` 허용 오차, 40~200 범위 막음, 772 회귀
- BE `positions()` 완화 뒤 각·정간 수 변경의 `PLAN_POSITIONS_CHANGED` 회귀

2단계:
- k = 시작-1·시작·끝-1·끝·마지막 각 경계
- 기호와 숫자의 같은 자리, `sourceSlots`가 있는 인식 악보, 반복·이어짐
- 실행 취소·다시하기, 자동 저장 재진입
- 해시 고정 테스트, 옛 앱 경로, 서버 의미 검사

DATA 생성기 계약(`tempo_repeat.py`)은 바꾸지 않는다. `common_preview.py`에는 기호·숫자 일치 검사만 추가한다.
