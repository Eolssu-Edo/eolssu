# Jenkins 실패 Mattermost 알림

S15P31E102-509. 사용자가 Jenkins 실패 시 누구의 무엇이 왜 실패했는지, 어떤 로그인지와 조치 방법을 CI/CD 채널로 받도록 요청했다. 로그는 최대 3줄·총 300자다.

운영 Jenkins 6개 eolssu-* 잡의 완료 결과를 각 조회 종료 후 30초마다 읽는다. 파이프라인에 의존하지 않아 checkout·구문·에이전트 관련 실패도 완료 결과가 생기면 감지한다. FAILURE와 UNSTABLE, 로그로 제한시간 초과를 확인한 ABORTED를 알리고 SUCCESS·정상 수동 ABORTED는 보내지 않는다. 실행 중인 실패는 완료 후 알린다. 최초 기동에는 이미 끝난 과거 빌드를 기준점으로 잡고 진행 중 빌드는 놓치지 않는다. 운영 초기 검증은 실제 과거 실패 1건을 재전송으로 명시해 게시한다.

메시지: 실행 계기(수동 실행자/상위 잡/SCM), 변경 작성자(원인 제공자로 단정하지 않음), 잡·빌드·실패 단계·검사 SHA, 근거로 확인한 실패 분류와 구체적 조치, 마스킹된 핵심 오류 3줄/300자, 단계·전체 로그 위치. 증거 부족은 원인 미확정으로 표시한다. 원시 로그 전체와 환경·인증 값은 전송하지 않는다. Jenkins는 현재 loopback만 공개하므로 로그 링크는 기존 SSH 터널 127.0.0.1:18080 기준임을 명시한다.

Jenkins API는 기존 관리자 인증을 service credential로 읽기만 사용한다. Mattermost는 기존 CI/CD incoming webhook을 사용한다. 목적지는 meeting.ssafy.com의 /hooks/ 고정 HTTPS로 검증한다. 환경의 민감값은 원문 저장·출력하지 않는다. systemd DynamicUser·LoadCredential·StateDirectory로 실행하고 앱·Jenkins·빌드를 재시작하지 않는다. 중복 방지 상태를 원자 저장하고, 전송 응답이 모호하면 uncertain으로 남겨 자동 재전송하지 않는다. 실패 자체와 알림 전송 실패를 구분해 journal·상태 파일로 확인한다.

검증: 실제 실패 재생, 격리된 HTTP/메시지·중복·동시 빌드·초기 기준점·전송 유실·로그 유출/길이 검사, 운영 dry-run, 실제 CI/CD 채널 전송 1건과 타이머 기동 확인. 운영 빌드 실패를 인위적으로 만들거나 임시 MySQL을 실행하지 않는다.
