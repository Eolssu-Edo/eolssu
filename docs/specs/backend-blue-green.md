# 백엔드 블루그린 배포

[S15P31E102-604](https://ssafy.atlassian.net/browse/S15P31E102-604) · [실행 계획](../plans/S15P31E102-604.md)

edo1의 정기 백엔드 릴리스에서 기존 HTTPS 진입점으로 요청을 계속 받는다. 새 버전이 운영과 같은 설정·DB로 준비 상태를 통과하면 Nginx 설정을 리로드해 새 연결을 전환한다. 이전 연결의 응답과 이전 버전에서 접수한 악보 인식을 처리할 때까지 그 백엔드를 보존한다.

- 준비 실패 시 현재 대상이 요청을 계속 처리한다. 전환 확인 실패나 실행 중단 시 배포 기록으로 이전 대상을 복구한다. 자동 원복은 이전 실행 인스턴스가 살아 있는 전환 구간을 다룬다.
- 이전 슬롯이 종료를 시작하면 새 연주 분석은 받지 않고, 이미 받은 분석(실행 중·대기열)은 `eolssu.analysis.shutdown-wait`(기본 제한 시간 + 5초)까지 끝낸 뒤 내려간다([S15P31E102-947](../plans/S15P31E102-947.md)). 그 안에 끝나지 않은 시도는 기존처럼 제한 시간 뒤 `TIMEOUT`이 되고 다시 시도할 수 있다.
- 악보 원본과 읽기 토큰은 접수한 슬롯에서 관리한다. 같은 DB에 접속하는 다른 슬롯은 그 슬롯의 대기·진행 작업을 복구하거나 선점하지 않는다. 원본의 접근 제한과 만료는 기존 계약을 따른다.
- 웹 수동 배포, MySQL 볼륨, 백업, Flyway 검사, 배포 순서 검사는 기존 운영 흐름을 사용한다. 스키마 변경은 구·신 앱이 함께 읽고 쓸 수 있어야 한다. 마이그레이션 적용 여부와 앱 롤백은 별도로 기록한다.
- 기존 단일 백엔드에서 처음 전환할 때는 호환 릴리스와 설정을 준비하는 설치 절차를 거친다. 정기 배포 검증과 초기 설치, 웹 배포, 호스트 장애 대응은 각각의 운영 작업이다.

격리 환경에서 연속 HTTPS 요청과 전환을 가로지르는 업로드, 후보 준비 실패, 롤백과 중단 복구, 이전 슬롯에 접수한 변환 작업 보존을 검사한다. 요청 실패와 중복 완료는 각각 0건을 목표로 한다.
