# 녹음 파일 규격 (PRA-02)

- Jira: [S15P31E102-168](https://ssafy.atlassian.net/browse/S15P31E102-168), Story S15P31E102-33, Epic S15P31E102-20
- 상태: 사용자 합의(2026-10-27, `coco-clarify`). BE·FE·AI·Infra 담당자 검토 전이다. 업로드 API·원본 저장소 연결·Nginx 한도는 S15P31E102-181에서 구현했고, 실제 R2 버킷 확인은 버킷 준비 뒤 한다([작업 기록](../plans/S15P31E102-181.md)). 크기·길이 숫자는 실측 전 시작값이다. 오류 응답은 API 명세 공통 형식을 따른다(2026-10-28 오은서 제안, 우동균 수락). 원본 저장소는 2026-10-28 GCS에서 S3 호환 저장소 + Cloudflare R2로 바꿨다(우동균 결정). 새 외부 저장소와 접근 키 운영은 팀 검토 뒤 확정한다. 웹 녹음용 WAV(PCM16) 업로드와 서버 AAC 변환은 2026-11-23 우동균이 결정했다(S15P31E102-1262의 (c)안). 서버 구현은 [S15P31E102-1272](https://ssafy.atlassian.net/browse/S15P31E102-1272)(MR !1036, 2026-11-24 develop 병합), 웹 녹음은 [S15P31E102-1262](https://ssafy.atlassian.net/browse/S15P31E102-1262)다.
- 관련 계약: [DB 스키마](../contracts/db-schema.md)의 `practice_sessions`. 원본 저장소는 S3 호환 객체 저장소이며 처음 쓰는 업체는 Cloudflare R2다. 이 작업 범위에서 연결한다([원본 저장소](#원본-저장소)).
- 클라이언트 범위: Android·iOS 앱과 웹. 웹은 WAV(PCM16)로 올리고 서버가 AAC m4a로 바꿔 저장한다.

## 목표

사용자가 연습 구간을 연주해 녹음하면 앱은 m4a(AAC) 파일 하나를, 웹은 WAV(PCM16) 파일 하나를 서버에 올린다. 서버는 규격에 맞지 않는 파일을 업로드 시점에 바로 거부한다. 맞는 m4a는 원본 그대로, WAV는 AAC m4a로 바꿔 저장한다. 저장한 m4a는 분석 전에 AI가 읽는 형식으로 바꾼다.

## 동작

### 클라이언트 녹음

- 앱 녹음 형식은 MP4 컨테이너의 AAC(`.m4a`) 하나다. 플랫폼이 허용하면 모노·AAC·128kbps·44.1kHz 또는 48kHz로 요청한다. 서버는 비트레이트·샘플레이트·채널 수로 거부하지 않는다.
- 녹음은 10:00에 자동으로 멈춘다. 업로드 전에 파일이 20MiB를 넘으면 앱이 먼저 알린다.
- 평가 녹음이 한도에서 멈추면 10분까지만 녹음할 수 있다고 안내한다. 녹음 파일이 유효하면 지금까지 녹음한 내용으로 평가할 수 있다.
- 웹은 브라우저마다 AAC 인코더 지원이 달라(Firefox 등 미지원) WAV 컨테이너의 16kHz·모노 PCM16(`pcm_s16le`)으로 올리고 서버가 AAC m4a로 바꾼다. 마이크 입력(보통 48kHz)을 저역 통과 필터를 거쳐 16kHz로 줄이며, 10분은 19,200,044바이트로 20MiB 안이다. 10:00 자동 정지와 크기 사전 안내는 앱과 같다.
- 웹 녹음은 탭 메모리에만 둔다. 업로드가 실패한 뒤 페이지를 새로 고치거나 닫으면 녹음이 사라져 '녹음 다시 보내기' 대신 다시 연주를 안내한다. 브라우저 저장소(IndexedDB) 보관은 후속 과제다.
- 웹은 마이크를 HTTPS(또는 localhost) 페이지에서만 열 수 있다. 브라우저의 에코 제거·잡음 억제·자동 이득은 악기 소리를 깎으므로 끄도록 요청한다(브라우저가 무시할 수 있다).
- 웹 평가 녹음 중 스피커 장단은 약 1/10(-20dB)로 줄인다. 앱은 기기 볼륨에 따라 줄이지만(S15P31E102-878) 브라우저는 기기 볼륨을 읽지 못한다(2026-11-24 사용자 결정).
- webm·ogg(Opus) 등 그 밖의 형식은 받지 않는다.

### 업로드

연습 세션 하나에 녹음 파일 하나를 multipart로 올린다(`POST /api/practice-sessions/{sessionId}/recording`, 파일 파트 이름 `audio`). 앱이 보낸 연주 종료 시각(`endedAt`)과 `Idempotency-Key`는 받지 않는다: `ended_at`은 서버 시각이고, 응답을 받지 못해 다시 보낸 업로드는 409를 받은 뒤 상태 조회로 결과를 확인한다(2026-10-28 우동균 결정, API 명세 초안과의 차이). 서버는 아래 순서로 검사하고, 먼저 걸리는 결과를 반환한다. 거부한 파일은 저장하지 않으며, 세션 상태도 바꾸지 않는다.

| 순서 | 조건 | 응답 | 세션 |
| --- | --- | --- | --- |
| 1 | 세션이 없거나 요청 사용자의 세션이 아님 | 404 | 변화 없음 |
| 2 | 만료: `RECORDING`이고 `started_at` + 40분이 지남, 또는 이미 `FAILED`·`UPLOAD_TIMEOUT`으로 정리됨 | 410 | 변화 없음. 정리는 아래 배치가 한다 |
| 3 | 그 밖에 `status`가 `RECORDING`이 아님(이미 저장됨, 분석 중·완료·다른 사유의 실패) | 409 | 변화 없음 |
| 4 | 파일 크기 > 20MiB(20,971,520바이트) | 413 | 변화 없음 |
| 5 | MP4 계열 컨테이너의 AAC 오디오도, WAV 컨테이너의 PCM16(`pcm_s16le`) 오디오도 아님, 또는 그 오디오 스트림의 샘플레이트·채널 수를 양수로 읽지 못함(확장자·MIME가 아니라 ffprobe 결과로 판정) | 415 | 변화 없음 |
| 6 | 오디오 스트림은 있으나 ffprobe 길이를 읽지 못함, 길이 < 1ms, 또는 ≥ 601.0초 | 422 | 변화 없음 |
| 7 | WAV이면 ffmpeg로 모노 AAC(64kbps) m4a로 바꾼다. ffmpeg가 읽지 못하거나 손상된 WAV는 415다. 변환본도 4~6번으로 다시 검사해 걸리면 그 응답(413·415·422)을 준다. ffmpeg를 실행할 수 없거나 30초 안에 끝나지 않으면 500이다 | 415·413·422·500 | 변화 없음 |
| 8 | 저장소 쓰기 실패 | 503 | 변화 없음, 같은 세션으로 재시도 가능 |
| 9 | 저장은 됐으나 DB 갱신 실패 | 500 | 변화 없음. 방금 저장한 객체를 지우고 같은 세션으로 재시도 가능 |
| - | 모두 통과 | 202 | 원본(WAV는 변환본) 저장, `recording_url`과 메타데이터 칼럼 기록, `ended_at` = 업로드 성공 시각(서버 UTC), `status`를 `PENDING`으로 변경하고 분석 시도를 시작(`analysis_attempt` + 1, `analysis_started_at` = 같은 시각). 분석 결과를 기다리지 않고 바로 응답한다. 본문 `result`는 `{sessionId, status: "PENDING", evaluationId: null, pollAfterMs: 2000}` |

- 만료(2번)를 409(3번)보다 먼저 판정해, 배치가 돌기 전이든 후든 만료된 세션은 410을 받는다. 정확히 `started_at` + 40분인 순간은 아직 만료가 아니다(배치도 같은 경계).
- 만료 판정의 "지금"은 서버가 업로드 요청을 받은 시각(UTC)이다. `started_at`은 세션을 만들 때 서버가 기록한 값이며 앱이 보낸 값을 쓰지 않는다.
- 길이 상한은 600초이며 AAC 앞뒤 패딩으로 1초 미만 길어지는 것은 허용한다. 연습 구간(BPM·시작~끝 음표)으로 계산한 길이와는 비교하지 않는다. 구간보다 짧은 녹음은 AI 채점의 `TOO_SHORT`가 처리한다.
- 4~9에서 거부되면 같은 세션에 다시 올릴 수 있다. 저장에 성공한 세션은 3에 걸려 409를 받으며, 다시 불려면 새 세션을 만든다.
- 저장 키는 업로드 요청마다 서버가 만든 `recordings/{practice_sessions.id}/{UUID}.m4a`이다. WAV는 변환본만 저장하고 업로드한 WAV는 남기지 않는다. 사용자가 보낸 파일명은 쓰지 않는다. 같은 세션에 동시에 올려도 서로의 객체를 덮어쓰지 않는다.
- WAV 변환은 10분 녹음(16kHz 모노)에 Apple M4 기준 약 4.6초 걸린다. 변환 상한 30초에 ffprobe 두 번(각 상한 10초)과 저장소 상한 40초가 모두 겹치면 Nginx `proxy_read_timeout` 기본값 60초를 넘어 504가 될 수 있다. 이때도 서버는 처리를 이어 가므로, 앱의 재전송은 409를 받고 상태 조회로 결과를 확인한다([전송이 끊겼을 때](#전송이-끊겼을-때)).
- 저장 뒤 조건부 갱신(`WHERE status = 'RECORDING'`)으로 세션을 바꾼다. 갱신이 0행이면 다른 요청이 먼저 성공했거나 배치가 만료시킨 것이다. 이때 **자기 요청이 만든 객체만** 지우고, 세션이 `FAILED`·`UPLOAD_TIMEOUT`이면 410, 아니면 409를 반환한다. 먼저 성공한 요청의 객체와 `recording_url`은 그대로 남는다.

#### 전송이 끊겼을 때

- 요청 시간 초과(HTTP 408 포함)나 연결 실패가 나면 앱은 전체 전송 한도 120초 안에서 1초를 기다렸다가 같은 세션에 같은 녹음을 한 번 더 보낸다. 서버가 첫 요청을 이미 접수했다면 재전송의 409를 받아 기존 세션의 분석 상태를 확인한다.
- 재전송 뒤에도 실패하면 녹음을 기기에 두고 시간 초과, 연결 실패, 서버 응답 오류에 맞는 안내와 ‘녹음 다시 보내기’를 표시한다. 서버가 5xx를 반환하면 자동 재전송 없이 같은 녹음으로 다시 보낼 수 있다.
- 410으로 만료되거나 404·413·415·422 등으로 요청이 거부되면 같은 세션과 파일의 재전송을 제안하지 않는다. [S15P31E102-679](https://ssafy.atlassian.net/browse/S15P31E102-679)

### 요청 크기 한도

본문은 여러 계층을 지나므로 앱 검사(20MiB)보다 앞 계층의 한도를 넉넉히 둔다.

| 계층 | 한도 | 넘었을 때 |
| --- | --- | --- |
| Nginx `/api/` | `client_max_body_size 25m` | Nginx가 413을 반환한다. 본문 형식은 보장하지 않으며 1~3번 검사도 하지 않는다 |
| Spring multipart | 파일·요청 25MiB | 413, `RECORDING_TOO_LARGE`(공통 오류 형식). 1~3번 검사는 하지 않는다 |
| 업로드 검사(4번) | 20MiB | 위 표의 순서대로 413 |

앱은 본문 형식과 관계없이 413을 `RECORDING_TOO_LARGE`로 처리한다. 20MiB 이하 파일은 항상 위 표의 순서대로 판정된다.

### 오류 응답

거부 응답 본문은 API 명세의 공통 오류 형식(`application/json`)이다. `{httpStatus, isSuccess: false, message, code, result: {errorCode}}`이며 `code`는 HTTP 상태 숫자, 앱이 안내를 고를 값은 `result.errorCode` 문자열이다. 구현은 S15P31E102-143의 `common/error`를 쓰고, 아래 코드를 그 `ErrorCode`에 추가한다. 다른 API와 같은 형식이어서 앱은 오류 파싱을 하나로 처리한다.

| 상태 | `result.errorCode` |
| --- | --- |
| 404 | `SESSION_NOT_FOUND` |
| 409 | `SESSION_NOT_RECORDING` |
| 410 | `SESSION_EXPIRED` |
| 413 | `RECORDING_TOO_LARGE` |
| 415 | `RECORDING_UNSUPPORTED_FORMAT` |
| 422 | `RECORDING_INVALID_DURATION` |
| 500 | `INTERNAL_SERVER_ERROR`(공통 코드) |
| 503 | `RECORDING_STORAGE_UNAVAILABLE` |

```json
{"httpStatus": "PAYLOAD_TOO_LARGE", "isSuccess": false, "message": "녹음 파일이 20MiB를 넘어요", "code": 413, "result": {"errorCode": "RECORDING_TOO_LARGE"}}
```

### 원본 메타데이터 (DB 칼럼)

저장 성공 시 저장한 파일의 업로드 검사 값을 `practice_sessions`에 함께 기록한다. WAV는 업로드한 WAV가 아니라 저장한 변환본(AAC m4a)의 값이다. 한도 실측과 실패 원인 추적에 쓰는 값만 둔다. 새 Flyway 버전으로 추가하며, 기존 행과 업로드 전 행은 NULL이다.

| 칼럼 | 값 |
| --- | --- |
| `recording_bytes` | 저장한 파일 바이트 수 |
| `recording_duration_ms` | 저장한 파일의 ffprobe 길이(ms, 반올림) |
| `recording_sample_rate` | 저장한 파일의 샘플레이트(Hz) |
| `recording_channels` | 저장한 파일의 채널 수 |

저장한 파일의 코덱은 항상 AAC라 칼럼으로 두지 않는다. SHA-256은 무결성·중복 확인 요구가 생기면 다시 정한다.

네 칸은 항상 함께 쓴다. V3 마이그레이션(S15P31E102-179)의 `chk_practice_sessions_recording_meta`가 전부 NULL 또는 전부 양수만 허용한다. 길이 하한을 1ms로 두는 이유도 이것이다. 0.5ms 미만은 반올림하면 `recording_duration_ms`가 0이 되어 이 제약에 걸리므로, 여유를 두어 1ms 미만을 업로드 검사에서 422로 먼저 거부한다.

### 세션 만료

- `RECORDING` 상태로 `started_at` + 40분(최대 녹음 10분 + 업로드·재시도 여유 30분)이 지난 세션은 만료다. 정확히 40분인 순간은 만료가 아니다.
- 업로드 요청은 위 2번 검사로 410을 받는다. 배치가 이미 정리한 세션도 같은 410이라 배치 주기와 관계없이 결과가 같다.
- 주기 배치가 만료 세션을 `FAILED`, `fail_reason = 'UPLOAD_TIMEOUT'`으로 바꾼다. `ended_at`은 NULL로 둔다. 배치 주기는 구현에서 정한다.

### 분석 요청과 결과 조회

- 저장 성공을 커밋한 뒤 백엔드가 백그라운드에서 AI 서비스에 HTTP로 분석을 요청한다. 요청에는 세션 ID, 곡·연습 구간·BPM, 원본을 15분 동안 읽을 수 있는 서명 URL(presigned URL)이 들어간다.
- AI가 결과를 돌려주면 백엔드가 평가 결과를 저장하고 `DONE`으로, 실패 사유(`DECODE_ERROR`·`NO_SOUND`·`TOO_SHORT`)를 돌려주면 `FAILED`로 바꾼다. 시간 초과(`TIMEOUT`)·연결 실패(`SERVER_ERROR`)를 포함한 실패 코드 전체, 늦은 결과 무시, 분석 다시 시도는 PRA-03 [연주 분석 실패 사유와 화면 안내](https://ssafy.atlassian.net/browse/S15P31E102-167)를 따른다.
- 앱은 업로드 202를 받으면 분석 대기 화면에서 [분석 상태 조회 규칙](practice-analysis-failure.md#상태-조회와-시간-초과)에 따라 세션 상태를 조회하고 `DONE`·`FAILED`가 되면 멈춘다.
- 큐·별도 작업 서비스는 두지 않는다. AI 요청·응답 본문은 분석 연동 작업([S15P31E102-186](https://ssafy.atlassian.net/browse/S15P31E102-186))에서, 시간 초과 값과 `PENDING`에 남은 세션 처리는 PRA-03에서 정한다.

### 분석용 변환

- **AI 서비스**가 서명 URL로 원본 m4a를 받아 분석 직전에 **16kHz·모노·PCM16** 오디오로 디코딩한다. 스테레오는 두 채널 평균으로 모노화한다. 백엔드는 원본 위치만 넘기며 ffprobe 검사와 웹 녹음 WAV의 AAC 변환 외의 디코딩은 하지 않는다.
- 변환 결과는 메모리 배열 또는 임시 WAV 파일로만 쓰고 분석 뒤 버린다. 저장소에 두지 않으며, 재분석 때는 원본에서 다시 만든다.
- 변환·디코딩이 실패하면 세션을 `FAILED`, `fail_reason = 'DECODE_ERROR'`로 바꾼다.

### 원본 저장소

### 보관

- S15P31E102-375로 바뀌었다([녹음 보관과 미저장 녹음 정리](recording-retention.md)). 저장한 기록의 녹음은 회원이 기록을 지우거나(REC-04) 탈퇴할 때까지 보관한다. 저장하지 않은 녹음은 업로드(`ended_at`) 30일 뒤 서버 정리 작업(매일 04:30 KST)이 `recording_url`을 비우고 파일을 지운다.
- 375 운영 전환 전에는 버킷 수명 주기 규칙(`recordings/` 접두사, 객체 생성 30일 뒤 삭제)이 저장 여부와 관계없이 지웠다. R2는 만료 뒤 보통 24시간 안에 지운다. 전환 뒤에는 이 규칙을 두지 않는다.
- 기존 스키마 주석의 `created_at` 기준 30일 삭제 배치는 만들지 않았고, 정리 작업이 `ended_at` 기준으로 대신한다.
- 회원 탈퇴 일괄 처리(USR-05)와 기록 삭제(REC-04)는 정리 작업과 별개로 해당 녹음을 바로 지운다. 저장소 계약에 객체 삭제가 있어야 한다.

## 완료 판정

- [ ] 44.1kHz 스테레오와 48kHz 모노 AAC m4a가 202를 받고 저장되며, `recording_url`과 메타데이터 칼럼 4개·`ended_at`이 채워지고, 상태가 `PENDING`이 된다.
- [ ] 20,971,521바이트 파일은 413, MP3를 `.m4a`로 이름만 바꾼 파일과 오디오 스트림이 없는 m4a는 415, AAC 스트림은 있으나 길이를 읽지 못하거나 1ms 미만인 파일과 601초 이상 파일은 422를 받고 저장되지 않는다.
- [ ] 백엔드가 만든 거부 응답(Nginx 413 제외)이 공통 오류 형식(`application/json`)이며 `result.errorCode`에 위 표의 값을 담는다.
- [ ] 21MiB 업로드가 Nginx를 지나 백엔드의 413 `RECORDING_TOO_LARGE`를 받는다(실제 Nginx 경유 확인).
- [ ] 600.5초 AAC 파일은 통과한다.
- [ ] 16kHz 모노 PCM16 WAV(10분 19,200,044바이트 포함)가 202를 받고, 저장된 객체가 AAC m4a이며 메타데이터 칼럼이 변환본 값이다. PCM16이 아닌 WAV, ffmpeg가 읽지 못하거나 손상된 WAV는 415를 받고 저장되지 않는다.
- [ ] 저장된 세션에 다시 올리면 409, 다른 사용자의 세션이면 404를 받는다.
- [ ] `started_at` + 40분이 지난 `RECORDING` 세션은 업로드 410을 받고, 배치 뒤 `FAILED`·`UPLOAD_TIMEOUT`이 되며 다시 올려도 410이다.
- [ ] 같은 세션에 동시에 두 번 올리면 하나만 202이고, 남은 저장소 객체는 `recording_url`이 가리키는 하나뿐이며 그 파일이 성공한 요청의 내용이다.
- [ ] 저장소 쓰기 실패를 흉내 내면 503을, DB 갱신 실패를 흉내 내면 500을 받고 저장한 객체가 지워지며 세션은 `RECORDING`으로 남아 재업로드가 성공한다.
- [ ] 변환 결과는 16kHz·1채널·PCM16 WAV이며 길이가 원본과 1초 미만 차이다. 깨진 원본은 `FAILED`·`DECODE_ERROR`가 된다.
- [ ] Android·iOS 앱이 10:00에 녹음을 멈추고, 만든 파일이 AAC m4a다.
- [ ] 웹(Chrome·Safari·Firefox)이 마이크 허용 뒤 16kHz 모노 WAV를 올려 202를 받고, 분석 결과까지 이어진다. 저장된 녹음은 앱의 기록 상세에서 재생된다.
- [ ] 저장에 성공한 원본이 R2 버킷의 `recordings/{id}/{UUID}.m4a`에 있고, 백엔드가 만든 서명 URL로 자격 증명 없이 15분 안에 읽히며 만료 후에는 거부된다.
- [ ] 버킷이 공개 접근 차단 상태이고 `recordings/` 30일 삭제 수명 주기 규칙이 설정돼 있다(S15P31E102-375 전환 뒤에는 규칙을 지우고 서버 정리 작업이 맡는다).
- [ ] 한도 실측 결과가 기록되고 스펙의 숫자가 갱신된다.

## 검증 방법

- **픽스처:** ffmpeg로 몇 초짜리 사인파 AAC(44.1kHz 스테레오·48kHz 모노), 이름만 바꾼 MP3, 오디오 스트림이 없는 m4a, 저비트레이트 무음 AAC(600.5초·601초 이상), 손상 파일을 만들어 테스트 자원으로 둔다. AAC는 프레임 하나가 수십 ms라 1ms 미만 파일은 만들기 어려우므로, 1ms 경계(0.999ms 거부·1ms 통과)는 ffprobe 결과를 입력으로 받는 길이 판정 단위 테스트로 확인한다. 큰 파일은 커밋하지 않고 테스트 중에 생성한다.
- **백엔드:** 검사 순서·오류 코드·저장 키·상태 변경을 저장소 대역으로 단위 테스트한다. 메타데이터 칼럼과 상태 변경은 DB 통합 테스트로 확인한다. ffprobe가 없는 환경에서는 해당 테스트가 실패해야 하며 건너뛰지 않는다.
- **변환:** AI 쪽 테스트에서 픽스처의 변환 결과(16kHz·1채널·PCM16)와 길이를 검사한다. AI 대역을 사용한 테스트를 실제 채점 검증으로 보고하지 않는다.
- **WAV 변환:** `mediaTest`가 테스트 중 ffmpeg로 16kHz 모노 WAV(2초·600초)와 48kHz 스테레오 WAV를 만들어 변환하고, 변환본이 AAC m4a 검사를 통과하며 길이가 같은지 확인한다. 이름만 바꾼 m4a·내용이 깨진 파일·빈 파일은 변환되지 않아야 한다. 업로드 순서·저장 대상·임시 파일 정리는 변환기 대역으로 단위 테스트한다.
- **ffmpeg 버전:** 로컬·CI·운영의 ffprobe 판정이 같도록 백엔드 실행 이미지의 패키지 버전을 고정한다. 고정 버전은 `ffmpeg=7:8.0.1-3ubuntu2`(실행 베이스 `eclipse-temurin:21-jre`의 Ubuntu 26.04 패키지)이며 S15P31E102-180에서 이미지의 `ffprobe`로 확인했다. 베이스의 Ubuntu가 바뀌면 이 버전도 함께 갱신한다. 운영 backend는 이 버전을 설치한 실행 이미지 `eolssu-backend-runtime:21-jre-ffmpeg8.0.1`로 실행한다. Jenkins `mediaTest`는 edo1 호스트(Ubuntu 24.04)의 `ffmpeg=7:6.1.1-3ubuntu5`로 실행하며, 같은 실제 파일 검사 5개가 6.1.1과 8.0.1에서 같은 결과임을 확인했다(S15P31E102-197). WAV 변환 명령도 두 버전의 컨테이너에서 같은 결과(변환본 길이·샘플레이트·채널, 이름만 바꾼 m4a·깨진·빈·잘린 WAV의 실패)임을 확인했다(2026-11-24, S15P31E102-1272).
- **저장소:** 단위 테스트는 저장소 대역을 쓰고, R2 연결은 테스트 전용 버킷에 실제로 올리고 읽어 확인한다. 동시 업로드는 객체 키가 요청마다 다르고 진 쪽이 자기 객체만 지우는지를 대역과 실제 버킷에서 확인한다. 인증 정보는 저장소에 커밋하지 않는다.
- **Nginx:** 21MiB·26MiB 요청을 실제 Nginx 설정으로 보내 각각 백엔드 413(공통 오류 형식)과 Nginx 413이 나오는지 확인한다.
- **앱:** 자동 정지는 Android·iOS에서 직접 실행해 확인한다. 단위 테스트만으로 완료로 보고하지 않는다.
