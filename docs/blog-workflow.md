# 블로그 사용 방식: TIL 작성부터 게시까지

글을 쓴 팀원이 요청하고, Codex가 초안을 정리하고, 작성자와 리뷰어가 공개 여부를 확인합니다. `blog`에 병합된 뒤의 빌드·GitHub 게시·Pages 공개는 자동입니다.

## 역할과 작업 위치

| 순서 | 담당 | 작업 위치 | 하는 일과 결과 |
| --- | --- | --- | --- |
| 1 | 작업한 팀원 | 개발 저장소의 `TIL/` | 직접 한 일·판단 이유·근거를 기록하고 공개 후보 표시 |
| 2 | 작성자 | GitLab 개발 작업 브랜치 → `develop` | TIL을 커밋·push하고 개발 MR을 통해 원본 반영 |
| 3 | 작성자 | 저장소를 연결한 자신의 Codex 채팅 | 가져올 TIL 경로·분야·글의 방향을 전달 |
| 4 | Codex | 최신 `origin/blog` 기준 별도 작업 브랜치 | 선택한 TIL을 초안으로 가져오고 글 구성·문장 정리 |
| 5 | 작성자 | Codex 채팅·로컬 미리보기 | 사실관계·선택 이유·근거·공개 가능 여부 확인 |
| 6 | Codex | 블로그 작업 브랜치 | 명시적인 요청을 받으면 공개 검사·빌드·commit·push 후 MR 제목과 본문 전달 |
| 7 | 작성자·팀 리뷰어 | GitLab 블로그 작업 브랜치 → `blog` | 작성자가 MR 생성, 리뷰어가 검토·병합 |
| 8 | Jenkins·GitHub Pages | 서버·GitHub | 변경 감지·Hugo 빌드·결과물 게시·사이트 공개 |

특정 팀원에게 발행 담당 역할이 자동 배정되는 구조는 아닙니다. 글 작성자가 내용 확인과 요청을 맡고, 리뷰어는 팀에서 정합니다. 이 채팅을 사용하는 담당자가 다른 작성자의 글을 준비할 때에는 원 작성자에게 확인받습니다.

## 1. 팀원이 개발 중 TIL 작성

TIL은 `develop`에서 분기한 개발 작업 브랜치의 `TIL/` 아래에 작성합니다. 예를 들어 AI 담당자가 녹음 처리 문제를 해결했다면 `TIL/ai/2026-10-28-audio.md`에 기록합니다.

- 어떤 작업을 했고 왜 필요했는지
- 어떤 방법을 선택했고 다른 방법을 포기한 이유
- 문제를 재현한 조건, 시도와 확인 과정
- 측정값·화면·설계·테스트 등 실제로 남은 근거
- 아직 확인하지 못한 내용과 남은 과제

글감은 [작성 기준](blog-editorial-guidelines.md)에 따라 넓게 모읍니다. 성과·설계·완성한 기능·문제 예방·자동화도 글감이며, 수치는 여러 근거 중 하나입니다.

공개 후보로 선택한 TIL에는 다음처럼 머리말을 붙입니다.

```yaml
---
title: "녹음 처리 작업 메모"
blog:
  candidate: true
  title: "녹음 형식을 통일하며 배운 점"
  slug: "audio-format"
  author: "작성자 닉네임"
  description: "녹음 형식 문제를 확인하고 처리 기준을 정한 과정"
  categories: ["ai"]
  tags: ["녹음", "오디오"]
---
```

이 아래에 본문을 작성합니다. 내부 메모가 섞여 있다면 공개할 본문만 `<!-- blog:start -->`와 `<!-- blog:end -->` 한 쌍 사이에 둡니다. 공개 구간 표시가 없으면 본문 전체를 가져오므로 후보 표시 전에 확인합니다.

작성자가 TIL을 커밋·push하고 MR을 통해 **develop에 반영**합니다. 도구는 커밋되지 않은 파일이나 팀원 PC에만 있는 파일을 읽지 않습니다.

## 2. 작성자가 Codex 채팅에 요청

작성자는 도구가 포함된 최신 블로그 코드를 자신의 개발 환경에 준비하고, 같은 Git 저장소를 Codex에서 엽니다. 준비와 설치 방법은 [TIL 가져오기 안내](til-import.md)를 따릅니다.

요청은 GitLab 댓글이나 팀 메신저가 아니라 **Codex 채팅에 직접** 전달합니다. GitLab 댓글·메신저 메시지를 읽어 자동 실행하는 봇은 없습니다.

예시 요청:

> develop의 `TIL/ai/2026-10-28-audio.md`를 블로그 글로 다듬어줘. AI 분야의 문제 해결기로 쓰고, 실제 측정한 결과와 실패한 시도를 중심으로 구성해줘. 근거가 부족한 부분은 질문하고, 우선 `draft: true` 초안까지만 만들어줘. commit·push·MR 생성은 하지 마.

어떤 글을 고를지 정하지 않았다면 먼저 “공개 후보 TIL 목록을 보여줘”라고 요청할 수 있습니다. 분야는 DATA·AI·INFRA·FE·BE 중 글의 중심에 맞게 정하고, 연관 분야와 여러 태그를 함께 사용할 수 있습니다.

## 3. Codex가 공개용 초안 정리

Codex는 최신 원격 내용을 확인하고 **origin/blog에서 분기한 별도 작업 브랜치**에서 작업합니다. 개발 브랜치 전체를 blog에 병합하거나 앱 코드를 함께 가져오지 않습니다.

```sh
git fetch origin develop blog
python scripts/til_to_blog.py list
python scripts/til_to_blog.py import TIL/ai/2026-10-28-audio.md --dry-run
python scripts/til_to_blog.py import TIL/ai/2026-10-28-audio.md
```

위 명령은 준비한 블로그 작업 트리에서 실행합니다. 도구는 선택한 공개 본문을 `content/posts/게시일-audio-format.md`에 **항상 `draft: true`**로 생성하고 원본 연결 정보를 `.til-imports.json`에 기록합니다.

가져오기 도구는 복사·중복 방지·상태 비교·패턴 검사를 담당합니다. 문장을 재작성하거나 성과 수치를 만드는 기능은 없습니다. Codex가 작성 요청에 따라 글의 배경·구성·설명을 정리하고 부족한 근거를 작성자에게 질문합니다. 기록에 없는 수치는 미측정, 확인하지 못한 사실은 미확인으로 남깁니다.

Codex는 초안 위치와 내용을 알려주고, 필요하면 `hugo server -D`로 작성자가 볼 미리보기를 준비합니다. 초안 상태에서는 일반 Jenkins 배포에 포함되지 않습니다.

## 4. 작성자가 내용·공개 여부 확인

작성자는 다음 세 가지를 확인하고 수정 사항을 Codex에 전달합니다.

1. 우리가 직접 한 일이 구체적으로 설명되는가?
2. 왜 그렇게 선택했는지 이유가 있는가?
3. 결과를 보여주는 근거가 하나 이상 있는가?

사실관계는 실제 작업자가 확인합니다. 내부 주소·설정·인증 정보·개인정보가 드러나지 않는지, 이미지·악보·음원 등의 출처와 공개 조건이 맞는지도 검토합니다. 도구의 패턴 검사 통과가 이 검토를 대신하지 않습니다.

이미지가 필요하면 작성자가 README의 이미지 절차에 따라 `team-edo/blog-images`에 공개 가능한 파일을 올리고 주소를 전달합니다. Codex가 별도 요청 없이 이미지를 업로드하지 않습니다.

## 5. 작성자가 검사·commit·push 요청

초안 검토가 끝나면 작성자가 Codex에 다음처럼 요청합니다.

> 초안 확인했어. `draft: false`로 바꾸고 검사·Hugo 빌드를 진행해줘. 통과하면 글과 가져오기 기록을 commit·push해줘. MR은 생성하지 말고 정해진 양식의 제목과 본문만 전달해줘.

Codex는 공개 전 검사를 실행하고 일반 Hugo 빌드에 글이 포함되는지 확인합니다. 게시일은 현재 또는 과거 날짜여야 합니다.

```sh
python scripts/til_to_blog.py check content/posts/게시일-audio-format.md
hugo --minify
```

Codex가 요청받아 commit·push할 때에는 **글 파일과 `.til-imports.json`을 함께** 반영합니다. 검사 결과·작업 브랜치·커밋·정해진 GitLab 양식의 MR 제목과 본문을 작성자에게 전달합니다. 테스트 글이나 로컬 빌드 산출물은 올리지 않습니다.

## 6. 작성자가 GitLab에서 MR 생성, 팀 리뷰어가 병합

작성자가 GitLab에서 전달받은 작업 브랜치로 MR을 생성합니다. 대상은 **blog**입니다. TIL 원본을 반영할 때의 develop 대상 MR과 구분합니다.

- Source: 글을 준비한 블로그 작업 브랜치
- Target: `blog`
- 제목·본문: 전달받은 내용을 저장소의 MR 양식에 맞춰 확인·작성
- 관련 Jira: 실제 연결할 Key를 확인하고 입력

리뷰어는 글 내용·공개 정보·검증 결과를 확인한 뒤 병합합니다. MR 생성과 병합은 사람이 하며, Codex는 명시적인 요청 없이 생성하지 않습니다. 작업 브랜치에 push한 것만으로는 공개되지 않습니다.

## 7. Jenkins가 GitHub에 자동 게시

`blog` 병합 뒤에는 다음 흐름이 자동으로 실행됩니다.

```text
blog 변경 → Jenkins가 1분 간격으로 감지
→ Hugo 빌드 → team-edo/team-edo.github.io의 main에 결과물 push
→ GitHub Pages 배포 → https://team-edo.github.io/ 공개
```

1분은 변경 확인 간격이며 전체 게시 완료 시간이 아닙니다. Jenkins 빌드·push·Pages 배포 시간이 추가로 필요합니다. 최종 게시 뒤에는 작성자가 글 주소·제목·작성자·이미지·카테고리를 확인합니다. 게시가 실패하면 Jenkins·Pages 결과를 확인할 수 있는 팀 담당자에게 확인을 요청합니다.

## 게시 후 수정

원본 TIL을 고쳤다고 게시된 글이 자동 변경되지는 않습니다. `list`·`diff`로 변경을 확인하고, 이미 편집·게시한 글은 필요한 내용을 직접 반영해 다시 검토·MR·병합합니다. 상세한 상태와 갱신 절차는 [TIL 가져오기 안내](til-import.md)를 따릅니다.

처음부터 블로그 글을 직접 작성하려면 README의 글 쓰기 절차로 `content/posts/`에 작성할 수 있습니다. 이 경우 TIL 후보 표시와 가져오기 단계는 생략하고, 작성자 검토부터 같은 공개 절차를 따릅니다.
