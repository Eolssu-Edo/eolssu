# S15P31E102-1056 이조 적용 시 황종 주파수가 웹(Wasm)에서 달라져 웹 테스트가 실패하는 문제 수정

- Jira: S15P31E102-1056 · Story S15P31E102-319 · 스프린트 59321 · 진행 중.

## 원인

- 웹 수동 배포(Jenkins `eolssu-frontend-web-수동배포용`, develop `7b0a3acd4`)가 `Wasm browser tests`에서 `SheetAdaptationPersistenceTest` 3건 실패로 멈췄다. 이후 빌드·배포 단계는 건너뛰어 운영 웹은 바뀌지 않았다.
- 세 건 모두 마지막 단언 "다시 적용해도 되돌린 +3이 살아나지 않는다"에서 실패했다. 악보에서 다른 값은 `hwangHz` 하나였다(기대 `311.1269837220809`, Wasm `311.12698372208087`).
- `applyAdaptation`이 `440 × 2^((기준 MIDI − 69) / 12)`로 `hwangHz`를 매번 다시 계산하고, 이 `pow` 결과의 마지막 자리가 실행 환경마다 다르다. Windows에서는 Android 호스트 테스트가 통과하고 Wasm은 매번 실패했다(2026-11-16, ChromeHeadless 157). 같은 Task의 다른 작업 기록에는 macOS Android 호스트 테스트도 실패했다고 남아 있다.

## 결정

- 현재 값과 대상 악기 기준음의 계산값 차이가 계산값의 1e-12 이내면 저장된 값을 그대로 둔다. 실제로 다른 기준음일 때만 계산값으로 바꾼다.
- 테스트의 기대값을 바꾸지 않고 제품 코드를 고쳤다. 웹에서 같은 기준음으로 다시 적용해도 악보가 바뀐 것으로 판정되던 동작도 함께 고쳐진다.
- 저장 형식·API·원본 음고 계약은 바꾸지 않았다.

## 검증

- 회귀 테스트 `SheetPitchAdaptationTest › keepsAStoredReferenceFrequencyThatAlreadyMatchesTheInstrument`: 두 플랫폼 값(`311.1269837220809`·`311.12698372208087`)을 모두 유지하고, 다른 기준음(315 Hz)은 바꾸는지 검사한다.
- 같은 브랜치에 먼저 올라온 커밋 `15c013025`와 거의 같은 수정이어서 합쳤다. 그 커밋은 develop에 먼저 병합됐다(`6f3a395`). 이 브랜치의 후속 변경은 이 기록과 코드 주석뿐이다. 같은 내용을 검사하던 1 ulp 기반 테스트는 빼고 위 테스트 하나만 남겼다. 뺀 테스트는 수정 전 Android 호스트에서 실패하는 것을 확인했었다.

- `:shared:testAndroidHostTest` 전체: 1945건 중 실패 0, 기존 제외 5(2026-11-16, Windows, 같은 통합 후).
