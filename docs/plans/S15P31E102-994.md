# 최신 자동 빌드 APK의 QA 앱 로그 수집 연결 복구

- Task S15P31E102-994, 담당 우동균, Epic21·Story328 관련, 활성 스프린트59321·진행 중을 MCP로 확인했다.
- 기준 develop c41d35d7. 전용 fix(infra) 브랜치이며 기존에 승인한 공백을 하이픈으로 바꾸는 표기를 따른다.
- [수집 계약](../specs/qa-installed-app-logs.md). 사용자의 현재 설치 앱 보존 지시가 최우선이다. APK 설치·앱 실행·강제 종료·재시작·화면 입력·reverse 변경·로그 ack를 수행하지 않는다.
- 재현: QA 웹은 앱 처리 기록0건이다. 같은 시점 설치된 Tab S9 FE의 qa-20261116.022919-59e0e700에는 보존된 성능 이벤트212건이 있으며 begin/read 첫 페이지128건을 확인했다. 원본 DB의 ack는0이다.
- 원인: 일반 자동 APK는 안전한 성능 이벤트를 SQLite에 저장하지만 EolssuLive logcat은 꺼져 있다. 일반 앱 실행 경로는 관측 수집기를 시작하지 않고 웹은 무조건 앱 로그 없음으로 덮어썼다. 실행 정보의 앱 버전도 격리 서비스 초기값이었다.
- 순서: 기존 앱의 내보내기 계약/삭제 경계 확인 → 기존 HTTP 경계에서 실패하는 회귀 → begin/read 전용 기기별 읽기·안전한 투영 → 기존 QA UI 연결 → 전체 회귀·실기기 원본 대조 → 중계에만 적용·정리·커밋.
- begin/read의 응답은 cache/qa-perf 아래 요청 UUID별 임시 파일이다. 자동 승인이 첫 조회를 차단했으나 실제 삭제는 ack에서만 발생함을 소스로 확인해 재검토 후 조회가 허용됐다. 현재 APK와 원본 events DB는 보존했다.
- S10은 USB/기존 무선 연결이 끊겨 있다. 사용자는 무선 방식을 선택했고 현재 기본 화면 IP:포트를 기다린다. 태블릿으로 독립 검증을 계속한다.

## 갱신 지연 후속 · 사용자 현재 앱 보존

- 사용자가 S10 TLS 기본 주소44709를 제공해 등록 ID 확인에 성공했고, 기존 실행 중 앱으로 복귀했다고 알렸다. PC 중계 파일만 교체했다. 앱 설치·실행·강제 종료·화면 입력·reverse 변경은 수행하지 않았다.
- 첫 경로로 태블릿의 실제 이벤트182건·36동작을 읽고 QA 웹221건·48동작 표시 및 새 이벤트 증가를 확인했다. 사용자는 실시간 갱신 지연을 추가로 보고했다. 기존 내보내기는 매 스냅샷에서 ACK부터 순차로 다시 읽어야 하며, ACK는 원본을 삭제하므로 사용하지 않았다.
- 최종 경로는 원본 성능 DB 파일의 읽기 전용 사본을 검증해 순번 뒤 새 이벤트만 가져온다. 앱 브로드캐스트도 보내지 않는다. 연속 동일 사본, readOnly SQLite·quick_check·원본 커서/순번·기기 고정·비밀값 제외·설치 경합을 검사한다. PC 원문 사본은 즉시 정리한다.
- 최종 Node120개가 통과했다. 이 중5개는 설치 앱 무조작·실제 HTTP 상태 연결·증분 갱신·사본 일관성·원본 ACK/바이트 보존·기기 격리·설치 배타·고정 ADB 경로를 검사한다.
- 지연 측정을 준비하던 중 S10 TLS44709가 닫혔고 태블릿 USB도 목록에서 사라졌다. 자동 검색은 두 기기 모두searching이다. 기기별 새 연결 주소를 요청했으며, 새 읽기 전용 경로의 실기기 지연을 아직 통과로 기록하지 않는다.


## 전체 로그·연결 복구 추가 범위

- 최신 사용자 지시: 현재 APK가 남기는 모든 로그 종류를 실시간 반영하고, PC 페어링 키 입력과 APK 버전 관리 UI를 제거한다. USB는 꽂혀 있을 때만 우선하며 없으면 TLS 무선을 계속 검색한다. 상단 최신 APK 적용/기존 보관 자료는 유지한다.
- 실제 DB 읽기: S10 34113은249856바이트·ACK3263 이후866건, 태블릿46857은94208바이트·ACK0 이후296건이었다. 둘 다 DELETE journal이며 고정 ID가 일치했다. 이 수는 조회 시점 기준이며 원본 ACK 요청은 보내지 않았다.
- 기존 수집기의500건 투영·flow/visit 필수 조건으로 storage marker가 빠졌고, 영상 online과 격리 서비스 응답도 수집을 막았다. 전체 원본 커서부터 증분으로 읽고 marker/원본 dataSource/버전/누락 수를 보존하며150건씩 탐색한다.
- 전송 선택 결함: USB serial로 시작하면 무선 감시를 켜지 않고, 무선 상태가 connected일 때만 USB를 확인했다. 일치하는 ID의 등록 정보를 재사용하고 검색 중에도 USB를 우선한다. 태블릿도 USB TLS 포트 힌트를 사용하며1초 주기·전체 검색 후5초 대기로 재시도한다. IP 변경/리스너 꺼짐은 포트 검색으로 해결되는 문제가 아니다.
- coco-security로 요청된 PC 키 제거의 경계를 검토했다. Android 일회 코드·등록 IP·동일 출처·이름 세션·현재 조작자·설치 배타·실행/재시도 제한을 유지한다. 키 없이200, 무세션401, 다른 출처403, 잘못된 값400, 다른 조작자409, 반복429를 회귀로 확인했다.
- 최종 Node 전체127개가 통과했다. 신규 조건은 수정 전 실패를 확인했다. 추가로 원본 마커/500건 초과·영상/검사 서비스 장애·과거 로그 탐색 중 새 로그 도착을 검사한다. 실제 운영 반영·무새로고침 지연 측정은 아래에 별도 기록한다.

## 운영 반영과 1차 실기기 확인 · 2026-11-16 KST

- 검증된 중계/웹13개 파일을 두 감독이 사용하는 release-edf90cc3에 해시 대조 후 반영했다. 중계만 cooperative stop으로 교체했고 격리 서비스/컨테이너/앱/원본 로그를 초기화하지 않았다. 두 감독이04:39:27~28 UTC 다시 실행됐고 각 등록 TLS 연결이 복구됐다.
- 초기 전체 DB866/296건은 여러 APK 버전의 누적이었다. 현재 버전 필터로 S10은4128~4129의 run_started/log_gap 2건, 태블릿은295~296의 같은 마커2건이며 웹 전체4건과 정확히 맞았다. 과거 APK 로그를 현재 동작으로 부풀리지 않는다. 새 동작이 기록되는 검증을 사용자에게 요청했다.
- S10 설치 버전qa-20261116.022919-59e0e700·PID1803은 재조회에서 같았다. 태블릿은 별도 조작으로 추정되는 버전qa-20261116.035005-0f54befa·PID6555 변경을 관측했다. 이 작업에서 APK 설치/앱 실행/입력 명령은 수행하지 않았으며, 태블릿의 이전 버전과 동일하다고 보고하지 않는다.
- Chrome의 이전 QA 탭은 사용자가 닫은 상태여서 새 QA 탭1882127041에 이름으로 입장했다. PC 키 입력/버전 관리 DOM이 없고 기본 전체 로그4건이 표시됐다. 이후 refresh/reload를 수행하지 않는다.
- USB가 없는 S10의 TLS 전송만04:41:58.716 UTC disconnect했다. 감시기가 스스로638ms 만에 같은34113 포트로 연결했다.04:42:06.430의 새 canvas 영상(끊은 뒤7.714초 이내)을 기존 문서에서 확인했고 Page loaderId가35530D1339DE14FBABFC29F9BCF4B7CD로 같았다. 첫 복구 프레임을 실시간 포착한 값은 아니므로 영상 지연은 상한이며, 이 검증은 포트 변경 실험이 아니다.

- 자체 검토에서 비동기 재시도 시작 시 unavailable을 collecting으로 덮어써 장애가 숨겨질 수 있음을 발견했다. 실패 상태는 실제 읽기에 성공할 때까지 유지하고, 버전/스트림 변경 시 이전 마지막 이벤트 시각도 지운다. 회귀의 수정 전 실패와 수정 후 통과를 확인하고 중계에 반영했다.
- 단순 UI 요청 외에 설치/수집 경합과 읽기 일관성, 인증/기기/출처 경계,1600건 이상 페이지,500건 초과·마커 보존을 스냅샷 전체에서 자체 검토했다. 독립 형식 검토는 수행하지 않았다.
- 설계 차이: 처음에는 begin/read 내보내기를 재사용했지만 ACK 없이 매번 처음부터 읽는 지연 때문에 읽기 전용 DB 사본으로 대체했다. 현재 APK의 데이터/로그/프로세스를 보존하는 사용자 요구는 동일하다. 코드에서 기록하지 않는 동작이나 이미 ACK된 이전 기록은 새로 만들지 않는다.

## 최종 검증

- 사용자가 현재 S10 앱에서 화면을 오갔다. 같은 Chrome 문서의 전체 로그가4→23→24건으로 자동 증가했고 앱 동작4개가 표시됐다. 기록은 화면 진입·앱 HTTP 응답·데이터 로드·그리기/종료·액션을 실제 원본에서 반영했다. 새로고침/앱 입력/실행/설치를 수행하지 않았다.
- 웹의 S10 순번4128~4149 22건과 태블릿295~296 2건을 원본의 순번·kind·ms·target·status·duration_ms 튜플과 프로그램으로 대조해24건 모두 일치했다. 원본 ACK는 각각3263/0으로 같았고 PID는1803/6555로 유지됐다.
- 실제 HTTP200은 앱의 HTTP 응답 근거이며, 이를 서버 수신/AI/DB 완료로 확대하지 않았다. 원본 앱의 단조 시각으로 단계 경과 시간을 표시하고 PC의 읽기 시각을 처리 시간으로 쓰지 않았다. 새 동작→브라우저 표시의 최초 지연을 정밀 계측한 값은 없으며500ms는 폴링 설정이다.
