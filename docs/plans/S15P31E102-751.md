# DB 백업 정렬 메모리 부족 복구

- Jira: S15P31E102-751 · Story S15P31E102-327 · 박찬형 · 스프린트 59321 진행 중.
- 브랜치: `fix(infra)/S15P31E102-751-DB-백업-정렬-메모리-부족으로-막힌-운영-배포-복구`, 시작 `80acdb16`. 시작 작업 트리는 깨끗했다.
- [계약](../specs/backup-dump-sort-memory.md): 덤프 연결에만 정렬 버퍼 8 MiB를 적용한다. 전역 DB 설정·기존 백업 형식·기본 키 정렬을 유지한다.

## 원인과 작업

2026-11-11 운영 읽기 전용 진단에서 기존 덤프는 `user_sheets`의 큰 JSON 행을 정렬하며 Error 1038, exit 3으로 실패했다. 같은 명령에 세션 정렬 버퍼 8 MiB만 지정한 진단은 exit 0이었다. 덤프 내용은 출력·저장하지 않았다. 이 실패로 비행기 단모리 코드가 포함된 서버 배포도 사전 백업 단계에서 멈췄다.

1. 공통 `DUMP` 옵션을 최소 변경하고 기존 백업 검사를 실행한다.
2. 폐기 가능한 MySQL 8.4 고정 JSON 데이터로 실패·성공과 복원 데이터 일치를 확인한다.
3. 검증한 변경을 커밋한다. 리뷰·Push·운영 도구 설치·실제 외부 백업·서버 배포는 실행 담당자가 이어서 확인한다.

## 검증

2026-11-11 구현 완료, 독립 리뷰·게시 대기. 실제 코드 변경은 공통 `DUMP` 옵션 한 줄이다.

- 기존 백업 검사: 캐시된 `python:3.12-slim`의 network-none 컨테이너에서 `python -B -m unittest discover -s infra/backup/tests -v` 실행, 15개 통과. 백업 실패 시 배포 중단 검사도 유지된다.
- 로컬 MySQL 8.4.13 폐기용 컨테이너: JSON 1,200,500바이트를 담은 고정 8행으로 전체 덤프(1,202,902바이트)·데이터 덤프(1,202,444바이트)를 실행했다. 변경 전후 덤프가 각각 바이트 단위로 같고 전체 덤프 복원 후 데이터 덤프도 같다. 전역·새 연결의 기본 정렬 버퍼는 모두 262,144바이트로 유지됐다.
- 이 로컬 데이터는 기본 키 인덱스 순회로 기존 덤프도 성공하므로 Error 1038 재현 증거로 쓰지 않는다. 실패→성공 증거는 앞의 운영 읽기 전용 진단이다. 로컬 검사는 형식·데이터·설정 범위 보존을 검증했다.
- 데이터 덤프 SHA-256: `4f86d09751594eb340b5e0a0671cea82541ce90ff7444bc97c7aa35bbf07d475`. 임시 MySQL 컨테이너·익명 볼륨과 생성 덤프는 정리했다.
- `git diff --check` 통과. 운영 도구 설치, 실제 암호화·외부 백업 영수증, 서버·앱 배포는 아직 수행하지 않았다.

## 운영 복구

독립 리뷰에서 최종 구현 `96146c7a`의 차단 결함이 없음을 확인했다. 2026-11-11 05:32 UTC에 edo1·edo2의 백업 타이머를 잠시 멈추고 관련 잠금 안에서 도구를 교체한 뒤 원래 타이머를 모두 재개했다. 이전 파일은 각각 `/opt/backups/eolssu-backup751-20261111T053225Z/`, `/opt/backups/eolssu-backup751-20261111T053208Z/`에 보존했다. 새 도구 SHA-256은 `c25448af3bdcfc235e4fb4d5fae0a12f65ed6727237fbb9f0c465eabbd9f628f`다.

실제 `backup.py send db`가 성공했고 edo2의 수신 영수증 `20261111T053226Z-d8473017f52a`를 재조회했다. 암호문은 769,877바이트이며 SHA-256 `19db13902b834045443b6b454de2626b1625a6a195cb71b0c1be2371444a022a`가 일치한다. Jenkins 백엔드 배포를 다시 시작했으며 서비스 배포·비행기 데이터 교체는 아직 진행 중이다. 백업 검사를 우회하지 않았다.
