# DB 백업 정렬 메모리 부족 복구

- Jira: S15P31E102-751 · Story S15P31E102-327 · 박찬형 · 스프린트 59321 진행 중.
- 브랜치: `fix(infra)/S15P31E102-751-DB-백업-정렬-메모리-부족으로-막힌-운영-배포-복구`, 시작 `80acdb16`. 시작 작업 트리는 깨끗했다.
- [계약](../specs/backup-dump-sort-memory.md): 덤프 연결에만 정렬 버퍼 8 MiB를 적용한다. 전역 DB 설정·기존 백업 형식·기본 키 정렬을 유지한다.

## 원인과 작업

2026-11-11 운영 읽기 전용 진단에서 기존 덤프는 `user_sheets`의 큰 JSON 행을 정렬하며 Error 1038, exit 3으로 실패했다. 같은 명령에 세션 정렬 버퍼 8 MiB만 지정한 진단은 exit 0이었다. 덤프 내용은 출력·저장하지 않았다. 이 실패로 비행기 단모리 코드가 포함된 서버 배포도 사전 백업 단계에서 멈췄다.

1. 공통 `DUMP` 옵션을 최소 변경하고 기존 백업 검사를 실행한다.
2. 폐기 가능한 MySQL 8.4 고정 JSON 데이터로 실패·성공과 복원 데이터 일치를 확인한다.
3. 검증한 변경을 커밋한다. 리뷰·Push·운영 도구 설치·실제 외부 백업·서버 배포는 실행 담당자가 이어서 확인한다.

## 검증

2026-11-11 구현 완료. 실제 코드 변경은 공통 `DUMP` 옵션 한 줄이며, 후속 리뷰·운영 적용 결과는 아래에 기록한다.

- 기존 백업 검사: 캐시된 `python:3.12-slim`의 network-none 컨테이너에서 `python -B -m unittest discover -s infra/backup/tests -v` 실행, 15개 통과. 백업 실패 시 배포 중단 검사도 유지된다.
- 로컬 MySQL 8.4.13 폐기용 컨테이너: JSON 1,200,500바이트를 담은 고정 8행으로 전체 덤프(1,202,902바이트)·데이터 덤프(1,202,444바이트)를 실행했다. 변경 전후 덤프가 각각 바이트 단위로 같고 전체 덤프 복원 후 데이터 덤프도 같다. 전역·새 연결의 기본 정렬 버퍼는 모두 262,144바이트로 유지됐다.
- 이 로컬 데이터는 기본 키 인덱스 순회로 기존 덤프도 성공하므로 Error 1038 재현 증거로 쓰지 않는다. 실패→성공 증거는 앞의 운영 읽기 전용 진단이다. 로컬 검사는 형식·데이터·설정 범위 보존을 검증했다.
- 데이터 덤프 SHA-256: `4f86d09751594eb340b5e0a0671cea82541ce90ff7444bc97c7aa35bbf07d475`. 임시 MySQL 컨테이너·익명 볼륨과 생성 덤프는 정리했다.
- `git diff --check` 통과. 위 검사는 구현 시점 결과이며 운영 적용·게시 결과와 구분한다.

## 운영 복구

독립 리뷰에서 최종 구현 `96146c7a`의 차단 결함이 없음을 확인했다. 2026-11-11 05:32 UTC에 edo1·edo2의 백업 타이머를 잠시 멈추고 관련 잠금 안에서 도구를 교체한 뒤 원래 타이머를 모두 재개했다. 이전 파일은 각각 `/opt/backups/eolssu-backup751-20261111T053225Z/`, `/opt/backups/eolssu-backup751-20261111T053208Z/`에 보존했다. 새 도구 SHA-256은 `c25448af3bdcfc235e4fb4d5fae0a12f65ed6727237fbb9f0c465eabbd9f628f`다.

실제 `backup.py send db`가 성공했고 edo2의 수신 영수증 `20261111T053226Z-d8473017f52a`를 재조회했다. 암호문은 769,877바이트이며 SHA-256 `19db13902b834045443b6b454de2626b1625a6a195cb71b0c1be2371444a022a`가 일치한다. 백업 검사를 우회하지 않았다.

## 서버·앱 게시

Jenkins backend #415는 `80acdb1688fea908ee4b5ac2fec8ca95299c0174`를 backend-green에 배포했고 Flyway V38과 사전·사후 백업이 성공했다. 공개 API에서 단소 132·소금 133·산조대금 134의 v1·77 BPM·단모리 7 연결을 확인했다. 정악대금 56은 별도 판본 게시 전까지 v1·90 BPM을 유지한다.

같은 SHA의 Android #234는 검사·APK 게시에 성공했다. `/opt/eolssu/apks/index.json`의 빌드 `20261111T055023Z-234-80acdb16`은 38,202,920바이트, SHA-256 `0167e4c3ae93a506ee4b2bc8681921a80d7dae56490b83aa1a0d46b1e6c6d1cb`다. iOS #127은 archive까지 성공했지만 export에서 `No Accounts`·`No signing certificate "iOS Distribution" found`로 실패해 IPA가 게시되지 않았다.

2026-11-11 사용자가 구 iOS 설치본의 정악대금 기존 결과 조회·새 채점 제한을 확인하고 **새 Android·웹을 먼저 제공한 뒤 정악대금 v2 공개**를 선택했다. Web #8도 성공했고 공개 `/__eolssu_release.json`의 SHA가 `80acdb1688fea908ee4b5ac2fec8ca95299c0174`와 일치했다. 이후 서버의 자동 후속 배포는 `7ce401bd`로 진행됐지만, 두 SHA의 backend·infra/catalog 및 구판 조회 관련 FE 코드는 같음을 독립 검증했다. 휴대폰 설치와 iOS 인증서·계정 변경은 수행하지 않았다.

정악대금 적용 직전 사용자가 새로 등록된 `4박 기본 반주`가 더 적합한지 확인을 요청했다. 운영 ID 12는 `덩·덕·궁·덕`, 묶음 `[1,1,1,1]`이며 기본 160 BPM은 별도 곡 Blue Valentine의 출발값이다. 비행기는 전통 단모리 지정 근거가 없으므로 4박 기본 반주를 77 BPM으로 쓰는 쪽이 적절하다고 판단했다. 이 확인 시점에는 56의 v2 게시와 네 곡의 ID 12 재연결을 실행하지 않았다. 기존 [판본 보존 게시 절차](../../infra/catalog/airplane-revision.md)의 단모리 검증 조건을 새 선택에 맞게 정리한 뒤 적용해야 한다. 원래 단모리용 생성물·영수증을 새 반주 검증 결과로 취급하지 않는다.

운영 변경 전 보존 기준은 연습 5행·평가 5행·음표 결과 125행이며 사용자 데이터 원문 없이 해시만 `/opt/eolssu/ops707-airplane-history-20261111/user-row-digests-prepublish-20261111.json`에 기록했다. 이 작업의 백업 복구는 완료했고 소스 반영은 Draft MR !593의 사람 검토·병합을 기다린다. 비행기 반주 선택 후속 작업과 iOS 서명 문제는 백업 복구 완료와 구분한다.
