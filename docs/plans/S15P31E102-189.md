## 이번 단위(1차)

인증(S15P31E102-143)이 아직 없어 회원 ID를 받는 검증·저장까지만 구현했다.

| 계층 | 내용 |
| --- | --- |
| domain | `ScoreViewSegment`: 키(출력 가능한 ASCII 1~100자), 음수, 인정 > 보인, 끝 < 시작, 보인 > 구간 길이 + 1초, 보인 > 수신 시각 − 시작 + 1초 검증. 마이크로초 정밀도로 맞춘 뒤 본문 비교. `ScoreViewRepository` 저장소 계약 |
| application | `RecordScoreView`: 검증 → 같은 키 조회(같은 본문이면 기존 구간, 다르면 충돌) → 곡 확인 → 저장. 저장 순간 같은 키가 먼저 들어오면 다시 읽어 비교한다. 결과는 `Created`·`AlreadyRecorded`·`Conflict`·`Invalid`·`SongNotFound` |
| infrastructure | `MyBatisScoreViewRepository`와 Mapper `findByUserIdAndIdempotencyKey`·`songExists`·`insert`. 중복 키(`DuplicateKeyException`)는 false로 바꾼다. 시각은 UTC `LocalDateTime` |

남은 단계(같은 Task): API 경로·요청/응답·오류 형식(Notion GRO-04, 공통 오류 형식), 인증 회원 연결, Spring Bean과 `Clock` 연결, 결과별 HTTP 상태(201·200·409·400·404·401).

## 결정과 스펙과의 차이

- Spring Bean으로 등록하지 않았다. 기본 실행은 DB 없이 뜨고(`BackendApplicationTests`), Mapper Bean은 `db` 프로필에만 있다. Mapper를 쓰는 Bean을 지금 등록하면 기본 기동이 깨진다. 어느 프로필에서 연결할지는 API를 붙일 때 정한다.
- 수신 시각 검사(스펙 R3)에도 구간 길이 검사와 같은 1초 반올림 여유를 뒀다. 앱이 구간을 닫자마자 보내면 반올림된 보인 시간이 수신 시각 − 시작보다 1초 미만으로 길 수 있어 정상 기록이 거절되기 때문이다. 스펙 반영이 필요하다.
- 곡 존재는 `songs` 행이 있는지만 본다. 숨김·삭제 표시된 곡의 기록도 받는다(오프라인에서 연습한 뒤 곡이 숨겨진 경우).
- 트랜잭션으로 묶지 않았다. MySQL REPEATABLE READ에서 같은 트랜잭션 안의 재조회는 먼저 읽은 시점의 스냅샷을 봐서, 동시에 저장된 행을 찾지 못한다.
