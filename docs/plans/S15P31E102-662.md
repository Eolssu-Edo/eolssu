## 작업과 완료 조건

1. 보고된 네 이름과 정상 종료 상태를 재현하고, 운영 이름·비정상 종료·조회 실패·edo2는 기존 판정을 유지하는지 테스트한다.
2. edo1 상태 수집기에서 확인된 롤백 보관본만 제외한다. 기존 릴레이와 컨테이너 상세 조회 경로를 유지한다.
3. 후보를 점검한 뒤 edo1 수집기 파일을 백업하고 교체한다. 동일한 전용 SSH 경로로 보고를 다시 렌더링해 장애 집계에서 보관본이 사라지는지 확인한다.

## 구현 검증

- 운영 이름이 중지된 재현에서 기존 보고는 장애 5건, 수정 후에는 운영 이름 1건만 표시했다. 비정상 종료·OOM·Docker 오류·일시정지·조회 실패·edo2는 기존 판정을 유지한다.
- `python3 -B -m unittest discover -s infra/edo-check/tests -v` 60건 통과. 독립 검토에서도 판정 범위와 회귀를 확인했다.
- 교체 전 후보 파일을 edo1의 실제 Docker·systemd·HTTP에 읽기 전용으로 실행해 내부 검사 37건에서 실패 0건과 운영 편집기의 미검증 표시를 확인했다.

## 운영 반영

- edo1의 기존 수집기를 `/var/backups/edo-check/S15P31E102-662/collector.py.before`에 보관하고 구현 커밋 `12e159be`의 파일로 원자 교체했다. 양쪽 SHA-256과 운영 파일의 `root:root 0644`를 확인했다.
- 11:28 KST에 운영 edo2 중계에서 전용 SSH·외부 HTTPS·렌더링을 재실행했다. 콜백은 로컬 출력으로 대체했다. 새 보고는 `장애 0 · 주의 0 · 미검증 6 · 미측정 0`이며 공개 웹·API, API 지표, 인증서가 정상이었다.
- 운영 편집기는 기존 시작 시각으로 실행 중이며 공개 설정 조회에서 HTTP 200과 `canBatch: true`를 다시 확인했다. 이전 컨테이너 네 개도 Docker에서 종료 상태로 보존됨을 확인했다.
- Jira는 활성 스프린트 5의 진행 중이며 Story [S15P31E102-41](https://ssafy.atlassian.net/browse/S15P31E102-41)에 연결했다. 저장소 통합은 후속이다.
