### 런북에 반영한 발견

- **zsh에서 `--resolve` 변수 실패:** `R='--resolve …'; curl $R`는 macOS 기본 셸 zsh에서 한 단어로 넘어가 `option … is unknown`으로 실패한다. 또 443용 `--resolve`는 `http://` 검사(80번)에 적용되지 않아, 기존 308 검사는 edo1로 갔을 것이다. 7단계를 옵션을 직접 쓰고 80번은 따로 지정하는 형태로 바꿨다.
- **다시 읽기 직후 옛 인증서:** `systemctl reload nginx`가 끝난 직후의 요청은 기존 작업 프로세스가 받아 IP 인증서로 응답했다. 2초 뒤에는 정상이다. 6단계에 대기를 넣었다.
- **승격 파일 위치:** 사전 준비가 세 파일을 모두 대기 앱 폴더에 두라고 했지만, 4-5단계는 복제 폴더에서 `replica.promote.compose.yml`을 찾는다. 사전 준비를 고쳤다.
- **인증서가 이미 있을 때:** 6단계는 백업의 인증서가 미리 둔 것과 같으면 복사를 건너뛰어도 된다. edo1이 갱신(만료 30일 전, 약 12-21)한 뒤에는 백업 쪽이 최신이므로 덮어쓴다.
- **4-2 결과가 `0000-00-00`:** 복제본이 재시작 뒤 아직 거래를 하나도 적용하지 않았으면 이 값이 나온다. 운영 복제본에서는 오늘 하루 안의 시각이 나오는 것을 읽기 전용으로 확인했다. 이 값이 나오면 손실 구간을 db 백업의 `snapshot_at`으로 판단한다.

연습용 명령 실수(런북 문제 아님): 원격 셸 따옴표 처리로 3단계 첫 실행이 Python 문법 오류로 멈췄다. 대기 앱 폴더를 일반 권한으로 읽으려다 빈 가상 호스트 파일이 한 번 적용됐다. 빈 파일이라 서버 블록이 없었고 바로 고쳤다.

### 이 리허설이 보여 주지 않는 것

- 실제 DNS 변경·반영 시간(8단계)과 SSAFY 응답 시간
- 4-1 감시·터널 중지와 실제로 받은 거래가 있는 상태의 4-3 대기. 사본은 받은 거래가 없다.
- 복제본 볼륨 그대로의 물리 사본. 사본은 논리 덤프라 InnoDB 파일 상태까지 같지는 않다.
- AI·OMR·재생 서비스. 연습 앱은 백엔드·프런트만 띄웠다. 녹음 업로드(R2 쓰기)와 채점은 하지 않았다.
- 원복 4–6단계와 edo1 ↔ edo2 간 전송
