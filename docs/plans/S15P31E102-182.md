## 범위와 완료 조건

- `RECORDING`이고 `started_at`이 현재(UTC) − 40분보다 이른 세션을 `FAILED`·`fail_reason = 'UPLOAD_TIMEOUT'`으로 바꾼다. 정확히 40분인 세션은 만료가 아니다. `ended_at`은 비워 둔다.
- 갱신 조건에 `status = 'RECORDING'`을 넣어 업로드(조건부 갱신)와 경쟁해도 한쪽만 반영된다. 여러 서버에서 동시에 돌아도 결과가 같다.
- 5분 간격(이전 실행 종료 기준)으로 실행한다. `db` 프로필에서만 만들고, 무DB 기본 프로필과 읽기 전용 `ops` 프로필에서는 만들지 않는다.

## 결정·제약

- 40분 기준과 `UPLOAD_TIMEOUT`은 domain에 둔다. 업로드 API(S15P31E102-181)의 410 판정이 같은 기준을 쓴다.
- 구성은 `config/RecordingUploadExpiryConfig`에서 연결한다. 시계는 `Clock.systemUTC()`이며 테스트는 고정 시계를 쓴다.
- `practice_sessions`에 `(status, started_at)` 인덱스가 없어 5분마다 테이블을 훑는다. MVP 규모에서는 두고, 행이 늘면 인덱스를 새 Flyway 버전으로 추가한다(S15P31E102-179·173과 버전 조율).
- 같은 `PracticeSessionMapper`를 S15P31E102-179가 고친다. 먼저 병합되는 쪽에 맞춰 다른 쪽을 맞춘다.

## 검증 결과

- 구현 전 새 테스트는 대상 클래스가 없어 컴파일 실패했다.
- `./gradlew --no-daemon clean build`: 성공. 기본 테스트 4개(새 단위 테스트 1개, 무DB 기동 시 만료 작업 빈이 없음을 확인하는 검사 포함), 실패 0개.
- `./gradlew --no-daemon databaseTest`: 성공. 임시 MySQL 8.4.9(로컬 loopback 포트·임시 데이터 디렉터리)에서 8개, 실패 0개. 새 검사는 40분 직전(1µs 전)·정확히 40분·이후 `RECORDING`과 오래된 `PENDING`을 넣고 1행만 바뀌는지, 두 번째 실행은 0행인지, 기존 `DONE` 행이 그대로인지 확인한다.
- 민감도: 기간을 39분으로 바꾸면 단위 테스트가, 조건을 `<=`로 바꾸면 DB 테스트가 실패했다. 둘 다 원복했다.
- 실제 서버에서 스케줄 실행은 확인하지 않았다(운영 DB 미연결).
