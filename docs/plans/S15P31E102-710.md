Cloudflare R2 목록에는 `eolssu-recordings`와 그 버킷 전용 `eolssu-backend-recordings` 토큰만 있었다. 악보용 `eolssu-sheet-audio` 버킷을 APAC·Standard로 만들고 Public Access Disabled, 개발 URL 비활성화, 연결된 사용자 도메인 없음, 기본 미완료 multipart 중단 규칙을 확인했다. 사용자 승인 후 `eolssu-backend-sheet-audio` 계정 토큰을 발급하고, `eolssu-sheet-audio` 한 버킷의 Object Read & Write만 있는 활성 토큰임을 재조회했다. 키는 브라우저에서 edo1의 일회용 공개키로 암호화했고 edo1 관리자 전용 공간에서 복호화했다.

운영 JAR의 소스 `e94e766e`에는 [684의 현행 계약](../specs/sheet-audio.md#임시-m4a-다운로드와-기기-재생-s15p31e102-684)이 들어 있다. SHT-13은 최대 10분간 임시 M4A 링크를 발급하며 `midi`는 null이다. MIDI는 내부 생성기 ZIP에서 확인한다. [534의 원본 비보관](../specs/user-sheets.md#업로드-원본-비보관-정책-2026-11-06-확정-s15p31e102-534)에 따라 이미지·PDF는 백엔드 임시 저장소에 둔다.

## 운영 반영 및 검증 절차

1. 악보 전용 버킷의 Cloudflare 설정에서 Public Development URL 비활성화와 연결된 사용자 도메인 없음, 대상 버킷에 한정한 Object Read & Write 권한을 확인한다. 녹음용 버킷·키와 구분한다. [권한 안내](https://developers.cloudflare.com/r2/api/tokens/) · [공개 경로 안내](https://developers.cloudflare.com/r2/buckets/public-buckets/).
2. 승인된 키를 보호된 운영 경로로 받아 `/opt/eolssu/.env`의 `SHEET_STORAGE_ENDPOINT`, `SHEET_STORAGE_BUCKET`, `SHEET_STORAGE_ACCESS_KEY_ID`, `SHEET_STORAGE_SECRET_ACCESS_KEY`, `SHEET_STORAGE_REGION`에만 주입한다. 변경 전에는 기존 파일을 root 전용으로 백업하고 운영 Compose를 `config --quiet`로 검사한다.
3. [블루그린 절차](../../infra/runtime/README.md)로 새 환경을 읽는 슬롯을 기동한다. 같은 SHA·이미지에 대해 `deploy-backend`가 `already_deployed`를 반환할 수 있다. 활성 컨테이너에서 설정값 유무와 환경 파일 일치 여부를 값 없이 확인한다. 실제 슬롯 전환 뒤 공개 readiness·Docker health와 프론트·MySQL·생성기의 컨테이너 ID 및 MySQL 볼륨을 다시 확인한다.
4. 승인된 운영 테스트 계정에서 공개 악보 한 곡을 `POST /api/users/me/sheets/copies`로 복사한다. 이번 실행 전용 멱등 키와 응답의 악보 ID로 정리 대상을 고정한다. SHT-12 POST의 202 이후 SHT-13 GET의 `pollAfterMs`에 따라 `DONE`까지 조회한다. `sheet-audio/`의 테스트 악보 아래에 M4A 한 개가 생기고 `midi`가 null인지 확인한다. 응답의 서명 URL은 메모리에서만 따라가고 GET 200, `audio/mp4`, 실제 본문 길이·SHA-256이 API 응답과 일치하는지 확인한다.
5. 검증 결과와 무관하게 이번에 만든 악보 ID만 SHT-02 DELETE로 정리한다. 204 뒤 악보 조회 404와 해당 M4A가 R2에서 사라졌는지 확인한다. 삭제 전에 읽었던 서명 URL이 여전히 유효하면 같은 URL로 404를 확인한다. 시간이 지났다면 인증된 HEAD로 확인해 서명 만료와 객체 삭제를 구분한다. 테스트 계정 세션을 새로 열었다면 로그아웃한다. 키·토큰·서명 URL은 출력하지 않는다.
