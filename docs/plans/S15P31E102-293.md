## 원인과 변경

2026-10-28 12:14:48 KST 복구가 `accounts-import`, MySQL 오류 1146에서 실패했다. 10월 29일 17:57:06~17:57:26 KST에 최신 DB 백업 `20261029T081456Z-5d65129c6236`으로 동일 실패를 재현했다. 정리는 성공했으며 `restore-last.json`의 실제 실패 때문에 15분 상태 검사도 비정상으로 판정했다. 백업 수신 최신성 자체는 정상이었다.

백업에는 CREATE USER 2개와 GRANT 10개, 그중 7개 테이블 대상 권한이 있었다. 빈 MySQL에 테이블을 만들기 전에 테이블 단위 GRANT를 넣는 순서가 원인이었다. [backup.py](../../infra/backup/backup.py)는 계정 생성 → 스키마·데이터 → 권한 순서로 복원한다. 계정은 DEFINER보다 먼저 준비하고, 어느 단계든 SQL 실패를 무시하지 않는다. 실패 phase도 세 단계로 구분한다.

배포된 백업 코드는 저장소 최신 develop보다 API 검사가 오래됐다. 기존 `/api/infra-smoke` JSON 404 검사를 저장소에 이미 반영된 Nginx 경유 공개 readiness의 HTTP 200/`status=UP` 검사로 맞췄다. 이를 업무 API 전체나 운영 profile의 DB 연결 검증 완료로 확대하지 않는다.

Android는 KVM 없는 Lightsail에서 Watchdog 반복 후 관리자가 16:35:50 KST에 의도적으로 중지한 실험이었다. 종료 143·OOM 아님이며 재실행하지 않았다. [collector.py](../../infra/edo-check/collector.py)는 root 관리 `/etc/edo-check/expected-stops.json`의 전체 ID·이름·정확한 종료 시각·종료 코드와 현재 상태를 함께 대조한다. [relay.py](../../infra/edo-check/relay.py)는 일치한 사건을 `실험 중지`로 표시하고 중지 이유를 남긴다. 이름 전체의 영구 예외나 자원 사용량 0 치환은 없다. 새 종료 사건·다른 ID·OOM·다른 코드·실행/일시정지 상태·잘못된 설정에는 기존 판정을 유지한다.

## 적용·복구·남은 경계

원본과 실패 결과는 edo2 root 전용 `/var/backups/edo2-repair-293/`에 보존했다: `backup.py.before`, `restore-last.before.json`, `collector.py.before`, `relay.py.before`, `timers-before.json`, `monitor-before.json`. 후보·테스트는 같은 디렉터리의 `candidate/`에 있다. 원본 실패 journal과 기존 백업 암호문은 보존했고 `reset-failed`로 이력을 지우지 않았다.

코드 교체 전 backup timer 3개의 활성 상태를 보존하고 잠시 정지한 뒤 원자 교체 후 원래대로 시작했다. 백업 수신·키·보관 기준은 변경하지 않았다. 점검 코드 적용 전 원본과 비밀파일의 내용/권한 서명을 root 내부에 저장해 전후 같음을 확인했고, `edo-check`만 한 번 재시작했다. Nginx·Docker·SSH·앱·Android는 재시작하지 않았다. IP·포트·명령 URL·토큰·방화벽·인증서 갱신 구성을 바꾸지 않았다.

복구 시에는 [백업 운영 안내](../../infra/backup/README.md)의 타이머·실행 작업 확인 후 root 백업의 원본을 같은 코드 경로에 root 소유 0755로 복원한다. 백업 원본은 SQL 순서 문제가 있으므로 복원 검증이 다시 실패할 수 있다. 점검 원본으로 되돌릴 때는 두 코드를 함께 복원하고 `edo-check`만 재시작한다. 이번에 새로 만든 `expected-stops.json`을 사용 중지하려면 동일 root 백업 경로로 옮겨 보존한다. 데이터·컨테이너·볼륨이나 키를 지우지 않는다.

최초 점검 폴더 전체 및 Python 파일 전송은 자동 승인 검토에서 내부 저장소 전송 범위의 명시적 승인 부재로 거부됐다. 사용자에게 collector/relay와 테스트 5개, 총 7개 Python 파일·edo2 목적지·검증 후 적용을 구체적으로 제시해 명시적 승인을 받은 다음에만 해당 파일을 전송했다. 비밀 설정·키·env는 전송하지 않았다.

실제 Mattermost 요청 수신→채널 callback 게시 검증은 메시지를 보내지 않기 위해 수행하지 않았다. 기존 명령 URL과 callback 정책은 보존했고 동일 앱 경로의 callback 직전까지 실제 검증했다. 백업 시간 80.41초는 준비된 edo2에서의 격리 시험이며 새 서버 프로비저닝·트래픽 전환을 포함하지 않는다. 원본 사용자별 grants 재조회 비교·binlog 시점 복원·키 오프라인 보관은 기존 범위 밖이다. Jira 완료 전환·커밋·Push·MR은 수행하지 않는다.
