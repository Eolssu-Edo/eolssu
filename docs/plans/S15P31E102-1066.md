# QA 웹 APK 적용의 앱 로그 읽기 대기 후 자동 설치

- Task S15P31E102-1066, 담당 우동균. Epic21·Story328 `Relates` 연결, 활성 스프린트59321·진행 중을 MCP로 재조회해 확인했다.
- 기준 develop e4a358fd6. S15P31E102-1051 실기기 검증 중 사용자가 요청한 후속이며, 거절 경로는 994에서 생겨 1051 완료 조건과 분리했다.
- 요청: `최신 APK 적용`이 앱 로그 읽기와 겹치면 `잠시 후 다시 설치하세요`(409)로 끝나 다시 눌러야 했다. 안내를 `앱 로그를 읽고 있습니다. 잠시 후 설치됩니다.`로 바꾸고, 읽기가 끝나면 재클릭 없이 설치하고, 대기 중 중복 클릭·중복 설치를 막는다.

## 결정

- 대기는 중계 서버의 설치 작업 안에서 한다. 브라우저가 재시도하면 탭이 닫히거나 다른 사람이 누를 때 중복 요청과 순서 경합이 생긴다.
- 설치 요청을 받는 즉시 기존 유지보수 잠금(`beginMaintenance`)을 건다. 이 잠금이 새 앱 로그 읽기(`app_log_installing`)·화면 입력·두 번째 설치(409)를 이미 막으므로 별도 대기열을 만들지 않는다. 소유자·epoch 검증도 요청 시점에 그대로 한다.
- 진행 중인 ADB 로그 복사는 중단하지 않는다. 자체 마감(앱 로그7초, DB 사본 읽기 각3초)으로 끝나며 성공·실패와 관계없이 끝나면 설치를 이어간다. 읽기 실패는 설치 안전과 무관하다.
- 대기 상한은30초다. 넘으면 설치하지 않고 `앱 로그 읽기가 끝나지 않아 설치하지 않았습니다. 기존 앱과 데이터는 보존했습니다.`로 실패 처리하고 잠금을 푼다.
- 설치 직전의 연결 확인(`inputFault`·`online`)과 요청한 빌드 ID 고정은 기존 그대로다. 대기 중 카탈로그가 바뀌어도 사용자가 고른 빌드를 설치하고, 웹은 그 빌드의 버전 일치로 완료를 판정한다.
- 응답: 대기하면 `202 {ok,waiting,message}`, `job.status='waiting'`·`job.message`. 설치가 시작되면 `installing`으로 바뀌고 message를 지운다. 대기가 없으면 기존 `202 {ok:true}`와 같다.
- 웹: 대기 중 일괄 적용 상태에 안내를 표시하고 버튼은 `설치 대기 중…`으로 잠근다. 실패하면 중계의 실패 사유를 그대로 보여준다.

## 검증

- 수정 전 실패: 새 `install-wait.test.mjs`가 export 부재로 실패했고, 기존 `installed-app-logs.test.mjs`의 설치 배타 검사는 409를 기대했다. 배타 불변식은 유지하고 "202 대기 → 스냅샷 종료 뒤에만 설치1회"로 바꿨다.
- `install-wait.test.mjs`: 대기→자동 설치1회, 대기 중 중복 설치409·새 로그 읽기409·입력409, 로그 읽기 실패 뒤 설치, 상한 초과 시 미설치·잠금 해제, 대기 없음은 기존 응답.
- `apk-update.test.mjs`: 대기 상태의 안내·버튼 잠금.
- 2026-11-17 Windows Node v24.19.0 `node --test`(infra/qa-phone): 129건 중127건 통과. 실패2건은 `relay-transport.test.mjs`가 `pwsh`를 실행하는데 이 PC에 PowerShell 7이 없어 `spawn pwsh ENOENT`로 실행되지 못한 것이다. 이번 변경과 무관하지만 이 환경에서는 미실행이다. 설치 관련6파일56건은6회 반복 모두 통과했다.
