# S15P31E102-385 내 정보 비밀번호 보유 여부

- Story: S15P31E102-22 / Epic: S15P31E102-14 / 스프린트 59245 진행 중
- 기준: origin/develop 2a0d4d9b, 시작 시 작업 폴더 깨끗함
- 진행: 구현 완료, DB 검증·정식 리뷰 대기

## 확정 계약

GET /api/users/me의 result.hasPassword를 필수 boolean으로 추가한다. users.password_hash가 null이 아니면 true, null이면 false다. 이메일이나 소셜 연결 존재로 추측하지 않는다. 기존 필드·인증·회원 상태 검증을 유지하며 해시는 내보내지 않는다. FE 분기용이며 서버의 비밀번호 확인·탈퇴 권한 검사를 대신하지 않는다. DB 스키마 변경은 없다.

## 작업 순서와 검증

1. HTTP 응답 테스트에 hasPassword=true를 요구하고 실패 확인.
2. 조회 모델·영속 매핑·응답 DTO에 boolean 전달.
3. 비밀번호 없는 회원의 false, 해시 미노출, 인증 회귀를 단위·실제 MySQL HTTP 테스트로 확인.
4. Swagger·Notion 계약 갱신, clean build·DB 검사와 자기 점검 후 작업 단위 커밋.

범위 제외: FE 코드·Push·MR·운영 배포. 정식 리뷰는 구현 커밋 뒤 별도다.

## 검증·제약

- 기존 HTTP 테스트는 result.hasPassword 누락으로 10개 중 1개 실패한 것을 확인한 뒤 구현했다.
- clean build 및 마지막 단위 테스트 추가 후 build 통과(484개, 실패·건너뜀 0). ACTIVE 본인만 조회하는 기존 인증 경계와 해시 원문 미노출을 유지한다.
- 실제 MySQL 8.4 databaseTest(MyInfo·OpenApi·ops OpenApi)는 13개 모두 애플리케이션 초기화 전에 차단됐다. 기준 develop에 V13__learning_tracks_and_progress.sql과 V13__reference_audio_assets.sql이 함께 있어 Flyway가 version 13 중복으로 실패한다. clean 후에도 소스에 두 파일이 있음을 재확인했다. 이번 Task에서 적용 이력·다른 담당 영역의 마이그레이션 번호를 임의 변경하지 않는다. DB 테스트 통과로 보고하지 않으며 병합 전에 중복 해결 후 재검증이 필요하다.
- Notion GET /users/me에 boolean 필드·예시를 추가하되 운영 미반영 상태를 표시한다.
- 자기 점검: 조회는 기존 JWT sub의 ACTIVE 본인만 허용한다. 응답에는 해시를 추가하지 않고 boolean만 전달하며 추가 쿼리·의존성은 없다. 구현은 요청 계약과 차이 없다. 테스트용 컨테이너 eolssu-task385-mysql은 제거했다.
- 구현 커밋은 이 문서를 포함하는 S15P31E102-385 커밋으로 추적한다.
- 범위: 기존 회원 조회 모델의 비밀번호 보유 boolean만 추가. 권한·탈퇴·비밀번호 정책 변경이나 DB 스키마 변경 없음.
