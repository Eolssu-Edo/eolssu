## 범위와 완료 조건

사용자가 프론트 웹의 develop 변경 감지·빌드·테스트·서버 배포 연결과 실제 자동 실행 검증을 요청했다. 기존 백엔드 자동 배포와 HTTPS·인증서 갱신·MySQL·데이터를 보존한다. Android/iOS 배포와 DB 스키마 적용은 포함하지 않는다.

기존 backend 잡의 성공 후 동일 SHA를 frontend 잡에 전달해 실행 순서를 고정한다. 프론트는 Kotlin/Wasm 배포 빌드와 기존 JS·Wasm 브라우저 테스트, 격리된 정적 자산 검증 후 불변 릴리스로 배포한다. 이전 프론트 복구·중단 복구·동일 아티팩트 재실행을 검증한다. HTTP/HTTPS 정적 자산·브라우저 앱 실행과 실제 Jenkins 자동 실행의 SHA·테스트·배포 결과를 확인해야 완료한다.

- Jenkins 사용자에게 프론트 빌드·브라우저 테스트 도구가 있는지 실제 명령으로 확인 중이다. 없는 검사나 도구를 통과로 보고하지 않는다.

### 구현·격리 검증

- Jenkins 사용자의 격리 workspace에서 `:webApp:wasmJsBrowserDistribution :shared:wasmJsTest :shared:jsTest`를 실제 실행했다. 첫 실행 6분 16초, JS·Wasm Chrome 테스트 합계 4개, 실패·오류·건너뜀 0. Google 공식 Chrome 156.0.8078.47을 설치했고 Gradle이 Node·Yarn·Wasm tooling을 준비했다. 웹 애플리케이션 소스·Gradle 모듈·의존성은 변경하지 않았다.
- backend/프론트 배포·lock·HTTP 정적 자산 회귀 검사 17개와 TLS/ACME 검사 8개가 통과했다. macOS의 localhost fixture는 sandbox 밖에서 실행했고 Ubuntu에서도 같은 검사가 통과했다. 격리 복제본에서 프론트 rollback 선택을 제거하면 회귀 검사가 실패했다.
- 실제 격리 Nginx Compose에서 읽을 수 없는 JS 파일 배포가 실패한 뒤 이전 웹 경로·HTTP 응답으로 복구됐다. fixture 컨테이너·네트워크·디렉터리는 제거했다.
- Jenkins 사용자가 만든 develop `3914b0e`의 웹 이미지에서 정적 파일 8개 전체 해시와 Wasm MIME을 검증했다. 후보는 비공개 internal network에서 실행했고 종료 후 정리했다.
- frontend·backend Pipeline이 실제 Jenkins Declarative linter를 통과했다. 서버 executor가 1개이므로 상위 잡은 `wait: false`로 프론트 잡을 예약하고 executor를 반환한다. 프론트 성공·배포 여부는 별도로 확인한다. 두 배포는 120초 상한의 공유 lock으로 직렬화하고 최신 SHA를 다시 확인한다.
- root 소유 배포 도구·Dockerfile·frontend Pipeline을 설치하고 프론트 잡을 disabled 상태로 준비했다. Jenkins의 새 sudo 권한과 상위 잡 연결은 아직 활성화하지 않았다.
- 운영·Jenkins·갱신 설정 백업은 `/opt/backups/eolssu-frontend73-d9pv8ct3/before.tgz`에 root 전용으로 보관했다. ACME 경로 변경 첫 staging 검증은 기존 도메인별 `webroot_map`이 우선해 404로 실패했고 기존 설정으로 복구해 HTTPS 200을 확인했다. `--webroot-map`을 추가하는 두 번째 시도는 Certbot 2.9가 도메인 변경으로 인식해 reconfigure를 거부했다. 각 실패 뒤 기존 구성을 복구했고, 원본 백업 후 ConfigObj로 저장된 두 webroot 항목만 원자적으로 변경하고 실제 저장값으로 staging 갱신·hook을 검증하는 방법으로 전환했다.


고정 ACME 경로의 공개 HTTP 도달성을 먼저 확인한 뒤 백업한 갱신 설정의 `webroot_path`·도메인별 `webroot_map`을 원자적으로 바꿨다. 저장된 설정을 사용하는 staging 갱신과 실제 deploy hook·HTTPS 검증이 통과했다. `/opt/eolssu/frontend-setup-receipt.json`에 `acme_ready`, backend/MySQL·env 보존, 백업 경로를 기록했다. 기존 인증서를 강제 재발급하지 않았다.

서버의 실제 웹 빌드 후 JS·Wasm yarn.lock 해시가 저장소와 일치했다. 최종 코드·테스트·운영 문서·계획·지식 기록을 자체 검토했다. 소스 입력 SHA·불변 릴리스·권한 범위·전체 자산 검사·TLS 유지·복구·120초 lock·단일 executor에서의 실행 순서를 확인했다. 독립 리뷰는 수행하지 않았다. 신규 frontend 잡은 여전히 disabled이고 새 sudo 위임과 상위 잡 활성화는 다음 단계다.

### 운영 활성화·실행 검증 — 2026-10-23

MR !25는 `ce06c5e7fa953b70bc44488113e7b15405067c65`로 develop에 병합됐고 Jira는 연동으로 완료 전환됐다. 사용자가 `deploy-frontend`의 sudo 실행과 프론트 자동 배포 활성화·실제 실행을 명시 승인했다. 서버는 호스트 Jenkins 서비스·executor 1개였고, 별도 Jenkins 컨테이너 전환은 적용하지 않았다.

- 원본 설정·배포 도구·Jenkins 잡·갱신 설정을 `/opt/backups/eolssu-activate73-20261023/before.tgz`에 root 전용으로 백업했다. 기존 웹 8파일의 복구 전제를 확인하고 독립 읽기 검토를 수행했다. 배포를 막는 구체적 결함은 발견되지 않았다.
- 병합 커밋의 두 배포 도구·두 Pipeline·프론트 Dockerfile을 root 소유로 설치하고 SHA-256 일치를 확인했다. 두 Pipeline은 현재 Jenkins linter를 통과했다. `/etc/sudoers.d/eolssu-frontend`에 해당 도구만 허용하는 한 줄을 0440으로 설치하고 visudo를 통과했다. Jenkins 사용자의 잘못된 SHA는 거부됐으며 `.env`는 읽을 수 없고 관리 도구는 쓸 수 없었다.
- frontend 잡을 활성화하고 backend 성공 후 같은 `REVISION`을 전달하도록 정의를 연결했다. backend의 1분 SCM polling은 유지했고 frontend에는 중복 polling을 추가하지 않았다.
- 검증 진입점으로 backend #9를 CLI에서 한 번 수동 시작했다. 47.921초에 SUCCESS, 기본 JUnit 1개 통과 후 frontend #1을 자동 시작했다. frontend #1의 실제 원인은 `Started by upstream project "eolssu-backend" build number 9`였고 양쪽 checkout·배포 SHA는 모두 `ce06c5e7`이다. 활성화 후 새 MR을 병합해 트리거한 검사는 수행하지 않았다. 기존 backend #8은 이 커밋을 SCM 변경으로 감지해 성공한 상태였다.
- frontend #1은 146.046초에 SUCCESS였다. 배포/lock/HTTP 검사 17개와 TLS/ACME/Nginx 검사 15개, Chrome JS·Wasm 테스트 4개가 실패·건너뜀 없이 통과했다. 웹 Gradle 빌드는 2분 5초였고 JUnit·웹 산출물 8개·배포 JSONL을 보관했다.
- 공개 HTTPS에서 정적 파일 8개 전체 해시, Wasm 2개의 `application/wasm`, 배포 marker의 SHA·manifest 해시, API JSON 404, 일반 HTTP 308과 실제 ACME HTTP 200을 확인했다. 브라우저에서 새로고침 후 `Click me!`로 `Compose: Hello, Web with Kotlin/Wasm!` 표시를 켜고 끄는 동작을 확인했다. 생성 번들에 Kotlin/Wasm memory 접근의 비차단 deprecation 진단이 남으며 앱 동작은 통과했다. 브라우저 확장 프로그램의 별도 오류는 앱 오류와 구분했다.
- 프론트 배포 journal의 보호 대상과 실제 backend/MySQL ID·물리 볼륨이 일치했다. backend #9 자체는 백엔드를 배포했고, 뒤이은 프론트 배포는 backend를 재생성하지 않았다. `.env`는 WEB_DIST_DIR 이외 내용과 0600을 유지했고 인증서·갱신 설정 해시는 활성화 전과 같았다. 동일 SHA·이미지로 Jenkins 사용자 sudo 도구를 다시 실행하면 `already_deployed`로 끝나며 프론트 ID가 유지됐다.

최종 배포 영수증은 서버 root 전용 `/opt/eolssu/frontend-activation-receipt.json`, 프론트 journal은 `/opt/eolssu/frontend-deployment.json`이다. manifest SHA-256은 `1cf06dcbdf9da816801bd204ca1d4b24a116e7ba5a67154861e52f123c34398b`다. 장애 시에는 [프론트 복구 절차](../../infra/runtime/README.md#프론트-웹-자동-배포)에 따라 자동 실행을 중지하고 journal의 `previous_web`로 복구한다. 실제 Nginx 격리 복구 검증 결과를 재사용했으며 운영에서 의도적인 실패를 주입하지 않았다.
