## 범위와 완료 조건

사용자가 프론트 웹의 develop 변경 감지·빌드·테스트·서버 배포 연결과 실제 자동 실행 검증을 요청했다. 기존 백엔드 자동 배포와 HTTPS·인증서 갱신·MySQL·데이터를 보존한다. Android/iOS 배포와 DB 스키마 적용은 포함하지 않는다.

기존 backend 잡의 성공 후 동일 SHA를 frontend 잡에 전달해 실행 순서를 고정한다. 프론트는 Kotlin/Wasm 배포 빌드와 기존 JS·Wasm 브라우저 테스트, 격리된 정적 자산 검증 후 불변 릴리스로 배포한다. 이전 프론트 복구·중단 복구·동일 아티팩트 재실행을 검증한다. HTTP/HTTPS 정적 자산·브라우저 앱 실행과 실제 Jenkins 자동 실행의 SHA·테스트·배포 결과를 확인해야 완료한다.

### 구현·격리 검증

- Jenkins 사용자의 격리 workspace에서 `:webApp:wasmJsBrowserDistribution :shared:wasmJsTest :shared:jsTest`를 실제 실행했다. 첫 실행 6분 16초, JS·Wasm Chrome 테스트 합계 4개, 실패·오류·건너뜀 0. Google 공식 Chrome 156.0.8078.47을 설치했고 Gradle이 Node·Yarn·Wasm tooling을 준비했다. 웹 애플리케이션 소스·Gradle 모듈·의존성은 변경하지 않았다.
- backend/프론트 배포·lock·HTTP 정적 자산 회귀 검사 17개와 TLS/ACME 검사 8개가 통과했다. macOS의 localhost fixture는 sandbox 밖에서 실행했고 Ubuntu에서도 같은 검사가 통과했다. 격리 복제본에서 프론트 rollback 선택을 제거하면 회귀 검사가 실패했다.
- 실제 격리 Nginx Compose에서 읽을 수 없는 JS 파일 배포가 실패한 뒤 이전 웹 경로·HTTP 응답으로 복구됐다. fixture 컨테이너·네트워크·디렉터리는 제거했다.
- Jenkins 사용자가 만든 develop `3914b0e`의 웹 이미지에서 정적 파일 8개 전체 해시와 Wasm MIME을 검증했다. 후보는 비공개 internal network에서 실행했고 종료 후 정리했다.
- frontend·backend Pipeline이 실제 Jenkins Declarative linter를 통과했다. 서버 executor가 1개이므로 상위 잡은 `wait: false`로 프론트 잡을 예약하고 executor를 반환한다. 프론트 성공·배포 여부는 별도로 확인한다. 두 배포는 120초 상한의 공유 lock으로 직렬화하고 최신 SHA를 다시 확인한다.
- root 소유 배포 도구·Dockerfile·frontend Pipeline을 설치하고 프론트 잡을 disabled 상태로 준비했다. Jenkins의 새 sudo 권한과 상위 잡 연결은 아직 활성화하지 않았다.
- 운영·Jenkins·갱신 설정 백업은 `/opt/backups/eolssu-frontend73-d9pv8ct3/before.tgz`에 root 전용으로 보관했다. ACME 경로 변경 첫 staging 검증은 기존 도메인별 `webroot_map`이 우선해 404로 실패했고 기존 설정으로 복구해 HTTPS 200을 확인했다. `--webroot-map`을 추가하는 두 번째 시도는 Certbot 2.9가 도메인 변경으로 인식해 reconfigure를 거부했다. 각 실패 뒤 기존 구성을 복구했고, 원본 백업 후 ConfigObj로 저장된 두 webroot 항목만 원자적으로 변경하고 실제 저장값으로 staging 갱신·hook을 검증하는 방법으로 전환했다.


고정 ACME 경로의 공개 HTTP 도달성을 먼저 확인한 뒤 백업한 갱신 설정의 `webroot_path`·도메인별 `webroot_map`을 원자적으로 바꿨다. 저장된 설정을 사용하는 staging 갱신과 실제 deploy hook·HTTPS 검증이 통과했다. `/opt/eolssu/frontend-setup-receipt.json`에 `acme_ready`, backend/MySQL·env 보존, 백업 경로를 기록했다. 기존 인증서를 강제 재발급하지 않았다.

서버의 실제 웹 빌드 후 JS·Wasm yarn.lock 해시가 저장소와 일치했다. 최종 코드·테스트·운영 문서·계획·지식 기록을 자체 검토했다. 소스 입력 SHA·불변 릴리스·권한 범위·전체 자산 검사·TLS 유지·복구·120초 lock·단일 executor에서의 실행 순서를 확인했다. 독립 리뷰는 수행하지 않았다. 신규 frontend 잡은 여전히 disabled이고 새 sudo 위임과 상위 잡 활성화는 다음 단계다.
