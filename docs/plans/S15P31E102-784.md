## 진행과 관찰

- 시작 절차: Jira MCP로 담당자·목적·상태·Story 링크·활성 스프린트를 확인했다. 기존 784 MR은 없다.
- 제공 자료: PDF 14개, PNG 22개, JPEG 4개. 여러 쪽 이미지는 곡별 묶음도 검증한다. 우물사이 JGB와 MusicXML은 대조 자료다.
- Android host 테스트·APK 빌드를 시작했다.
- 첫 OMR Docker 빌드는 고정한 `ca-certificates=20260816ubuntu0.24.04.1`을 저장소에서 찾지 못해 실패했다. 모델 실행 전 환경 실패이며 악보 변환 실패와 구분한다. 실제 패키지 후보를 조회해 고정을 갱신한 뒤 같은 빌드를 재실행한다.
- 율명 음역 대조 PDF의 글자층 추출은 6각×4정간을 읽었다. API 출력의 실제 음고 대조는 다음 단계다.
- 실제 모델에서 보허자·해령 PNG 3장과 AuClair 정간보 PNG가 `NO_GRID_FOUND`였다. 리더의 칸 너비 범위(85~110px)에 맞지 않았으며, 앞의 3장은 모델 기준 높이 3091px로 정규화하고 AuClair는 2/3배로 축소하면 모두 변환된다. 단순 2배 확대는 실패해 채택하지 않았다.
- AuClair 오선보는 Audiveris의 최소 오선 길이(30칸) 때문에 마지막 짧은 악단 두 마디를 버렸다. 최소 20칸으로 실행한 실제 출력은 16마디이며, 성부의 대표 음 길이를 비교해 44음의 낮은 선율을 선택할 수 있었다. 기존 시작 수 2배 기준은 44/23에서 높은 반주를 선택했다.
- 수정 범위: 기존 성공 경로를 먼저 유지하고 실패한 격자에만 추가 크기를 시도한다. 원본 bbox·시간 예산·최대 화소 제한을 유지한다. 성부는 시작 수가 더 많고 대표 음 길이가 절반 이하인 경우도 지속음 반주로 판단하며, 비슷한 길이는 높은 성부를 유지한다. 스캔의 음표 정확도와 변환 성공은 구분한다.
- Android 실제 파일 선택 → 업로드 → 실제 인식 → 24음 편집 → 음역 조정·확인 → 확정 저장 → 목록의 `연습 가능`과 API의 판본 2·24음·초안 없음까지 확인했다. 음원 사전검사는 실제 sample-free 생성 로직이며 CAT 음원 합성은 수행하지 않았다.
- 추가 대조: AuClair 정간보 PNG는 크기 변경만으로 44음이 나와도 56칸으로 합쳐지고 두 단의 순서가 섞였다. 기존 `grid_boxes.find_blocks`는 얇은 선을 읽어 올바른 순서의 64칸을 얻는다. 마지막 크기 재시도에서 이 엄격한 격자 경로를 사용한다. 악보 덩어리가 여럿이면 임의 선택하지 않는다. 실제 모델로 44음의 율명·옥타브·시작·길이 일치가 확인된 방식이다.
