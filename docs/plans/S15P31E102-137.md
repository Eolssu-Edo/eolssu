## 확인과 결정

- **develop에서 분리한 이유**: "실제 배포 전까지 main 역할인 develop에는 관리 대상 코드만 둔다"는 팀 의견. 확인해 보니 백엔드 develop 잡은 경로 필터 없이 모든 develop 커밋에 테스트·운영 배포를 하고 프론트 잡까지 실행한다(최근 백엔드 1분 30초~3분, 프론트 3분 30초~4분). 블로그 글 머지마다 앱 전체가 재배포되고 있었다.
- 검토한 선택지: ① develop 유지 + 앱 잡에 경로 조건, ② 같은 저장소의 블로그 전용 브랜치(B), ③ GitHub로 완전 이전(원본+Actions). 사용자가 **B**를 선택했다(2026-10-26). GitLab MR·Jira 흐름과 기존 Jenkins 구성을 유지하면서 develop을 비운다.
- `blog` 브랜치는 develop과 공통 조상이 없어 서로 머지되지 않는다. 블로그 글 브랜치는 `origin/blog`에서 만들고 `blog`로 MR한다. 루트 `AGENTS.md`의 "새 작업 브랜치는 develop에서" 규칙에 이 예외를 한 줄로 적었다(팀 공유 규칙 변경이므로 MR 리뷰에서 확인 필요).
- **이미지**: 같은 저장소의 다른 브랜치라도 기본 clone은 모든 브랜치를 받으므로 이미지가 쌓이면 clone이 커진다. 이미지는 GitHub `team-ido/blog-images`(Pages, `https://team-ido.github.io/blog-images/<파일>`)에 두고 글에는 주소만 쓴다. 폴더 대신 파일명 앞에 `YYYY-MM-`를 붙인다(웹 업로드에서 폴더 지정이 번거로움). 배포 토큰에는 이 저장소 권한을 주지 않는다. 선택지(LFS·외부 호스팅·최소화) 중 사용자가 이미지 저장소 + 최소화를 선택했다.
- Hugo는 미래 날짜 글을 빌드하지 않는다. 글 `date`는 오늘이나 지난 날짜로 쓰도록 README에 적었다.

## 검증과 결과

- `blog` 브랜치 Jenkinsfile의 Build 단계를 Jenkins와 같은 구조(작업 폴더 `site/` + `blog-build/`)로 로컬 Docker에서 실행: 16페이지 빌드 성공, `deploy.sh` 문법 통과.
- 이미지 주소를 넣은 임시 글(브랜치에 넣지 않음)로 `<img src=https://team-ido.github.io/blog-images/2026-10-test-image.png alt="테스트 이미지">` 생성을 확인. 처음엔 날짜가 내일이라 글이 빠져서 미래 날짜 동작을 확인했다.
- 남은 확인: `blog` push 후 Jenkins 잡 브랜치 변경·실행, `blog-images` 실제 주소, develop MR 머지 후 develop에 블로그 파일 없음.
