## 범위와 완료 조건

- 공개 POST /api/auth/password-reset: PASSWORD_RESET 인증 완료 토큰(30분) 1회 소비, 비밀번호 정책·Argon2id 저장, 회원의 refresh 전부 폐기, 자동 로그인 없음·204 빈 본문.
- ACTIVE·WITHDRAWAL_PENDING 회원 대상. 재설정은 탈퇴를 취소하지 않는다. users와 refresh_tokens를 함께 다룰 때 users 먼저 잠근다.
- 207 보완: DB collation으로 같은 회원을 찾았더라도 재설정 메일은 입력 주소가 아닌 DB에 저장된 주소로 보낸다. 확인 코드/토큰도 이 이메일에 묶는다.
- 완료 조건: 단위·실제 HTTP·MySQL DB(토큰 재사용·동시 소비·폐기·대기 상태 유지·주소 변형) 검사, clean build·databaseTest 통과, 자체 점검·작업 단위 커밋. 정식 리뷰는 별도다.

## 독립 선행 보완

- 재설정 메일 주소·코드 HMAC·인증 행을 DB의 등록 이메일에 묶는다. `users.email` collation이 같은 변형을 기존 회원으로 판정해도 입력 변형 주소로 발송하지 않는다. 회원이 없는 요청은 기존처럼 입력값 기반 가상 행과 같은 202 정책을 유지한다.
- 단위 검사: `mémber@example.com`을 DB가 `member@example.com` 회원으로 찾는 대역에서 수신 주소/인증 행을 확인했다. 기존 코드에서 입력 주소로 발송해 실패한 뒤 수정 후 집중 15개 통과.
- ACCOUNT_MERGE 발송의 동일 문제는 211에서 새 등록 주소 조회를 재사용해 적용해야 한다. 이번 선행 변경은 PASSWORD_RESET만 대상이다.
- 재설정 소비 구현 시에는 사전 토큰 조회로 회원을 식별하되 잠금은 users → 인증 행 → refresh_tokens 순서로 잡아, 209의 users → 인증 행 삭제와 순서가 뒤집히지 않게 한다. 오래된 입력 변형 주소로 발급된 토큰은 DB 저장 이메일과 정확히 일치하는지도 확인해야 한다.

## 선행 보완 검증·인계

- JDK 21, 격리 MySQL 8.4에서 `clean build databaseTest`: 기본 검사 289개·DB 검사 73개 실패 0. 실제 HTTP 이메일 요청/확인과 MySQL accent-insensitive 조회를 거쳤고, 메일 전송 경계는 수신 주소를 수집하는 대역이다.
- DB 테스트 민감도: 무시되는 `backend/build` 복사본에서 발송 주소만 입력값으로 되돌렸을 때 집중 검사 1개가 수신 주소 불일치로 실패했다. 원본 코드는 변경하지 않았다.
- 자체 점검: 기준 `f891dfa`, 선행 메일 보완과 계획/목록 9개 파일. `git diff --check` 통과. 동작은 합의한 DB 저장 이메일 발송과 일치하며 추가 정책 변경은 없다. 정식 리뷰는 대기 중이다.
- 비밀번호 재설정 API 본체는 아직 구현 전이다. 잠금 관계·무효 토큰 응답·동일 비밀번호 처리의 사용자 답변을 받은 뒤 이어간다. Jira는 진행 중/스프린트 59139를 유지하며 Push/MR은 하지 않는다.
