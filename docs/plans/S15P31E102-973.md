# 하단 시트·키보드·상태 표시줄 여백 처리 정리 (973)

- Jira: S15P31E102-973 `[FE] 하단 시트·키보드·상태 표시줄 여백 처리 정리`, Story S15P31E102-109, 활성 스프린트 5, 진행 중(시작 절차는 961 세션이 처리).
- 범위: [961 점검 목록](S15P31E102-961.md)의 F1~F6과 A9를 사용자가 고른 after대로 고친다. 다른 그룹(A~E, 968~972)이 같은 파일을 만질 수 있어 담당 줄 밖은 고치지 않는다.
- 의심 항목(F1·F2·F4·F5)은 먼저 문제가 실제로 있는지 확인한다.

## 확인 방법과 한계

- 이 Mac에는 Xcode가 없어(`xcode-select -p` = CommandLineTools) iOS 시뮬레이터를 쓸 수 없다.
- 남아 있는 Android 가상 기기(`/private/tmp/eolssu-*`)는 설정 파일이 없는 잔여물이고, 연습·홈·결과 화면은 로그인이 필요해 새 가상 기기에서도 들어갈 수 없다.
- 웹은 시스템 여백(inset)이 0이라 이 문제들이 나타나지 않는다.
- 그래서 실제 화면 대신 라이브러리 바이트코드·klib과 앱 코드로 확인했다. 아래 `확인`은 코드상 반드시 생기는 것이며 기기에서 본 결과가 아니다.

## 항목별 확인 결과와 처리

| F2 | 확인. 연습 설정 시트는 `Dialog` 안에서 바깥 상자 전체에 `safeDrawing` 여백을 준다. 게다가 iOS·웹 `DialogProperties.usePlatformInsets` 기본값(true)은 창 내용을 안전 영역 안으로 줄이고(ui klib 문서), Android `decorFitsSystemWindows` 기본값(true)은 대화 창을 시스템 바 밖에 둔다(javap). 시트가 홈 막대·내비게이션 바 높이만큼 떠 있다. | 플랫폼별 `practiceSheetDialogProperties()`(expect/actual)로 창을 화면 끝까지 그리게 하고, 바깥 상자는 위·양옆 여백만 받는다. 하단 여백은 시트 안쪽 아래에 `safeDrawing` 하단 + `sheetBottomPadding(24.dp)`로 넣어 시트 바탕이 바닥까지 닿는다. |

CMP iOS 기본 `OnFocusBehavior.FocusableAboveKeyboard`는 입력칸이 키보드에 가리면 화면 전체를 끌어올리는데, 앱 화면 틀(`EolssuScaffold`)은 `imePadding`으로 이미 비킨다. | `ComposeUIViewController(configure = { onFocusBehavior = OnFocusBehavior.DoNothing })`. 입력칸이 있는 화면은 모두 `imePadding` 화면 틀(`EolssuScaffold`·`AuthScaffold`·`ProfileScaffold`·이번에 고친 `SongTabletScaffold`), 시스템 여백을 넣는 `ModalBottomSheet`, 키보드 여백을 기본 처리하는 `Dialog` 안에 있다. |
