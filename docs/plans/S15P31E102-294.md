## 검증과 보존

기존 완료 백업 `.cms`·`.json`의 존재·크기·mtime이 삭제 전과 모두 같았다. 복호화 키·Jenkins 별도 키·점검 SSH 키/호스트키·relay 비밀 설정·백업 실행 코드의 내용 해시와 소유/권한도 같았다. 비밀값이나 해시 자체를 채팅·저장소에 복사하지 않고 서버 root 내부에서 비교했다. 비교용 메타데이터는 새 root 전용 `/var/backups/edo2-cleanup-294/before.json`에 있다. 기존 `/var/backups/edo2-migration-287`, `/var/backups/edo2-repair-293` 등 복구 사본은 변경하지 않았다.

nginx·edo-check·Docker·SSH의 MainPID가 코드 반영 전후 같고 active였다. 인증서 갱신과 backup status/prune/restore-test timer도 active였다. 서비스 정지·reload·restart 없이 예외 설정을 제거하고 새 SSH 수집마다 읽는 collector 코드를 반영했다. relay 디스크 소스도 예외 없는 버전으로 맞췄다. 이미 실행 중인 relay 프로세스의 메모리 코드는 재시작하지 않았으며, 기존 렌더러와 예외 필드가 사라진 새 collector의 실제 연결도 별도로 검증했다. 기존 프로세스에 남은 분기는 새 collector가 해당 필드를 만들지 않아 사용되지 않는다. 다음 정상 기동부터 디스크의 예외 없는 relay 전체가 로드된다.

서버의 기존 원본 두 파일이 저장소의 293 예외 추가 전 소스와 SHA-256까지 같은지 확인한 뒤 서버 내부에서 후보를 만들었다. 해당 소스로 **Linux 기존 회귀 51개 통과**, 로컬의 새 회귀 2개(동일 Android 이름·종료 143·과거 expected_stop 필드가 있어도 장애 판정 유지)도 통과했다. 폐기한 예외 기능용 4개 검사는 새 정책을 검증하는 위 2개로 대체했다. 실제 edo-check 계정의 전용 loopback SSH·sudo dispatch·HTTPS·기존 렌더러 보고서 경로에서 server/health 정상, containers `컨테이너 없음`을 확인했다. 세 결과에 `실험 중지`가 없고 장애 0이었다. 실제 Mattermost callback은 전송하지 않았다.

최초 삭제 전 참조 검사는 Docker 짧은 ID와 전체 ID 비교 때문에 중단됐으며 그 시점에는 삭제하지 않았다. 전체 inspect ID 비교로 고친 후 대상 한정 삭제를 수행했다. 코드·테스트 7개 파일의 신규 전송은 자동 승인 검토가 294 전송에 대한 명시적 승인 부재로 거부했다. 이를 다른 전송 방식으로 우회하지 않고, 이미 서버에 보관돼 있던 동일 원본을 검증해 사용했다. 실제 네트워크 파일 전송은 없었다.
