# S15P31E102-763 평가 제출부터 점수 표시까지 단계별 시간 계측

- Jira 스프린트 5 진행 중. Story S15P31E102-326, 에픽 S15P31E102-20. 기준 `origin/develop` `866d9064`.
- QA706의 `evaluation-timing`에 기록된 !564 정상 두 회차의 제출~총점 첫 그리기는 7.909초와 9.174초다. 한 회차에서 제출 후 첫 조회까지 2,987ms, 조회 5회로 완료 확인까지 4,278ms를 관측했다. 후속 빌드는 별도의 소스·실행 증거로 기록한다.

## 구현·검증 계획

1. 기존 Android QA 성능 방문에 세션 생성과 녹음 전송, 재시도 요청의 경과 시간·결과를 추가한다. 실제 첫 상태 요청과 첫 완료 확인을 기록하고 기존 총점 첫 그리기 이벤트까지 흐름 번호로 연결한다.
2. 녹음 업로드와 분석 재시도의 선택 헤더로 무작위 진단 ID를 보낸다. 최초 업로드 및 분석 재시도가 실제로 새 시도를 큐에 넣을 때만 이 ID를 전달한다. 서버는 단조 시계로 작업 대기와 처리 시간을 측정한다. 원본 세션 ID, 사용자 정보, 녹음 및 접근 자격 증명은 새 진단 이벤트에 넣지 않는다.
3. 합성 응답으로 정상·녹음 재전송·서버 재시도, 중복 상태 조회, 화면 복귀, 허용 필드와 단조 시간을 검증한다. 같은 QA 기기에서 서버·앱·수집기의 대응 버전을 확인할 수 있으면 정상과 재시도를 수집한다.
4. 앱 내부 경과 시간과 서버 내부 경과 시간을 비교한다. 상태 조회 조정은 동일 QA 환경에서 서버 완료와 앱 완료 확인의 관계가 확인된 뒤 판단한다.

## 단계와 식별자

| 위치 | 항목 | 측정 구간 |
| --- | --- | --- |
| 앱 | `session_create` | 세션 생성 호출 시작부터 호출 결과까지 |
| 앱 | `recording_upload` | 앱의 녹음 보관·전송 호출 시작부터 결과까지. 내부 HTTP 재전송과 대기 포함 |
| 앱 | `analysis_retry` | 분석 재시도 요청 시작부터 응답 해석까지 |
| 앱 | `first_status_request`, `analysis_ready` | 방문의 첫 상태 조회 호출 직전과 첫 `DONE` 해석 직후. 백그라운드 복귀·재시도에서도 각 한 번 |
| 앱 | `score_drawn` | 전체·구간 평가 결과에서 총점이 처음 그려진 시점. 분석 방문과 같은 `flow` |
| 서버 | `evaluation_analysis_timing` | 실행기 제출 직전~워커 진입의 `queue_ms`, 워커 진입~결과 저장 반환의 `processing_ms`. 워커의 상태 조회·악보 준비·AI 호출·저장을 포함 |

- 앱 제출~첫 그리기는 같은 `run_id`·`flow`의 제출 `action`과 `score_drawn`에서 `ms` 차이로 계산한다. 앱의 `ms`는 프로세스의 단조 시계 기준이다. 서버 지연도 동일 서버 프로세스 안의 단조 시계로 잰다. 서버 로그 UTC와 앱 `ms`를 빼거나, 업로드 응답과 겹칠 수 있는 서버 구간을 앱 총 시간에 더하지 않는다.
- PRA-02 `POST /practice-sessions/{sessionId}/recording`과 PRA-03 `POST /practice-sessions/{sessionId}/retry`의 선택 요청 헤더는 `X-Evaluation-Timing-Id`다. 소문자 UUID v4 문자열 36자다. Android QA에서 무작위로 만들며 누락·형식 불일치 시 계측 ID를 무시한다.
- 앱의 `evaluation_timing_id`와 서버의 `id`를 맞춘다. 같은 화면에서 녹음을 다시 보내면 업로드 ID를 재사용하고, 분석 재시도 요청에는 새 ID를 만든다. 중복 업로드나 이미 분석 중인 재시도는 새 작업을 만들지 않는다. 앱을 재시작하면 이전 업로드 ID가 복구되지 않을 수 있다. `NOT_ENQUEUED`·`STALE`은 소요 시간 집계에서 제외한다.
- 새 계측의 값은 무작위 ID·앱 내 흐름 번호·시도 번호·고정 상태·시간이다. 회원·기기·원본 세션·평가 ID, 녹음·파일 경로, 서명 URL·쿠키·멱등키는 새 이벤트에 기록하지 않는다.
- EDO2의 새 허용 목록을 앱 계측 로그 수집 전에 반영해야 한다. 기존 수집기는 새 단계가 포함된 배치를 거부한다. 검증 대상은 새 계측이 들어간 Android QA APK·백엔드·EDO2 수집기의 조합이다.

## 비교와 남은 실기기 확인

!564의 Galaxy S10 USB 계측은 APK `qa-20261110.235951-0177277d`에서 얻었다. 보고서의 후속 !592 설치본 `7ce401bd`와 이번 기준 `866d9064`를 별도 버전으로 본다. `866d9064`에서 이미 있던 제출 동작·상태 조회 요약·총점 첫 그리기 경로는 소스에서 확인했다. 이번 변경의 실기기 전후 시간 및 기기·서버 UTC 편차는 아직 측정하지 않았다.

동일 QA 폰에서 APK와 백엔드 커밋을 확인하고 같은 곡·판본과 연결 조건으로 정상 제출 및 녹음 재전송을 실행한다. 분석 실패·재시도는 격리 QA에서 합성 응답으로 재현한다. 진단 ID로 서버의 새 시도 수와 단계별 경과를 연결하고 앱의 첫 상태 조회·완료·총점 표시를 대조한다. 상태 조회는 처음 8초 동안 1초, 이후 2초로 유지한다. 조회 간격 조정은 정상·재시도에서 완료 감지 지연과 조회 수를 비교한 뒤 결정한다.

Notion PRA-02·PRA-03 명세, API 상위 문서, 테스트 문서는 연결된 계정에서 404를 반환했다. 선택 헤더의 미병합 구현 계약은 위 표와 설명에 기록했다.

Chrome 전용 탭 생성은 `Browser is not available: chrome`을 반환했다. Windows 창 조회도 `Computer Use helper already has an active request` 상태가 재연결 뒤까지 이어졌다. [PRA-02](https://www.notion.so/401a0252aa4581c1acdfd43c26760883)·[PRA-03](https://www.notion.so/401a0252aa458182aff0e8ea5e805311)의 Chrome 페이지 본문은 확인 대기 중이다. Chrome 연결이 사용 가능해지면 편집 권한이 있는 Notion 세션으로 열어 요청 헤더 표·예시를 수정하고 다시 확인한다.

- 백엔드 `gradlew.bat test`의 업로드·분석 실행기·분석·재시도 컨트롤러·설정 대상 7개 클래스 72건을 통과했다. MockMvc에서 유효 UUID만 업로드 데이터에 전달되고 잘못된 헤더를 붙인 중복 업로드는 409임을 확인했다. 합성 분석 중 서버 벽시계를 3초 뒤로 옮겨도 작업 대기 60ms, 처리 240ms, 종료 이벤트 1건이 기록됐다. 전체 `test`에서는 `BackendApplicationTests`의 Prometheus 스크레이프 HTTP 시간 초과가 관측됐고 실행을 종료했다.
