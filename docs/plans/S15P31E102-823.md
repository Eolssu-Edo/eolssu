## 배포 후 검증 결론

2026-11-13에 MR !669가 포함된 운영 웹 배포와 같은 계정의 최근 연주 카드 표시를 확인했다. 배포 전후 보관본의 교차 측정에서는 클릭 후 기록 요청이 5건에서 0건으로 줄었고, 점수 표시 중앙값은 780.8ms에서 332.0ms로 낮아졌다. 실제 운영 주소의 배포 후 점수 표시 중앙값은 435.6ms였으며, 경로 전환과 기록 응답 준비 뒤에도 432.0ms가 남았다. 첫 운영 순차 측정의 66.2ms 증가는 교차 측정에서 재현되지 않았지만, 당시 구간별 기록이 없어 그 원인을 확정하지 않았다.

이 문서의 운영 수치는 해당 두 배포 버전 전체를 비교한 결과다. MR !669만의 기여도, 모든 계정·기기에서의 속도, 실제 픽셀 표시 시점까지 증명하지는 않는다.

## 구현 순서

1. 같은 기록 응답으로 기존 마이페이지 경로의 요청 수를 재현하고, 새 경로는 한 번만 요청하도록 검사한다.
2. 첫 개선으로 카드에서 REC-02 최신 연주 한 건과 서버 주간 횟수를 사용한다. 주간 요약을 제공하지 않는 응답에는 전체 기록 조회를 적용한다.
3. 사용자 요청에 따라 REC-05에서 최신 연주 한 건과 주간 집계만 조회하고, 앱에서 우선 사용한다. 로그인한 홈에서 백그라운드로 시작하고 마이페이지에서 진행 중인 조회 또는 성공 후 30초 이내 요약을 재사용한다. 기록 저장·삭제 및 계정 전환 시 캐시를 지운다.
4. 같은 MySQL 데이터에서 기존 전체 조회, REC-02 단건, REC-05를 교차 측정한다. 카드 값과 요청 수, 홈 선조회 뒤 마이페이지의 추가 요청 여부, 연습 기록 목록·상세·비교의 회귀를 확인한다. 앱 변경을 되돌리면 이전 마이페이지 경로로 복구할 수 있다.

## 완료 조건

- REC-05를 지원하는 서버에서는 응답 한 건으로 카드 데이터가 준비된다. 홈 선조회가 성공하면 같은 로그인·같은 주의 30초 안에는 마이페이지에서 REC-05 요청을 추가하지 않는다. 최신 연주는 연주 시작 시각으로 고르고, 이번 주 횟수는 KST 월요일부터 일요일까지의 삭제되지 않은 저장 기록을 센다.
- 홈 선조회가 잠금 대기를 포함해 300ms 안에 끝나지 않으면 취소한다. 홈·마이페이지 외 화면으로 이동하거나 로그아웃을 확인하면 즉시 취소한다. 홈 선조회에서 받은 401은 토큰 갱신을 시작하지 않는다.
- 빈 결과와 요청 실패를 구별하고, 갱신 중과 실패 시 같은 로그인·같은 주의 마지막 요약을 유지한다. 이전 로그인이나 저장·삭제 전에 시작된 조회가 캐시를 복구하지 않는다.
- 고정 응답으로 요청 파라미터와 횟수, 구 서버, 빈 결과, 실패, 계정 격리, 기록 변경을 검사한다. Android 호스트 테스트를 실행하고 운영 응답 시간과 실제 기기에서 확인할 범위를 기록한다.

## 카드 데이터 준비 시간

Windows에서 같은 Spring 서버의 루프백 HTTP/1.1 연결과 격리 MySQL 8.4.13을 사용했다. 시드곡 1·2의 저장 기록을 고정하고 `weekOf=2026-11-01`로 조회했다. 각 계정에 해당 KST 주 기록은 4건이며 나머지는 지난 주에 있다. 2곡 계정에서 한 곡의 101건은 더 늦게 저장했고, 다른 곡의 1건은 더 늦게 연주했다.

첫 HTTP 요청 직전부터 마지막 응답의 JSON으로 카드 값을 만들 때까지 잰 값이다. 세 경로의 실행 순서 여섯 가지를 순환해 데이터별 12회 예열, 60회씩 측정했다. 전 실행의 요청 수와 최신 연주의 식별자·곡·시각·범위·점수 및 주간 횟수가 맞았고 HTTP 오류는 없었다. 본문 크기는 압축 전 합계다.

## 홈 선조회 300ms 제한과 취소

- 홈 선조회도 로그인 쿠키를 쓰므로 프로필 조회와 로그아웃이 사용하는 인증 잠금을 잡는다. 로컬 REC-05의 p95는 고정 데이터 두 가지에서 23.5~29.2ms였다. 빠른 응답을 받을 여유를 두면서 선조회의 대기를 제한하려고 사용자와 300ms를 초기 상한으로 정했다. 300ms를 정할 당시에는 운영 RTT가 미측정이었다. 아래 운영 재측정은 단일 계정의 성공 응답 범위를 보완하며, 이 값만으로 상한을 다시 결정하지 않았다.
- 수정 전 가상 시계에서 인증 잠금 대기 200ms 뒤 시작한 선조회가 300ms에도 프로필 조회를 막았다. 수정 뒤 같은 조건에서 선조회가 300ms에 취소되고 프로필 조회가 성공했다.
- 수정 전 선조회 401은 REC-05 뒤에 토큰 갱신과 REC-05 재요청을 일으켰다. 수정 뒤 선조회 401은 GET 한 건으로 종료됐다. 뒤이은 프로필 조회가 성공했고 마이페이지 정식 조회에서 401을 받았을 때 토큰을 갱신해 한 번 재시도했다.
- 홈에서 마이페이지로 이동하는 동안 진행 중인 요청 한 건을 공유했다. 같은 로그인·같은 주의 성공 응답은 29초 뒤에도 추가 요청 0건으로 재사용했고 30초에 갱신했다. 다른 화면으로 이동하거나 로그아웃을 확인하면 가상 시계가 진행하기 전에 취소됐다. 로그아웃에서는 대기 중이던 마이페이지 조회가 새 GET을 시작하지 않았고 로그아웃 요청이 처리됐다.
- 최종 코드에서 `:shared:testAndroidHostTest` 1,543건 통과·기존 선택 실행 4건 건너뜀·실패 0건, `:androidApp:assembleDebug`와 웹 공통 코드의 `:shared:compileKotlinJs`·`:shared:compileKotlinWasmJs` 통과. 위 동작은 가상 시계와 HTTP 대역으로 확인했다. 이 자동 검사에는 iOS·실기기와 운영 네트워크가 포함되지 않는다. 후속 운영 웹·Android 확인은 아래에 구분해 기록했다.

## 운영 웹 구간별 재측정

- 2026-11-13에 Windows Chrome 157, 1280×900, 같은 운영 테스트 계정·최신 연주 기록으로 재측정했다. 운영에 보존된 `2857c0d9`와 `75ca986e`의 정적 파일을 같은 Chrome에 로컬에서 공급하고, 두 빌드의 HTTP API 요청은 실제 운영 백엔드로 보냈다. 같은 운영 주소에서 배포 후 빌드도 별도로 확인했다. 마이페이지 버튼이 보인 뒤 750ms를 두고 클릭했다. 각 빌드를 한 번 예열한 뒤 보관본 전후 12쌍, 배포 후 보관본과 실제 운영 8쌍을 실행 순서를 번갈아 측정했다. 모든 쌍이 완료됐고 양쪽이 같은 최신 기록의 점수를 표시했다.

- 배포 전 보관본은 클릭 후 REC-02를 매회 5건 호출했다. 첫 요청까지 141.7ms, 첫 요청부터 마지막 응답까지 487.7ms였다. 해당 구간은 각 요청 시간과 요청 사이의 앱 대기를 포함한다. 배포 후 보관본은 12회 모두 클릭 약 2.3초 전에 선조회가 완료됐다. 실제 운영에서도 8회 모두 선조회가 완료된 상태에서 들어갔다. 브라우저에서 관측한 운영 REC-05 요청 시간은 37.5ms(34.1~56.3ms)였다.
- 보관본 12쌍에서 배포 후가 모두 빨랐다. 같은 쌍의 차이 중앙값은 −411.9ms, 쌍을 복원 추출한 95% 구간은 −481.4~−371.1ms였다. 이전 운영 순차 측정의 +66.2ms는 교차 측정에서 재현되지 않았다. 배포 후 동일 SHA의 보관본과 운영 주소를 비교한 쌍별 차이는 −106.2~+153.1ms였고, 운영 주소만의 표시 시간 범위는 347.5~531.1ms였다. 이전 표본의 정확한 원인은 당시 단계별 기록이 없어 소급해서 확정할 수 없다.
- 운영 재측정에서 최근 연주 응답은 클릭 전에 끝났고 마이페이지 주소는 클릭 뒤 2.4ms에 바뀌었다. 이후 점수 표시까지 432.0ms가 걸렸다. 클릭부터 표시까지 관측한 메인 스레드 긴 작업 시간의 중앙값은 143ms였고, 그 구간에 폰트 HTTP 응답은 관측되지 않았다. 별도 4쌍에서 마이페이지 클릭 직전부터 Chrome 렌더러 CPU를 2배 느리게 설정하면 모든 쌍에서 점수 표시가 늦었다. 두 조건 모두 선조회에 성공한 두 쌍에서도 같은 방향이었다. 남은 지연은 마이페이지 화면을 표시하는 브라우저 구간에 있으며, 이 운영 측정에서는 함수별 프로파일을 수집하지 않았다.
- 비교는 운영 배포 버전 전체와 단일 Chrome·계정에 한정한다. 보관본 비교는 정적 파일 전송 시간을 포함하지 않으며, 운영 주소 검사는 이미 배포된 새 버전만 사용했다. 운영 설정·제품 코드는 변경하지 않았다.
