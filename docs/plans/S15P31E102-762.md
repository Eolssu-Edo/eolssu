## 작업 범위와 결정

- [x] 제공곡 상세에서 연주 평가에 진입할 때 같은 로그인에서 확인한 게시 판본을 재사용한다. 곡 ID가 맞는 최근 묶음 하나를 메모리에 두고, 미적중 시 서버에서 상세와 악보를 조회한다.
- [x] 평가 결과와 취약 구간에서 서버가 응답한 곡 ID와 판본이 묶음과 일치하면 재사용한다. 취약 구간 저장소는 평가 상세가 매핑한 악보를 함께 받는다. 평가·추천·비교 데이터는 요청마다 현재 회원의 권한으로 조회한다.
- [x] 로그아웃·회원 전환·동일 회원 재로그인 시 묶음을 지운다. 상세와 악보의 교차 검증까지 성공한 응답을 보관하고, 실패하거나 취소된 최신 판본 조회 뒤에는 기존 묶음을 게시 판본으로 재사용하지 않는다.
- [x] 새 녹음 시작과 분석 제출 전에는 현재 판본을 서버에서 다시 확인한다. PRA-01은 녹음의 `expectedScoreVersion`과 부모 세션 판본을 확인한다. [녹음 판본 계약](../specs/recorded-score-version.md)
- [ ] 수정 빌드에서 실기기 첫 표시와 GET 수를 같은 조건으로 다시 잰다.

2026-11-11 Windows에서 최종 Kotlin/JS 소스와 테스트를 컴파일했다. 같은 테스트 모듈의 대상 38개가 Chrome Headless 156과 Node/Mocha에서 각각 통과했다. 곡 ID `42`, 평가 세션 `50`·`51`, 판본 1·2, 회원 A·B를 사용했다.

- `HistoricalEvaluationTest`에서 게시 판본 변경, 로그아웃과 같은 회원 재로그인, 악보 요청 취소·503 뒤 새 조회 성공을 확인했다.

- Node 재현은 `frontend`에서 링크 및 npm 준비 후 `build/js/packages/eolssu-shared-test`에서 `node ../../node_modules/mocha/bin/mocha.js --grep 'ApiWeakSectionRepositoryTest|HistoricalEvaluationTest|PracticeDirectEvaluationTest|HttpPracticeSessionTest' --reporter dot kotlin/eolssu-shared-test.js`를 실행한다. 링크에는 `:shared:jsTestTestDevelopmentExecutableCompileSync`, npm 준비에는 `:kotlinNpmInstall`을 사용한다.

- 단소 아리랑의 새 평가 결과에서 취약 구간 선택과 반복을 한 번씩 열었다. 선택 화면은 평가·추천 조회와 게시 판본 확인 때문에 곡 상세·악보 GET을 각각 1회 보냈다. 반복 화면에서는 평가 GET 1회와 곡 묶음 재사용을 관측했다. 두 방문의 진입 → 마지막 GET 완료는 430ms와 22ms였다.

## P2 후속 수정과 검증

- 공개 곡 상세와 악보 요청은 서로 독립적으로 실행한다. 로그인 세대는 응답을 사용할 때 검사하고, 늦게 끝난 이전 조회가 더 최근 조회의 재사용 데이터를 덮어쓰지 못하게 한다.
- 취약 구간은 기록 판본의 악보를 표시한다. 현재 게시 판본은 판본 파라미터 없는 곡 상세 GET으로 확인한다. 캐시 미적중에서 정본 악보 GET은 기록 판본으로 한 번 발생한다.
- 2026-11-11 Windows에서 `frontend`의 `.\gradlew.bat :shared:testAndroidHostTest -Pkotlin.compiler.execution.strategy=in-process --offline --no-build-cache --max-workers=1`를 실행했다. 1,415개 중 1,411개 통과, 별도 조건이 있는 4개 건너뜀, 실패·오류 0개였다.
- `HistoricalEvaluationTest › aSlowScoreDoesNotDelayOrReplaceTheNextSong`에서 곡 42의 악보 응답을 보류하는 동안 곡 43 조회가 완료됐고, 곡 42 응답을 푼 뒤에도 곡 43이 재사용 대상으로 남았다.
- `ApiWeakSectionRepositoryTest › coldSelectionChecksPublicationWithoutDownloadingAnotherScore`에서 캐시가 빈 상태로 기록 판본 1을 열었다. 게시 판본이 1과 2인 두 경우 모두 기록 판본 곡 상세 GET 1회, 기록 판본 악보 GET 1회, 현재 게시 판본 곡 상세 GET 1회였다. 게시 판본이 2일 때 불일치로 판정했다. 수정 전 동일 흐름은 현재 게시 판본 악보도 GET해 악보 GET이 2회였다.
- 새 녹음 판본 검증은 수정본의 `PracticeDirectEvaluationTest`·`SectionLoopRecordingTest`·`HttpPracticeSessionTest`·`RecordingRevisionTest`·`AnalysisSessionTest`에서 다시 실행했다. 시작 전 판본 변경 차단, 녹음 판본의 `expectedScoreVersion` 전송, 오래된 녹음 및 세션 생성 거절 뒤 업로드 차단을 확인했다. 백엔드 세션 생성의 판본 일치·불일치·삽입 경합은 위의 기존 15개 통과 결과를 재사용했다.
- 화면 검증은 Android 12(API 31, x86_64) 전용 AVD, 1,920×1,200·200dpi, APK `qa-762-p2`, 루프백의 단소 아리랑(29)과 검증곡(30)으로 제한했다. APK 설치와 Activity 실행 요청까지 확인했다. System UI 응답 없음과 재실행 시간 초과로 곡 목록에 도달하지 못해 B곡 첫 표시 순서는 미확인이다. 취약 구간의 GET 수와 새 녹음 판본 판정은 위 자동 테스트로 확인했다.
