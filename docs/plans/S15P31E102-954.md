## 목적과 범위

이 작업은 **비동기 작업의 동시성·큐 처리·자원 부하·장애 복구 검증**이다. 요청 응답이나 DB 행 생성에 그치지 않고, 실제 인식·합성 프로세스와 파일 전달이 끝나고 다음 작업을 처리할 수 있는지 확인한다. 최대 수용 인원 산정이나 장시간 스트레스 테스트는 별도 목표다.

우선순위는 데이터 손실·다른 계정/판본 혼입·핵심 흐름 불능, 큐 정체·중복 실행·자원 미반환, 오류 복구와 화면 상태 순이다. 기대 동작은 확정 명세에서 정한다. 미정 지연 목표나 처리량을 새 통과 기준으로 만들지 않는다. 원인 가설은 재현된 결함과 분리한다.

## 환경과 입력 준비 — Q0

실행 시작 때 다음 조건을 고정하고, 빠진 조건은 해당 검사의 실행 불가 사유로 남긴다. 계획 기준 develop을 배포 버전으로 간주하지 않는다.

1. 현재 배포 Android APK의 버전·빌드·SHA-256과 서버/OMR/playback 이미지 digest·소스·설정·명세를 대응시킨다. 배포본 검사와 수정 후보 검사를 별도 실행 ID로 기록한다.
2. 기본 환경은 폐기 DB·전용 임시 저장소·시험 계정 4개를 가진 격리 환경이다. 운영과 같은 설정의 복제본을 사용하되 실제 CPU·메모리·swap·tmpfs·디스크·worker 수·대기열 한도·timeout·정리 주기를 기록한다. 운영 DB·버킷·메일로 연결되지 않음을 확인한다.
3. 실행 담당은 박찬형이다. 무거운 실제 OMR/CAT 검사는 필요한 엔진·CAT 자산·전용 저장 공간·자원 관찰 수단이 준비된 격리 호스트에서 순차 실행한다. 에뮬레이터와 빌드 등 다른 작업이 부하를 섞지 않게 한다. 환경이 부족하면 대역 검사만 따로 기록한다.
4. 악보 자료는 `C:\Users\kingc\Downloads\악보 추가 편집 테스트 자료`를 사용한다. 원본·사본·압축본·변환 산출물은 Git에 넣지 않는다. 입력 식별용 이름·해시·크기·실제 쪽 수·선택 이유만 기록한다. 파일명으로 쪽 수나 처리 가능성을 단정하지 않는다.
5. 오선보와 정간보에서 작은 정상 입력 각 1개를 먼저 선정한다. 글자층·스캔은 실제 파일 형식을 확인해 구분한다. 반복·구간 빠르기·장단이 있는 입력, 긴/복잡한 입력은 작은 입력의 결과가 확보된 뒤 추가한다. 손상·빈 파일·형식 불일치 등은 원본을 바꾸지 않는 외부 임시 자료로 만든다.
6. 초기 동시성은 **1 → 2 → 4개 요청**이다. 대기와 실행을 구분하며, 회원당 제한을 검사할 때 외에는 서로 다른 계정을 쓴다. 4건은 진단 시작 범위일 뿐 서비스 수용 인원이나 SLO가 아니다. 작업 접수·종료·정리까지를 한 회차로 하며 늘리기 전에 결과를 확인한다.

## 동시성·큐 판정 상세

- **접수 추적:** 실행 ID·클라이언트 요청 ID·멱등 키·회원·악보 ID·변환/생성 시도·확정 버전·입력 해시를 연결한다. API 응답이 유실된 경우도 같은 키로 조회/재전송해 접수 여부를 확인한다. 모호한 결과를 새 키로 다시 요청해 숨기지 않는다.
- **작업 수 대조:** 재사용·거절 요청과 새 작업 접수를 분리한다. 같은 관찰 시점에서 접수된 고유 작업 수가 대기·실행·종료 작업으로 모두 설명돼야 한다. 삭제는 삭제 직전 상태와 정리 기록으로 설명한다. 요청 수와 작업 수가 같아야 한다고 가정하지 않는다.
- **실행 제한:** 명세가 정한 회원당 활성 1건, 음원 생성 전역 1건, OMR 선점/슬롯 정책을 실제 실행 시작·종료 기록으로 확인한다. 음원 생성과 길이 계산이 서로 다른 자원을 공유하는 경우 둘의 중첩도 별도 측정한다. 배포 슬롯별 소유권과 전체 엔진 제한을 혼동하지 않는다.
- **공정성:** 접수 순 선점이 계약인 큐에서만 FIFO를 요구한다. 첫 작업의 실패/시간 초과 뒤 다음 작업이 진행하는지 확인한다. 단순히 최종 DONE 개수만 세지 않는다.
- **편집 경합:** 같은 baseScoreVersion의 동시 확정 저장, 초안 revision 충돌, 길이 계산 도중 판본 변경, 생성 중 저장·삭제, 이전 작업의 늦은 완료를 검사한다. 조용한 덮어쓰기와 다른 판본 음원 저장이 없어야 한다.
- **상한 경계:** 잘못된/빈 입력, 파일 크기·쪽 수·음원 길이·파일 크기·회원 요청 제한의 경계와 거절 후 정상 요청을 확인한다. 큐 깊이 상한이 확정된 경우 최소 입력/대역으로 경계를 검사한다. 상한이 없는 큐에 임의의 거절 동작을 요구하거나 4건만으로 포화 검증을 주장하지 않는다.
- **권한:** 비로그인, 다른 회원의 악보·작업 ID, 로그아웃/계정 전환 중 늦은 응답을 검사한다. 기존 인증·소유권 계약을 유지하며 보안 정책을 바꾸지 않는다.

## 복구·파일·Android 판정 상세

- OMR 원본은 성공·실패·삭제 때 정리되고 최대 수명은 30분이다. 재시작한 backend가 이전 QUEUED/RUNNING을 실패 처리하고 재업로드를 요구하는 현재 정책을 따른다. 기존 원본을 자동 재시도해야 한다고 판정하지 않는다. 긴 수명 경계는 격리된 시계 검사와 실제 정리 경로 검사를 구분한다.
- 음원 생성 timeout, 생성기 BUSY, backend 재시작은 각각 현재 계약의 재대기/실패/정리 조건으로 판정한다. 음원 생성 90초·수신 100초, 길이 계산 대기 5초·실행 10초·수신 15초 등 확정 제한은 Q0에서 대상 버전 설정과 대조한다. 누락된 복구 기한은 임의로 정하지 않는다.
- 유효한 이전 M4A는 새 생성·저장 실패 시 정책대로 보존한다. 10분 다운로드 기한은 폴링으로 연장되지 않으며 만료 후 새 생성과 이미 저장한 기기 파일 재생을 구분한다. 서버 시계를 바꾸지 않고 고정 시계 검사와 실제 시간 경과 검사를 분리한다.
- 부분 응답·잘못된 해시·잘린 M4A·네트워크 취소·저장 공간 부족을 다룬다. 다운로드/임시 파일이 정상 저장본으로 노출되지 않고 재시도 시 복구되는지 확인한다. 공간 부족은 전용 제한 볼륨 또는 폐기 에뮬레이터에서 만들며 개인 기기 디스크를 채우지 않는다.
- 화면 이동, 백그라운드/복귀, 앱 종료/재시작, 완료 직전 로그아웃을 검사한다. 성공 알림 중복·잘못된 악보 열기·이전 계정 파일 노출이 없어야 한다. 앱 종료 중 OS 알림처럼 명세 밖의 기능은 요구하지 않는다.
- actual OMR/CAT 자식 프로세스와 ffmpeg/Audiveris 등 하위 프로세스의 종료를 확인한다. 장애 응답을 받은 뒤에도 PID·파일·슬롯이 남아 다음 작업을 막으면 복구 성공이 아니다.

## 관찰·중단·정리

각 실행은 접수, 선점, 엔진 시작/종료, 파일 공개, 다운로드 완료, 기기 재생 시각을 남긴다. 큐 대기 시간·실처리 시간·전체 시간·정상/예상 거절/실패 수를 분리하고 표본 수를 함께 쓴다. 적은 표본의 p95나 최고 동시 요청 수를 운영 용량으로 일반화하지 않는다.

CPU, RSS/컨테이너 메모리 peak·OOM, tmpfs/디스크 사용량, 열린 파일·연결, 자식 프로세스, 큐 깊이·가장 오래된 작업·DB 풀 대기를 측정한다. 생성 중뿐 아니라 느린 응답 전송과 종료 후 정리 구간을 포함한다. 캐시로 유지되는 메모리를 누수로 단정하지 않고 같은 유한 시나리오를 초기 3회 반복해 증가 추세와 자원 소유자를 확인한다. 회차마다 끝난 뒤 다음 정상 요청을 넣는다.

다음 상황에서는 요청 수 증가와 다음 혼합 단계를 중단한다: OOM/예상치 못한 재시작, 계정·판본 혼입, 작업 유실·중복 공개, 원본/유효 파일 손실, 기한이 지나도 해제되지 않는 슬롯·고아 프로세스, 지속적인 자원 증가, health 미복구. 원인·입력·마지막 정상 구간을 보존하고 소유한 부하 발생기만 중단한다. 테스트를 통과시키려고 timeout·worker·메모리 제한이나 검증 강도를 바꾸지 않는다.

정리는 실행 ID에 속한 시험 계정·악보·파일·프로세스·폐기 환경만 대상으로 한다. 범위와 절대 경로를 확인한 뒤 처리하고 관련 없는 데이터·공유 서비스에는 적용하지 않는다. 실패 시 정리되지 않은 자원을 명시한다. 실행 환경·공유 계약 변경이 필요하면 영향과 대안을 정리한 뒤 합의한다.

## 결함 처리와 산출물

실행은 `coco-verify`로 실제 경계를 확인하고 `coco-review`로 코드와 확정 기대 동작을 대조한다. 재현된 확정 결함은 `coco-build`에서 최소 수정·관련 회귀·작업 단위 커밋을 수행하고 같은 재현 절차로 재검증한 뒤 변경 코드 리뷰를 받는다. 공유 계약·보안 정책·기획 결정 변경만 확인 대상으로 남긴다. 관련 없는 리팩터링·기능 추가는 포함하지 않는다.

실행 기록은 이 계획의 해당 ID에 연결한다. 재사용 가치가 있는 최종 결과는 `docs/knowledge/infra/async-resource-validation.md`에 정리하고 docs 목록에 연결한다. 원시 계측·추적 자료는 Git 밖의 `C:\higher\qa-artifacts\S15P31E102-954\<run-id>`에 두고 위치·입력 식별값·조건·요약을 기록한다. 비밀번호·쿠키·서명 URL·원본 자료는 문서나 로그에 복사하지 않는다.

문제별 기록 필드: 검사 ID / 배포·소스·환경 / 입력과 사전 상태 / 재현 절차 / 기대 결과와 확정 근거 / 실제 결과 / 사용자 영향 / 재현 여부 / 증거 위치 / 수정·동일 절차 재검증·영향 회귀·리뷰. 재현 실패나 원인 미확인은 의심 항목으로 남긴다.

최종 보고는 **수정·검증한 문제 / 남은 문제와 영향 / 환경 부족으로 미실행한 검사 / 화요일 사람이 확인할 항목**을 나눈다. 사람 확인에는 실제 배포 버전 일치, 실기기의 음원·악보 판본/리듬 일치, 체감 대기와 완료 알림, 네트워크 변경 후 복구를 포함한다. 대역·로컬·에뮬레이터 결과로 실제 엔진·운영 용량·실기기 통과를 대신하지 않는다.
