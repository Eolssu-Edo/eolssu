## 범위와 순서

현재 후속 단계: 시김새207개 근거 감사 완료 → V16/315관계 명시적 매핑 및 API의 실패 확인 → 구현/격리 DB·실제430개 검증 → 독립 리뷰·커밋. 원래 기본음219개 관계와 기준22/단소15 계약은 유지한다. 시작 작업 트리는 develop5410d416 병합 후 깨끗하며 다른 파트 파일은 수정하지 않는다.

1. V14에서 nullable FK와 연결 근거를 추가한다. 기본음만 연결하고 기존 행은 null로 유지한다.
2. 실제 파일·명시적 매핑을 검증하는 별도 CLI로 `(yul, octave)`를 해석한다. 단소 기본음 30개 매핑을 기록한다.
3. 조회 API에 nullable 문자열 `pitchId`와 선택 필터를 추가한다. 재생·검수·채점 상태는 보존한다.
4. Python 단위/실제 MySQL, Kotlin clean build/databaseTest, 실제 430개 매핑을 검증하고 계약·운영 절차를 갱신한다.

- 고아 FK·기본음 scalar에 시김새 연결·근거 없는 연결을 DB에서 거부한다. V16은 시김새를 역할별로 연결한다.

## 시김새 후속 구현·검증

- 기존 라벨 전수 감사 결과207시김새 모두 기존22개 pitches에 대응한다. 역할 테이블V16+명시적 매핑4파일로315관계(207LABEL,88SEQUENCE,10LOWER_ANCHOR,10DESTINATION)를 추가했다. 기존 기본음 scalar는 유지한다.
- API는 pitchRelations 배열과 relatedPitchId 필터를 추가했다. 관계는 배치 조회하고 필터는 EXISTS를 사용해 반복음으로 자산이 중복되지 않는다. 상세 metadata가 evidencePath의 기준이다. 재생 경로는 그대로다.
- 최초 relatedPitchId=01의200 응답을400으로 바꾸는 실패→성공과 관측anchor 순서·labelAnchorIndex 검사를 확인했다. Python34개(격리MySQL 포함)가 모두 통과했다. 전체 clean build 단위436개 통과, DB162개 중 기존마이그레이션기대15의 실패를16/새테이블 기대로 갱신한 뒤 전체162개 재실행이 통과했다. 실패·오류·건너뜀0.
- 새 폐기 DB eolssu_pitch_sigimsae430에서 V1~V16/430적재/기본219/시김새315관계·재실행·기존import를 검증했다.426자산 연결·4미연결·inferred430·채점가능0·DRAFT430·40,899,691바이트이며 모든 기존 자산 전체행과 관계재실행 스냅샷이 같다.
- 독립 읽기 전용 데이터 감사에서207자산·315관계·원본path/순서/선택anchor/목표22음이 전부 일치했다. 코드검토에서 동일원본음의 LABEL/선택SEQUENCE 또는 DESTINATION이 서로 다른pitch로 적재될 수 있던 검증누락을 찾아, 동일원본음의 역할별target 일치검사와 회귀를 추가했다. 해당수정도 리뷰어가 재확인했다. 커밋 후 최종스냅샷 리뷰는 부모 작업에 인계한다.
