- [DB 정본](../contracts/db-schema.md)의 기존 MySQL 8.4 V1을 사용한다. 컬럼·제약·미결 정책의 의미를 변경하지 않는다.
- Spring Boot 4 호환 MyBatis 4.0.0, Boot 관리 Flyway·MySQL Connector/J를 추가한다.
- 기능별 infrastructure에 12개 테이블의 저장 행 모델과 PK 조회 Mapper를 두고 SQL은 `resources/mybatis/<기능>`에 배치한다. 업무 API·정책·빈 계층은 추가하지 않는다.
- 기존 무DB 기동을 유지하고 `db` 프로필과 환경변수로 실제 DB 기능을 활성화한다. 운영 DB 이름·접속 정보가 앱에 아직 연결되지 않은 배포 현황을 고려했다.
- 작은 고정 데이터와 격리된 MySQL 8.4로 V1 신규 적용·재실행·12개 테이블 매핑과 주요 제약을 확인한다. 기본 `clean build`는 외부 DB 없이 실행한다.

## 결정·제약

- 스키마는 SQL이 정본이다. ERDCloud 재조회나 스키마 수정 없이 기존 V1을 연결한다.
- JSON 열은 저장소에서 원문 문자열, DATETIME은 UTC를 나타내는 LocalDateTime, nullable 열은 Kotlin nullable로 매핑한다. 공통 JSON 계약은 새로 확정하지 않는다.
- Mapper는 저장 계층의 PK 조회만 제공한다. 등록·상태 전이·소프트 삭제·재채점은 해당 기능 구현에서 정한다.
- GitLab API는 기존 Git 인증으로 401을 반환했다. Git Push 인증은 별도로 사용하고 MR은 로그인된 브라우저에서 처리한다.

- 작업 중 원래 checkout에 Task 73의 인프라 변경이 나타나, 이번 변경만 별도 managed worktree `mybatis-flyway`로 이동했다. 원래 checkout은 Task 73 브랜치와 변경을 보존했다. 이 MR에는 해당 인프라 변경을 포함하지 않는다.


## 검증 결과

- 구현 전 DB 의존성만 추가했을 때 기존 HTTP 기동 검사가 DataSource 미설정으로 실패했다. 기본 프로필 제외와 db 프로필을 구성한 뒤 같은 검사가 통과했다.
- XML 위치 설정 전 실제 Mapper 호출이 `Invalid bound statement`로 실패했다. `mapper-locations`와 생성자 매핑 설정 후 12개 테이블 검사가 통과했다.
- 전용 worktree에서 `./gradlew --no-daemon clean build databaseTest`: 성공. 기본 HTTP 검사 1개와 MySQL 통합 검사 3개, 실패 0개.
- MySQL 8.4.9를 임시 데이터 디렉터리와 임의 loopback 포트로 격리해 실행했다. 서버 기본 시간대를 +09:00으로 바꿔도 앱 세션은 +00:00이었다. 고정 fixture는 검사 종료 후 롤백되었다.
- 패키지의 실제 의존성: MyBatis Starter 4.0.0, MyBatis 3.5.19, MyBatis-Spring 4.0.0, Flyway 12.4.0, Connector/J 9.7.0. JAR에 Mapper XML 12개가 들어 있다.
- 실제 패키지 JAR에 `SPRING_PROFILES_ACTIVE=db`, `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 주입해 MySQL/Flyway 기동과 미등록 경로 HTTP 404를 확인했다.
- 별도 임시 DB의 이력 없는 기존 스키마를 자동 baseline하지 않고 기동을 거부했다. 임시 DB의 V1 checksum을 바꾼 경우도 기동을 거부했으며, 원래 checksum 복구 후 정상 JAR 기동을 다시 확인했다.
- V1은 기준 커밋과 바이트 단위로 동일하다. XML 구문·namespace·statement, 로컬 문서 링크와 `git diff --check`를 확인했다.
