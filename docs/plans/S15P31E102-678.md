# S15P31E102-678 Android QA APK 화면 재조회·데이터 재사용 계측

- [Jira 작업](https://ssafy.atlassian.net/browse/S15P31E102-678) · [실기기 검증 환경·앱 배포 Story](https://ssafy.atlassian.net/browse/S15P31E102-328)
- 구현 기준은 `origin/develop`의 `3af7b31f`다. Android QA APK가 진단 이벤트를 앱 전용 저장소에 기록한다. Mattermost에서 `/applog`를 실행하면 미수집 로그를 전량 가져오고, EDO2가 저장을 확인한 범위는 앱에서 삭제한다.

## 기록으로 답할 질문

1. 사용자가 화면을 이동하는 동안 앱이 같은 곡·악보·평가의 HTTP 요청을 몇 번 시도하는가?
2. 다음 화면이 앞서 받은 값을 실제 사용했는가? 다시 읽었다면 직접 진입, 판본 불일치, 실패 재시도, 상태 확인 중 어느 경우인가?
3. 탭한 뒤 사용자가 처음 점수·기록 카드·연습 악보를 볼 때까지 어디에 시간이 걸리는가? 모범연주에서 첫 재생을 요청하기까지 어떤 준비를 기다리는가?

예를 들어 평가 응답으로 **81점**을 받았는데, 오류 위치를 악보에 표시할 준비가 끝날 때까지 화면 전체가 로딩 중이면 악보 준비가 첫 점수 표시를 막는 의존이다. 점수는 평가 응답으로 표시하고, 오류 위치는 악보가 준비됐을 때 붙일 수 있다. [661은 이 동작을 Android 에뮬레이터에서 검증했다](S15P31E102-661.md). 이번 계측은 데이터 준비와 실제 콘텐츠 그리기 시점을 함께 기록해 다른 화면에서도 이런 대기를 찾도록 한다.

## `/applog` 요청과 결과

재현 후 Mattermost에서 `/applog`를 입력하면, 실행자에게 접수 메시지가 먼저 표시된다. 명령은 기존 QA 웹에 등록된 **휴대폰**에 연결한다. Windows 중계에 설정된 기기 식별 정보와 전송 세션을 사용한다. 앱이 열린 상태에서 진단 기록을 지원하는 QA APK가 보관한 미수집 로그 전체를 요청한다. 앱을 재시작하거나 같은 QA 패키지의 APK를 갱신한 뒤에도 이전 로그를 포함한다. 앱이 열려 있지 않음, 기기 연결 끊김, 설치 중, 미수집 로그 없음은 각각 안내한다. [QA 기기·연결 절차](../../infra/qa-phone/OPERATIONS.md) · [ADB 대상 확인](../../infra/qa-phone/adb.mjs)

1. EDO2의 기존 [Mattermost 명령 중계](../../infra/edo-check/README.md)에 선택 기능으로 연결한다. `/applog` 전용 토큰과 설정에 등록된 팀·채널·실행자 ID를 확인하고 인자 없는 명령만 받는다. 접수와 결과는 실행자에게만 표시한다. 중복 요청 검사와 콜백 주소 검증은 기존 방식을 사용하고, 수집 작업은 서버 점검과 별개의 실행 슬롯 한 개로 제한한다. [Mattermost 명령 응답](https://developers.mattermost.com/integrate/slash-commands/custom/)
2. EDO2는 기존 휴대폰의 loopback SSH 터널을 통해 Windows 중계의 고정 내부 경로에 요청 ID를 보낸다. 내부 경로는 공개 QA URL의 프록시 경로 밖에 두고 전용 서버 간 자격 증명을 확인한다. QA 웹 접속 키와 앱 로그인 토큰은 이 경로의 권한으로 사용하지 않는다. Windows는 기존 ADB 전송 세션·기기 식별자와 설치 APK의 패키지를 대조한다. 명령에서 기기나 경로·ADB 인자를 바꿀 수 없다. [QA 터널과 프록시](../../infra/qa-phone/README.md) · [QA 프록시 경로](../../infra/qa-phone/nginx.location.conf)
3. Windows는 ADB에서 등록된 Android 사용자와 `com.ssafy.eolssu.qa` 패키지를 지정해 고정된 수집 요청을 보낸다. 앱이 화면에 떠 있을 때 등록한 수신기는 ADB 셸이 보유한 `android.permission.DUMP` 권한을 요구한다. 앱의 기록 작업자가 요청 전 대기열의 저장을 마친 뒤 마지막 순번을 확정한다. 그 순번까지가 이번 명령의 범위다. 이후 기록은 다음 명령에 포함한다. 앱은 순번 범위별로 임시 파일을 한 개씩 만들고 Windows는 완료 표시·요청 ID·범위를 확인한 후 `run-as`로 해당 파일을 읽고 정리한다. QA 기기에서 권한과 `run-as` 동작을 실제로 확인한 뒤 채택한다. [Android 수신기 권한](https://developer.android.com/develop/background-work/background-tasks/broadcasts) · [Android 셸 권한](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/Shell/AndroidManifest.xml) · [AOSP run-as](https://android.googlesource.com/platform/system/core/+/master/run-as/run-as.cpp)
4. EDO2는 요청 ID·APK 버전·스키마·크기·순번을 검증하고 `/var/log/eolssu-qa-perf/events.sqlite3`에 이벤트와 저장 순번을 한 트랜잭션으로 기록한다. 저장을 확정한 뒤 연속으로 받은 마지막 순번을 확인 응답으로 보낸다. 앱은 해당 로그와 응답이 같은 기기 로그 세대 및 요청에 속하고 이미 내보낸 범위 안에 있는지 확인한다. 그런 다음 확인 순번 갱신과 해당 범위 삭제를 앱 전용 저장소의 한 트랜잭션으로 처리한다. 기기에 저장이 확인되지 않은 구간이 남아 있으면 다음 명령이 그 구간부터 이어서 수집한다. 전용 경로는 기존 syslog 디렉터리 권한과 독립적이다.
5. Mattermost에는 APK 버전, 수집한 범위, 요청 수·재사용·첫 표시 시간, 누락 여부, 조회용 요청 ID를 보여준다. 요청 시 확정한 순번까지 EDO2 저장과 앱 삭제가 확인되면 완료로 표시한다. 일부만 받았거나 앱의 삭제 응답을 확인하지 못하면 저장된 범위와 확인이 남은 범위를 안내한다. 원문은 승인된 운영자가 SSH로 읽는다. EDO2의 보유기간 제안 7일은 수집된 원문에 적용한다. [프로젝트 로그 보유 기준](../../infra/privacy/README.md)

기존 Jenkins QA 빌드의 `com.ssafy.eolssu.qa`와 debug 조건을 둘 다 충족할 때 진단 기록과 요청 수신기를 연결한다. 각 실행의 `versionName`·`versionCode`를 함께 저장하고 QA APK 카탈로그의 전체 커밋 SHA와 Jenkins 빌드 번호에 대조한다. `develop` 병합 후 그 커밋을 포함한 첫 QA APK와 EDO2·Windows 중계 설정이 함께 준비되어야 명령을 사용할 수 있다. [QA 빌드 설정](../../infra/qa-phone/qa-android.init.gradle) · [Android 진입점](../../frontend/androidApp/src/main/kotlin/com/ssafy/eolssu/MainActivity.kt) · [APK 카탈로그](../../infra/qa-phone/publish-apk.py)

## 앱 API와 수집의 분리

- 앱의 UI·저장소·Ktor에서는 시각과 허용된 값만 대기 없이 큐에 넣는다. 별도 백그라운드 작업자가 작은 묶음으로 앱 전용 SQLite에 기록한다. 진단 DB와 임시 파일은 앱 백업 범위 밖에 둔다. 앱 API와 UI는 진단 저장·내보내기·삭제가 끝나기를 기다리지 않는다.
- Windows의 별도 ADB 작업이 `/applog` 실행 중에만 데이터를 순서대로 가져온다. 기기별 동시 요청 한 건과 묶음당 128KiB 이하로 제한한다. 서버는 Windows의 읽기·정리 시간보다 길게 한 요청에 최대 9초, 명령 전체에 10분을 허용한다. 묶음 크기는 한 번의 전송에만 적용한다. 시간이 지나거나 전송이 끊기면 저장·삭제 확인 범위를 알려주고, 다음 `/applog`에서 이어 받는다. APK 설치와 수집은 서로 실행을 막고, 수집·영상·기기 조작은 별도 작업으로 처리한다.
- 미수집 로그는 EDO2 저장 확인을 받을 때까지 보존한다. 가용 공간이 초기 여유 기준인 64MiB 미만이면 새 진단 기록을 중단하고, 공간이 회복되면 기록을 재개한다. 포화나 저장 실패는 다음 저장 성공 시 누락 이벤트로 기록한다. 앱 강제 종료 직전 아직 저장되지 않은 이벤트 수를 확인할 수 없으면 누락 가능으로 표시한다. 디스크에 확정된 로그가 재시작 뒤에도 수집되는지 검증한다.

## 순번과 삭제

- 설치 데이터에 속한 임의 `stream_id`와 앱 저장 트랜잭션에서 부여한 증가 순번으로 이벤트를 식별한다. 앱 재시작과 같은 패키지의 APK 갱신 뒤에도 이어지고, 앱 데이터 초기화 뒤에는 새 로그 세대를 사용한다. EDO2는 같은 세대·순번·내용의 재전송을 한 건으로 처리한다. 같은 순번의 내용이 다르거나 중간 순번이 비어 있으면 그 지점에서 확인을 중지한다.
- EDO2에 저장됐지만 응답이 끊긴 경우 다음 명령에서 재전송을 확인하고, 서버에 원문이 남아 있는 연속 구간의 저장을 다시 확인한다. 보유기간이 지나 원문이 만료된 구간은 앱이 여전히 보관하고 있으면 다시 저장한 뒤 확인한다. 앱이 삭제를 완료한 뒤 결과 응답이 끊긴 경우 앱에 저장된 확인 순번으로 처리 여부를 확인한다.

## 기록 구조

모든 시각은 같은 프로세스의 단조 시계를 사용하며 단위는 ms다. 앱 시작 시 생성하는 임의 `run_id`와 버전으로 기록을 구분한다. 사용자 동작부터 이어지는 화면에는 같은 `flow_id`를 넘기고, 화면 방문마다 `visit_id`를 새로 준다. 예를 들어 곡 상세와 연습은 같은 흐름의 다른 방문이다. 직접 진입은 새 흐름으로 기록한다. 백그라운드 작업과 다음 화면이 서로의 요청을 가져가지 않도록 각 로드의 코루틴에 문맥을 명시적으로 전달한다. 관련 화면을 벗어나거나 계정이 바뀌면 흐름을 종료한다.

| 이벤트 | 남기는 내용 | 판단에 쓰는 방법 |
| --- | --- | --- |
| `run_started` | 스키마 버전, 앱 버전명·코드, `run_id` | 비교할 APK 확인 |
| `action`, `visit_started` | 동작명, 출발·도착 화면 열거값, `flow_id`, `visit_id`, 상대 시각 | 탭부터 화면 방문까지 연결 |
| `data_load` | 로컬 작업 ID, 데이터 종류, 리소스 별칭, 검증된 판본 별칭, 조회 이유, 실제 사용한 데이터 출처, 시작·소요 시간, 결과 | 네트워크 조회, 기존 화면에서 전달받은 값, 화면 내부 보관값을 구분 |
| `http_attempt` | `data_load`의 로컬 작업 ID, 정해진 경로 이름, HTTP 메서드, 최초 전송·인증 갱신·갱신 후 재전송 구분, HTTP 코드 또는 오류 분류, 소요 시간 | 실제 앱 전송 횟수와 네트워크 대기 확인 |
| `poll_summary` | 상태 확인 횟수, 정상 대기·실패 수, 첫 확인과 최종 관측 시각, 종료 이유 | 상태를 기다리는 정상 폴링을 화면 이동 재조회와 구분 |
| `milestone`, `flow_end` | 준비 완료, 최초 콘텐츠 그리기, 플레이어 시작, 종료 이유, 누락 수 | 준비와 표시 사이 간격, 실패·취소·불완전 수집 확인 |

- 데이터 종류는 `evaluation`, `song_bundle`, `song_detail`, `score`, `record_page`, `model_audio_metadata`, `model_audio_timeline`처럼 고정한다. 조회 이유와 출처는 독립적이다. 예를 들어 상세 재시도에서 평가는 화면 보관값을 쓰고 악보는 네트워크로 다시 요청할 수 있다. 실패·취소·미완료를 성공 시간 집계와 구분한다.
- 리소스 별칭은 한 흐름 안에서만 유지하는 임의 값이다. 앱 내부에서는 같은 요청 대상, 의미 있는 필터·페이지, 로그인 세대를 비교하고, 성공 후 검증한 판본에는 별도 별칭을 매긴다. 계정 교체·로그아웃·같은 계정 재로그인 때 이전 흐름을 닫고 별칭을 새로 부여한다. 이미 저장한 허용 필드의 이벤트는 수집 확인까지 보존한다.
- 같은 경로·리소스의 전송 시도 수와 성공 후 같은 판본을 다시 받은 횟수를 따로 센다. 판본을 확인할 수 없는 재요청은 후보로만 남긴다. 곡 상세와 악보는 각각 다른 경로로 세고, 두 요청을 포함한 `song_bundle`의 반복 횟수도 별도로 집계한다. 정상 폴링, 인증 재전송, 이전 실패 재시도, 의도적 판본 확인은 각각 다른 분류로 집계한다. 이 데이터의 측정 범위는 앱의 전송 시도까지다. 서버 내부 조회 수는 서버 쪽 지표로 판단한다.
- 로그에 들어갈 필드는 코드에서 허용 목록으로 제한한다. 사용자·곡·세션 원본 ID, 제목·점수·녹음·악보 본문, URL·쿼리·헤더, 토큰, 서명 URL, 예외 원문은 제외한다. 별칭의 용도는 QA 기록 내 연결로 한정한다.
- 초기 설계 상한은 저장 대기 이벤트 256개, 동시 활성 흐름 8개, 흐름별 별칭 256개, 개별 이벤트 1KiB다. 기록을 받지 못한 구간은 누락 수나 누락 가능 상태로 남긴다. 정상 폴링은 요약으로 모은다. 시작부터 끝까지 흐름 내 순번이 이어지고 누락 수가 0인 기록만 요청 수 비교에 쓴다. 요청 순간 아직 완료되지 않은 흐름은 진행 중으로 표시한다.

| 평가 결과 | 평가 데이터를 사용할 수 있게 된 시점과 점수 내용이 처음 그려진 프레임을 각각 기록한다. 악보 상세 준비는 별도 시점이다. |
| 연습 화면 | 검증된 악보를 그릴 수 있게 된 시점과 악보가 처음 그려진 프레임을 기록한다. 조작 버튼 활성 시점은 별도로 기록한다. |
| 기록 첫 화면 | 첫 기록 카드가 처음 그려졌을 때 기록한다. 빈 기록과 오류 상태는 별도 결과다. |
| 모범연주 | 재생 탭, 시간표 준비 완료, 플레이어에 음원 로딩을 요청한 시점, Android 플레이어 시작을 구분한다. 실제 소리가 들리기 시작하는 시점은 실기기에서 따로 확인한다. |

콘텐츠가 있는 UI 분기의 첫 그리기에 한 번만 기록한다. 스켈레톤, 상태 갱신, 재구성은 콘텐츠의 첫 그리기와 구분한다. 첫 그리기는 앱의 관측 시각이며 화면 합성 완료 시각은 포함하지 않는다. [Android 플레이어](../../frontend/shared/src/androidMain/kotlin/com/ssafy/eolssu/platform/audio/AndroidAudioPlayer.kt)의 `Playing`은 `MediaPlayer.start()` 직후다.

## 구현 순서와 인수 조건

1. 공통 계측 타입과 무출력 구현을 `shared`에 두고 Android 전용 출력은 플랫폼 주입으로 연결한다. [Ktor의 실제 전송 경계](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/core/network/HttpClients.kt)에서 최초 전송과 인증 갱신·재전송을 센다. 이 시각은 HTTP 응답 관측까지이며, 본문 처리·판본 검증을 마친 시각은 저장소에서 기록한다. 앱 내부 작업 ID로 화면과 각 요청을 연결한다.
2. [곡 상세→연습](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/app/navigation/EolssuNavHost.kt)과 [취약 구간 화면 이동](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/app/navigation/WeakSectionNavigation.kt)을 우선 연결한다. [곡 조회](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/data/song/ApiSongRepository.kt), [취약 구간 조회](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/data/practice/WeakSectionRepository.kt), [평가 재시도](../../frontend/shared/src/commonMain/kotlin/com/ssafy/eolssu/feature/result/ResultViewModel.kt)의 실제 사용 분기에서 기록한다. 기록 목록과 모범연주도 첫 APK 범위에 포함한다. 이번 변경의 완료 기준은 관측 가능성이다. 조회 동작을 최적화할 때 이 APK의 로그를 비교 기준으로 쓴다.
3. [로컬 API 검증 설정](../../frontend/README.md)으로 응답 지연과 오류를 재현한다. 합성 데이터로 곡 상세→연습에서 현재의 두 조회 묶음, 취약 구간 `source()` 한 번에 정상 경로 5 GET, 곡 상세 503 뒤 평가 GET 총 1회와 점수 우선 표시를 확인한다. 401 갱신·재전송, 폴링, 앱 이탈, 계정 A→B→A, 직접 진입과 판본 불일치도 검증한다. 로그 필드 허용 목록과 누락 판정, 일반 앱의 무출력을 확인한다.
4. Android 호스트 테스트와 QA APK 빌드를 통과시킨다. QA 휴대폰에 설치한 버전을 카탈로그와 대조한다. 앱 재시작과 APK 갱신 전후에 여러 전송 묶음에 걸친 기록을 만들고 `/applog`로 가져온다. 이전·현재 APK의 로그가 빠짐없이 EDO2에 남고, 저장 확인을 받은 로그만 앱에서 삭제되며, 요청 중 생성한 로그가 다음 명령에서 수집되는지 확인한다. 서버 저장 전 단절, 저장 후 확인 응답 유실, 앱 삭제 후 결과 유실을 각각 재현해 중복·누락과 잘못된 삭제가 없는지 확인한다. 저장소 포화, 기기 오선택, 권한 없는 명령, 공개 URL의 내부 경로 접근, APK 설치 중, 빈 기록도 검증한다.
5. 같은 QA 폰에서 같은 API 시나리오를 계측 비활성, 계측 활성·명령 미실행, API와 `/applog` 동시 실행 조건으로 비교한다. 앱 API 요청 수·순서·재시도·응답과 탭→첫 표시 시간을 기록한다. 수집 타임아웃 및 큐 포화에도 API·재생·QA 제어가 정상이어야 한다. 로그 수집이 요청 순서·횟수를 바꾸거나 통제된 반복에서 첫 표시를 일관되게 늦추면 반영을 보류한다.

## 검증 기록

- 2026-11-10 Android 37 에뮬레이터에서 로컬 API와 Node 휴대폰 중계, Python EDO2 수집 코드, 임시 SQLite를 연결했다. 곡 상세에서 연습으로 이동했을 때 곡 상세 GET 2회와 악보 GET 2회를 동일한 리소스·판본 및 흐름의 두 방문으로 구분했다. 이 표본의 연습 악보 최초 그리기는 탭 후 252ms였다.
- 위 요청의 이벤트 13개를 서버 저장한 뒤 앱 삭제 확인 13을 받았다. 같은 기기에서 다시 요청하니 미수집 로그가 없었다. 별도 검증에서 동일 패키지 QA APK 갱신 전후 로그 보존, 미내보낸 범위의 삭제 거절, ACK 재실행과 서버 저장 뒤 ACK 유실 복구를 확인했다.
- 최종 로컬 QA 빌드로 갱신하고 같은 경로를 반복했다. 두 버전에 걸친 미수집 이벤트 16개를 순번 14–29로 저장했고, 앱 삭제 확인 순번도 29였다. 새 빌드에서 동일 리소스의 두 방문에 걸친 GET 4건과 첫 악보 그리기 287ms를 확인했다. 다음 수집은 미수집 0건이었다. 단일 로컬 표본의 시간이며 실기기 성능 비교는 남아 있다.
- 공통 Android 호스트 검사 1,207개와 앱 호스트 검사 3개가 통과했다. 공통 조건부 검사 4개는 건너뛰었다. Android QA APK 빌드와 lint 오류 0건, iOS Arm64·JS·Wasm 컴파일, EDO2 Python 검사 65개와 Windows Node 검사 82개를 확인했다.
- 운영 EDO2의 기존 중계와 휴대폰 터널이 응답했고, 후보 유닛은 운영 Linux의 `systemd-analyze verify`를 통과했다. 기존 QA 폰의 공식 APK 설치, Windows 수집 경로 반영, Mattermost 실제 등록·호출, 실기기 API와 수집의 동시 실행 검증은 대기 중이다.

## 운영 적용 순서

1. MR을 `develop`에 병합한 커밋의 공식 Jenkins QA APK를 게시하고 QA 휴대폰에 갱신 설치한다. 설치된 APK의 패키지·버전을 해당 SHA의 카탈로그와 대조한다. [공식 QA APK 설치 절차](../../infra/qa-phone/OPERATIONS.md)
2. Windows의 휴대폰 중계에만 검증한 코드와 설정을 적용한다. 휴대폰 감독 설정의 `ApplogTokenFile`은 제한된 전용 토큰 파일을 가리키고, `ApplogDeviceIdentity`에는 운영자가 ADB로 확인한 기기 식별값을 설정한다. 적용 전 감독 설정과 실행 경로를 복구용으로 보존한다.
3. EDO2 수집 설정과 Mattermost 명령을 활성화한다. 기존 점검 health와 내부 경로의 외부 차단을 확인하고, QA 앱을 연 상태에서 `/applog`로 서버 저장·앱 삭제와 두 번째 요청의 미수집 로그 없음을 확인한다. 문제가 생기면 EDO2에서 `applog` 설정을 제거해 수집을 끄고 Windows 휴대폰 감독 설정을 복구한다. 앱에 남은 미수집 로그와 서버에 이미 저장한 로그는 보존한다. [EDO2 적용·중단 절차](../../infra/edo-check/README.md#qa-앱-로그-수집)
