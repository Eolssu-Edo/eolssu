## 확정 사항

- 사용자 답변: 미가입 소셜 계정은 401 SOCIAL_ACCOUNT_NOT_REGISTERED, mergeTicket 유효기간10분. 앱 등록·콜백 URI·state FE 합의는 아직 없으며 서버 시작 API 방향으로 설계한다.
- 소셜 신규 가입 없음. 연결된 제공자 ID로만 즉시 로그인, 탈퇴 대기는 로그인 성공 시 취소. 같은 이메일 기존 계정은 자동 연결하지 않고 동의를 받는다.
- 제공자가 확인한 이메일은 동의만, 나머지는 비밀번호 또는 ACCOUNT_MERGE 완료 토큰으로 확인한다. 회원 ID·기록·설정 보존, users를 refresh_tokens보다 먼저 잠근다.
- 제공자 토큰·인가 코드·state·mergeTicket·verificationToken을 로그나 toString에 담지 않는다. 키 누락 시 해당 제공자 거절. 실제 제공자 호출은 로컬 대역으로 검증하며 운영 앱 등록 완료로 보고하지 않는다.

## 미정·의존 사항

- 사용자 확정: state와 mergeTicket의 소비 기록은 MySQL에 해시로 저장한다. 유일키만으로 재사용을 막던143의 안을 대체한다. 임의256비트 토큰+DB 해시 조회이므로 서명 토큰 대신 불투명한 임의 토큰을 쓰며 제공자 ID·이메일을 클라이언트 토큰에 담지 않는다.
- 사용자 확정: POST /api/auth/oauth/{provider}/start(로그인), POST /api/users/me/social-accounts/{provider}/start(연결). state10분·1회 사용·브라우저 쿠키 결속. FE는 authorizationUrl을 열고 기존 완료 API를 호출한다.
- 사용자 확정: 계정 연결 비밀번호 확인은 회원별 독립15분 내5회 실패·15분 잠금. 잠겨도 이메일 인증 경로 허용. 기존 로그인/현재 비밀번호 카운터는 변경하지 않는다.
- 실제 앱 등록·redirect URI는 FE/제공자 설정 회신이 필요하다. 주소가 없는 제공자는 기능 거절로 처리하고 가상 URL을 운영 허용 목록에 넣지 않는다.

## 근거

- Notion AUTH-05 `/auth/oauth/{provider}`와 AUTH-09 `/auth/oauth/merge`의 필요한 두 페이지만 읽었다. 원격 문서 Status·비고는 수정하지 않았다.
- 제공자 규칙: [Kakao REST](https://developers.kakao.com/docs/en/kakaologin/rest-api), [Google UserInfo](https://developers.google.com/identity/openid-connect/reference), [Naver 로그인](https://developers.naver.com/docs/login/api/api.md). Kakao는 is_email_valid·is_email_verified, Google은 email_verified를 확인하고 확인 신호가 없는 경우 verified로 추정하지 않는다.

## 구현 결과·검증

- API6개(시작2·로그인·병합·연결·해제)를 추가했고 기존 내 정보 linkedProviders 저장 조회를 재사용했다. 전체29개 업무 API를 실제 매핑과 OpenAPI로 대조했다. 공통 오류 envelope·쿠키·ACTIVE 확인·테스트 회원 무기한 세션 정책은 유지한다.
- state·mergeTicket: 원문/서명 payload 대신 임의256비트 값과 MySQL SHA-256을 사용한다. START와 MERGE를 구분하고 브라우저·제공자·목적·회원·정확한 콜백에 결속한다. state는 코드 교환 전에 한 번 소비하며 제공자 장애 뒤에도 재시작이 필요하다. merge는 회원 PK 잠금 뒤 소비·연결·로그인 발급을 한 트랜잭션으로 묶는다. 실패 시 증명 소비와 모든 쓰기를 되돌린다.
- 같은 제공자 시작은 브라우저 결속 쿠키를 교체해 이전 흐름을 무효화한다. Google은 S256 PKCE를 추가했다. RestClient는 고정 엔드포인트·연결3초/읽기5초·리다이렉트 미추적이며 원격 오류 본문/토큰을 예외에 담지 않는다.
- 비밀번호 확인은 별도 LoginAttemptLimiter 인스턴스로 회원별 카운터를 사용한다. 1차 기존 정책처럼 서버 메모리이며 재시작 시 초기화된다. 이메일 확인은 목적·주소·유효기간·미소비를 잠금 뒤 재검증하고1회 소비한다. 회원 이메일 DB 콜레이션만 같고 실제 문자열이 다른 경우에는 제공자 확인 이메일만으로 연결하지 않는다.
- V8은 oauth_proofs1개 테이블을 추가한다. FK 대신 완료 때 회원을 다시 확인하며 매분 최대500개 만료 행을 지운다. 운영 모니터링 권한을 추가하거나 DB에 직접 적용하지 않았다. backend/.env.example·runtime Compose·runtime/.env.example에 값 없이 제공자별 콜백 목록을 연결했다.
- 테스트 먼저: 제공자 parser 정상 응답3개 실패→4개 통과, state 골격2개 실패→2개 통과, MySQL 골격 저장2개 실패→지속성·동시 소비·만료/삭제2개 통과, RestClient 골격 실패→4개 통과, HTTP 시작401 실패→전체 사용자 흐름8개 통과. JSON fixture의 잘못된 따옴표와 테스트 import 모호성은 실행 가능한 실패를 확인한 뒤 바로잡았다.
- 최종 `clean build databaseTest` 통과(JDK21·전용 MySQL8.4 max_connections500): 단위330개·DB109개, 실패/오류/skip0. 정상 로그인·탈퇴 취소·미가입 거절·동의/비밀번호/이메일 증명·독립 잠금 중 이메일 허용·잘못된 목적·다른 브라우저·만료/사용 티켓·연결 후 해제·다른 회원 소유·동시 병합1개 성공/1개 충돌 및 실패 티켓 롤백을 확인했다. db·ops OpenAPI/UI6개도 포함된다.
- 테스트 민감도: 무시되는 build 복사본에서 브라우저 결속, Naver 이메일 미확인 판정, mergeTicket 소비를 각각 제거했다. 대응 검사3개가 각각 기대 false/실제 true, 해제 후 티켓 재사용 기대410/실제200으로 실패했다. 원본은 변경하지 않았고 복사본은 제거한다. 결과 요약과 로그는 backend/build/oauth211-sensitivity.log에 보관한다.
- Compose는 가짜 필수 변수로 `config --quiet` 통과(기동·배포 없음). 자체 점검은 bf07d4b 기준 backend·관련 docs·runtime 변수 전달 범위이며 사용자 미추적 파일6개는 제외했다. scope collector 결과는 backend/build/oauth211-review-scope.json에 둔다. 정식 독립 리뷰는 아직 하지 않았다.
