## 변경

1. `infra/backup/backup.py` `prune()`: config 사본도 DB처럼 7일이 지나면 UTC 날짜별 최초 성공본만 남기고, 상한은 30일로 유지한다. 최근 7일의 배포 전후 사본은 모두 보존한다. 11-09~11-15 실적 기준으로 안정 상태는 약 75 GiB다. 첫 실행 때 약 91 GiB를 회수할 것으로 예상한다.
2. `infra/retention/retention.py`(신규): edo1 `/opt/eolssu/bin/eolssu-retention`. 기본은 계획만 출력하고, `--apply`를 줄 때만 지운다.
   - 보호 대상: `.env`의 `BACKEND_JAR`·`WEB_DIST_DIR`, `deployment.json`·`frontend-deployment.json`의 현재·직전 릴리스와 SHA, 컨테이너가 bind하는 릴리스. 여기에 최근 SHA 20개와 7일 이내 항목을 더한다. 보존 대상 릴리스의 ci 이미지와 컨테이너가 쓰는 이미지는 지우지 않는다.
   - 배포 상태가 `deployed`가 아니거나, 참조가 관리 루트 밖이거나, 키가 중복되면 실패하고 아무것도 지우지 않는다. `.env`에서는 두 키만 읽는다.
   - 릴리스 디렉터리는 공용 배포 lock(`/run/lock/eolssu-backend-deploy.lock`) 안에서 지운다. 오래된 이미지 태그와 72시간 지난 빌드 캐시는 배포가 읽지 않으므로 lock을 푼 뒤 정리한다.
   - 넓은 범위의 `docker system prune`은 쓰지 않는다. 이미지는 `repo:ci-<SHA>` 태그를 `docker image rm`(강제 옵션 없음)으로 하나씩 지운다.
3. `eolssu-retention.service`·`.timer`: 매일 04:50 KST `--apply`. 설치해도 timer 활성화는 별도로 승인받는다.

- `infra/retention` 단위 테스트 12건이 통과했다. 대상: 보호 규칙, 진행 중 배포 거부, 관리 루트 밖 참조·중복 키 거부, dry-run 무변경, 계획한 대상만 삭제, lock 범위, 심볼릭 링크 거부, 날짜 해석.

## 운영 1회 적용 결과 (2026-11-15, 사용자 승인)

- **backup.py 반영**: edo1·edo2의 `/opt/eolssu-backup/backup.py`가 develop 원본(SHA-256 앞 16자 `c25448af3bdcfc23`)과 같은지 확인했다. 확인 후 `a61189aaa1b01d32`로 교체했다. 이전 파일은 각 서버 `/var/backups/eolssu-backup-921-20261115T05375{1,2}Z/`에 보관했다.
- **edo2 prune 1회**(`systemctl start eolssu-backup-prune.service`, 05:38~05:50 UTC, Result=success): config 1,283개(167G)가 507개(75G)로 줄었다. `/`의 사용량은 185G에서 92G로, 여유는 125G에서 218G로 바뀌었다. 10-25~11-07은 날짜별 1개만 남았고 11-08 이후는 전부 남았다. `backup.py status`도 정상이다.
- **edo1 정리 1회**: 첫 `--apply`는 05:52 UTC 배포가 lock을 쥐고 있어 120초 대기를 넘겼다. 그래서 아무것도 지우지 않고 실패했다. 다시 dry-run해 같은 규칙과 대상 수(릴리스 209·이미지 373)를 확인한 뒤 재실행했다.
  - 결과: 여유 117.3 → 163.0 GiB, 이미지 650 → 277, 빌드 캐시 42.3 → 14.2 GB, 릴리스 399 → 191, 태그 삭제 실패 0건.
  - 정리 후 readiness·웹·`/api/terms`가 모두 HTTP 200이었다. 활성·직전 JAR, 현재·직전 웹 디렉터리도 그대로 있다.
- **확인된 부작용**: `prune()`은 지울 사본마다 SHA-256을 대조하면서 receive lock을 쥐고 있다. 이번에는 약 12분간 수신이 막혔다. 수신 대기는 120초라서 이 시간대의 배포 전 백업은 실패할 수 있다. 실제로 그 사이 실패한 Jenkins 백엔드 배포는 없었다. 이후 일별 정리는 하루치만 지우므로 짧아진다. 대조를 lock 밖으로 옮기는 개선은 후속으로 남긴다.

## 운영 적용 절차 (승인 후)

1. **edo2 백업 보관**: 새 `backup.py`를 기존 [백업 설치 절차](../../infra/backup/README.md)대로 edo1·edo2의 `/opt/eolssu-backup/backup.py`에 반영한다. 같은 lock을 쓰는 `sudo /opt/eolssu-backup/backup.py prune`을 1회 실행하고, 전후 `df -h /`와 config 개수를 기록한다. `status`가 정상인지 확인한다.
2. **edo1 산출물 정리**: `install -o root -g root -m 0755 infra/retention/retention.py /opt/eolssu/bin/eolssu-retention`으로 설치한 뒤 `sudo /opt/eolssu/bin/eolssu-retention`으로 dry-run 목록을 다시 검토한다. 승인되면 `--apply`로 1회 실행하고, 결과 JSON의 `free_bytes_before/after`와 `docker system df`를 기록한다. 그다음 `sudo /opt/eolssu/bin/deploy-backend --recover`와 health를 확인한다.
3. **자동 실행**: 단위 파일을 `/etc/systemd/system/`에 설치하고 `systemctl daemon-reload`한다. `systemctl enable --now eolssu-retention.timer`는 별도로 승인받은 뒤 실행한다.
4. **되돌리기**: timer를 `disable --now`로 끈다. 지운 릴리스는 같은 SHA로 다시 배포하면 생성된다. 백업 보관 변경은 이전 `backup.py`로 교체하면 되돌아가지만, 이미 정리한 사본은 복구할 수 없다.

## 남은 일

- 1·2(1회 적용)는 위와 같이 끝냈다. edo1 `/opt/eolssu/bin/eolssu-retention`은 설치돼 있다. 3(systemd 단위 설치와 timer 활성화)은 승인을 기다린다.
- `backup.py prune`이 lock 안에서 대조하는 시간을 줄인다.

- 릴리스를 SHA별로 한 번만 보관하는 백업 중복 제거는 필요할 때 후속으로 검토한다.
