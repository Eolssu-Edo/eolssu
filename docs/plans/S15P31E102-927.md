3. NavHost 공통 활성 lifecycle에 조회·스낵바·편집기 이동을 연결한다. 음원 알림의 표시/소비 로직을 재사용한다.

- 업로드 접수 추적·상태 전이·재시도·계정 세대·pause·연속 조회 실패·동시 조회를 구현한 뒤 변환 저장소7건, 기존 음원 저장소9건·공통 표시3건 focused 검사가 통과했다. `C:/higher/tmp/omr927-focused.log`.
- 별도 읽기 전용 사전검토에서 ‘다른 알림 뒤에 기다리던 완료 항목이 삭제된 뒤 표시되는’ 경계가 지적됐다. 대기 표시 취소와 실제 삭제 API 연결을 보완하고 회귀를 추가한다.
- 위 삭제 대기 회귀는 보완 전 2건 중 1건이 실제로 실패했다(`omr927-deletion-red.log`). 404/확인된 DELETE를 tombstone으로 보관하고 표시 대기를 취소하도록 보완했다. 늦은 상태 응답도 삭제를 되살리지 않는다.
- 상단바의 공통 Android·Wasm 컴파일은 통과했으나 Wasm 실행 파일 생성은 기본 Kotlin daemon 3GiB에서 `GC overhead limit exceeded`로 실패했다. 검사를 줄이지 않고 Android 검사와 웹 실행 파일 생성을 나눠 실행하며, 웹 컴파일은 기존 문서의 단일 worker/in-process 힙 조정 방식을 사용한다. 저장소 메모리 설정은 바꾸지 않는다.
- 전체 host 첫 실행 1,759건 중 1건은 ‘삭제404 뒤 같은 ID가 다시 Accepted로 복구된다’는 합성 대역 기대 때문에 실패했다. 실제 SHT-14 Controller/ConversionQueue는 삭제 시404, 원본 폐기된 기존 작업은409만 반환하며 삭제된 변환 행도 cascade 제거한다. 이 계약을 근거로 테스트를 ‘실패 뒤 Accepted를 주는 인터페이스 재시도’와 ‘삭제 뒤 늦은 DONE/진행 응답도 영구 무알림’으로 분리했다. 실패를 숨기거나 삭제 가드를 약화하지 않았다. 인터페이스 Accepted 회귀를 운영 재시도 성공으로 보고하지 않는다.
