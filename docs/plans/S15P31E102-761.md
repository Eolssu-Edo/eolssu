# 연습 기록 목록의 악기 정보와 페이지 조회 개선

- [S15P31E102-761](https://ssafy.atlassian.net/browse/S15P31E102-761) · Story S15P31E102-23 · 에픽 S15P31E102-14 · 스프린트 5, 진행 중
- 기준: `origin/develop` `866d9064` · QA S15P31E102-706의 `api-record-list`
- 계약: [REC-02](../specs/practice-records.md#rec-02-get-apiusersmepractice-records)

기존 REC-02 응답과 목록 소비자는 유지한다. 곡 묶음의 악기 코드를 우선 사용하고, 값이 없거나 모르는 코드에만 기존 카탈로그를 조회한다. 기록 화면은 펼친 곡의 첫 페이지와 사용자가 요청한 다음 페이지만 가져온다. 최신 연주 기준 곡 순서와 저장 기록 기준 주간 집계는 페이지 조회와 분리한다. 비교·마이페이지의 전체 목록 소비는 이 변경과 분리한다.

1. DB 통합 검사에서 인증 회원의 곡 악기·숨김 곡·정렬·주간 요약·기존 응답을 확인한다.
2. 앱에서 초기·필터·정렬·펼치기·다음 페이지·오류 재시도·직접 상세 진입·회원 변경을 검증한다.
3. 같은 고정 데이터로 전후 요청 수와 로딩 시간을 비교한다.

## 구현과 검증

- 첫 조회는 곡 묶음 전체와 기본 곡의 20개를 받는다. 다른 곡은 펼칠 때 0페이지를 받고, ‘더 보기’는 다음 페이지를 이어 붙인다. 현재 화면에서 이미 받은 페이지는 다시 펼칠 때 재사용한다.
- 곡 머리의 개수·최고점과 주간 요약은 서버 집계다. 저장 시각과 연주 시각의 순서가 다른 경우에도 앱은 최근 연주 기준으로 곡을 선택한다. 구 서버의 응답에 주간 요약이 없으면 앱은 일부 페이지를 집계한 값을 대신 표시하지 않는다.
- 기록 상세로 바로 들어가면 해당 ID로 상세를 요청한다. 지난 연주와 비교할 때만 그 곡의 후보 페이지를 읽는다. 마이페이지와 비교 화면의 기존 목록 소비는 계속 지원한다.
- 격리 MySQL 8.4.13에서 `databaseTest --tests '*PracticeRecordApiDatabaseTests'` 11건 통과. 회원별 묶음·행·주간 요약 격리, 인증 실패, 비공개 곡 악기, 기존 필드와 기본 정렬, 빈 목록, 잘못된 쿼리, NEW 상태, 페이지 경계를 HTTP로 검사했다.
- 백엔드 전체 `test` 첫 실행에서 723건 중 1건 실패·1건 건너뜀. 기본 프로필의 `BackendApplicationTests › prometheus scrape returns jvm and http request metrics`는 HTTP 타임아웃으로 재실행에서도 실패했다. 같은 재실행에서 기록 Controller·서비스 검사 8건은 통과했다.

- 프런트엔드 `:shared:jsTest`에서 본 코드와 테스트 소스 컴파일을 통과했다. Chrome 실행 파일을 만드는 `compileTestDevelopmentExecutableKotlinJs` 단계에서 3GB Kotlin 데몬의 구세대 힙 사용률이 99.99%에 달했고 Full GC가 271회에서 395회로 늘어도 실행 파일이 생성되지 않아 중단했다. 이 실행에서는 브라우저 테스트를 시작하지 못했다.
- 2026-11-11 복구된 Android SDK 37.0·JDK 21의 Windows 호스트에서 `:shared:testAndroidHostTest --tests '*RecordList*Test' --tests '*History*StateTest' --tests '*RecordDetail*Test' --tests '*HttpPracticeRecordRepositoryTest' --tests '*AccountIsolationRegressionTest' --tests '*ApiWeakSectionRepositoryTest' --console=plain --max-workers=1`을 실행했다. 기준은 `62932adf`이며 10개 스위트 56건이 통과했다(실패·오류·건너뜀 0건). 첫 페이지, 펼치기·재펼치기, 다음 페이지 실패·재시도, 정렬·필터, 계정 변경, 상세·기존 응답 소비 경로를 확인했다.

## 리뷰 반영

- 삭제한 행을 화면의 페이지에서 즉시 빼고, 해당 곡의 마지막 기록이면 곡 묶음도 제거한다. 새 목록 조회에 실패하면 남은 목록과 다시 시도 버튼을 표시한다. 삭제 전에 시작한 조회는 최신 목록을 다시 요청하기 전에 적용하지 않는다.
- 목록에서 선택한 한 건의 전체 연주·구간 정보를 같은 로그인 세션의 상세 화면에 넘긴다. 이전 악보를 읽지 못해도 전체 연주 기록의 비교 진입을 유지한다.
- 태블릿 가로에서 오래된순 첫 페이지로 최신 기록을 알 수 없으면 REC-02의 최신순 첫 한 건을 요청한다. 목록 정렬은 유지하고, 조회 실패는 상세 칸에서 재시도할 수 있다.
- 구 서버 응답에서 주간 요약이 생략돼도 성장 화면 링크를 표시한다. OpenAPI의 REC-02 설명을 `groupOrder` 기본값과 `weekOf` 집계 기준에 맞췄다.
- 리뷰 반영 후 `test --tests '*OpenApiRequestExampleTests' --tests '*PracticeRecordListControllerTests' --console=plain --max-workers=1`에서 4건 통과(실패·건너뜀 0건).
- 위와 같은 Android 호스트 필터로 본 코드와 테스트 소스를 컴파일했다. Gradle Test Executor 연결이 120초에서 시간 초과돼, 같은 Gradle Test 태스크의 Java 21 런처·런타임 클래스패스·JVM 인자로 JUnit 4.13.2를 직접 실행했다. 같은 10개 스위트 59건이 통과했다.
- 대역 검증에서 목록 진입 REC-02 5→1건, 다른 곡 첫 펼치기 0→1건, 다시 펼치기 추가 0건을 재확인했다. 오래된순 태블릿 기본 선택은 `sort=NEWEST&page=0&size=1` 실패 후 같은 요청으로 재시도해 최신 기록을 열었다.
- 이번 직접 실행에서 목록 데이터 준비 시간은 125.35→156.74ms, 다른 곡 펼치기는 0.041→9.67ms였다. 같은 대역의 일회 측정이며 실제 네트워크와 화면 표시 시간은 포함하지 않는다.
