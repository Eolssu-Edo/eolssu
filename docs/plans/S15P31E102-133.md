# S15P31E102-133: edo2 Mattermost 점검

관련 Task는 [S15P31E102-133](https://ssafy.atlassian.net/browse/S15P31E102-133), Story는 S15P31E102-41, Epic은 S15P31E102-21이다. Jira가 업무 단계의 기준이며 스프린트 59139 배정·진행 중 전환·Story Relates 연결을 MCP로 확인했다.

## 범위와 완료 조건

- `/edo2-server`, `/edo2-containers`, `/edo2-health`를 CI/CD 채널에서 실행해 같은 채널에 공개한다. 기존 edo1 명령·토큰·채널 제한을 보존한다.
- CPU·Load·RAM·swap·파일시스템/inode·Docker 저장공간·컨테이너 자원·실패 서비스/OOM을 기존 정의로 수집한다. 판정·시각·대상과 다음 조치가 실제 서버에 맞아야 한다.
- edo2 health는 실제 systemd 서비스·타이머·oneshot 이력, 중계 HTTP·Nginx 구성·UFW·자체 HTTPS·IP 인증서를 확인한다. 실행만 확인한 것과 실제 응답·완료 검증을 구분한다.
- 명령별 토큰·대상 구분, 정해진 SSH 세 명령·시간 제한, 비밀값 비노출과 edo1 회귀를 검증한다. 최종 세 명령은 실제 MM 입력으로 확인한다.

## 확인한 구성과 설계

- 기준 develop `caf1234675e73d67220f0a2a920ffc7e9fd58dc8`, 전용 기능 브랜치 `feat(infra)/S15P31E102-133-Mattermost-슬래시-명령으로-edo2-서버-점검·보고-구성`. 시작 작업 트리는 깨끗했다. 완료된 Task 95·MR !33은 재개하지 않는다.
- edo2의 Docker는 설치·활성 상태이며 현재 컨테이너는 0개, 이미지 약 3.039GB다. Docker 실패를 미사용으로 감추지 않고 빈 컨테이너 목록만 명확히 표시한다. edo1의 필수 컨테이너·Grafana/Metabase/n8n 검사는 edo2에 적용하지 않는다.
- nginx·edo-check·docker·ssh가 active/running, UFW active, Nginx 구성 검사와 내부/자체 HTTPS `/healthz`가 정상이다. certbot·백업 status/prune/restore-test timer가 active/waiting이다. 백업 status oneshot은 성공 이력이 있으나 restore-test oneshot은 systemd 실행 이력이 없다. 실행 이력이 없는데 성공으로 표시하지 않는다.
- 중계는 기존 edo-check의 nologin·NoNewPrivileges·ProtectSystem을 유지한다. 새 잠긴 edo2-check 계정·전용 키·127.0.0.1 호스트 키 pinning·root 소유 forced dispatch와 sudo 세 고정 명령으로 loopback SSH 수집을 수행한다. 일반 셸·SFTP·포워딩은 허용하지 않는다. 별도 root IPC/결과 파일 방식보다 기존 경계를 재사용하는 변경이 작다.
- command+token에서 서버·모드를 결정하고 form의 target/mode는 받지 않는다. 대상별 rate limit을 나누고 수집 결과의 target을 검증한다. 코드와 6개 토큰 설정을 함께 검증·교체·복구한다.
- edo2 IP 인증서 수명은 160시간으로 7일 경고를 적용하면 항상 주의가 된다. edo2는 만료 24시간 미만을 갱신 확인 기준으로 두고 timer도 따로 검사한다. 자체 IP HTTPS는 외부 관측점으로 표현하지 않으며 실제 MM 요청·공개 callback으로 도달성을 검증한다.
- 읽기 전용 독립 설계 감사에서 NNP·nologin·대상 혼선·TLS 경고·timer/oneshot·미사용/장애·교체 순서 위험을 확인하고 위 설계에 반영했다. 감사자는 코드·서버를 변경하지 않았다.

## 실행 순서와 검증

서버별 판정·인증 회귀의 실패를 먼저 관찰하고 수집기·중계를 확장한다. 전용 접근 경계를 검증한 뒤 MM 명령을 등록하고 코드·설정을 함께 배포한다. 잘못된 키/명령/서버 대상, 고정 시간 제한·부분 실패·빈 컨테이너·oneshot 이력·단기 인증서 경계를 검사한다. 실제 edo2 세 보고와 기존 edo1 보고를 확인한 후 작업 단위 커밋·Push·검토용 MR로 결과를 남긴다. 자동 복구·정리·패키지 설치·방화벽 확장은 범위에 없다.

## 구현·검증 결과

- command+token 기반 서버 선택, 서버별 SSH 설정, 응답 target/mode 검증, 대상별 간격 제한을 적용했다. 기존 edo1 3명령 설정도 기동 호환한다. 수집·표·조치는 서버별 기대 구성에 맞춘다.
- Docker가 없는 것과 조회 실패·빈 목록을 구분하고, systemd daemon/timer/oneshot·Nginx 구성·UFW·중계 JSON 응답·자체 HTTPS·IP TLS를 추가했다. 컨테이너 mount 이름이 서버 target을 덮어쓰던 문제도 회귀 검사로 고쳤다.
- 기존 대비 target 회귀가 실패하는 것을 먼저 확인했다. 최종 `python3 -B -m unittest discover -s infra/edo-check/tests -q`는 **45개 통과**했다. 두 dispatch의 `sh -n`, 예시 설정 JSON 검증, `git diff --check`도 통과했다.
- 독립 설계 감사와 별도 읽기 전용 소스·보안 리뷰를 수행했다. target 변수 덮어쓰기 발견을 수정했고 최종 relay `332961d3…`의 시각 서식 변경까지 재검토해 미해결 발견은 없다. 리뷰는 이 변경 범위의 증거이며 모든 운영 장애에 대한 보증은 아니다.

## 운영 반영과 접근 제한

2026-10-26 18:01 KST 전후 edo2에 전용 collector·dispatch·sudoers와 잠긴 edo2-check 계정·별도 loopback 키·고정 호스트 키를 구성했다. 기존 중계의 edo-check nologin·NoNewPrivileges=yes·ProtectSystem=strict를 보존했다. 실제 NNP 실행 환경에서 server/containers/health 세 명령이 성공했다. `id`, 추가 인자, `health; id`, 빈 명령, SFTP는 종료 64, 포워딩은 255, 임의 sudo id는 1로 거부됐다. sudoers의 visudo 검증도 통과했다.

새 MM 토큰 3개를 edo2의 비공개 설정으로 전송하는 작업은 자동 승인 검토에서 구체적 자격 증명 전송 승인 부족으로 거절됐다. 사용자가 토큰 3개·edo2 주소·비공개 설정 저장을 명시 승인한 뒤 전송했다. 토큰은 채팅·저장소·로그에 출력하지 않았다. 기존 edo1 토큰·채널 제한 보존과 6개 명령 후보 검증을 완료했다. 보호된 `/var/backups/edo-check/S15P31E102-133/`에 코드·설정·unit을 함께 백업하고 묶음 교체·daemon-reload·중계 기동·healthz 성공을 확인했다. 설정 권한은 root:edo-check 640이다. 임시 로컬·서버 토큰 파일과 후보 설정 사본은 성공 확인 후 제거했다.

실제 보고에서 systemd 시각의 이모지 변환을 발견해 시각을 inline code로 감싸고 회귀 테스트를 추가했다. 최종 중계만 재기동하고 새 공개 health 보고의 DOM·화면에서 `09:00:00`이 그대로 읽히는 것을 확인했다. 최종 운영 SHA-256은 relay `332961d305a6fcb3b0d7d4a08ba40d2451f2697a6ba081717dfbcc880cfeb705`, edo2 collector `d1710c1b4d046d293903d3cbae6cff2b4cc5e45655fd04f1f12da50e26bf23d6`이다. edo1 collector·앱 컨테이너·백업 작업·방화벽은 변경하지 않았다.

복구 시 같은 백업의 relay.py.before·relay.json.before·edo-check.service.before를 원래 경로와 소유권·권한으로 함께 복원한 뒤 daemon-reload·중계 시작·healthz를 확인한다. 신규 토큰이 없는 이전 설정으로 돌아가면 edo2 명령은 거부된다. 새 수집 계정·키만 회수해 edo2 점검 접근을 별도로 중단할 수도 있다.
