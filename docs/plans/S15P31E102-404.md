### U1 대상 목록 만들기

- 내용: 공개 곡 목록·상세 API로 단소 id 5~50의 제목·판본·출처·`score_version`·악보를 읽는다. 제목이 같은 곡을 D-4로 정리하고, AI 평가 4곡(id 1~4)과 제목이 겹치는 곡도 표시한다. 곡마다 시김새 수, 박 단위, 장단 유무를 센다.
- 수락: 대상·제외 목록과 이유가 이 문서에 표로 있다. 대상 곡 수가 확정된다.
- 검증: API로 읽은 곡 수가 46개이고, 대상과 제외를 합치면 46개다.
- 사용자 시간: 판본 겹침이 애매한 곡만 확인(10분).

### U2 원본 확보 (사용자 작업)

- 내용: 대상 곡의 원본 JGB와 PDF를 내려받는다. 노션 jgb 모음의 단소 46개(v2)와, 곡마다 원본 PDF 쪽수와 올린 사람을 함께 적는다.
- 수락: 대상 곡마다 JGB와 PDF가 있다. 운영 `provenance.jgbSha256`과 같은 파일인지 표시한다(달라도 U3 내용 대조로 판단).
- 막히면: 원본이 없는 곡은 멈추고 사용자와 정한다.

### U3 정답 등록과 운영 대조

- 내용: 곡마다 `data/annotations/scores/<원본 ID>/<제목>_단소.jgb.json`과 `.review.json`을 만든다. 원본 ID는 기존 이름(`ngc-standard-2022-p<쪽>`, `school-textbook-danso-p<쪽>`)을 따른다. 변환 결과를 운영 악보와 D-5 필드로 비교한다.
- 수락: 대상 곡 모두 운영 악보와 D-5 필드가 같거나, 다른 곡은 차이를 기록하고 D-7로 처리한다.
- 검증: `python -m unittest discover -s data/tests -p "test_*.py" -v`(SoundFile이 있는 환경). 테스트의 서비스 단소 정답 목록에 새 원본 ID를 넣는다.

### U3a 시김새 있는 단소 곡의 변환 확인

- 내용: 시김새가 있는 곡을 하나 골라 변환기(`score_data.py`)가 시김새를 운영 악보와 같은 위치·표현으로 남기는지 먼저 확인한다(403 취타 고급처럼 별도 음으로 바뀌는 경우가 있는지).
- 수락: 시김새 있는 곡 하나가 운영과 같다. 다르면 나머지 시김새 곡을 일괄 처리하기 전에 사용자와 처리 방식을 정한다.

### U4 사람 검수 (사지한)

- 내용: 대상 곡의 검수 화면을 한꺼번에 만든다. 먼저 D-6 숨표 규칙을 단소 원본 2곡으로 확인하고, 나머지에 일괄 적용한 뒤 사용자가 율명·숨표를 확인한다. 숨표 위치는 번호 붙인 원본 그림으로 확인받고, 확인자와 날짜를 검토 기록에 남긴다.
- 수락: 대상 곡 모두 `reviewed`, 숨표 확인 기록이 있다. 검수 뒤에도 운영 악보와 D-5 필드가 같다.
- 사용자 시간: 곡마다 5~10분. 40곡이면 4~7시간이라 2~3번에 나눠 한다.

### U5 단소 채점 계획과 격리 DB 확인

- 내용: `infra/catalog/scoring-plans/danso.json`을 만든다. `currentSha256`은 API 악보, `breathEventIds`는 정답, `targetSha256`은 도구의 `patch` 결과로 구한다. 곡과 정답의 짝을 테스트로 고정한다.
- 수락: 폐기용 MySQL 8.4 컨테이너에서 읽기 실행이 대상 곡 대기, `--apply` 뒤 모두 채점 켜짐·숨표 일치, 재실행 0건, 실행 사이 한 곡을 바꾸면 쓰기 전에 멈추고 일부만 바뀌지 않는다.
- 검증: `python -m unittest discover -s infra/catalog -p "test_*.py" -v`.
- 위험: 중간. 계획 값이 틀리면 운영 실행이 멈추지만 쓰지는 않는다.

### U6 독립 검토

- 수락: 지적을 재현해 확인하고, 고칠 것은 고친다.
