# 웹 마이페이지 첫 진입 글꼴 준비 비용 줄이기

2026-11-15 사용자가 Push·MR·병합을 요청해 `develop` 통합과 MR 병합까지 범위를 확장했다. `origin/develop` `6ebd0b8fb6fa4f902acd4f4a71f87d626e58ca55`를 통합하면서 문서 목록 충돌은 양쪽 링크를 보존해 해결했다. 홈 스크롤 복귀 변경과 글꼴 준비 호출이 함께 유지됨을 확인했다. 이번 통합은 정적 대조·충돌 표식·공백 검사로 확인하며 전체 빌드·타이밍 재측정은 반복하지 않는다.

2026-11-15 사용자는 홈 진입 직후 준비를 시작하는 개선을 제안하고 빌드에 많은 시간을 쓰지 않도록 요청했다. 시작 시점을 홈 진입으로 앞당기고 첫 프레임 뒤 유휴 시간마다 등록한다. 기존 펼침 조건과 고정 200ms 대기를 제거한다. 글꼴·굵기 순서·화면 이탈 취소·미지원 브라우저 경로를 유지한다. 이번 변경은 호출 관계와 expect/actual 시그니처, 차이·공백을 정적으로 확인한다. 이전 테스트 결과는 이전 코드의 결과이며 변경된 시작 시점의 런타임·성능 확인은 미실행이다.

정적 확인에서 공통 선언과 Android·iOS·웹 구현의 무인자 시그니처, 홈 진입 호출 1곳, 화면 이탈 취소를 확인했고 공백 검사를 통과했다. 새 빌드·전체 테스트·성능 재측정은 수행하지 않았다. 실제 홈 첫 표시와 입력 반응의 영향은 미확인이다.

2026-11-15 사용자는 기존 속도 개선과 관측된 입력 대기 120ms·71ms를 확인한 뒤 사전 등록 적용을 명시적으로 요청했다. 이번 적용은 이 트레이드오프를 수용한 결정으로 앞의 미채택 판정을 대체한다. 기존 생산 빌드와 실제 UI 실행을 통과했던 동일 구현을 복원하고 `coco-build`로 빌드·회귀 확인 및 작업 단위 커밋까지 수행한다.

앞선 구현은 홈이 완전히 펼쳐진 뒤 다음 프레임과 200ms를 기다리고 유휴 시간마다 Bold·SemiBold·Regular를 준비한다. 화면 이탈 시 대기 콜백을 취소한다. iOS·Android 구현은 아무 작업을 수행하지 않는다. 기대한 사전 등록 방식을 그대로 적용했으며, 입력 대기 관측값을 수용하는 선택이 기존 채택 기준을 대체했다.

## 재현과 관측 지점

2026-11-15 최초 채택 검증에서 사전 등록 중 실제 입력 차단이 119.98ms와 70.68ms로 관측됐다. 당시 미채택 판정은 이후 사용자의 명시적 적용 요청으로 대체됐다. 관측 근거는 [사전 등록 채택 검증 결과](#사전-등록-채택-검증-결과)에 보존한다.

1. 같은 Gradle·JDK에서 원본과 후보를 `frontend`의 `gradlew.bat :webApp:wasmJsBrowserDistribution`으로 빌드한다. 정적 자산만 바꾸는 실험은 같은 빌드를 재사용한다. 배포용 파일을 같은 루프백 서버 설정과 MIME으로 제공하고 외부 네트워크를 차단한다. Windows 헤드리스 Chrome 1280×900, DPR 1, 동작 줄이기 설정에서 테스트마다 새 브라우저 컨텍스트를 사용한다.
2. 루프백에만 로그인 완료 상태를 심고 홈을 연다. 회원·악기·진도·내 악보·REC-05는 고정 응답을 사용한다. 최근 기록은 사용자 악보 제목과 점수 92, 주간 횟수 4를 반환한다. 닉네임과 악보 제목은 KS X 1001 밖의 한글과 일반 한글을 포함한다.
3. 홈의 CTA와 펼치기 버튼이 픽셀로 처음 표시된 프레임을 받으면 실제 펼치기 입력을 즉시 보낸다. 탐색 시작 → 홈 첫 표시, 입력 전송 예약·호출 → 처리(`pointerdown`) → 홈의 첫 픽셀 반응을 따로 잰다. 입력을 보내기까지 걸린 캡처 전송 지연도 기록한다. 빠른 진입에서는 펼친 뒤 마이페이지 버튼이 보이고 입력 가능한 첫 프레임에서 실제 클릭을 보내며, 이때 REC-05가 완료되지 않았으면 따로 표시한다.
4. 주 비교에서는 버튼이 처음 표시된 뒤 750ms가 지나고 홈 선조회가 끝난 상태에서 누른다. 홈으로 돌아와 30초 안에 재진입한다. HTTP 캐시를 끄고 최초 홈부터 두 번째 마이페이지 안정화까지 요청 시작·완료를 연속 수집한다.
5. 각 진입에서 실제 점수 숫자 및 ‘점’이 모두 보이는 첫 캡처와 둘 중 하나라도 없던 직전 캡처를 각각 입력 시점 기준으로 환산한다. 원본의 마지막 미표시 하한에서 후보의 첫 완성 상한을 빼 쌍별 보수적 개선 하한을 구한다. 접근성 이름 ‘92점’ 관측 시각은 픽셀과 분리한다. 화면이나 상태를 임의로 설정해 통과시키지 않는다.

## 비교 순서와 채택 기준

- 동일 조건 예열 1회씩을 제외하고, 원본→후보와 후보→원본을 번갈아 주 비교 6쌍 및 빠른 진입 6쌍을 측정한다. 각 측정의 중앙값·최솟값·최댓값과 쌍별 차이, 캡처 간격, 시간 초과를 남긴다. 후보에만 발생한 시간 초과·오류는 탈락으로 집계한다. 양쪽 모두에 영향을 준 계측 실패가 있으면 이유를 남기고 그 쌍을 다시 잰다.
- 750ms 및 선조회 완료 조건의 **보수적 개선 하한 중앙값 ≥32ms, 개선 하한이 양수인 쌍 ≥5/6**일 때만 채택한다. 관측된 상한의 중앙값도 함께 보고한다. 양쪽 캡처 간격 합이 33.4ms를 넘는 쌍이 2개 이상이고 캡처 간격 때문에 판정이 달라지면, 캡처 빈도를 높여 한 번만 6쌍 재측정한다. 같은 빈도에서도 판정 불가면 보류한다.
- 홈 첫 표시와 재진입은 후보의 쌍별 중앙값 지연이 16.7ms 이하여야 한다. 첫 펼치기 입력 발행부터 픽셀 반응까지 및 빠른 마이페이지 클릭 발행부터 완성 점수까지의 지연은 각각 쌍별 중앙값 32ms 이하여야 한다. 홈 첫 표시 변동 때문에 16.7ms 한계의 어느 쪽인지 불명확하면 같은 설정으로 6쌍을 한 번 추가하고 전체를 합산해 판단한다. 빠른 클릭에 선조회 미완료가 섞이면 완료/미완료를 분리해 보여 주며 그 표본을 주 비교에 넣지 않는다.
- 홈이 펼쳐진 뒤 200ms를 기다려 글꼴을 등록하는 후보가 주 비교를 통과하면, 같은 버튼의 픽셀 확인 시점에 200·275·350ms를 더한 예약 시각에 각각 원본/후보를 한 쌍씩 비교한다. 예약→발행→`pointerdown`→완성 픽셀을 분리한다. 예약부터 완성까지의 후보 지연이 쌍별 중앙값 32ms를 넘거나, 등록이 입력을 50ms 이상 더 막은 구간이 확인되면 채택하지 않는다. 첫 진단의 캡처가 실제 등록 콜백과 겹치지 않으면 트레이스에서 확인한 예약 구간을 기준으로 세 쌍을 한 번 더 잰다. 추가 진단은 먼저 잰 표본이나 기준을 대체하지 않는다. 주 비교 미달이면 이 별도 진단은 생략한다.
- 닉네임·마이페이지 카드의 사용자 악보 제목·내 악보 목록 제목에서 드문 한글이 원본처럼 보이고, 카드의 점수·단위 및 글꼴 굵기와 접근성 이름 ‘92점’ 한 덩어리가 유지되어야 한다. 주 비교에서 최초 클릭 전 완료된 REC-05 200 한 건, 이후 REC-05 0건, 전 구간 REC-02 0건, 두 진입의 같은 기록을 확인한다. 글꼴 파일이나 연결이 바뀌면 실제 요청한 각 굵기의 글꼴 cmap 및 모양·폭·힌팅·조합·메타데이터 보존을 확인한다.
- 원본/후보에 863 실험용 축소 글꼴을 적용하지 않는다. 후보는 기존 글꼴을 무손실로 싸서 Skia에 전달하는 바이트를 줄이는 방법(WOFF1, 글리프 테이블 변환 없는 WOFF2)과, 원본 파일 그대로 홈을 펼친 뒤 200ms 후 유휴 시간마다 굵기 하나씩 등록하는 방법을 비교한다. 이전 운영 수치는 가설에만 사용한다. 결과와 기각 이유를 이 문서에 남기고 에이전트가 만든 실행 자료만 정리한다.

## 1차 실험과 후속 재평가

750ms 시나리오에서 원본 TTF 사전 등록의 완성 점수 표시 상한 중앙값은 226.9→163.3ms, 쌍별 보수적 개선 하한 중앙값은 53.7ms였고 5/6쌍에서 개선됐다. 최초에는 홈 첫 펼치기의 +47.7ms와 200~350ms 진단의 +33.3ms를 근거로 적용을 보류했다. 후속 동일 바이너리 A/A·A/B에서 첫 펼치기 지연은 재현되지 않았고 실제 글꼴 등록은 첫 반응 뒤에 시작했다. 첫 펼치기를 사전 등록의 성능 회귀로 본 판단을 정정한다. 사전 등록은 재검토 대상으로 남긴다. WOFF1·WOFF2와 후속 섹션별 LazyColumn은 반복 개선 기준을 충족하지 않았다. 실험 제품 코드는 원복하고 원본 TTF를 유지한다. 후속 측정과 한계는 아래 기록을 따른다.

200~350ms 진단에서 예약→완성의 쌍별 지연 중앙값은 **+33.3ms**로 32ms 한계를 넘었다. 세 표본에서 첫 유휴 콜백 요청은 버튼 픽셀 뒤 491.5~539.5ms에 나왔고 마이페이지 이동으로 취소됐다. 따라서 이 세 표본의 지연을 글꼴 등록이 직접 일으켰다고 볼 수 없다. 추가 진단 575ms 표본에서는 버튼 픽셀 뒤 566.2ms에 시작한 39.5ms짜리 `FireIdleCallback`이 클릭 발행 시점을 가로질렀고, 발행→`pointerdown`이 2.1→24.4ms였다. 이 표본에서 예약→완성은 같은 175.0ms였다. 525ms 표본에서는 47.0ms짜리 콜백이 클릭 전에 끝났다. 이 구간의 원인 확인은 표본 세 쌍에 한정된다. 두 진단의 완성 직전 캡처 간격은 각각 8.3ms, 8.3~16.8ms였다.

### 글꼴·접근성·REC-05 회귀 확인

- 네 조건 모두 Regular 400, SemiBold 600, Bold 700의 세 리소스를 실제 요청했다. 각 굵기의 유니코드 cmap 12,224개(현대 한글 완성 음절 11,172개 전체)와 개별 cmap 매핑이 일치했다. WOFF1은 압축 해제 후 모든 SFNT 테이블 바이트와 체크섬이 같다. WOFF2는 비어 있는 DSIG 헤더를 제거하고 head의 체크섬 조정값과 무손실 압축 표시 비트만 바꿨으며 나머지 테이블은 동일하다. 글리프 윤곽·폭·힌팅·조합·이름 메타데이터를 그대로 유지했다. 사전 등록 빌드는 세 TTF의 SHA-256이 원본과 동일했다.
- 원본과 각 후보에서 닉네임 ‘똠뷁 닉넴’, 마이페이지 최근 연주와 내 악보의 ‘쀍힣 사용자 악보’, ‘92’·‘점’, ‘이번 주 4회 연습’을 확인했다. 첫 진입·재진입의 프로필과 카드, 내 악보 제목 행의 원본과 후보 PNG 픽셀이 일치했다. 접근성 표시의 점수 이름은 두 진입 모두 ‘92점’ 한 덩어리였다. 첫 진입에서는 Chrome 접근성 트리의 버튼 이름 1개, 재진입에서는 같은 접근성 DOM 노드와 카드 문구를 확인했다.

### 등록 중 실제 입력 대기

총 6쌍을 AB/BA로 시도했다. 아래는 각 후보의 세 번째 유휴 콜백과 실제 마이페이지 입력이다. 단위 ms이며 입력은 실제 발행 시각이다. ‘등록 잔여’는 발행부터 해당 등록 콜백 종료까지의 구간이다.

| 실행 | 목표 간격 | 등록 작업 길이 | 시작 뒤 실제 발행 | 발행 → pointerdown | 등록 잔여 | 실제 겹침 |
| --- | --- | --- | --- | --- | --- | --- |
| 예열 | 15 | 41.70 | 15.57 | 26.39 | 26.12 | 예 |
| 1 | 5 | 58.72 | 14.48 | 44.56 | 44.24 | 예 |
| 2 | 15 | 39.35 | 147.13 | 8.10 | 0 | 아니요 |
| 3 | 25 | 41.36 | 31.15 | 10.52 | 10.21 | 예 |
| 4 | 5 | **134.10** | 14.12 | **120.48** | **119.98** | **예** |
| 5 | 15 | 0.58 | 22.87 | 2.83 | 0 | 아니요 |
| 6 | 25 | **102.18** | 31.50 | **71.14** | **70.68** | **예** |

- 실행 4는 REC-05 200이 클릭보다 873.16ms 먼저 완료됐고, 이후 추가 REC-05·REC-02가 없었다. 첫 진입과 재진입의 `92점` 버튼은 각각 1개였다. 입력은 등록 시작 뒤 14.12ms에 발행됐으며 등록이 끝난 지 0.49ms 뒤에 처리됐다. 선조회 성공 상태에서도 등록 작업의 119.98ms 잔여 구간이 입력을 직접 차단했다.
- 실행 6은 등록 종료 0.46ms 뒤에 입력이 처리됐다. 이 실행의 최초 선조회는 첫 등록 콜백 시작보다 2860.42ms 앞서 취소됐고, 마이페이지에서 재요청했다. 카드·캐시 조건을 충족한 비교에는 사용할 수 없다. 실제 등록 구간의 입력 차단 70.68ms는 별도 안전성 관찰로 남긴다.
- 완료된 원본의 입력 발행→pointerdown은 1.60~3.73ms였고, 실제 겹침을 만족한 완전한 쌍은 실행 1·3의 2쌍이었다. 두 쌍의 추가 입력 대기는 42.78ms와 8.60ms였다. 실행 4는 상대 원본의 선조회가 취소되어 쌍별 차이를 계산하지 않았다. 실제 등록 잔여 구간 119.98ms는 직접 관측한 차단 시간이다.
- 실행 2는 외부 측정기 발행이 늦어 등록 구간을 놓쳤고, 실행 5는 등록 작업이 이미 캐시된 짧은 경로였다. 겹침 성공으로 집계하지 않았다.
- 실행 4의 원본은 선조회 취소로 사전 조건을 충족하지 못했다. 실행 6의 원본은 최초 홈 픽셀 포착에 실패했다. 따라서 6쌍 전체의 통계적 성능 판정은 미완료이며 완전한 결과 쌍은 4개다. 실패·추가 요청·겹침 실패를 포함해 기록했다.

### 판정과 확인 범위

- **입력 안전성은 실패다.** 성공한 선조회·기록 재사용 상태의 실행 4에서 등록 자체가 입력을 119.98ms 막았고, 기존 50ms 한계를 넘었다. 유휴 시간에 작업을 시작해도 한 굵기의 동기 등록을 실행 중간에 양보할 수 없다는 제약이 실제 입력에서 드러났다.
- 계획의 안전성 통과 조건에 도달하지 않아 750ms 정상 진입 6쌍과 가장 빠른 진입 6쌍의 후속 채택 비교를 진행하지 않았다. 기존 53.7ms 개선을 이번 코드의 재현된 성능 향상으로 올리지 않는다.
- 완전한 결과 쌍 4개의 첫 진입·재진입 전체 PNG는 각 원본/후보 간 일치했다. 닉네임 `똠뷁 닉넴`, 사용자 악보 제목 `쀍힣 사용자 악보`, 점수·단위·주간 4회와 접근성 `92점`을 확인했다. 이 관찰은 전체 시나리오·실기기 검증 완료를 의미하지 않는다.
- 이번 실행은 Windows Chrome의 합성 입력·고정 응답 조건이다. Android/iOS·다른 브라우저·운영 서버에서 실행하지 않았다. 제품 변경을 남기기 위한 추가 회귀 검사와 정식 리뷰 단계에는 진행하지 않았다.
- 사용자가 요청한 조건부 적용의 실제 선택은 미채택이다. 입력 차단 문제가 확인돼 실패한 제품 변경을 원복하고 재현 조건·실패 근거를 이 문서에 남긴다. S15P31E102-872의 담당자는 우동균이며 Story 322 연결과 기존 진행 중 상태를 유지한다.
