### 근거(조사 결과)

- 어느 지원 방식이든 실시간 음높이(`pitchReadings`·`level`·`captureBoundary`)를 위해 브라우저에서 AudioWorklet으로 PCM을 받아야 한다. PCM이 이미 있으므로 WAV가 가장 단순하다.
- 16kHz·모노·16bit WAV는 600초에 19,200,044바이트로 20MiB(20,971,520) 한도 안이다. AI는 어차피 16kHz 모노 PCM16으로 디코딩한다(`ai/src/ai_service/pipelines/audio.py:24-55`). 따라서 16kHz 파일이 채점 입력의 품질을 떨어뜨리지 않는다.
- Chrome MediaRecorder WebM은 Duration 요소가 없어 ffprobe가 길이를 못 읽으면 현재 검사에서 422가 된다. 그래서 (a)도 서버 변환이 필수다.
- 저장 녹음 재생 서명 URL이 `audio/mp4`로 고정이다(`backend/.../config/OpenApiContracts.kt:207`, `LocalRecordingReadController.kt:23`). 저장 키도 `.m4a`다(`UploadRecording.kt:42`). WAV를 그대로 저장하면 재생·AI·보관 규칙이 흔들리므로 서버가 m4a로 바꿔 저장한다.
- 백엔드 실행 이미지에 ffmpeg가 이미 있다(`backend/Dockerfile:16`, `ffmpeg=7:8.0.1-3ubuntu2`). 이 Mac에는 Homebrew ffmpeg 8.1.2가 PATH에 있다.
- 브라우저 지원 출처: [caniuse AudioEncoder](https://caniuse.com/mdn-api_audioencoder), [MDN Codec selection](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API/Codec_selection), [Chromium MP4 MediaRecorder Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/p1OMVj1FrMI), [Mozilla bug 1631143](https://bugzilla.mozilla.org/show_bug.cgi?id=1631143). 버전 숫자 일부는 2차 자료 기준이다. (b)를 고르면 구현 시 `AudioEncoder.isConfigSupported()`로 확인한다.

## 구현 단계: (c) WAV + 서버 변환(선택됨)

순서는 백엔드 → 공통 계약 → 웹 구현 → 문서 → 검증이다. 백엔드와 프론트는 서로 기다리지 않고 진행할 수 있다.

### 1. 백엔드: WAV를 받아 m4a로 변환 — S15P31E102-1272로 분리, 구현·검증함

- 서버는 WAV 컨테이너의 `pcm_s16le`을 받는다. 업로드 WAV의 크기(20MiB)·길이(1ms 이상 601초 미만)를 먼저 검사하고, ffmpeg로 모노 AAC 64kbps m4a로 바꾼 뒤 변환본을 다시 검사해 변환본과 그 메타데이터로 저장한다. 변환 실패는 415, ffmpeg 실행 실패·30초 초과는 500이다.
- 웹이 지킬 계약: multipart 파트 `audio`에 16kHz·모노·PCM16 WAV를 올린다. 파일 이름·MIME은 판정에 쓰지 않지만 `recording.wav`·`audio/wav`로 보낸다. 10분 WAV는 헤더 44바이트를 더해 19,200,044바이트로 20MiB 안이다.
- 자세한 변경·검증·Notion 수정안은 [1272 작업 기록](../S15P31E102-1272.md). 1272 MR은 1262 프런트보다 먼저 병합돼야 웹 업로드가 415를 받지 않는다.

### 2. 공통 계약(commonMain)

1. `AudioRecorder`에 `suspend fun prepare() {}`(기본 no-op)를 추가한다. 웹만 마이크(getUserMedia)·AudioContext·AudioWorklet 모듈을 비동기로 연다. `start()`·`stop()`은 동기식으로 유지한다. 웹은 준비가 끝난 뒤 `start()`에서 노드만 연결하므로 바로 시작하고, `stop()`은 메모리의 PCM으로 WAV를 만들어 즉시 돌려줄 수 있다. 이렇게 하면 Android·iOS 구현과 호출부 시그니처를 바꾸지 않는다.
    - 대안: `start()`·`stop()`을 `suspend`로 바꾸기. 호출부 3곳과 Android·iOS 구현·테스트 대역이 모두 바뀌어 충돌 범위가 크므로 추천하지 않는다.
2. 호출부의 `prepare()` 호출: `PracticeViewModel.runCountdown()`은 카운트다운 시작과 함께 준비를 시작하고 끝에서 기다린다(실패하면 `failRecording()`). `LearnPracticeViewModel.startListening()`은 `recorder.start()` 앞에서 부른다. `PitchStepNoteJudge.listen()`은 `scope.launch` 안에서 준비한 뒤 `start()`한다.
3. `RecordingFiles`에 `size(path): Long?`·`open(path): Source`를 추가하고, 기본 구현은 kotlinx-io 파일 시스템으로 둔다. `AppModule.kt:152`에서 `getOrNull<RecordingFiles>()`가 있으면 그 함수를 `HttpRecordingUploader`의 `fileSize`·`openFile`로 넘긴다.
4. `HttpRecordingUploader`: 경로가 `.wav`로 끝나면 `Content-Type: audio/wav`, `filename="recording.wav"`를 쓴다.
5. commonTest: 업로더의 WAV 헤더, `prepare()` 실패 시 평가가 시작되지 않는지(`RecordingSupportTest`·`PracticeDirectEvaluationTest` 대역 확장), WAV 바이트 생성 함수 단위 테스트.

### 3. 웹 구현(webMain)

1. `platform/audio/WebAudioRecorder.kt`: `prepare()`에서 `getUserMedia({audio: {echoCancellation:false, noiseSuppression:false, autoGainControl:false}})`, `AudioContext` 생성·`resume()`, AudioWorklet 모듈 등록(모듈 코드는 Blob URL 또는 `webApp/src/*/resources`의 정적 JS)을 한다. 워크릿은 128프레임 Float32 묶음을 `port.postMessage`로 보낸다.
    - `start()`: 소스→워크릿 연결, 버퍼 초기화, 세그먼트 1, `CaptureBoundary(sampleRate = context.sampleRate, monotonicNanos = performance.now 기반, timestampValid = true)`.
    - 수신 처리: 레벨(Android와 같은 피크→0..1 식), HOP마다 창을 잘라 `YinPitchEstimator`+`PitchConfirmation`으로 `PitchReading`을 발행한다(창 크기는 입력 샘플레이트에 비례, 48kHz면 약 2229/960). 파일용으로는 16kHz로 다운샘플(구간 평균 또는 선형 보간)해 `ShortArray` 버퍼에 쌓는다. 10분 상한은 부르는 쪽이 잰다.
    - `pause()`/`resume()`: 연결 해제와 새 세그먼트. `stop()`: 연결 해제, 트랙 정지, 16kHz WAV(44바이트 `RIFF` 헤더)를 만들어 `WebRecordingStore`에 `web-recording-<id>.wav` 키로 넣고 `RecordedAudio(key, size)`를 돌려준다. `cancel()`: 버퍼 폐기와 트랙 정지. `interrupted`: 트랙 `ended` 이벤트(장치 분리·권한 회수)면 true. `measuresLevel = true`.
2. `platform/permission/WebMicPermission.kt`: `request()`는 getUserMedia를 한 번 열고 닫아 성공 여부를 돌려준다. `isGranted()`는 마지막 결과 캐시이며, 가능하면 `navigator.permissions.query({name:'microphone'})`로 초기화한다(미지원 브라우저는 false). `NotAllowedError`면 `isPermanentlyDenied() = true`, `openSettings() = false`.
3. `platform/audio/WebRecordingFiles.kt` + `WebRecordingStore`(single): 메모리 `Map<String, ByteArray>`. 페이지를 새로 고치면 녹음이 사라지므로 `RecordingUploads`가 `Missing`으로 정리한다(단발 업로드). IndexedDB 보관은 후속 과제로 둔다.
4. webMain `PlatformModule.kt`: `factory<AudioRecorder>`, `single<MicPermission>`, `single<RecordingFiles>`, `single<WebRecordingStore>`를 등록한다.
5. 보안 컨텍스트: getUserMedia는 HTTPS 또는 localhost에서만 동작한다. 운영 웹이 HTTPS인지 1269(배포) 세션과 확인한다.

## 다른 선택지를 고를 때의 구현 단계

### (a) Opus + 서버 변환

1. 백엔드: 1번과 같지만 허용 형식이 `matroska,webm`/`ogg`(opus)와 Safari mp4(aac)다. 길이를 못 읽는 webm 때문에 길이 판정을 변환 **뒤**로 옮겨야 한다(검사 순서 표 변경).

### (b) 브라우저 AAC 인코딩

1. 서버 변경은 없다.
2. 웹: AudioWorklet PCM → `AudioEncoder({codec:'mp4a.40.2'})` → mp4 muxer(npm 의존성 추가, Wasm에서 JS 모듈 로딩 경로 필요)로 m4a를 만든다. `AudioEncoder.isConfigSupported()`가 false면 녹음기를 등록하지 않거나 준비 실패로 처리해 `recordingSupported=false`가 되게 한다.
3. Firefox·Linux Chrome·Safari 25 이하 사용자를 위해 아래 '미지원 안내'도 함께 필요하다.

### 미지원 유지

1. 홈·곡 정보·구간 고르기에서 웹이면 '연주 평가는 앱에서' 안내를 먼저 보이고 앱 설치 안내를 검토한다(현재 안내 문자열은 `practice_recording_unsupported`, `PracticePlayer.kt:334`).

3. 웹에서 효과 없는 '퍼펙트 스코어' 토글을 정리한다. 관련 파일은 `data/practice/PracticeSettingsStore.kt`, `feature/practice/component/PracticePanels.kt`·`PracticeSideDock.kt`·`PracticeHeaderParts.kt`, `feature/practice/LivePitchMark.kt`다(검색으로 찾은 후보이며 토글 위치는 미확인).

## 위험

- 업로드 계약(415 조건) 변경은 공유 계약의 의미 변경이라 BE 합의 전에는 1272를 병합하지 않는다. 1262 프런트는 1272 병합 뒤에 병합한다.
- AudioWorklet 메시지를 메인 스레드에서 처리하면서 Wasm으로 YIN을 계산하는 부하(48kHz 창 약 2229샘플, 초당 50회). 느리면 분석 창을 건너뛰고 `analysisAvailable=false`로 보낸다.
- 브라우저의 에코 제거·잡음 억제·자동 이득이 켜지면 악기 소리가 깎인다. 제약으로 끄지만 브라우저가 무시할 수 있다.
- 메모리 보관이라 업로드 실패 뒤 새로 고치면 녹음이 사라진다. 스펙에 웹 한계로 적는다.
- `requestAnalysis` 직접 진입 문제는 (c)에서도 남는다. 같은 Task에서 함께 고칠지 정해야 한다.
- 16kHz 파일은 기존 스펙의 '44.1kHz 또는 48kHz로 요청'(앱 녹음)과 다르다. 서버는 샘플레이트로 거부하지 않는다. 1272에서 스펙의 앱·웹 형식을 나눠 적었고, 웹 클라이언트 동작(샘플레이트·자동 정지)은 1262에서 스펙에 더한다.
- 모든 상한(ffprobe 10초 ×2, 변환 30초, 저장소 40초)이 겹치면 업로드가 Nginx 60초를 넘어 504가 될 수 있다. 웹 업로드 오류 처리는 앱과 같게 5xx 재전송 → 409 → 상태 조회를 따라야 한다.
