## 3. 웹에서 막혀 있던 이유

- 웹 구현이 처음부터 없었다. 483은 2026-11-06 `완료`로 바뀌었지만 그 Key의 커밋·브랜치·MR·문서는 없다. 명세의 "웹 우선 실연동 준비"(2026-10-29)는 같은 날 Android 우선 지시로 대체됐고, 이후 Android(App Links)와 iOS(서버 중계)만 구현됐다.
- 웹 DI에 `ExternalBrowser`·`IncomingLinks`·`OAuthRoute`가 없어 `OAuthViewModel`·`SocialLinkViewModel`·`WithdrawViewModel`이 바로 `Unsupported`가 됐다. 그런데 `socialProviders()`는 등록된 경로가 없으면 Android 기본 목록을 돌려줘 버튼은 보였다.
- 서버는 코드 변경 없이 웹을 받을 수 있다. 허용 목록이 환경변수(`AUTH_OAUTH_{KAKAO,GOOGLE,NAVER}_REDIRECT_URIS`)이고, 결속 쿠키 `oauth_flow_<제공자>`는 `Path=/api; HttpOnly; SameSite=Lax; Max-Age=600`이라 같은 탭 복귀 뒤 같은 출처 완료 POST에 실린다.

설계 메모

- 웹에 이름 없는 `SecureStore`를 등록하면 `ApiAuthRepository`·`LoginPreferences`도 그것을 받아 로그인 쿠키·자동 로그인 동작이 바뀐다. 그 영역은 S15P31E102-1264 범위라 이름 붙은 등록으로 분리했다. 1264가 이름 없는 저장소를 등록해도 시도 상태는 탭 저장소에 남는다(테스트로 고정).
- 주소창을 먼저 `/`로 바꾸는 이유: `styles.css`·`webApp.js`가 상대 경로라 `/auth/oauth/kakao/callback`에서는 `/auth/oauth/kakao/webApp.js`로 풀리고, Nginx SPA 대체가 HTML을 돌려줘 앱이 뜨지 않는다. 인가 코드도 주소창·방문 기록에 남지 않는다. Nginx 접근 기록은 `$uri`만 남겨 쿼리를 기록하지 않는다.

### 로컬 웹 확인(2026-11-24, 인앱 브라우저 Chromium)

`:webApp:wasmJsBrowserDevelopmentExecutableDistribution` 산출물을 작은 모의 서버(Nginx처럼 없는 경로에 `index.html`을 주는 SPA 대체 포함)로 `http://127.0.0.1:8093`에 띄웠다. 모의 서버의 start는 실제 서버처럼 `oauth_flow_<제공자>` 결속 쿠키(`HttpOnly; SameSite=Lax; Path=/api`)를 주고, 존재하지 않는 `https://provider.invalid/...`를 authorizationUrl로 돌려준다(실제 제공자에 닿지 않음). 완료 API는 state·목적·정확한 redirectUri·결속 쿠키를 검사한다. 제공자 복귀는 주소창에 복귀 주소를 직접 넣어 흉내 냈다.

| 경우 | 결과 |
| --- | --- |
| 시도 없이 `/auth/oauth/kakao/callback?code=…&state=…` 직접 열기 | 주소창이 `/`로 바뀌고 로그인 화면이 떴다. 받아 둔 주소는 꺼내져 지워지고 완료 요청은 없었다 |
| 로그인: 카카오 버튼 → 복귀 | start에 `redirectUri=http://127.0.0.1:8093/auth/oauth/kakao/callback`. 같은 탭이 제공자 주소로 이동했다. 복귀 뒤 완료 POST에 코드·같은 redirectUri·결속 쿠키가 실렸고(모의 서버 검사 통과) 홈으로 갔다. 시도 상태는 지워지고 주소창에 코드가 남지 않았다 |
| 연결(로그인 상태): 마이페이지 네이버 '연결' → 다른 state로 복귀 | 무시됐다. 완료 요청 없음, 시도 유지, "네이버 화면에서 계속해 주세요" 화면 |
| 연결: 올바른 state로 복귀 | 완료 POST(결속 쿠키 포함) 통과, "네이버 계정을 연결했어요." 알림 |
| 탈퇴 재인증: 네이버 시도를 카카오 경로로 복귀 | 거절됐다. 시도 삭제, 완료 요청 없음, "네이버 계정을 확인하지 못했어요. 처음부터 다시 시도해 주세요." |
| 탈퇴 재인증: 올바른 복귀 | 완료 POST(`WITHDRAW`, 결속 쿠키 포함) 통과 → 앱이 탈퇴 요청(`DELETE /api/users/me`)을 보냈다. 모의 서버가 일부러 거절해 실제 탈퇴는 없다 |
| 제공자 화면에서 브라우저 뒤로 가기 | **초안(`location.assign`)에서 결함**: 간편 로그인 화면(`#auth/oauth/Kakao`)이 다시 열려 곧바로 새 시도를 시작하고 제공자 화면으로 되돌아갔다. `location.replace`로 고쳤다(아래 재확인) |
| 연결을 마친 뒤 돌아가는 화면 | **초안에서 결함**: 복귀한 페이지의 화면 기록이 [홈 → 연결]이라 마이페이지 대신 홈으로 갔다. `OAuthReturnEffect`가 마이페이지를 먼저 깔도록 고쳤다(아래 재확인) |

고친 뒤 재확인(위 자동 테스트와 같은 커밋의 웹 빌드)

| 경우 | 결과 |
| --- | --- |
| 마이페이지 카카오 '연결' → 제공자 화면에서 뒤로 가기 | 마이페이지(`#my`)로 돌아왔다. 새 시작 요청은 없었다 |
| 로그인 화면 Google 버튼 → 제공자 화면에서 뒤로 가기 | 로그인 화면(`#auth/login`)으로 돌아왔다. 새 시작 요청은 없었다. 남은 시도는 다음 시작 때 지워진다 |
| 카카오 연결 → 올바른 복귀 | 완료 POST 통과 뒤 마이페이지(`#my`)로 돌아왔고 카카오가 '해제'(연결됨)로 바뀌었다 |
| Google 로그인 → 올바른 복귀 | 완료 POST 통과 뒤 홈으로 갔다. 이로써 카카오·네이버·Google 세 경로를 로컬에서 모두 지났다 |

관찰: Chromium의 미리 읽기(preload scanner)가 `<head>` 스크립트 실행 전에 `/auth/oauth/kakao/styles.css`·`/auth/oauth/kakao/eolssu-logo.webp`를 한 번씩 요청했다(SPA 대체로 HTML을 받음). 실제로 쓰인 것은 주소창을 바꾼 뒤의 `/styles.css`라 동작에는 영향이 없고, 쿼리(인가 코드)는 붙지 않는다.

확인하지 못한 것: 저장소를 막은 브라우저, Safari·Firefox, iOS 홈 화면 앱(단독 창), 실제 제공자 화면.

2. **운영 서버 `.env`에 같은 주소 추가(1263 MR 병합 전). 2026-11-24 10:24 KST 완료.** 사용자 요청으로 Claude가 edo1에서 반영했다. 백업은 `/opt/eolssu/.env.before-web-oauth-1263-20261124T012408Z`(root 0600)이고, 세 줄만 바뀌었으며(기존 Android·iOS 주소 유지), `config --quiet` 검사를 통과했다. 다음 develop 커밋의 백엔드 배포부터 적용된다. 아래는 다시 해야 할 때의 절차다. edo1에서 root 전용 백업을 만든 뒤 고친다.

## 9. 위험

- 콘솔·`.env` 반영 전에 배포하면 웹 간편 로그인은 제공자 오류(redirect_uri 불일치)나 서버 허용 목록 거절(`401 OAUTH_VERIFICATION_FAILED`)로 실패한다. 지금도 쓸 수 없는 기능이라 나빠지지는 않지만 화면에 "계정을 확인하지 못했어요" 계열 오류가 보인다.
- `index.html` 스크립트가 상대 경로 자원보다 뒤로 밀리면 콜백 페이지에서 웹 앱이 뜨지 않는다.
- iOS Safari에서 같은 탭 복귀는 1st-party 쿠키라 문제없을 것으로 보지만 실기기로 확인하지 않았다.
- 저장소를 막은 브라우저에서는 시도 상태가 남지 않아 복귀 뒤 첫 화면으로 돌아간다(오류 안내 없음). Android의 "시도 없음" 처리와 같다.
