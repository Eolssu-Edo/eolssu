## 변경

`frontend/shared/src/webMain/kotlin/com/ssafy/eolssu/platform/storage/SheetFilePicker.web.kt` 한 파일만 고쳤다.

- **바이트 직접 읽기:** `readAsDataURL` → 문자열 → `Base64.decode` 대신 `readAsArrayBuffer` → `Int8Array(...).toByteArray()`로 읽는다. 크기 검사(합계 > `SHEET_MAX_BYTES`면 `TooLarge`)는 읽기 전에 그대로 한다.
- **취소 대체 처리:**
  - `PickerDialog`가 창이 열려 결과를 기다리는지(`waiting`)와 대체 처리 Job을 가진다. `open()`은 `input.click()` 직전, `close()`는 `change`·화면 이탈 때 부른다. `cancel()`은 기다리는 중일 때만 `Cancelled`를 한 번 보낸다. `input`의 `cancel` 이벤트도 `cancel()`을 부른다.
  - `PageReturn`이 `window`의 `focus` 리스너를 앱 전체에서 한 번만 달고, 지금 열린 `PickerDialog`에만 알린다. 알림을 받으면 `CANCEL_FALLBACK_MS`(1,000ms) 뒤 `cancel()`을 예약한다. 그 전에 `change`·`cancel`이 오면 예약을 취소한다.
  - 대체 처리로 `Cancelled`를 보낸 뒤 늦게 온 `change`도 그대로 처리한다. ViewModel은 `picking = false` 상태에서 `Selected`를 받아도 정상 반영한다.
  - `visibilitychange`는 쓰지 않는다. `kotlinx-browser`의 `Document`에 `visibilityState`가 없어 숨김과 복귀를 구분할 수 없고, 모바일에서 고르는 중에 취소될 위험이 있다.
- **이 Mac에서 찾은 버그 수정:** Windows 초안의 `scope.launch { delay(CANCEL_FALLBACK_MS); cancel() }`에서 `cancel()`이 `PickerDialog.cancel()`이 아니라 launch 블록의 `CoroutineScope.cancel()`로 해석됐다. 그래서 1초 뒤 자기 Job만 취소하고 끝나 대체 처리가 전혀 동작하지 않았다. 컴파일은 통과하므로 브라우저 확인에서만 드러났다. `this@PickerDialog.cancel()`로 고치고 주석을 남겼다.

### 측정 (19MB PDF, 같은 기기·같은 브라우저)

| 항목 | develop 빌드 | 이 변경 |
| --- | --- | --- |
| 파일을 고른 뒤 메인 스레드가 막힌 긴 작업(3회) | 347·122·123ms | 128·84·88ms |
| 업로드 버튼을 누른 뒤 막힌 긴 작업(1회) | 543ms | 534ms |
| 업로드 직후 JS 힙(`performance.memory`) | 약 347MB | 약 347MB |

- 읽기는 매번 한 번의 긴 작업이었다. 처음 한 번은 둘 다 느렸고, 그 뒤에는 약 120ms에서 약 85ms로 줄었다.
- `toByteArray()`는 `kotlinx-browser` 0.5.0 Wasm 구현에서 `ByteArray(length) { this[it] }`처럼 한 바이트씩 JS를 거쳐 복사한다(klib 확인). 그래서 시간 단축은 크지 않다.
- 메모리 최고점은 재지 못했다. 계산상 Data URL 방식은 Base64 문자열(약 27MB)을 Kotlin 문자열로 바꾸고(UTF-16, 약 54MB) 잘라 낸 사본(약 54MB)을 더 만든 뒤 20MB로 디코드한다. 바이트 방식은 ArrayBuffer와 ByteArray(각 20MB)만 만든다. 이 값은 계산이며 측정값이 아니다.
- 업로드 직렬화는 develop과 이 변경 모두 약 0.53초 동안 메인 스레드를 막았다(1초 미만). 다만 힙이 업로드 직후 약 350MB까지 올라간다. Ktor 멀티파트 본문을 만들며 바이트 사본이 여러 번 생기는 것으로 보이며 원인은 확인하지 않았다.

## 위험

- `cancel`이 없는 브라우저가 파일 창을 열 때 window를 blur하지 않으면 `focus`도 오지 않아 대체 처리가 동작하지 않는다. 이때는 예전처럼 멈추고, 화면을 나갔다 오면 `SheetImportRoute`의 dispose가 상태를 풀어 준다.
- 대체 처리로 `Cancelled`를 보낸 뒤 1초 넘게 늦게 `change`가 오면(예: 클라우드 파일 내려받기), 읽는 동안 '파일 읽는 중' 대신 일반 상태로 보인다. 결과는 정상 반영된다.
- Kotlin/Wasm에서 같은 람다로 `removeEventListener`를 불러도 떼어지지 않을 수 있다는 점은 확인하지 않았다. 확인하지 않아도 안전하도록 전역 리스너 1개로 만들었다.
