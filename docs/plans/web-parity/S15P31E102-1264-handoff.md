## 3. 다섯 가지 문제와 처리

### 3.1 여러 탭에서 토큰 갱신이 겹친다 → 수정

- 원인: `HttpClients.kt`의 `TokenRefresher`는 탭 하나 안에서만 갱신을 합친다. 서버(`TokenRefreshService`)는 이미 회전된 리프레시 토큰이 다시 오면 그 회원의 토큰을 모두 폐기하므로, 두 탭이 같은 쿠키로 동시에 갱신하면 모든 기기가 로그아웃된다.
- 처리: 웹은 `SharedRefreshLock`(`WebRefreshLock`)으로 탭 사이에서도 한 번에 하나만 갱신한다. 순서는 탭 Mutex → 세대 확인 → 탭 간 잠금 → 세대 재확인 → 갱신 → 성공하면 세대 올림. 시작한 갱신은 부른 쪽이 취소돼도(화면 닫기, 다른 탭 계정 변경) 응답까지 받는다(`NonCancellable`). 중간에 끊으면 서버는 토큰을 바꿨는데 쿠키는 옛 토큰으로 남아 다음 갱신이 재사용으로 감지된다. 이 보호는 앱에도 같이 적용된다. 잠금을 기다리는 동안 다른 탭이 갱신했으면 다시 갱신하지 않고 새 쿠키로 원래 요청만 재전송한다. 세대는 localStorage `auth.refresh_generation`에 둔다.
- Web Locks가 없는 브라우저(보안 연결이 아닌 주소 포함)에서는 잠금 없이 실행해 지금 위험이 남는다.

### 3.2 자동 로그인을 끄면 새로고침할 때마다 로그아웃된다 → 수정

- 원인: `LoginPreferences.endSessionOnLaunch()`가 '프로세스당 1회'를 companion 변수로 판정했다. 웹은 새로고침·새 탭마다 Wasm 모듈이 새로 올라와 매번 새 실행이 됐다.
- 처리: 실행 범위를 `LaunchSession`으로 분리했다. 앱은 `ProcessLaunch`(기존 동작), 웹은 `BrowserLaunchSession`이다. 웹은 페이지를 열 때마다 만료 없는 표지 쿠키를 쓰고, 표지가 없던 페이지(브라우저를 새로 연 첫 페이지)만 새 실행으로 본다. 로그인 회원이 있을 때만 묻는 시점에 맡기지 않도록 웹 플랫폼 모듈을 만들 때 바로 만든다.
- 탭 A가 자동 로그인을 끄고 로그인해 남긴 표시를 탭 B가 따르면서 지우지 않도록, `LoginPreferences`의 회원 변경 리스너는 이 탭이 바꿨을 때만 돈다(`onChange(ownChangesOnly = true)`).

### 3.3 한 탭에서 계정을 바꾸면 다른 탭이 이전 계정 화면으로 새 계정 데이터를 다룬다 → 수정

- 원인: `SignedInMember`는 생성될 때 localStorage `auth.member_id`를 한 번만 읽는다. 다른 탭이 바꿔도 세대가 그대로라 `AccountWork`·`screenScope`의 계정 격리가 동작하지 않았다.
- 처리: `WebTabSignIns`가 `storage` 이벤트마다 `auth.member_id`를 다시 읽어, 이 탭의 회원과 다르면 `SignedInMember.follow`로 세대를 올려 진행 중 작업을 버리고 `#경로` 없는 주소로 페이지를 다시 연다(`location.replace`). 이때는 저장하지 않은 변경의 떠나기 확인(1265)을 건너뛴다. `follow`는 저장소를 다시 쓰지 않는다. 값을 바꾼 탭에는 이벤트가 오지 않아 새로고침이 되풀이되지 않는다.

### 3.4 오프라인에서 로그아웃하면 쿠키가 남는다 → 수정

- 원인: 웹의 로그인 쿠키는 HttpOnly라 서버 응답(`Set-Cookie`)으로만 지워진다. sign-out이 서버에 닿지 못하면 쿠키가 남고 서버 토큰도 폐기되지 않는다.
- 처리: `ApiAuthRepository.logOut()`은 sign-out을 보내기 전에 localStorage `auth.pending_sign_out=true`를 남기고, 서버에 닿았을 때만(401 포함) 지운다. 연결 실패·시간 초과·5xx이거나 응답 전에 탭을 닫으면(공용 PC) 표시가 남는다. 401은 액세스 토큰이 만료돼 갱신까지 실패한 경우로, 갱신 실패 응답이 쿠키를 지운다. 앱 시작 때 `retrySignOut()`이 표시가 있으면 다시 보내고, 그사이 다시 로그인했으면 보내지 않고 표시만 지운다. 로그인은 재전송이 끝날 때까지 기다린다. 앱(Android·iOS)은 기기 쿠키를 직접 지우므로 표시를 읽지도 쓰지도 않는다.

### 3.5 '아이디 기억하기' 이메일이 localStorage에 평문으로 저장된다 → 의도 유지

- 2절 결정대로 바꾸지 않고 `LoginPreferences` KDoc에 이유를 남겼다.

| ② 자동 로그인 끔 | 통과. 끄고 로그인(`auth.end_session_on_launch=true`, 표지 쿠키 있음) → 새로고침·새 탭에서 유지, sign-out 없음 → 표지 쿠키를 지우고 새로고침(브라우저를 새로 연 상태 흉내) → sign-out 1회, 로그인 화면, 표지 다시 씀 | 통과(새로고침 유지, 표지 삭제 뒤 sign-out 1회, 다른 탭도 로그인 화면) |
| ③ 계정 전환 | 통과. A 마이페이지 로그아웃 → B가 2초 안에 새로 열려(`navigate`) 로그인 화면. A에서 계정 B로 로그인 → B가 새로 열려 홈, 마이페이지 닉네임 '계정B' | 통과(같은 결과) |
| ④ 오프라인 로그아웃 | 하지 않음(Chrome에서 확인) | 통과(최종 빌드). 모의 서버를 오프라인으로 두고 로그아웃 → 로그인 화면, `auth.pending_sign_out=true`, 쿠키(회원 101)가 실린 sign-out이 닿지 못함, 서버 토큰 유지. 다른 탭도 다시 열리며 시작 재전송을 시도했으나 닿지 못함 → 온라인으로 바꾸고 새로고침 → sign-out 재전송·처리, 표시 지움, 서버 액세스 토큰 0개. 오프라인 로그아웃 뒤 다시 로그인한 경우: 다른 탭이 시작할 때 표시만 지우고 sign-out을 보내지 않음, 새로고침 뒤에도 새 로그인 유지 |

- ①~③은 코드 검토 반영(갱신 취소 보호, 대기 표시를 보내기 전에 남김)과 1265 rebase 전 빌드로 확인했다. 두 수정은 ①~③의 경로를 바꾸지 않는다. ④는 최종 빌드로 확인했다.
- 미확인: Safari(Apple 이벤트 JavaScript나 원격 자동화를 켜야 조작할 수 있어 하지 않음), 실제 브라우저 종료(Cmd+Q) 뒤 자동 로그인 끔, 미저장 편집이 있는 탭에서 다른 탭 계정 변경 때 확인 창이 뜨지 않는지(건너뛰기 자체는 1265의 `BrowserBackInterceptorTest`가 검사), 운영 서버.

관찰
- 인앱 브라우저는 앞에 보이는 탭만 화면을 그린다. 배경 탭에서 다시 열린 페이지는 앞으로 가져와야 앱이 시작된다(Compose가 그리기 프레임을 기다림). 그래서 탭을 번갈아 앞으로 가져와 확인했다. 실제 Chrome의 확장 탭 묶음은 두 탭이 모두 보이는 상태였다.
- 첫 시도는 갱신 지연(2·6초)이 탭 전환 시간보다 짧아 두 탭이 겹치지 않았다. 20초로 늘려 겹침을 만들었다.

## 6. 남은 일

- Safari 26.2(macOS)와 iPhone Safari에서 ①~④를 한 번 확인한다. 로컬 모의 서버가 없으면 운영에서 계정 두 개로 ③과 자동 로그인 끔(Safari를 종료했다 열기)만 봐도 된다.
- 운영 웹 배포 뒤 한 번: 탭 두 개로 로그아웃·다른 계정 로그인, 자동 로그인 끄고 브라우저 종료(Cmd+Q) 뒤 다시 열기.
- 미저장 편집이 있는 탭에서 다른 탭이 로그아웃할 때 확인 창 없이 다시 열리는지 확인한다.
- 후속 후보(8절): 로그인·로그아웃의 탭 간 직렬화, 서버 세션 쿠키로 자동 로그인 끔 정확히 하기(BE), `online` 이벤트 재전송.

## 8. 위험

- Web Locks는 보안 컨텍스트(https·localhost)에서만 쓸 수 있다. 없으면 잠금 없이 실행되어 3.1 위험이 남는다. 최신 주요 브라우저는 지원한다.
- 브라우저의 '이전 세션 복원'(Chrome '중단한 위치에서 계속하기', Safari 창 복원)은 세션 쿠키도 되살리므로 그때는 자동 로그인 끔이 지켜지지 않는다. macOS에서는 창을 모두 닫아도 브라우저를 종료(Cmd+Q)하지 않으면 세션 쿠키가 남는다. 완전한 해결은 서버 세션 쿠키(BE 변경)이며 후속 후보다.
- 다른 탭의 계정 변경 때 바로 다시 열므로 그 탭의 저장하지 않은 작업이 사라진다. 사용자 결정으로 수용했다.
- 새 계정 쿠키가 설정된 순간부터 `storage` 이벤트가 도착하기 전까지의 아주 짧은 구간에는 이전 화면의 요청이 새 쿠키로 나갈 수 있다. 완전히 막으려면 요청마다 localStorage의 회원과 비교해야 한다.
- 오프라인 로그아웃 뒤 sign-out이 닿기 전에 다시 로그인하면 재전송을 보내지 않으므로, 이전 세션의 서버 토큰은 만료(리프레시 14일)까지 남는다. 브라우저 쿠키는 새 로그인 것으로 덮여 이전 토큰을 더 쓰지 않는다.
- 대기 중 로그아웃의 401 판정: 갱신 요청이 503이면 sign-out 401이 와도 쿠키가 남을 수 있는데, 닿은 것으로 보고 표시를 지운다. 서버 장애 중 로그아웃이 겹친 드문 경우다.
- 로그인·로그아웃·재전송·갱신은 탭 사이에서 직렬화하지 않는다(갱신끼리만 잠금). 예: 대기 중 로그아웃이 있는 상태에서 새 탭의 시작 재전송과 다른 탭의 로그인이 거의 동시에 일어나 sign-out 응답이 늦게 오면, 그 쿠키 삭제가 새 로그인 쿠키를 지워 '로그인 만료'가 된다. 드문 경우라 이번에는 고치지 않았다(2026-11-24 코드 검토에서 확인). 막으려면 `ApiAuthRepository`의 로그인·로그아웃·재전송도 같은 탭 간 잠금 안에서 하고 로그인 성공 때 세대를 올린다.
- `onChange`의 첫 인자로 `ownChangesOnly`(기본값 있음)가 생겼다. 다른 작업이 `onChange(::f)`처럼 위치 인자로 부르면 컴파일 오류가 난다. 지금 develop의 호출은 모두 뒤따르는 람다다.
