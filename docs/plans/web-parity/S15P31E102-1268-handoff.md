## 1. 목표와 완료 조건

Compose의 `horizontalScroll`·`LazyRow`는 손가락 밀기만 끌기로 받고 마우스 끌기는 무시한다(`PointerType.Mouse` 제외). 그래서 데스크톱 웹에서는 정간보·편집 패널을 Shift+휠이나 트랙패드 가로 밀기로만 넘길 수 있었다. 또 연습 화면은 창 너비로만 배치를 골라, 휴대폰 가로 웹 창(높이 300~430dp)에서 악보·버튼이 잘렸다.

Jira 완료 조건:
1. 데스크톱 웹에서 마우스로 끌어 정간보·편집 패널을 가로로 넘길 수 있다.
2. 휴대폰 웹 가로 화면에서 연습 화면이 잘리지 않는다.
3. Android 터치 스크롤 동작은 그대로다.
4. `:shared:compileKotlinWasmJs` 통과, 관련 commonTest 통과.

## 3. 변경

- `core/ui/component/MouseDragScroll.kt`(신규) `Modifier.mouseDragScroll(state, reverseDirection, enabled, onDragStart)`
  - `PointerEventPass.Initial`에서 마우스 왼쪽 단추 누름만 받는다. 손가락·펜과 오른쪽·가운데 단추는 건드리지 않아 Android·iOS 터치 스크롤은 그대로다.
  - 가로로 터치 슬롭을 넘으면 끌기를 시작하고, 세로로 먼저 넘으면 이번 끌기를 맡지 않는다(세로 스크롤 부모와 다투지 않게).
  - 끌기를 시작하면 `onDragStart`를 부르고 `stopScroll(MutatePriority.UserInput)`으로 진행 중인 스크롤(재생 따라가기)을 멈춘다. 끄는 동안 움직임을 소비해 안쪽 셀·자판 누름은 취소된다.
  - 놓을 때 `VelocityTracker` 속도로 `ScrollableDefaults.flingBehavior()` 관성을 준다. 놓는 순간도 속도 표본에 넣어 멈췄다 놓으면 관성이 없다. 속도가 마지막으로 끈 방향과 반대로 추정되면 관성을 주지 않는다(아래 검증의 표본 부족 사례).
  - `reverseDirection`은 오른쪽부터 읽는 `horizontalScroll(reverseScrolling = true)`용이다.
- 적용한 곳
  - `core/ui/score/JeongganboView.kt`: 악보 가로 스크롤(`reverseDirection = true`, `enabled = userScrollEnabled`, `onDragStart = onUserScroll`). 연습·결과·기록·비교·편집 악보에 모두 적용된다. 마우스 끌기는 `DragInteraction`을 내보내지 않으므로 재생 따라가기 멈춤은 `onDragStart`로 직접 알린다.
  - `feature/song/edit/component/CommonStaffEditor.kt`: 오선 편집 `LazyRow`.
  - `feature/song/edit/component/EditInputPanel.kt`: 탭 줄, 율명 자판(좁은 패널), 붙인 시김새 줄(같은 `ScrollState`를 쓰도록 변수로 꺼냄), 시김새 자판.
  - `feature/song/component/SongSearchParts.kt`: 한 줄 난이도 칩(D4).
- 낮은 창(D1·D2)
  - `core/ui/adaptive/WindowLayout.kt`: `WindowBreakpoints.MediumMinHeight = 480.dp`(Material 3 Compact 높이 기준)와 `WindowLayout.isCompactHeight`를 더했다. 기존 `isShortHeight`(650dp 미만)는 그대로다.
  - `feature/practice/PracticeScreen.kt`: `compactHeight`(기본값 `currentWindowLayout().isCompactHeight`)면 너비로 고른 배치를 `LandscapeLayoutMinHeight`(650dp) 높이로 그리고 페이지를 `verticalScroll`로 감싼다. 배치 안 스캐폴드의 스낵바 대신 창 아래에 `EolssuSnackbarHost`를 따로 띄운다. 카운트다운·불러오기 막·설정 시트·확인 창은 페이지 밖이라 창 기준 그대로다. `PracticeRoute.kt`는 고치지 않았다.
  - `frontend/docs/architecture.md` 9장 기준값 표와 낮은 창 문단.
- 테스트: `commonTest/.../core/ui/adaptive/WindowLayoutTest.kt`에 800×380·844×390·932×430·780×300·1280×479.9는 `isCompactHeight`이고 1280×480·1280×600·1366×625·600×900·390×844는 아니라는 경계 검사를 더했다.

## 4. 검증

모두 2026-11-24 macOS(Apple Silicon)에서 했다.

- 웹 빌드: `./gradlew :webApp:wasmJsBrowserDevelopmentExecutableDistribution --max-workers=2`가 통과했다(JDK 21). 바꾼 파일에서 새 경고는 없었다.
- 자동 검증(`8ea33e8e5` 기준): `./gradlew :shared:wasmJsTest :shared:jsTest :shared:testAndroidHostTest :androidApp:assembleDebug :shared:compileKotlinIosArm64 --max-workers=1`이 통과했다(3분 42초). Wasm·JS 브라우저 테스트 각 2,017개, Android 호스트 테스트 2,070개(기존 건너뜀 5개) 중 실패 0이고, 세 타깃 모두 `WindowLayoutTest` 8개(새 경계 검사 2개 포함)가 통과했다. 이 Mac에는 Xcode가 없어 iOS는 `iosArm64` klib 컴파일까지만 확인했다.
- 병합 전 재검증: develop에 S15P31E102-1263이 병합돼 `820245188`을 브랜치에 합쳤다(겹친 파일은 `docs/README.md`뿐). 합친 `6149f0cde`에서 `./gradlew :shared:wasmJsTest :shared:jsTest :shared:testAndroidHostTest --max-workers=1`이 통과했다(1분 48초, Wasm·JS 각 2,031개, Android 호스트 2,080개, 실패 0).
- Android: 터치 입력 경로는 바꾸지 않았다(`PointerType.Mouse`만 처리). 기기·에뮬레이터 화면은 보지 않았다.
- 브라우저 확인 방법: 개발 배포본(`webApp/build/dist/wasmJs/developmentExecutable`)을 Python 서버로 띄우고 `/api`만 운영 서버로 넘겼다. 모범 연주 음원(R2)은 CORS 허용 주소인 `localhost:8080`에서만 재생된다. 이미 로그인된 계정으로 제공 곡 경복궁타령(`songId` 7)의 연습 화면과, 그 곡을 복사한 편집기(저장하지 않음)를 열었다. 재생 소리는 `HTMLMediaElement.play`를 감싸 음소거했다.
- Chrome(앱 내장 브라우저, 1024×768)
  - 연습 악보를 마우스로 끌면 넘어간다. 끄는 동안 음이 선택되지 않고, 짧게 클릭하면 운지법 창이 열린다.
  - 모범 연주 재생 중 끌면 따라가기가 멈추고 `현재 위치로`가 나타난다. 4초 뒤에도 끌어 둔 자리에 머물고, `현재 위치로`를 누르면 다시 따라간다(`onDragStart = onUserScroll`이 재생 따라가기와 다투지 않음).
  - 편집기 악보, 좁은 창(390×844)의 율명 자판 줄·시김새 자판 줄, 320×700의 편집 탭 줄이 끌려 넘어간다. 자판·탭 위에서 끌기를 시작해도 눌리지 않았다(실행 취소가 꺼진 채, 선택 탭 유지).
  - 처음 구현에서는 편집기 악보를 좌우로 번갈아 끌면 3~4번에 한 번꼴로 시작 위치로 되돌아갔다. 브라우저 도구의 끌기는 움직임 표본이 두 개뿐(0·6·39ms)이라 2차 추정 속도가 끈 방향의 반대(약 -13px/ms)로 나와 반대쪽 끝까지 관성이 튀었다. 놓는 순간을 표본에 넣고 반대 방향 관성을 막은 뒤 같은 조건 5번이 모두 끈 방향대로 넘어갔다.
- 낮은 창(Chrome 창 크기 흉내)
  - 800×380(태블릿 세로 배치), 844×390(태블릿 가로 배치), 568×320(휴대폰 배치) 모두 연습 화면이 650dp 높이로 그려지고, 세로로 스크롤해 상단 바부터 하단 `모범 연주` 탭·재생 막대·`연주 평가 시작`까지 잘리지 않고 보인다. 마우스 휠은 악보 위에서도 페이지를 스크롤한다.
  - 이번 변경이 적용되지 않는 800×500·1280×520은 악보 칸이 좁아지지만(악보 안 세로 스크롤) 버튼은 잘리지 않는다.
- macOS Safari: 확인하지 않았다(2026-11-24 사용자 결정으로 생략). 실제 마우스·트랙패드 입력도 확인하지 않았고, 위 끌기는 모두 브라우저 도구가 만든 마우스 이벤트다.
- 오선 편집기(`CommonStaffEditor`)는 지금 호출하는 화면이 없어 브라우저로 확인하지 못했다. 붙인 시김새 줄은 넘칠 만큼 시김새를 붙여야 해서 확인하지 않았다.

## 5. 남은 일·주의

- macOS Safari와 실제 마우스·트랙패드 끌기는 확인하지 않았다. 운영 배포(S15P31E102-1269) 뒤 Safari에서 연습 악보 끌기와 낮은 창 스크롤을 보면 된다.
- 연주 중 하단 버튼(중단 등)이 낮은 창에서 스크롤 아래에 있을 수 있다(D1-A의 단점으로 받아들임).
- 연습 화면 배치 선택부(`PracticeScreen.kt` `PracticeScreen`)를 배치 감싸기로 바꿨다. 같은 부분을 고치는 1261·1262는 병합 때 이 감싸기 안쪽에 맞춘다.
- 480~650dp(`isShortHeight`만 참) 창과 연습 외 화면의 낮은 창 처리는 정하지 않았다(D2).
- 마우스 휠·트랙패드 가로 스크롤은 여전히 `DragInteraction`을 내지 않아 재생 따라가기를 멈추지 않는다(기존 동작).
- 배우기 단계·연습 운지법 페이지는 마우스로 끌어 넘길 수 없다(D3).
- `isCompactHeight`는 공통 코드라 Android·iOS의 아주 낮은 창(화면 분할 등)에서도 연습 화면이 세로 스크롤된다. 휴대폰은 세로로 고정돼 있어 보통은 생기지 않는다.
- 새 기준값(`MediumMinHeight`)은 architecture.md 9장 규칙에 따라 상대 개발자(권영민)에게 MR 리뷰로 알린다.
