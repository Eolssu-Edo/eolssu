## 이번 범위와 결과

현재 백업 상태를 읽기 전용으로 확인하고 위치·주기·보관 기간을 추천한다. [조사 결과](../knowledge/infra/backup-restore-assessment.md)에 실측·출처·권고·한계를 기록했다. 확인한 SQL은 10월 22일 생성한 이전 DB(`eolsu`)의 덤프이며, 앱 정기 백업과 외부 사본은 점검 범위에서 발견하지 못했다. 기본안은 시간별 DB 덤프와 S3 외부 보관, 일별·변경 전 설정 백업이다. 아직 팀의 확정 정책이 아니다.

파일 메타데이터·스케줄 흔적·SQL 구조·DB 용량·binlog·영속 mount·edo2 디스크를 조회했다. `.env` 값·DB 행 데이터·비밀키를 출력하지 않고 신규 덤프·업로드·복원·서버 설정 변경은 수행하지 않았다. 외부 클라우드 스냅샷·계정 사본은 미확인이다.

## 후속 순서와 완료 기준

1. 보관 계정·비용·주기·기간·RPO/RTO·키 보관자를 합의하고 현재 설정과 복구 의존성 목록을 확정한다.
2. 현재 DB와 설정을 백업하고 외부 저장소에서 사본·해시·manifest를 읽어 검증한다.
3. 격리된 빈 환경에 복원해 스키마·데이터·계정/권한·서비스 기동을 대조하고 복구 시점·시간을 측정한다.
4. 정기 생성·외부 보관·누락/실패 감지를 검증하고 운영·복구 절차를 문서화한다. 이 증거 전까지 Task 완료로 처리하지 않는다.

검증 결과: 로컬 링크 1개·문서 목록 연결 2개·공백 검사를 통과했다. 읽기 전용 독립 검토에서 실측·권고의 방향이 일치함을 확인했고, RPO를 성공본의 DB 스냅샷 시각 기준으로 명확히 하고 이전 DB 덤프의 날짜 표현을 수정했다. 이번 단계는 조사·문서 작성이며 커밋·Push·MR·운영 변경을 포함하지 않는다.

## edo2 자동 보관·실제 복원 구현 — 2026-10-25

사용자가 edo2 보관처·추천 주기 자동화·격리 복원 검증을 승인했다. S3를 생성하지 않고 같은 Task에서 [운영 안내](../../infra/backup/README.md)의 전용 키·암호화·불변 수신·정기 백업·보관 정리·배포 전후 연결·격리 복원을 구현한다. 기존 조사 문서·목록 변경도 같은 Task 소유 변경으로 보존한다.

기존 edo1 앱·DB·볼륨과 edo2 중계를 보존하며 신규 전용 계정에는 고정 수신 외의 셸·파일 읽기·삭제·Docker 접근 권한을 주지 않는다. 외부 채널 메시지는 보내지 않는다. 구현·검증·작업 단위 커밋까지 수행하고 Push·MR·Jira 완료는 포함하지 않는다.

### 결과와 증거

- edo2에 Ubuntu 저장소의 Docker 29.1.3과 동일 버전 태그의 공식 복원 이미지를 준비했다. 기존 edo-check·Nginx는 active를 유지했다.
- edo1→edo2 전용 SSH 키·강제 수신·출발지 제한, CMS 암호화·파일별 해시, 중복 ID의 동일 내용 재수신·다른 내용 거부, 불완전 전송 재개와 root 전용 저장을 구성했다. 실제 일반 셸·삭제·잘못된 업로드 3개 명령의 거부와 동일 암호문 재전송을 확인했다.
- 시간별 DB, 일별 설정·Grafana·Jenkins·별도 키의 최초 외부 사본을 저장했다. 첫 DB 암호문 약 148KB, 설정·릴리스 약 70MB, Jenkins 핵심 약 68MB, Grafana 약 9MB다. 전체 홈 5.2G를 매일 중복 보관하지 않는다.
- 첫 전송은 코드 상위 디렉터리의 umask에 따른 0700 때문에 실패했다. 코드 디렉터리만 0755로 고친 뒤 보존된 암호문을 재전송했다. 비밀 경로 0700/0600은 유지했다.
- 첫 DB 계정 복원은 SQL 오류 1827로 실패했다. MySQL batch 조회가 CREATE USER의 해시 문자열을 이중 이스케이프하는 것을 값 비공개 비교로 확인하고 `--raw` 조회로 수정했다. 기존 잘못된 사본은 덮어쓰지 않고 수정한 새 사본으로 복원했다.
- 최종 실제 복원: **2026-10-25 16:41:20~16:42:50 KST, 89.86초, passed**. 테이블/뷰 116개·기본 테이블 103개·데이터 3,013행, 모든 테이블의 데이터 해시 일치. 웹 실제 내용·200과 기존 API JSON 404, Grafana SQLite 무결성·HTTP DB 정상, Jenkins 관리자 CLI·executor 0·별도 키 일치·Credentials 복호화 성공. 임시 컨테이너·익명 볼륨·네트워크·디렉터리를 정리했다.
- 최종 복원 대상 ID: DB `20261025T073434Z-5180590b25ec`, config `20261025T074031Z-758423a024d3`, Grafana `20261025T072438Z-26d6df41ba7e`, Jenkins `20261025T073455Z-30377f6707fd`, key `20261025T073501Z-83dcaf0388be`. 운영 영수증은 edo2 `/var/lib/eolssu-backup/restore-last.json`이다.
- 양 서버 8개 타이머를 enable·active로 확인했다. 다음 DB는 10월 25일 17:10 KST, 설정은 10월 26일 03:20 KST, 주간 복원은 11월 1일 04:40 KST로 예약됐다. 상태 검사·보관 정리 서비스도 실제 실행했다. 미래 예약 실행의 성공을 미리 보장하지 않는다.
- Jenkins 배포 전 외부 DB·설정 백업 실패 시 교체 차단, 배포 후 설정 사본 연결을 설치했다. 설치 전 도구는 edo1 `/opt/backups/eolssu-backup112-20261025T073446Z/`에 보존했다. 연결 설치 전후 앱·DB 컨테이너 ID가 같았다. 이번 작업에서 새 앱 릴리스 배포는 실행하지 않았다.
- 최종 코드 SHA-256 `5883d37b29275ce6a32a66052337df7f70036c0ca150afcbade4fa5244bbf8e5`가 양 서버와 저장소에서 일치했다. 배포 도구 해시도 저장소와 일치했다.
- 16:45 KST에 15분 상태 검사 타이머가 실제 발화했고 Result=success·ExecMainStatus=0을 확인했다. 수동 점검 예시의 systemctl 패턴 조회는 실제 실행에서 명시적인 `list-units --failed`가 필요함을 확인해 수정했다.

### 검사·리뷰와 한계

백업/훅 검사 10개와 기존 배포 회귀 검사 17개 통과. 최초 미구현 5개 검사의 실패와 구현 후 통과, 거대 PAX 헤더 회귀의 수정 전 실패·후 통과를 확인했다. 로컬 loopback 검사와 바이트코드 캐시 경로는 기본 sandbox에서 제한되어, loopback 검사만 승인된 범위로 실행하고 구문은 파일을 쓰지 않는 AST 검사로 확인했다.

독립 코드 검토 3회에서 데이터 내부 VIEW 문자열 오인식, 압축 확장/확장 헤더 제한, 익명 볼륨 정리, 보관 정리 중단 재개, Jenkins 키 복호화 증거를 보완했다. 마지막 범위에 남은 차단 사항은 없었다. 독립 문서 검토에 따라 UTC 일별 보관 기준과 계정·권한 검증 범위를 명확히 했다. 최종 로컬 링크 7개·구문·공백·비밀키 비포함 검사는 통과했다.

API 준비 상태 계약의 새 구현, Metabase 프로세스 기동, MySQL binlog 외부 보관·시점 재생, 원본 `hey-*` 서비스 백업, 외부 메시지 알림과 복호화 키의 오프라인 보관은 포함하지 않았다. 복원 시간은 준비된 edo2에서의 시험이며 새 서버 프로비저닝·트래픽 전환 시간을 포함하지 않는다. 실제 업무 상태는 Jira 진행 중이며 MR 병합·완료 전환을 수행하지 않는다.
