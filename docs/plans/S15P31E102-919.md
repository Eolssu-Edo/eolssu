# S15P31E102-919 edo2 상태 변화 능동 알림

- 운영 모니터링 Story 41, 스프린트 5, 진행 중. [Jira 작업](https://ssafy.atlassian.net/browse/S15P31E102-919) · [운영 안내](../../infra/edo-check/README.md#상태-변화-능동-알림)
- 문제: 자동 알림은 Jenkins 실패(509)뿐이다. edo1 다운, 복제 중단, 백업 실패·지연, 디스크 포화는 누군가 `/edo1`·`/edo2`를 실행해야 드러난다. 11-11 백업 연속 실패도 늦게 파악했다(754). edo1의 독립 HTTPS 검사(709)는 journal에만 기록한다. Prometheus에는 경보 규칙이 없다.
- 범위: edo2에서 매분 실행하는 감시기. 상태 변화만 알린다. 579 대기계·복제 구성, 디스크 정리 자동화, Prometheus 규칙은 범위 밖이다.

## 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 실행 위치 | edo2, 기존 `edo-check` 계정 | edo1 전체가 죽어도 감시가 남는다. 중계의 고정 SSH 키·수집 모드를 재사용하므로 새 권한이 필요 없다 |
| 판정 원천 | 중계 `external_health`와 수집기 `health`·`server` | `/edo1`·`/edo2` 표와 같은 판정을 쓰므로 알림과 점검 결과가 어긋나지 않는다 |
| 주기 | 외부 HTTPS 1분, edo2 상태 5분, 서버 15분, edo1 상태 30분 | edo1 상태 수집은 R2 합성 객체 쓰기·삭제를 포함한다. 30분 주기면 하루 48회다 |
| 확인 | 같은 판정 2회 연속. 의심되는 변화는 다음 실행에서 바로 재수집(정기 실행마다 1회, 정기 일정은 유지) | 단발성 실패를 거르면서 느린 원천도 약 1분 안에 확인한다. 값이 오가도 R2 점검이 매분 실행되지 않는다 |
| 무시 | `미측정`·`미검증`, RAM·CPU 주의 | 근거가 없거나 순간 표본이라 오탐이 많다 |
| 디스크 | 85% 주의, 95% 장애(공간·inode 중 큰 값) | 수집기의 80% 주의 표시보다 알림 기준을 높여 반복 알림을 줄인다 |
| 전송 | 확실한 미전달만 재시도, 모호하면 재전송하지 않음 | Jenkins 알림(509)과 같은 중복 방지 원칙 |

## 검증

- `python3 -B -m unittest discover -s infra/edo-check/tests`: 152건 통과(신규 21건). 연속 확인, 단발 실패 무시, 미측정 무시, 주의→장애 변경, 사라진 항목의 복구, 수집 실패 시 가짜 복구 방지, 주기·의심 재수집과 값이 오갈 때의 재수집 제한, 확실한 미전달 재시도·모호 전송 미재전송, 본문 마스킹·행 제한·멘션 조건, webhook 주소 고정, 유닛 권한을 확인한다.
- 실제 `relay.py`를 불러 `App`·`external_health`·`PublicHTTPS`가 있는지 확인했다. 운영 서버 적용과 실제 게시는 아직 하지 않았다.
