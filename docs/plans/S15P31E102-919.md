# S15P31E102-919 edo2 상태 변화 능동 알림

- 운영 모니터링 Story 41, 스프린트 5, 진행 중. [Jira 작업](https://ssafy.atlassian.net/browse/S15P31E102-919) · [운영 안내](../../infra/edo-check/README.md#상태-변화-능동-알림)
- 문제: 자동 알림은 Jenkins 실패(509)뿐이다. edo1 다운, 복제 중단, 백업 실패·지연, 디스크 포화는 누군가 `/edo1`·`/edo2`를 실행해야 드러난다. 11-11 백업 연속 실패도 늦게 파악했다(754). edo1의 독립 HTTPS 검사(709)는 journal에만 기록한다. Prometheus에는 경보 규칙이 없다.
- 범위: edo2에서 매분 실행하는 감시기. 상태 변화만 알린다. 579 대기계·복제 구성, 디스크 정리 자동화, Prometheus 규칙은 범위 밖이다.

## 결정

## 검증

- `python3 -B -m unittest discover -s infra/edo-check/tests`: 152건 통과(신규 21건). 연속 확인, 단발 실패 무시, 미측정 무시, 주의→장애 변경, 사라진 항목의 복구, 수집 실패 시 가짜 복구 방지, 주기·의심 재수집과 값이 오갈 때의 재수집 제한, 확실한 미전달 재시도·모호 전송 미재전송, 본문 마스킹·행 제한·멘션 조건, webhook 주소 고정, 유닛 권한을 확인한다.
- 실제 `relay.py`를 불러 `App`·`external_health`·`PublicHTTPS`가 있는지 확인했다.

## 운영 적용과 검증 (2026-11-15 KST)

- edo2에 배포된 `relay.py`는 develop과 `/applog` 필드 검증만 다르다(763 미배포분). 감시기가 쓰는 함수는 같으므로 중계 코드는 바꾸지 않고 `alert.py`와 두 유닛만 설치했다. 설치 전 `/opt/edo-check`는 `/var/backups/edo-check/S15P31E102-919-20261115T053243Z`에 보관했다. 세 파일의 SHA-256이 저장소와 일치했고 `systemd-analyze verify`를 통과했다.
- `--dry-run`(edo-check 계정, 전송·상태 없음): 다섯 원천 수집 28초. 장애는 713 블로그 편집기 이전 보관 컨테이너 2개(exited)뿐이었다. `/edo1`도 같은 항목을 장애로 표시한다.
- 사용자 승인에 따라 Team 이도 (CI/CD,서버점검) 채널(`e102-cicd`)에 채널 고정 incoming webhook `edo 감시`를 새로 만들었다. 기존 Jenkins용 webhook과는 별개다. URL은 표준 입력으로만 `/etc/edo-check-alert/webhook-url`(root 600, 상위 700)에 저장했고 형식 검사만 출력했다. 멘션은 설정하지 않았다.
- 15:32 `--test-notice` 게시를 채널에서 확인했다. 15:33 첫 실행 뒤 타이머를 활성화했고, 15:33:40에 위 보관 컨테이너 2건의 장애 알림 1건이 게시됐다.
- 실제 경보 검증: 15:33:50에 edo2 `eolssu-backup-status.timer`를 중지했다. 15:39:57에 `edo2 백업 상태 확인 예약` 장애 알림 1건이 게시됐다(6분 7초). 이후 2분 동안 추가 전송은 0건이었다. 15:42:18에 타이머를 다시 시작했고, 15:45:10에 `장애 5분 뒤 복구` 알림 1건이 게시됐다. 15:45:00 백업 상태 확인 실행은 성공(종료 0)했다. 세 게시물에는 webhook 주소·토큰이 없었다.

- 15:33 첫 알림의 장애 2건은 713에서 롤백용으로 남긴 블로그 편집기 이전 보관본(종료 코드 0)이었다. 662의 보관본 예외는 `-writable-(before|rollback|pre)-<8자리>` 이름만 인식해 713 이름(`<편집기>[-writable]-<작업>-<UTC 시각>-before`)을 장애로 판정했다. 보관본은 지우지 않고 예외 이름 형식만 넓혔다. 비정상 종료나 비슷한 다른 이름, 운영 편집기 중지는 계속 장애로 남긴다. edo1 수집기를 `/var/backups/edo-check/S15P31E102-919-collector-20261115T070427Z`에 보관한 뒤 교체했다. `edo1:health`를 바로 두 번 실행해 16:04:43에 두 보관본의 `복구 2` 알림 1건이 게시됐다. 운영 편집기 두 개는 `/config` HTTP 200으로 정상이었다.
