## 원인 (2026-11-23 로그 확인)

`eolssu-ios-qa` #315~#323(11-22 11:29~17:43 UTC)이 모두 ABORTED였다. #312~#314는 `numToKeep 10`으로 이미 지워져 확인할 수 없었다. 마지막 성공은 #311(11-20)이다.

- **Mac 끊김:** 컨트롤러 로그에서 `mac-ios-eunseo`가 11-22 11:11 UTC부터 11-23 03:10 UTC까지 잠깐 붙었다가 `ChannelPinger … Ping failed` → 60초 뒤 `Idle timeout expired` → `ClosedChannelException`으로 끊기기를 반복했다. S15P31E102-908과 같은 잠자기·DarkWake 패턴이다.
- **노드 대기가 timeout에 포함됨:** 45분 `timeout`이 파이프라인 전체 `options`에 있었다. 콘솔은 `Timeout set to expire in 45 min` → `Still waiting to schedule task` / `‘mac-ios-eunseo’ is offline` → `Cancelling nested steps due to timeout` 순서였다. #315·#317·#318·#320·#323은 Mac을 한 번도 받지 못하고 대기만 하다 45분에 ABORTED됐다. #316은 9분 대기 중 관리자가 중단했다.
- **노드를 받은 빌드(#319·#321·#322):** Mac이 잠깐 붙은 순간 executor를 받았지만 첫 `checkout`의 원격 호출에서 `ClosedChannelException`으로 실패했다. `retry(agent())`가 재시도를 시작했으나 다시 `is offline` 대기에 들어가 남은 45분이 지나 ABORTED됐다. 서명·컴파일 단계에는 가지 못했다.
- **약 45분 간격:** backend 잡이 iOS 입력이 바뀐 develop 커밋마다 `eolssu-ios-qa`를 `wait: false`로 예약했다(#3607~#3619). REVISION이 모두 달라 큐에서 합쳐지지 않았고, `disableConcurrentBuilds()` 때문에 앞 빌드가 45분 timeout으로 끝날 때마다 다음 빌드가 시작됐다. 간격은 트리거 주기가 아니라 timeout 길이였다. 같은 커밋 중복은 #318 하나(backend #3613·#3614, 같은 REVISION)였고 Jenkins가 큐에서 이미 합쳤다.
- **#324(11-23, FAILURE):** Mac은 정상이었고 `5211fa975`의 Kotlin 오류(`IosStoreUpdates.kt:65 numberWithLongLong`)로 실패했다. S15P31E102-1257의 fix로 develop에서 고쳐졌다. 잡 문제가 아니다.

## 변경

- 45분 빌드 제한을 Mac executor를 받은 뒤(`node` 안쪽)로 옮겼다. Declarative의 stage `options` timeout은 agent 할당 전부터 세므로 쓰지 않았다.
- Mac 대기를 15분으로 제한했다. 같은 `parallel`의 감시 분기가 `node`를 받지 못한 채 15분이 지나면 Mac 확인 방법을 담은 메시지로 FAILURE를 낸다(`failFast`로 대기 중인 `node` 요청도 취소). `nodesByLabel`(Pipeline Utility Steps)은 서버에 없고, Jenkins API를 쓰는 방식은 sandbox 승인이 필요해 고르지 않았다.
- `disableConcurrentBuilds(abortPrevious: true)`: 새 REVISION이 들어오면 실행·대기 중인 이전 빌드를 중단(NOT_BUILT)한다. Mac 복구 뒤 쌓인 옛 커밋을 차례로 빌드하지 않는다.
- 전체 `timeout`은 재시도(최대 3회 × (15분 대기 + 45분 빌드))를 덮는 4시간 안전장치로 남겼다.
- `apply-jenkins.groovy`의 후보 경로·검사 문자열을 새 정의에 맞췄다.
