# Jenkins backend 잡의 폐기용 MySQL databaseTest 단계

[작업 S15P31E102-946](https://ssafy.atlassian.net/browse/S15P31E102-946) · [배포 환경·CI Story](https://ssafy.atlassian.net/browse/S15P31E102-40) · 스프린트 5

## 목적과 범위

`databaseTest`(실제 MySQL 8.4에 대한 Flyway·MyBatis·HTTP 통합 검사)가 CI에서 돌지 않아, DB 관련 회귀가 병합 전에 걸리지 않았다(예: 656). 이 작업에서는 다음을 한다.

- 저장소의 `infra/jenkins/backend.Jenkinsfile`에 실행마다 폐기용 MySQL을 띄워 `databaseTest`를 돌리는 단계를 추가한다.
- 로컬에서 같은 방식으로 실측한다.

운영 Jenkins 잡 정의에 반영하는 일은 발표(11-18) 뒤 사용자 확인을 받고 진행한다(아래 '운영 적용 절차').

## 결정

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| DB 기동 방식 | 잡 안에서 `docker run`으로 띄우는 일회용 컨테이너 (`infra/jenkins/run-database-tests.py`) | 호스트 에이전트(`edo1-host`)는 이미 Docker 그룹 권한이 있다. Testcontainers는 테스트 의존성과 코드를 바꿔야 하고, 사이드카는 Declarative Pipeline에서 정리 시점을 보장하기 어렵다. |
| 이미지 | `mysql:8.4.13` | 운영 MySQL(`infra/runtime/compose.yml`)과 같은 태그다. |
| 격리 | `127.0.0.1` 임의 포트 publish, 데이터는 tmpfs, 운영 Compose 네트워크에 붙이지 않음 | 운영 DB·네트워크와 섞이지 않고, 디스크를 쓰지 않는다. edo1의 디스크 압박은 [921](S15P31E102-921.md) 참고. |
| 비밀번호 | 실행마다 `secrets.token_urlsafe`로 만들고 `-e NAME` 환경변수로만 전달 | 명령 인자·로그에 남지 않는다. 기존 `infra/backup/backup.py` 격리 복원과 같은 방식이다. |
| 정리 | 끝나면 항상 `docker rm --force`(SIGTERM은 정리 중 지연), 시작할 때 라벨 `com.eolssu.ci.database-test=backend`가 붙은 이전 잔여 컨테이너 제거 | 실패·중단에도 남지 않는다. 잡은 `disableConcurrentBuilds()`라서 같은 라벨의 컨테이너는 모두 이전 실행의 잔여물이다. |
| 자원 상한 | `--memory 1536m --cpus 2`, 로그 5 MB | 실측 최고 962 MiB에 여유를 둔 값이다. |
| 서버 옵션 | `--max-connections=1000 --disable-log-bin` | 캐시된 Spring 컨텍스트마다 Hikari 풀이 있어 기본값 151로는 부족하다(메모리 `backend-test-env-macos`와 같은 이유). |
| 권한 | 테스트 계정에 `performance_schema.data_locks`, `data_lock_waits`, `threads` SELECT 부여 | 잠금 대기 검사가 이 표들을 읽는다. 첫 실측에서 `threads` 권한이 없어 `ConversionQueueDatabaseTests` 1건이 실패했고, README에도 이 내용을 추가했다. |
| 시간 제한 | 단계 10분, 파이프라인 20분에서 25분으로 | 이 단계가 약 2~3분을 더한다. 시간 제한 때문에 마지막 배포 트랜잭션 단계가 도중에 끊기지 않게 했다. |
| 실패 처리 | 발표 동결(11-18)까지는 경고 모드: `catchError(buildResult: 'UNSTABLE')`. 시간 초과도 이 안에서 잡고, 결과 파일이 없어도 실패로 만들지 않는다 | 배포는 빌드 결과를 보지 않으므로 배포가 계속되고, Jenkins Mattermost 알림이 UNSTABLE을 알린다. 발표 뒤 `catchError`를 빼고 `allowEmptyResults: false`로 바꿔 차단 모드로 돌린다. |

## 실측 (2026-11-15, 로컬 macOS · Docker 29.5.2 · JDK 21)

`backend`에서 `python3 -B ../infra/jenkins/run-database-tests.py -- ./gradlew --no-daemon databaseTest`를 실행했다. macOS 임시 폴더 심볼릭 링크 문제 때문에 `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<실제 경로>`를 붙였다. Linux CI에는 해당하지 않는다.

- 1차 실패는 `ubuntu` 계정 문제였다. 테스트 앱이 JVM 임시 폴더의 `/tmp/eolssu-sheet-imports`(Jenkins 테스트가 11-06에 만든 `jenkins` 소유 0700 폴더)를 쓰려다 권한 오류가 났다. Jenkins 잡은 `jenkins` 계정으로 실행하므로 해당하지 않는다. 2차에서는 `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<임시 폴더>`로 피했다.
- 실행 중 부하(load)는 최대 9.17이었다(4 vCPU). 운영 응답 지연은 수십 ms 수준으로 늘었고 실패는 없었다.
- 실제 잡에서는 앞 단계가 이미 컴파일했고 Gradle daemon도 재사용하므로, 이 수치보다 짧을 것으로 예상한다. 단계 제한 10분과 전체 25분은 그대로 둔다.

## 운영 적용 절차

backend 잡은 SCM이 아니라 잡 설정의 inline Pipeline(`CpsFlowDefinition`)을 쓴다. 943에서 서버에만 있던 QA 큐 단계가 저장소로 옮겨졌고, develop을 병합한 뒤의 `infra/jenkins/backend.Jenkinsfile`은 운영 inline 정의에 이 작업의 변경(단계 2개·시간 제한)만 더한 것과 같다(2026-11-15 대조). 반영은 다음 순서로 한다.

1. 실행·예약 중인 backend 빌드가 없을 때 진행한다. 현재 잡 `config.xml`과 서버 사본을 백업한다.
2. edo1에서 `docker image inspect mysql:8.4.13`으로 이미지가 있는지, 여유 메모리가 2 GiB 이상인지 확인한다.
3. 래퍼와 테스트가 develop에 병합된 뒤에 반영한다. 새 단계가 develop 체크아웃의 `infra/jenkins/run-database-tests.py`와 그 테스트를 실행하기 때문이다. 먼저 반영하면 `Database wrapper tests`가 테스트를 찾지 못해 실패한다. 반영 직전 운영 inline 정의가 위 대조 때와 같은지 다시 확인한다.
4. Jenkins linter를 통과한 정의만 관리자 CLI `update-job`으로 저장한다. 서버 사본도 같은 내용으로 갱신한다.
5. 첫 빌드에서 다음을 확인한다.
   - 단계 시간과 통과 수
   - `docker ps -a --filter label=com.eolssu.ci.database-test=backend`가 비어 있는지
   - 운영 MySQL과 앱 응답에 영향이 없는지
6. 되돌릴 때는 백업한 `config.xml`의 정의로 `update-job`한다. 래퍼는 상태를 남기지 않으므로 따로 정리할 것이 없다.
