# S15P31E102-541 운영 Compose 교체 시 Jenkins 읽기 권한 유지

- [Jira Task](https://ssafy.atlassian.net/browse/S15P31E102-541) · [스펙](../specs/runtime-compose-install.md) · develop 기준 `9f6f9388`.
- `2026-11-06 14:05:58.126 KST`에 edo1 sudo 저널에 `sudo python3 -`가 기록됐다. 약 47ms 뒤 현재 Compose inode가 생성됐고 14:05:58.695에 root의 `docker compose config --quiet`가 실행됐다. stdin에 전달된 Python 본문은 저널에 없다.
- 14:04:47과 15:54:47의 암호화 설정 백업에서 Compose만 대조했다. 차이는 내 악보 R2용 `SHEET_STORAGE_*` 변수 매핑 다섯 줄 추가였다. #285~#288은 교체 파일의 `root:root 0600` 때문에 실패했고, 기존 권한을 되돌린 #289는 배포까지 성공했다.

1. 격리 파일에서 권한을 설정하지 않고 임시 파일을 rename했을 때 Jenkins 계정의 Compose 검사가 실패하는지 확인한다.
2. 운영 설치 도구를 만들고 배포 안내의 교체·복원 경로를 전환한다.
3. 격리된 실제 Docker Compose 검사에서 설치 성공, 권한 유지, 잘못된 후보 거부와 기존 파일 보존을 확인한다.
4. edo1에 도구를 설치하고 현재 파일과 같은 바이트로 실제 교체한다. 새 inode·파일 해시·권한, Jenkins 검사와 운영 readiness를 대조한다.

## 검증 결과

- edo1 격리 디렉터리에서 기존 방식으로 `0600` 임시 파일을 교체했다. root의 Compose 검사는 통과하고 Jenkins 계정은 `permission denied`로 실패했다.
- 설치 도구는 실제 Docker Compose와 Jenkins 계정으로 검사했다. 정상 후보는 새 inode에 `root:jenkins 0640`으로 설치됐다. 잘못된 YAML과 CI 필수 값 누락은 각 검사에서 거절됐고 기존 inode·내용을 보존했다. 배포 잠금이 사용 중인 경우도 교체하지 않았다.
- edo1에 `/opt/eolssu/bin/install-runtime-compose`를 설치했다. 운영 파일을 같은 내용으로 교체해 inode `2170661 → 2170629`와 동일 SHA-256, `root:jenkins 0640`, Jenkins Compose 검사 통과를 확인했다. 이전 파일은 `/opt/eolssu/config/compose.yml.backup-kolfggfi`에 `0600`으로 보관됐다.
- 교체 전후 운영 `.env`의 해시·권한과 프론트·백엔드·MySQL 컨테이너 ID가 같았다. 운영 readiness가 HTTP 200과 `UP`을 반환했다.
- `python3 -B -m unittest discover -s infra/scripts/tests -v`에서 8개 통과, Docker·OpenSSL을 요구하는 Nginx 통합 검사 13개는 기본 설정으로 건너뛰었다.
