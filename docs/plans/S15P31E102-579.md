## 운영 도메인과 전환 권한

- `k15e102.p.ssafy.io`의 권한 DNS에 직접 조회했다. A는 edo1 `43.203.215.107` 한 개이며 TTL은 300초다. AAAA·CNAME과 하위 존 NS 위임은 관측되지 않았다. `ssafy.io` 권한 서버는 AWS Route 53을 사용한다.
- 서버 SSH 접근과 DNS 편집 권한은 별개다. 팀이 해당 A 레코드를 수정할 수 있는 계정이나 장애 시 변경을 처리할 담당자는 확인되지 않았다. `ssafy.io` 존 관리자를 통해 **A 레코드 변경·원복 권한 또는 담당자 대응 절차**를 확인한다. Route 53은 레코드 이름·유형·변경 동작에 한정한 위임을 지원한다. [레코드별 IAM 권한](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-permissions.html)
- 무상 운영의 기본은 기존 A 레코드의 수동 전환이다. 장애 전환값은 edo2 `15.165.144.7`, 최초 원복값은 edo1 `43.203.215.107`이다. A를 바꾸면 권한 DNS에 반영된 뒤에도 리졸버와 기기에 이전 캐시가 남을 수 있다. 여러 네트워크에서 DNS·인증서를 확인한다. Route 53 자동 전환은 헬스체크 비용과 계정 조건이 확인될 때 별도로 판단한다. [Route 53 헬스체크 요금](https://aws.amazon.com/route53/pricing/#Health_Checks)
- 로컬 SSH 별칭 `edo1`이 현재 운영 도메인을 사용한다. 전환 전에 두 서버의 주소와 호스트 키를 별도로 검증해 서버 관리·배포·백업 작업이 서비스 DNS를 따라 다른 서버로 가지 않도록 분리한다. DNS 권한을 확보하기 전에도 edo2 준비와 리허설은 진행할 수 있다. 이 상태에서 edo1이 내려가면 같은 주소의 서비스 복구는 DNS 담당자 대응에 의존한다. 별도 HTTPS 주소를 쓰는 경우 웹·모바일 API 주소·OAuth 허용 주소를 검증해야 한다.

## 배포 순서

1. **edo2에 격리된 후보를 준비한다.** 검증한 동일 JAR·웹 자산·AI/OMR·재생 이미지와 모델·음원 자산을 버전별로 전달한다. 앱 포트는 loopback 또는 내부 네트워크에 두고 edo2 호스트 Nginx에 서비스 도메인 전용 가상 호스트를 추가하는 구성을 검증한다. IP 가상 호스트·점검 중계·백업은 계속 사용한다. 공유 저장소와 동일 인증 서명에 필요한 설정만 권한을 제한해 주입한다.
2. **격리 DB에서 기능과 용량을 확인한다.** 별도 테스트 DB와 테스트 객체 경로에서 동일 호스트명으로 edo2를 강제 지정하는 HTTPS 검사를 수행한다. 웹·readiness·약관·로그인과 기존 토큰·녹음 업로드/재생/채점·악보 인식·재생을 확인한다. 동시 사용에서 한 서버로 버틸 수 있는 부하를 재고, edo2 점검과 백업에도 영향이 있는지 확인한다. 운영 도메인용 TLS 인증서와 갱신 책임·갱신본 배포 방법도 전환 전에 검증한다.
3. **운영 DB에 접근하는 상시 대기 앱을 준비한다.** 확인된 공인 SSH 경로 위에서 권한을 제한한 전용 포워딩이나 기존 사설망 연결을 사용한다. MySQL은 공용 3306으로 열지 않고 DB 연결 지연·재접속·터널 종료 감지와 기존 데이터 전송 한도를 검증한다. 평소 edo2의 HTTP 진입은 제한하고 예약 작업·큐 소비를 끈다. 앱 장애 때는 살아 있는 운영 DB 한 곳을 사용한다. [운영 Compose](../../infra/runtime/compose.yml) · [예약 작업 설정](../../backend/src/main/kotlin/com/ssafy/eolssu/backend/config/SchedulingConfig.kt)
4. **이후 릴리스는 edo2 검증부터 한다.** 한 번 만든 릴리스로 edo2를 갱신하고 검사를 통과하면 edo1에 배포한다. 스키마 변경은 격리 검증 뒤 구·신 버전 모두 읽고 쓸 수 있는 변경만 기존 잠금과 백업 절차 아래 운영 DB에 한 번 적용한다. edo2 검증이 실패하면 해당 노드를 이전 검증본으로 되돌리고 edo1 배포를 멈춘다. edo1이 실패하면 기존 배포 복구 또는 검증한 edo2 경로를 사용한다.

## 장애 전환과 복귀

| 상황 | 전환 순서 |
| --- | --- |
| edo1 앱만 장애, 프록시·MySQL 정상 | 새 배포를 멈추고 edo2의 운영 DB 연결 및 실제 HTTPS 업무 경로를 검사한다. edo1 프록시가 살아 있으면 검증된 edo2 경로로 요청을 전환한다. 프록시도 사용할 수 없으면 DNS 수동 전환 절차를 사용한다. 기존 작업자가 정지했음을 확인한 뒤 필요할 때만 edo2 작업자를 켠다. |
| edo1 MySQL 또는 서버 전체 장애 | 기존 주 DB가 다시 쓰기를 받지 않도록 차단하고 운영 배포를 멈춘다. 확인한 가장 최근 유효 백업을 별도 edo2 운영 볼륨으로 복원한다. 스냅샷 이후 데이터 손실 범위를 기록하고 팀의 허용 기준을 확인한다. edo2 앱을 새 DB에 연결해 HTTPS·DB 읽기/쓰기·업로드·채점과 작업자 단일 실행을 확인한다. edo1 프록시가 살아 있으면 검증된 경로로 edo2에 전달할 수 있다. 서버 전체 장애 시 DNS 담당자가 A를 edo2로 변경한다. |
| edo1 복구 | edo2가 쓰기를 받은 뒤에는 edo2 데이터를 기준으로 edo1을 동기화한다. 계획한 전환 시점에 기존 쓰기를 중지하고 마지막 데이터와 호환성을 검증한다. edo1에서 업무 검사가 통과하면 진입점과 작업자를 되돌리고, 외부에서 DNS·TLS·로그인·업로드를 다시 확인한다. |

- 새 DB를 열기 전에 기존 주 DB의 쓰기 차단을 확인한다. 트래픽 전환 전에 DB/릴리스 호환성, 정상 TLS, 업무 검사를 확인한다. DNS 전환에는 레코드를 변경하고 원복할 담당자가 필요하다.
- 서버 전체 장애의 초기안은 **백업 복원과 수동 전환**이다. 유실 가능 범위는 장애 시점과 최신 유효 스냅샷의 차이로 잰다. 복구 시간은 장애 선언부터 실제 쓰기 요청이 성공할 때까지 재고, 운영 DNS를 바꾸는 경우에는 접속 전환 시간도 포함한다. 이 수치가 팀 기준을 넘으면 MySQL 복제와 수동 승격을 다음 단계로 설계한다. GTID 전환과 원본 서버 차단을 별도로 검증한다.
- 완료 기준은 edo2의 대기 릴리스 검증, 한쪽 앱 장애 전환, edo1 전체 장애를 가정한 격리 복원·업무 검사·DNS 변경 및 원복 리허설, 그리고 소요 시간 기록이다. 이번 점검에서 실운영 배포·장애 전환·DNS 편집은 실행하지 않았다.

## 2026-11-09 edo2 격리 배포 및 실검증

사용자가 DNS 권한을 확인하기로 했다. edo2의 격리 앱 배포와 로그인·녹음 업로드·채점 확인을 먼저 수행했다. [격리 환경 설정과 접속 절차](../../infra/standby/README.md)를 추가했다.

- edo1에서 실행 중인 백엔드 `a28d80ee`와 웹 `3e5e42fe`를 각각 가져왔다. JAR SHA-256, 웹 파일 142개의 배포 목록 SHA-256, Nginx·MySQL·백엔드 런타임·AI·OMR·재생 이미지 ID를 대조했다. AI 빌드는 `371137a1`, OMR은 `2a14b65f`, 재생은 `d03fd028`이었다. 재생용 자산도 해당 디렉터리에서 복사했다.
- edo2의 별도 Compose에 웹·API·MySQL·AI·OMR·재생을 띄웠다. 운영 앱의 `ops` 프로필을 사용하고 격리 DB에만 Flyway V30까지 적용했다. 운영 계정·DB·스토리지 키 대신 임의의 격리 키, 기본 카탈로그, 합성 테스트 계정, 로컬 녹음·악보 저장소를 사용했다.
- HTTPS에서 배포된 웹 원문, API 준비 상태 `UP`, 미인증 요청 401, 내부 API 경로 404를 확인했다. 틀린 비밀번호는 401, 올바른 로그인은 200이었다. 로그인 쿠키로 아리랑 0~7번 음의 연습 세션을 생성해 201을 받았다.
- 합성 AAC 녹음 3.75초를 업로드해 202 및 `PENDING`을 확인했다. 격리 저장소의 원본 61,462바이트가 업로드한 파일과 일치했다. 세션 1은 `DONE`이 됐고 평가 1 조회에서 200, 100점, 음표별 결과 8개를 받았다. 첫 채점은 업로드 응답 후 15.55초였고 AI 로그에 실제 실행 완료가 기록됐다. 동일 세션 재업로드는 409였고 원본 파일은 보존됐다.
- edo2의 18443 포트가 루프백에서만 열리고 외부에서는 연결되지 않는 것을 확인했다. 기존 edo2 공개 점검은 정상이고 운영 DNS는 그대로 edo1을 가리켰으며, edo1 운영 API는 `UP`을 반환했다. SSH 터널로 접속해 `UP`을 다시 확인했다. 배포한 Compose·Nginx 파일의 해시는 저장소와 일치했고 기존 백업 상태에서 만료 항목은 없었다.
- 검증은 합성 녹음 한 건을 사용한 HTTPS API 경로를 대상으로 했다. 모바일 기기 녹음, 소셜 로그인·R2 연동, 실사용 채점 품질, 장애 전환은 별도 검증 범위다. 격리 환경과 합성 평가 결과는 edo2에 남겼다.

## 2026-11-09 백업 복원·장애 전환·원복 리허설

SQL 가져오기는 전용 스키마 권한으로 제한하고 바이너리 로그를 끈 세션에서 실행했다. 백업 내용은 edo2 안에서만 복호화했다. 원본 계정 권한과 운영 비밀값은 앱에 적용하지 않았으며, 데이터 해시를 검증한 뒤 기존 비밀번호 해시를 사용할 수 없는 테스트 값으로 바꾸고 합성 계정을 넣었다.

## 운영 적용 순서

사용자가 운영 적용을 요청했다. 이번 적용은 기존 서버·백업·이미지를 사용한다. 먼저 edo2에 별도 복제 DB와 전용 SSH 전달 경로를 준비한다. 운영 트래픽을 바꾸기 전에 복제본의 데이터와 지속 연결을 확인한다. DNS 편집은 기존 존 관리 절차에 의존한다.

1. 기존 백업 상태와 되돌릴 사본을 확인하고, 서비스 포트 충돌과 원본 MySQL의 현재 복제 모드를 점검한다. 대상은 edo1 MySQL 8.4.13의 `eolssu` 스키마와 별도 edo2 읽기 전용 DB다. 기존 격리 앱의 DB·볼륨을 재사용하지 않는다.
2. SSH 키는 edo2에서 생성한다. edo1의 새 전용 계정은 edo2 고정 IP에서 지정한 루프백 포트로의 포워딩만 허용한다. MySQL 포트는 인터넷에 열지 않는다. 원본 호스트 키를 기존 신뢰 연결로 확인하고 edo2에서 고정한다.
3. 온라인 GTID 전환과 초기 사본 복원은 사전 백업과 배포 잠금을 잡은 뒤 수행한다. 복제 검증 전에는 edo2 앱에 운영 쓰기 자격을 주지 않는다. 복제본에 수신·적용 오류가 있거나 원본 HTTPS 준비 상태가 실패하면 다음 단계로 진행하지 않는다.
4. 앱 전환 경로와 쓰기 차단 정책은 각각 검증한다. 복제 수신 중단이 애플리케이션의 로그인·저장에 미치는 영향과 연결 복구 후 쓰기를 여는 기준을 확인한다. 수동 승격은 실제 원본 장애 때에만 수행한다.

- 이번 반영에서는 서버에 접속하지 않았다. 저장소 파일과 edo2의 `/opt/eolssu-replication-579`·`/opt/eolssu-standby-579`, systemd 유닛의 SHA-256 대조는 읽기 전용으로 따로 수행한다.
