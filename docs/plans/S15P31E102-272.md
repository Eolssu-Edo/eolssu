## 범위와 검증

운영에 배포된 `S3RecordingStorage`의 put/readUrl/delete를 직접 실행한다. HTTP 클라이언트는 인증 헤더 없이 서명 URL을 사용한다. 합성 객체의 본문 일치, 무서명 접근 거부, 메서드·객체 키 변조 거부, 짧은 TTL와 실제 900초 만료, 삭제 후 GET/HEAD를 확인한다. Cloudflare 화면에서 공개 개발 주소·사용자 도메인·수명 주기를 읽는다.

사용자가 2026-10-29 운영 버킷의 전용 테스트 객체 생성·삭제를 승인했다. 기존 녹음·DB는 보존한다. 최초 요청은 정책·서버 설정을 바꾸지 않는 검증이었다. 이후 사용자가 서버 버킷명 정정·backend 재생성·기존 규칙을 보존한 30일 삭제 규칙 추가와 재검증을 승인했다. 이 범위에서 coco-build로 설정 수정을 진행하고 문서 커밋을 남긴다. 스펙의 GET 15분·비공개·recordings/ 30일 기준 자체의 변경은 없다. 최초에는 Push·MR을 제외했으며, 후속 요청으로 리뷰·coco-push·MR 생성·병합·Jira 완료까지 승인됐다.

## 진행 기록 (2026-10-29 KST)

- Jira 검색에서 R2 연결 241은 완료, 검증 목적 Task는 없어 272를 생성했다. Story 40 관련됨 연결과 Epic 21, 활성 스프린트·진행 중을 MCP로 확인했다.
- 운영 컨테이너의 R2 변수 5개가 모두 존재하고 공백·미치환 변수가 없으며 서버 `.env` 값과 일치한다. 값 자체는 출력하지 않았다.
- 운영 버킷 설정 `eolssu-backend-recordings`로 배포 JAR의 PUT와 DELETE가 403 AccessDenied. 단순 기동·변수 존재가 실제 연결 성공을 뜻하지 않는다.
- 사용자 로그인 후 Cloudflare 버킷 목록에서 실제 버킷 `eolssu-recordings`를 확인했다. 공개 개발 URL 꺼짐·사용자 도메인 없음. 30일 객체 삭제 규칙은 없고 기본 멀티파트 중단 7일 규칙만 활성화돼 있다.
- 검증 프로세스에만 실제 버킷명을 지정하자 같은 JAR·키로 PUT와 서명 GET(200·본문 일치)이 성공했다. 운영 `.env`나 컨테이너는 수정하지 않았다.
- 무서명 GET 400 InvalidArgument, GET 서명으로 PUT·객체 키 변조는 403 SignatureDoesNotMatch. 3초 URL은 5초 뒤 403 ExpiredRequest, 같은 객체의 900초 URL은 계속 200.
- 실제 900초 URL은 13:14:49 서명, 13:29:49 만료(KST). 13:29:52 기존 URL 403 ExpiredRequest·새 URL 200, 13:29:55 삭제 후 GET·HEAD 404·정리 성공.
- backend·AI 최근 15분 로그에서 `X-Amz-Signature`·`X-Amz-Credential`·`audioUrl` 일치 0건. 이 관찰 구간에 한정하며 전체 로그 무노출을 증명하지 않는다.

## 최초 발견 사항과 후속 조치

1. 서버 `RECORDING_STORAGE_BUCKET`를 실제 버킷명과 맞추고 backend에 다시 주입해야 한다. 이후 사용자 승인으로 정정·재생성을 완료했다.
2. 기존 멀티파트 규칙은 보존하고 `recordings/` 접두사·생성 30일 뒤 객체 삭제·Enabled 규칙을 추가해야 한다. 이후 사용자 승인으로 추가하고 기존 규칙 보존을 확인했다.
3. 위 수정 후 실제 API의 녹음 업로드·분석 소비 흐름은 별도 통합 검증에서 확인한다. 검증 프로세스의 버킷명 대체 성공을 운영 수정 완료로 보고하지 않는다.
4. 30일 자동 삭제의 실제 실행은 이번 단기 검사로 확인할 수 없다. 규칙과 새 객체의 만료 메타데이터 확인, 이후 만료된 합성 객체의 소멸 관찰을 구분한다.

세부 결과·재현 조건은 [R2 검증 기록](../knowledge/infra/r2-storage-verification.md)에 남긴다.
