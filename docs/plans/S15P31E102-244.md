## 검증 (2026-11-15, 로컬 macOS arm64·Docker 29.5.2)

- 단위 테스트: `python3 -B -m unittest discover -s infra/jenkins/tests` 중 새 `test_build_ai_image.py` 11개, `test_deploy_ai.py` 12개, `infra/retention/tests` 15개 통과. ai의 `uv run pytest tests/unit/test_warmup.py tests/unit/test_api.py` 42개 통과.
- 실제 이미지 게이트(커밋 `e66f4a29`): `plan`이 수동 이미지 대비 `deploy`, `build`가 라벨을 붙인 이미지 생성, `test` 301 통과·1 제외(JUnit 보관 확인), `smoke`가 비root·읽기 전용에서 `/health` `pyin-9`와 예열 채점 성공(5.6~11.2초).
- 게이트가 실패를 잡는지: 첫 시도의 수집 실패 20건, 두 번째의 기존 플랫폼 실패 1건에서 `test`가 종료 코드 1로 멈췄다.
- 배포 도구 통합(로컬 Compose 프로젝트 `eolssu-runtime`, ai + curl backend 대역): 정상 후보 배포 → `deployed`, `rollback` 태그=이전 이미지. 같은 후보 재실행 → 컨테이너를 다시 만들지 않음. 바로 종료하는 이미지 → `Recreate ai service` phase 실패 후 이전 이미지로 복구, journal `rolled_back`. 보호 서비스·lock·백업·Git 순서 검사는 이 통합에서 대역으로 바꿨다(단위 테스트로 검사).
- 확인하지 못한 것: 운영 edo1(amd64)에서의 빌드 시간과 Jenkins agent의 실제 권한·sudoers, Jenkins linter 검사, 운영 MySQL·frontend가 있는 상태의 보호 서비스 비교. 적용 절차의 4단계에서 확인한다.

## 남은 일

- 2단계 `omr`·`playback`: 같은 방식으로 일반화하되 다음을 더 다룬다.
  - `omr`은 저장소 루트 맥락·BuildKit(`ADD --checksum`)·`scanner` 단계가 있고, 이미지에 JGB 변환기가 들어 있어 위 15개 테스트를 이미지 안에서 돌릴 수 있는지 먼저 본다.
  - 둘 다 진행 중 작업(`sheet_conversions` QUEUED·RUNNING, `sheet_audios` RUNNING)이 끝날 때까지 기다려야 한다. backend 배포의 `jobs_done` 조회를 참고한다.
  - `playback`은 Compose 프로필과 자산 볼륨이 필요하다. 두 서비스 모두 `/health`는 이미 있다.
- 후속(이 작업 밖): `omr_service` 테스트가 `JGB_GENERATOR_DIR` 없이 실패하는 15건, Windows 전용 실험 테스트의 다른 OS 실패 1건.
