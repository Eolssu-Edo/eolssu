## 현재 코드에서 확인한 사실

- 백엔드에는 `practice_sessions`의 PK 조회(`PracticeSessionMapper.findById`)만 있다. 인증, 세션 생성 API, 업로드 API, 공통 오류 형식, 파일 저장소 구현이 없다.
- 기능 코드는 `feature/<기능>/{api,application,domain,infrastructure}`에 두고 `config`에서 구현을 연결한다([backend README](../../backend/README.md#폴더와-코드-배치)).
- 필수 검사는 `./gradlew clean build`이고, 저장 모델·마이그레이션 변경에는 `./gradlew databaseTest`(`TEST_DB_*` 필요)를 병합 전에 수행한다. Jenkins는 `clean build`를 실행한다([backend.Jenkinsfile](../../infra/jenkins/backend.Jenkinsfile)).
- 백엔드 실행 이미지는 `eclipse-temurin:21-jre`이며 ffmpeg가 없다. 배포는 서버의 `/opt/eolssu/config/backend.Dockerfile`로 이미지를 만든다.
- AI는 `ai/`의 Python 채점 코드만 있고 서버에서 실행되는 AI 서비스·분석 요청 흐름이 없다.

### U1 메타데이터 칼럼 마이그레이션

- 범위: 다음 Flyway 버전(develop에 V2가 있어 V3 이상, PRA-03의 S15P31E102-173과 번호가 겹치지 않게 조율)으로 `recording_bytes`, `recording_duration_ms`, `recording_sample_rate`, `recording_channels`를 NULL 허용으로 추가한다. `PracticeSessionRow`·Mapper XML 조회 열, [DB 스키마 문서](../contracts/db-schema.md)와 ERD 미결 표를 갱신한다. V1은 수정하지 않는다. 집계 SQL이 `practice_sessions`를 `SELECT *`로 읽지 않는지 확인하고 DATA에 칼럼 추가를 알린다.
- 완료 조건: 기존 행은 NULL, 4개 칼럼이 Row로 매핑된다.
- 검증: `./gradlew clean build`, `./gradlew databaseTest`(기존 버전부터 새 버전까지 신규 적용, 재실행, 고정 행 매핑).
- 되돌리기: 운영 DB 적용 전이면 새 버전 파일 제거. 적용 후에는 새 버전으로만 변경한다.

### U2 녹음 파일 검사기

- 범위: domain에 검사 결과(통과·`TOO_LARGE`·`UNSUPPORTED_FORMAT`·`INVALID_DURATION`)와 메타데이터 모델, infrastructure에 ffprobe 호출 구현. 크기는 읽기 전에 판정하고, 컨테이너가 MP4 계열이며 AAC 오디오 스트림이 있는지, 길이가 0 초과·601.0초 미만인지 본다. Spring multipart 한도를 20MiB 파일 + 여유로 설정한다. 백엔드 이미지와 Jenkins 빌드 환경에 ffmpeg를 설치해 패키지 버전을 고정하고, 확인한 버전을 스펙의 검증 방법에 기록한다. README에 로컬 설치 방법을 적는다.
- 완료 조건: 스펙 완료 판정의 413·415·422 경계(20,971,520/20,971,521바이트, MP3 이름 바꾸기, 0초, 600.5초 통과, 601초 거부)가 검사기 단위에서 맞다.
- 검증: 테스트 중 ffmpeg로 픽스처를 생성하는 단위 테스트, `./gradlew clean build`. ffprobe가 없으면 테스트가 실패해야 하며 건너뛰지 않는다. 이미지에서 `ffprobe -version` 확인.
- 위험: Jenkins 에이전트에 ffmpeg가 없으면 `clean build`가 깨진다. 이미지·에이전트 변경은 Infra와 같은 MR 또는 선행 MR로 맞춘다.

### U3 업로드 API

- 범위: `feature/practice`에 업로드 엔드포인트와 application 서비스. 스펙의 검사 순서(404→409→410→413→415→422→503)를 따르고, 저장 성공 후 `recording_url = recordings/{id}.m4a`, 메타데이터 4개, `ended_at`(업로드 성공 시각), `status = PENDING`을 한 번의 조건부 갱신(`WHERE status = 'RECORDING'`)으로 기록한다. 갱신 0행이면 409로 처리하고 방금 저장한 객체를 지운다. 성공은 202. 거부는 `common/error`의 ProblemDetail + `code`(D6, 스펙 표의 7개 코드). domain 저장소 계약과 GCS 구현(D4: 객체 쓰기·삭제, 15분 V4 서명 URL 생성), 테스트용 메모리 대역. 버킷 공개 차단·수명 주기 규칙 설정 방법과 환경변수 예시를 README에 기록한다.
- 완료 조건: 스펙 완료 판정의 성공·409·404·410·503·재업로드 항목.
- 검증: 저장소 대역을 쓴 application 단위 테스트, 고정 시계로 만료 경계(40분 직전·직후), `databaseTest`로 조건부 갱신과 동시 업로드 2건 중 1건만 성공. 테스트 전용 GCS 버킷에 실제 쓰기·읽기·삭제 1회(인증 정보가 필요한 수동·별도 검사로 두고 `clean build`에는 넣지 않는다).
- 위험: 저장 성공 후 DB 갱신 실패 시 고아 파일. 실패 경로에서 삭제를 시도하고, 남은 파일은 버킷의 30일 수명 주기 규칙이 정리한다.

### U4 업로드 만료 배치

- 범위: `RECORDING`이고 `started_at < now - 40분`인 세션을 `FAILED`·`UPLOAD_TIMEOUT`으로 바꾸는 `@Scheduled` 작업. 주기는 5분 제안. 갱신 조건에 `status = 'RECORDING'`을 넣어 업로드와 경쟁하지 않게 한다.
- 완료 조건: 40분 경계 전후 행이 올바르게 바뀌고 다른 상태 행은 그대로다.
- 검증: 고정 시계·고정 행으로 `databaseTest`. 스케줄러 자체는 기본 프로필(무DB)에서 생성되지 않아야 하므로 기존 시작 테스트가 계속 통과하는지 `clean build`로 확인.

### U5 분석용 변환

- 범위: AI 서비스가 원본 m4a를 16kHz·모노·PCM16으로 디코딩한다(메모리 배열 또는 임시 WAV, 분석 후 폐기). AI 실행 환경에 ffmpeg를 둔다. 실패 시 `FAILED`·`DECODE_ERROR`.
- 완료 조건: 픽스처 변환 결과가 16kHz·1채널·PCM16이고 길이 차이 1초 미만, 손상 파일은 `DECODE_ERROR`.
- 검증: 해당 파트의 단위 테스트(AI면 `uv run pytest`). 실제 채점 품질 검증으로 보고하지 않는다.
- 차단: 분석 요청 흐름(백엔드→AI)이 없다. 변환 함수와 테스트는 먼저 만들 수 있지만 `FAILED` 기록은 흐름이 생긴 뒤 연결한다.

- 완료 조건: 스펙 완료 판정의 앱 항목.
- 검증: 플랫폼별 실제 실행(Android 에뮬레이터·iOS 시뮬레이터). 저장된 파일을 ffprobe로 확인한다. 단위 테스트만으로 완료 보고하지 않는다.

### U7 한도 실측

- 범위: U6의 녹음 기능으로 플랫폼별 10분 녹음을 만들어 ffprobe 값과 디코딩 프레임 수를 기록하고, 스펙의 크기·길이 숫자와 U2 설정을 갱신한다.
