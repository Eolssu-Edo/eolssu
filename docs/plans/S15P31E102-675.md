# S15P31E102-675 내 악보 생성 음원의 연주 위치 정보 연결

- [Jira 작업](https://ssafy.atlassian.net/browse/S15P31E102-675) · [내 악보 작성·편집](https://ssafy.atlassian.net/browse/S15P31E102-319)
- 작업 기준 `origin/develop` `8d958652`. SHT-13과 생성기의 호환 계약은 [음원 스펙](../specs/sheet-audio.md)에 기록한다.
- 완료 조건은 내려받은 M4A의 반복·빠르기·길이 기호가 연습의 강조와 탐색에 반영되고, 기존 다운로드 및 생성기와 함께 동작하는 것이다.

## 작업 순서

1. 생성 HTTP 요청에서 시간표를 선택적으로 요구한다. 최종 M4A와 확정 악보 스냅샷의 해시·버전을 시간표에 연결한다.
2. 백엔드는 기존 ZIP과 새 ZIP을 모두 읽는다. 요청과 결과의 신원·용량을 확인하고, 현재 음원의 임시 다운로드 응답에 시간표를 함께 제공한다.
3. 앱은 내려받은 파일과 시간표를 함께 기기에 저장하고, 내 악보 연습에서 기존 `ScorePerformance`를 재사용한다. 시간표가 없는 예전 파일은 기존 악보 시각을 쓴다.
4. 작은 반복·빠르기·길이 기호 사례, ZIP 호환, 저장 시 버전·해시 대조, 시간표 유무에 따른 연습을 검증한다.

## 진행

- Jira에서 기존 작업 재개와 활성 스프린트 배정을 확인했다.
- 구현을 마치고 병합 전 검증을 진행한다.
- 선택적인 내부 요청 헤더와 ZIP 항목을 사용한다. 기존 생성기·백엔드는 요청 헤더가 없거나 시간표가 없는 경로를 처리한다.
- 검증한 시간표는 기기 음원 메타데이터에 원자적으로 저장한다. 정간 표시와 탐색은 기존 연주 시간표 모델을 사용한다. 장단은 실제 연주 경과 시간과 생성 BPM에 맞춘다.
- Python 렌더러에서 반복·빠르기·길이 기호를 함께 적용해 8.750초의 연주 시간표와 최종 AAC-LC M4A 해시를 대조했다. 내부 HTTP의 선택 요청, 백엔드의 응답 해시 대조, 앱의 기존 저장본과 시간표 연결을 단위 검사했다.
- 운영과 실기기 검증은 아직 진행하지 않았다.

## 검증 기록

- 구현 커밋 `e58775d1`. `develop` `7caf0b73`을 통합한 `f834021d`에서 동작을 확인했다.
- `python -m pytest -q data/src/playback/tests`에서 247개 테스트와 1,432개 하위 사례가 통과했다. 로컬 CAT v1.3·FFmpeg 7.1.1 HTTP 검증에서 원본 단소 악보를 소금 음색으로 렌더했다. 시간표의 8개 구간은 8.750초, M4A는 꼬리 0.550초를 포함해 9.300초였다. 확정 악보와 최종 M4A의 SHA-256이 각각 일치했다.
- 백엔드 HTTP 클라이언트 검사에서 이전 ZIP과 선택 시간표를 모두 수신했다. 악보 해시·악보 버전·M4A 해시가 다르면 시간표를 제외했다.
- 격리 MySQL의 음원 검사 38개가 두 실행에서 모두 통과했다. 처음 실행에서는 로컬 실제 음원 확인 요청과 전역 렌더 슬롯을 공유해 한 건이 대기로 돌아갔다. 이 테스트는 단독 재실행에서 통과했다. 장단 포함 테스트는 로컬 장구 검사용 합성 파형을 사용했다.
- 백엔드 전체 단위 검사에서 카카오 요청 기한 검사 한 건이 실패했다. 해당 테스트와 음원 HTTP 검사를 별도로 다시 실행했을 때는 통과했다.
- Android 호스트 검사는 1,228개 중 1,224개가 통과했고 4개는 건너뛰었다. 기기 저장 파일의 재열기, 버전이 다른 시간표 제외, 반복된 정간 강조와 탐색, 기존 다운로드를 검사했다. Windows에서 iOS 실기기는 검사하지 않았다.
