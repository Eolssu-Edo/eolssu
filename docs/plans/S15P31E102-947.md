## 문제

- `PracticeAnalysisConfig`의 분석 실행기(업로드 뒤 분석·다시 시도, 작업자 2·대기열 50)는 `setWaitForTasksToCompleteOnShutdown(false)`였다. 블루그린 배포가 이전 슬롯을 내리면 실행 중인 분석은 중단되고 대기열의 분석은 버려졌다. 그 세션은 제한 시간(60초) 뒤 `TIMEOUT`이 되어 사용자가 다시 시도해야 했다.
- 실행기는 Bean이 아니라서 Spring Boot가 `executor_*` 지표를 붙이지 않았고, 백엔드 코드에 `MeterRegistry` 사용이 없었다. 대기열이 밀리거나 거절되는지 볼 수 없었다.
- 배포 스크립트(`infra/jenkins/deploy-backend.py`)는 이전 슬롯을 내리기 전에 Nginx 연결과 악보 변환만 기다리고 연주 분석은 확인하지 않는다.

## 결정

| 항목 | 선택 | 근거 |
| --- | --- | --- |
| 종료 시작 | `ContextClosedEvent`에서 실행기의 `initiateShutdown()`을 부른다. 새 분석은 받지 않고, 이미 받은 분석(실행 중·대기열)은 계속 처리한다 | 웹 서버 마무리(최대 120초)와 같은 때 시작해야 Bean을 닫을 때 기다리는 시간이 컨테이너 종료 대기(250초) 안에 든다. Spring 실행기 Bean의 기본 동작(`acceptTasksAfterContextClose=false`)과 같다 |
| 기다리는 시간 | `eolssu.analysis.shutdown-wait`, 기본 제한 시간 + 5초(65초) | 종료 전에 시작한 시도는 이 시간 안에 모두 마감을 넘긴다. 마감 뒤 결과는 저장되지 않으므로 더 기다려도 얻는 것이 없다 |
| 다 못 끝낸 분석 | 바꾸지 않는다. 예전처럼 `PENDING`으로 남아 제한 시간 뒤 상태 조회가 `TIMEOUT`으로 끝내고, 사용자는 다시 시도한다 | 174·175의 기존 흐름을 그대로 쓴다 |
| 종료 중 거절 | 업로드 뒤 분석은 `PENDING`으로 남는다(기존 대기열 가득 참과 같다). 다시 시도는 그 시도를 바로 실패로 기록한다(`RetryPracticeAnalysis.failStart`) | 전환 뒤에는 Nginx가 새 슬롯으로 보내므로 이전 슬롯에 새 요청이 거의 오지 않는다 |
| 배포 스크립트 | 바꾸지 않는다 | `compose stop`(제한 270초)이 앱 종료를 기다리고, 앱이 분석을 기다린다. 스크립트에서 분석을 따로 셀 방법(슬롯별 표시)이 DB에 없다 |
| 지표 위치 | 설정 계층(`AnalysisExecutorMetrics`)에서 `TaskDecorator`·`RejectedExecutionHandler`·`ExecutorServiceMetrics`로 붙인다 | 분석 업무 코드(`AnalyzePracticeSession`)에 Micrometer를 들이지 않는다 |

## 지표

| Prometheus 이름 | 종류 | 뜻 |
| --- | --- | --- |
| `executor_active_threads{name="analysis"}` | 게이지 | 지금 분석 중인 작업자 수 |
| `executor_queued_tasks{name="analysis"}` | 게이지 | 대기열에서 기다리는 분석 수 |
| `executor_queue_remaining_tasks{name="analysis"}` | 게이지 | 대기열 남은 자리 |
| `executor_pool_size_threads`·`executor_pool_core_threads`·`executor_pool_max_threads{name="analysis"}` | 게이지 | 작업자 스레드 수 |
| `executor_completed_tasks_total{name="analysis"}` | 카운터 | 끝난 분석 작업 수 |
| `eolssu_analysis_ready` | 게이지 | 분석 연결(AI 주소·악보 음표·녹음 URL)이 갖춰졌으면 1 |
| `eolssu_analysis_queue_wait_seconds` | 타이머 | 실행기에 넘긴 뒤 작업자가 잡기까지 걸린 시간 |
| `eolssu_analysis_run_seconds` | 타이머(분포 100ms~120s) | 작업자가 분석 하나를 처리·저장한 시간. p95 계산용 `_bucket` 포함 |
| `eolssu_analysis_rejected_total{reason}` | 카운터 | 받지 못한 분석. `queue_full`·`shutdown` |
| `eolssu_analysis_outcomes_total{outcome}` | 카운터 | 결과 코드별 수. `DONE`·`SERVER_ERROR`·`TIMEOUT`·`NOT_PENDING`·`STALE`·`DISCARDED`와 AI 실패 사유(`NO_SOUND` 등) |

두 카운터는 알려진 이유·결과 코드를 앱 시작 때 0으로 만들어 둔다. 슬롯이 바뀐 뒤 첫 사건에서 계열이 처음 생기면 `increase()`가 그 1건을 놓치기 때문이다.

Grafana [백엔드 성능 대시보드](../../infra/monitoring/dashboards/eolssu-backend.json)에 `연주 분석 실행기` 행(실행 중·대기열, 실행·대기 시간, 결과·거절)을 더했다. Prometheus는 `frontend:8081`로 **활성 슬롯만** 수집하므로 내려가는 슬롯의 종료 중 수치는 보이지 않는다. 종료 확인은 아래 로그로 한다.

## 운영 적용 절차

2026-11-15 사용자 결정으로 `develop` 병합 직후 Jenkins 블루그린 배포가 반영한다.

1. MR을 `develop`에 병합하면 기존 Jenkins 백엔드 배포가 블루그린으로 반영한다. 설정·Compose·배포 스크립트 변경은 없고 기본값(65초)을 쓴다. 기다리는 시간을 바꿔야 하면 운영 Compose는 backend 환경 변수를 이름으로만 넘기므로 `infra/runtime/compose.yml`의 `backend-env`에 `EOLSSU_ANALYSIS_SHUTDOWN_WAIT`(초)를 더하는 변경을 따로 한다. 값은 `stop_grace_period`(250초) − 웹 마무리(120초)보다 짧게 둔다.
2. 배포 뒤 수집을 확인한다. `docker exec eolssu-monitoring-prometheus-1 wget -qO- http://frontend:8081/api/actuator/prometheus | grep -E '^(eolssu_analysis_ready|executor_active_threads\{name="analysis")'`에서 `eolssu_analysis_ready 1.0`과 실행기 줄이 보여야 한다.
3. Grafana에서 [백엔드 성능 대시보드](../../infra/monitoring/README.md#grafana-백엔드-성능)를 다시 가져와 `연주 분석 실행기` 행을 확인한다.
4. 그다음 배포 때 이전 슬롯 로그(`/var/log/eolssu/ordinary/`)에서 `Commencing graceful shutdown` 뒤에도 `Analysis finished session=…` 줄이 이어지는지 본다. 65초 안에 못 끝내면 Spring이 `Timed out while waiting for executor` 경고를 남긴다. 그 세션은 제한 시간 뒤 `TIMEOUT`이 되므로 다시 시도로 회복된다.
5. 되돌리기: 이전 JAR로 블루그린 배포를 다시 하거나 커밋을 되돌린다. 스키마·설정 변경이 없어 앱만 바꾸면 된다.
