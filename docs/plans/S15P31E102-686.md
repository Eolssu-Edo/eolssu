# S15P31E102-686 이메일 인증번호 발송의 이메일 형식 검증 강화

- Jira: [S15P31E102-686](https://ssafy.atlassian.net/browse/S15P31E102-686)
- 브랜치: `fix(be)/S15P31E102-686-이메일-인증번호-발송의-이메일-형식-검증-강화`, 기준 `origin/develop` `1a6e28b4`

## 목표와 범위

- 문제: 비밀번호 찾기에서 `a@b`처럼 형식이 틀린 이메일도 인증번호를 "보냈어요"로 처리했다. 서버는 Hibernate `@Email`과 320자 검사만 했고 `@Email`은 점 없는 도메인·연속 점 도메인 등을 통과시킨다. 앱 정규식 `^[^\s@]+@[^\s@]+\.[^\s@]+$`도 `a@b..com`, `a..b@c.com`, `a,b@c.com`, `a@b.c`를 통과시켰다.
- 완료 조건: `POST /api/auth/email-verifications`가 모든 `purpose`에서 형식이 틀린 이메일을 `400 INVALID_REQUEST`로 거절하고 인증 행을 만들거나 메일을 보내지 않는다. 앱은 같은 규칙으로 보내기 전에 막고 기존 `EmailInvalid` 오류를 보인다.
- 범위 밖: 로그인 요청(`SignInRequest`)의 서버 검증, 로그인 화면 파일(S15P31E102-683 담당). 가입 요청은 아래 '가입 요청과의 관계'처럼 별도 변경 없이 같은 규칙이 적용된다.

## 채택한 규칙

서버 `feature/auth/domain/EmailPolicy`와 앱 `core/model/EmailRule`에 같은 규칙을 한 곳씩 둔다(기존 `PasswordPolicy`·`PasswordRule` 짝과 같은 배치).

- 로컬부: ASCII `A-Z a-z 0-9 . _ % + -`, 점으로 시작·끝나거나 점이 연속하면 안 되고 64자 이하.
- `@`는 정확히 하나.
- 도메인: 점으로 나눈 라벨이 둘 이상. 라벨은 영문·숫자·하이픈 1~63자이고 하이픈으로 시작·끝나지 않는다.
- 최상위 도메인: 영문 2~63자.
- 전체 320자 이하(로컬 64 + `@` + 도메인 255).
- 서버는 소문자화한 값을, 앱은 앞뒤 공백을 자른 값을 검사한다(앱은 자른 값을 보낸다).

선택 이유: 국내 메일 서비스와 회사·학교 주소를 모두 받으면서 사용자가 실수로 넣는 형식 오류(점 누락·연속 점·쉼표·공백·한 글자 TLD)를 막는 실용 규칙이다. RFC 5322의 따옴표 로컬부·IP 리터럴·국제화 주소는 받지 않는다. 현재 가입은 이 API의 인증을 거쳐야 하므로 기존 이메일 회원 주소는 모두 ASCII 형식이다.

## 유지한 정책

- 비밀번호 찾기·계정 연결은 형식이 맞으면 회원이 아니어도 `202`로 답하고 메일은 보내지 않는다(계정 존재 노출 방지). 형식 검사는 회원 조회 전에 하므로 `400`이 회원 여부를 드러내지 않는다.
- 재설정은 DB 비교로 찾은 등록 주소로만 보낸다. 다만 악센트 변형(`mémber@…`)은 이제 형식 단계에서 `400`이므로, 이 경로의 테스트는 대소문자 변형과 등록 주소 발송으로 바꿨다.

## 가입 요청과의 관계

`POST /api/auth/sign-up`은 `SIGN_UP` 인증 토큰의 이메일과 요청 이메일이 같아야 가입되므로, 새 규칙을 통과한 주소만 가입할 수 있다. 가입 요청 자체의 `@Email` 검사는 그대로 두었다.

## API 계약 변화

- 요청 `email`: 기존 `NotBlank`·`@Email`·320자에 위 형식 규칙이 더해진다. 어긋나면 모든 `purpose`에서 `400 INVALID_REQUEST`이며 인증 행·발송·발송 한도 기록이 생기지 않는다.
- 응답 필드·상태 코드 종류는 바뀌지 않는다.
