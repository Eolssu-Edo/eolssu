### 예외 중단과 바이너리 롤백

- 새 버전을 유지하며 예외만 중단할 때는 `AUTH_NON_EXPIRING_USER_IDS`를 비워 backend에 다시 주입한다. 이 동작은 구버전 JAR로의 롤백과 다르다.
- 구버전은 `RefreshTokenRow.expiresAt`이 non-null이므로, NULL 세션이 있는 상태에서 JAR만 되돌리면 refresh 조회가 500이 될 수 있다.
- 구버전 복구 순서: 예외 발급 중단 → NULL 세션을 아래 SQL로 만료·폐기 → NULL 행이 0인지 확인 → 기존 JAR·Compose·환경 설정 복구 → readiness·기존 로그인·refresh 확인. V7의 nullable 스키마를 다시 NOT NULL로 바꿀 필요는 없다.

```sql
UPDATE refresh_tokens
SET expires_at = UTC_TIMESTAMP(6),
    revoked_at = COALESCE(revoked_at, UTC_TIMESTAMP(6)),
    revoke_reason = COALESCE(revoke_reason, 'SIGN_OUT')
WHERE expires_at IS NULL;
SELECT COUNT(*) FROM refresh_tokens WHERE expires_at IS NULL;
```

- 폐기용 MySQL 8.4에서 활성 무기한·이미 ROTATED인 무기한·일반 유효 세션 각각 한 행으로 검증했다. SQL 후 NULL 행 0, 활성 무기한은 SIGN_OUT, 기존 ROTATED 사유는 보존, 일반 세션의 만료 시각·미폐기 상태도 보존됐다. 운영 데이터에 이 검증 SQL을 실행하지 않았다.
