# edo1·edo2 Docker 기본 로그 크기 회전 제한 준비

[작업 S15P31E102-713](https://ssafy.atlassian.net/browse/S15P31E102-713) · [운영 모니터링 Story](https://ssafy.atlassian.net/browse/S15P31E102-41) · 스프린트 5

## 범위와 완료 조건

- 712에서 회전 한도가 없는 `json-file` 컨테이너를 edo1 11개, edo2 7개 확인했다. 양쪽 모두 Docker 기본 드라이버는 `json-file`이며 데몬 구성 파일·실행 인자에 별도 로그 옵션이 없다.
- 신규 기본 `json-file` 컨테이너에 10 MiB 파일 3개 한도를 준비한다. 18개 모두 이 한도로 바뀌면 명목 상한은 약 540 MiB다. 최대 증가량을 보인 edo2 대기 OMR의 1.04 MiB/일 표본을 기준으로 용량 경계를 정했다. 파일 회전은 날짜 기준의 보존 정책과 별도로 적용한다.
- 두 운영 호스트의 Docker 버전에서 구성 문법을 검사한다. 별도 컨테이너의 합성 로그로 파일 회전과 최신 로그 조회를 검증한다. 앱 일반 로그 14일 정책, 기존 로그 파일, 컨테이너별 드라이버와 운영 적용 순서는 별도 관리한다.

## 검증과 적용 상태

- edo1 Docker 29.9.2와 edo2 Docker 29.1.3에서 후보 파일의 `dockerd --validate`가 통과했다.
- edo2에서 기존 로컬 이미지를 사용해 네트워크가 없는 일회용 컨테이너를 실행했다. 동일한 10 MiB·3개 옵션에 합성 4,600줄을 기록해 파일 3개와 합계 28,031,554바이트를 확인했다. `docker logs`는 오래된 첫 줄 대신 1,211번째 줄부터 시작했고 마지막 4,600번째 줄을 조회했다. 일회용 컨테이너를 제거했다.
- 운영 적용 전 상태다. edo2는 아래 단계별 계획에 따라 먼저 검토한다.

## 운영 재시작 영향 (2026-11-11 KST)

- 양 호스트 모두 `LiveRestoreEnabled=false`다. 현재 구성에서 Docker 데몬을 재시작하면 edo1 실행 컨테이너 19개와 edo2 실행 컨테이너 7개가 각 호스트의 재시작 동안 중단된다. 모두 `unless-stopped`이므로 재기동 대상이며 실제 중단 시간은 측정 전이다.
- edo1은 공개 웹·API, 운영 MySQL, Jenkins 및 모니터링이 영향 범위다. edo2는 대기 애플리케이션과 대기·복제 MySQL이 영향 범위다. edo2의 복제 터널은 활성 상태이며 `docker.service`를 요구한다. 적용 시 컨테이너 상태와 별도로 터널·복제 재연결을 확인한다.
- Docker 재시작으로 기본값을 적용해도 기존 컨테이너의 로그 옵션은 생성 당시 값을 유지한다. 현재 실행 중인 미설정 `json-file` 컨테이너는 호스트별 7개다. edo1의 중지 보관본 4개를 포함한 기존 컨테이너 전환은 로그 보존과 재생성 시점을 따로 검토한다. [Docker live restore](https://docs.docker.com/engine/daemon/live-restore/) · [로깅 기본값 적용 범위](https://docs.docker.com/engine/logging/configure/)

## edo2 우선 적용 계획 (2026-11-11 KST)

- 데몬 기본값을 바꾸는 대신 기존 Compose 서비스에 회전 옵션을 지정해 재생성 범위를 한 서비스로 제한한다. 실제 대기·복제 Compose 파일에 후보 설정을 읽기 전용으로 병합해 7개 모두 로그 설정만 달라지는지 확인했다. 7개 모두 실행 이미지 ID와 설정 해시가 원본 파일의 현재 값과 일치했다.
- 대기 OMR로 먼저 검증하고 나머지 대기 서비스를 한 번에 하나씩 전환한다. 운영 복제 MySQL은 마지막 변경 구간에 같은 볼륨과 네트워크로 재생성한다. 대기 웹·API 세 경로는 현재 HTTP 200이며, 운영 복제 수신·적용은 모두 정상이고 지연은 0초다.
- 다음 단계로 넘어가려면 대상의 기동과 새 로그 옵션, 다른 컨테이너 ID, 대기 HTTPS와 복제를 확인한다. 복제 MySQL 전환 후에는 감시 성공 2회와 원본 GTID 적용을 확인한다. 각 단계는 직전 Compose 파일로 되돌릴 수 있다. [실행·복제 확인·롤백 절차](../../infra/docker/README.md#edo2-단계별-적용)
- edo2에서 실제 중단 시간과 복제 재접속·GTID 확인 시간을 기록하고 그 결과로 edo1 적용 여부를 결정한다.

### 리뷰 P2 보완 검증

- 두 MySQL에 적용·롤백 공통 종료 유예 60초와 종료 이벤트 확인을 추가했다. edo2 Compose 모의 실행에서 대기·복제 MySQL 각각 지정한 컨테이너만 재생성 대상으로 잡혔다. 조회 전후 실행 컨테이너 7개의 ID는 같았다. Docker 종료 이벤트 조회는 실행됐으며 조회 구간에 종료 이벤트는 없었다.
- 터널과 타이머를 따로 확인했다. 실제 두 유닛과 복제 점검기가 통과했고, 둘 중 하나를 존재하지 않는 유닛으로 대체한 두 읽기 검사에서 각각 실패를 확인했다. 60초 journal 조회에서 감시 정상 완료 3건을 확인했다. 문서의 셸 예제 5개는 문법 검사를 통과했고, 점검 분기 4개와 이미 종료된 MySQL의 이벤트 조회 생략을 격리 입력으로 확인했다.
- 감시·GTID 미통과와 볼륨·네트워크 불일치에서 적용을 중단하고, 불일치 시 기존 대상을 식별할 때까지 상태를 보존하도록 복구 절차를 보완했다. 실제 MySQL 종료·재생성·롤백과 전환 후 GTID는 운영 적용 단계에서 확인한다.
