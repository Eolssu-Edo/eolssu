## 범위와 완료 조건

- 712에서 회전 한도가 없는 `json-file` 컨테이너를 edo1 11개, edo2 7개 확인했다. 양쪽 모두 Docker 기본 드라이버는 `json-file`이며 데몬 구성 파일·실행 인자에 별도 로그 옵션이 없다.
- 신규 기본 `json-file` 컨테이너에 10 MiB 파일 3개 한도를 준비한다. 18개 모두 이 한도로 바뀌면 명목 상한은 약 540 MiB다. 최대 증가량을 보인 edo2 대기 OMR의 1.04 MiB/일 표본을 기준으로 용량 경계를 정했다. 파일 회전은 날짜 기준의 보존 정책과 별도로 적용한다.
- 두 운영 호스트의 Docker 버전에서 구성 문법을 검사한다. 별도 컨테이너의 합성 로그로 파일 회전과 최신 로그 조회를 검증한다. 앱 일반 로그 14일 정책, 기존 로그 파일, 컨테이너별 드라이버와 운영 적용 순서는 별도 관리한다.

## 운영 재시작 영향 (2026-11-11 KST)

- 양 호스트 모두 `LiveRestoreEnabled=false`다. 현재 구성에서 Docker 데몬을 재시작하면 edo1 실행 컨테이너 19개와 edo2 실행 컨테이너 7개가 각 호스트의 재시작 동안 중단된다. 모두 `unless-stopped`이므로 재기동 대상이며 실제 중단 시간은 측정 전이다.
- edo1은 공개 웹·API, 운영 MySQL, Jenkins 및 모니터링이 영향 범위다. edo2는 대기 애플리케이션과 대기·복제 MySQL이 영향 범위다. edo2의 복제 터널은 활성 상태이며 `docker.service`를 요구한다. 적용 시 컨테이너 상태와 별도로 터널·복제 재연결을 확인한다.
- Docker 재시작으로 기본값을 적용해도 기존 컨테이너의 로그 옵션은 생성 당시 값을 유지한다. 현재 실행 중인 미설정 `json-file` 컨테이너는 호스트별 7개다. edo1의 중지 보관본 4개를 포함한 기존 컨테이너 전환은 로그 보존과 재생성 시점을 따로 검토한다. [Docker live restore](https://docs.docker.com/engine/daemon/live-restore/) · [로깅 기본값 적용 범위](https://docs.docker.com/engine/logging/configure/)

### 적용 직전과 단계 사이 확인

1. 작업 직전에 배포·백업·대기계 승격과 겹치지 않는지 확인한다. 적용 대상의 ID, 실행 이미지 ID, 포트·마운트·네트워크·재시작 정책, 운영 웹·API와 복제 기준 상태를 기록한다. 직전 실행 정의와 이미지, 보존이 필요한 기존 로그는 호스트의 권한 제한 경로에 보관한다. 원본과 복구 대상을 식별할 수 있을 때 시작한다.
2. 모니터링 `/home/ubuntu/eolssu-monitoring/compose.yml`의 세 서비스와 Jenkins `/opt/eolssu/jenkins/compose.yml`의 `controller`는 설치 설정과 실행 이미지·구성 해시가 일치했다. 운영 Compose에 읽기 전용으로 병합한 후보는 각각 해당 서비스의 `logging`만 달라졌다. 실행 승인 후 실제 후보로 `config --quiet`와 설정 차이를 다시 확인하고 지정한 서비스 한 개에만 `up -d --no-deps --pull never --no-build --wait --wait-timeout <초> <서비스>`를 사용한다. 적용 후 새 `LogConfig`, 같은 이미지·데이터 마운트·네트워크, 다른 컨테이너 ID와 서비스 응답을 확인한다. 모니터링의 수집 주기는 15초이며 준비 이후 60초 이내 두 대상의 새 성공을 확인하는 것을 기준으로 제안한다. [모니터링 절차](../../infra/monitoring/README.md) · [Compose 적용 옵션](https://docs.docker.com/reference/cli/docker/compose/up/)
3. 블로그 두 개와 복제 프록시는 독립 컨테이너다. 현재 포트와 마운트는 확인했고 배포에 사용하는 실행 원본은 확인이 남아 있다. 각 단계는 기존 배포 경로, 회전 옵션만 바뀐 실행 정의, 같은 포트와 데이터로 되돌리는 경로를 재현할 수 있을 때 진행한다. 블로그는 다음 편집 API 배포 창에 적용하는 것을 우선한다. 공개 편집 경로는 `https://team-edo.github.io` Origin을 사용한 읽기 요청으로 검증한다.
4. Jenkins는 진행 중 빌드·배포가 끝날 때까지 기다리고 `quiet-down` 상태에서 실행 중 빌드와 대기열이 모두 비었는지 확인한다. 대기열을 비울 수 없으면 창을 미룬다. 기존 종료 유예 120초를 유지하고 기동·준비에는 180초를 둔다. 재기동 뒤 빌드 시작이 계속 제한되는지 확인하고 필요하면 즉시 `quiet-down`을 다시 적용한다. 기존 온라인 에이전트의 복귀와 운영 웹·API를 확인한 뒤 작업 전 빌드 수락 상태를 복원한다. 기존 홈과 인증 자료를 그대로 사용한다. [Jenkins 컨트롤러 절차](../../infra/jenkins/controller/README.md)
5. 각 단계 전후에 edo2의 `eolssu-replication-tunnel.service`와 `eolssu-replication-watch.timer`를 개별 확인하고 기존 복제 점검기를 실행한다. 프록시 전환 직전 복제본의 실행 GTID를 기록한다. 전환 후 TCP 수신부터 최대 60초 안에 감시 2회 연속 성공을 확인한다. 수신·적용 모두 `Yes`, 오류 번호 모두 `0`, 원본 ID `1`, GTID 자동 위치 `1`, 지연 `0–10초`가 기준이다. edo1 원본에서 읽은 전환 후 기준점에 edo2가 `WAIT_FOR_EXECUTED_GTID_SET(기준점, 30) = 0`으로 도달하고 전환 전 GTID가 보존됐는지 확인한다. 새 GTID가 생긴 경우 전달 여부를 별도로 기록한다. [복제 점검과 GTID 확인](../../infra/docker/README.md#edo2-단계별-적용)
6. 대상 기동·서비스 응답·로그 옵션 검증 실패, 예상과 다른 이미지·마운트·네트워크·다른 컨테이너 ID, 운영 웹·API 상태 악화, 복제 기준 미달 중 하나라도 발견되면 다음 단계를 중단한다. 실패한 대상의 상태와 로그를 보관하고, 대상과 데이터 경로가 일치하면 그 단계의 직전 정의로 복원해 같은 검사를 반복한다. 데이터 경로나 복구 대상이 다르거나 복원 후에도 장애가 남으면 현재 상태를 보존하고 장애 대응으로 전환한다. 단계별로 실제 응답 공백, 준비·복제 회복 시간, 검증 결과와 롤백 여부를 기록한다.

읽기 전용 기준 확인에서 운영 웹·약관·준비 상태는 HTTP 200이고 준비 상태는 `UP`이었다. Grafana·Prometheus·Jenkins가 응답했고 두 수집 대상이 `up`이었다. 공개 블로그 편집·조회수 응답과 edo2 터널·타이머·복제 점검도 통과했다. 실제 작업 창의 Jenkins 빌드·대기열과 독립 컨테이너 실행 원본은 적용 전 확인 항목으로 남아 있다.
