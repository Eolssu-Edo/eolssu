# S15P31E102-940 발표 전 가입·주요 API 동시 접속 리허설

- 운영 모니터링 Story 41, 스프린트 5, 진행 중. [Jira 작업](https://ssafy.atlassian.net/browse/S15P31E102-940) · [결과](../knowledge/infra/demo-load-rehearsal.md) · [실행 방법](../../infra/loadtest/README.md)
- 문제: 부하 시험 도구나 결과가 없었다. 이메일 인증이 전역 잠금 안에서 SMTP를 보내 동시 가입 때 503이 날 수 있다는 코드 조사만 있었다.
- 범위: 격리된 로컬 환경에서 시연 규모(동시 10~30명)로 가입·로그인·조회·업로드→분석을 재현해 수치·병목·시연 대책을 남긴다. 운영 서버 부하와 코드 수정은 범위 밖이다(main 반영 11-17 직전).

## 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 도구 | 표준 라이브러리 Python(`infra/loadtest/`) | k6가 설치돼 있지 않았다. infra의 다른 스크립트와 같이 의존성 없이 Jenkins `python3 -B -m unittest`로 검사할 수 있다 |
| 메일 | STARTTLS 가짜 SMTP + JVM 전용 truststore | 백엔드가 STARTTLS 필수·서버 이름 확인을 코드로 고정한다(`SmtpVerificationMailSender.kt:68-79`). 코드나 설정을 바꾸지 않고 실제 발송 경로를 그대로 탄다. `memory` 모드는 인증번호를 밖에서 읽을 수 없다 |
| AI | 고정 지연 대역 | 백엔드 실행기·60초 제한은 실제 코드로 두고 분석 비용만 운영 실측값(4초·6초)으로 바꾼다. 동시 실행 수를 늘리는 효과는 이 대역으로 판단하지 않는다 |
| 프로필 | `ops` | 운영과 같은 풀 10·대기 2초·`socketTimeout=2000`으로 실패 양상을 맞춘다. 마이그레이션은 배포와 같은 1회성 `db` 실행으로 적용했다 |
| 시연 방식 (2026-11-15 사용자 결정) | 청중은 미리 준비한 계정으로 로그인하고, 녹음 체험은 한 번에 10명 이하로 나눈다 | 이메일 가입은 동시 3~10명에서 503이 난다. 로그인 30명은 문제가 없고, 녹음 10명은 분석 4~6초 기준 모두 결과를 받는다(마지막 22~32초 대기) |

## 검증

- `python3 -B -m unittest discover -s infra/loadtest/tests -p 'test_*.py'`: 8건 통과(Python 3.9.6, 3.12). 백분위, 단계별 성공 판정, 쿠키·multipart, 메일 로그의 인증번호 읽기, 가짜 SMTP 지연·기록, AI 대역 응답 형식을 확인한다.
- 실제 실행(2026-11-15 KST): 폐기용 MySQL 8.4.9, 백엔드 `bootJar`(`25f7d263`), 가짜 SMTP·AI로 smoke 1명(가입→로그인→업로드→DONE)을 통과한 뒤 23개 시나리오를 측정했다. 수치는 [결과](../knowledge/infra/demo-load-rehearsal.md)에 있다. 측정 뒤 프로세스를 종료했고, 임시 MySQL은 종료·파일 해제를 확인한 뒤 데이터 폴더를 지웠다.
