## 확정안(2026-10-27, 오은서)

이 채팅에서 사용자가 추천안 그대로 확정했다.

### 마이페이지 간편 로그인 연결·해제

| 기능 | 경로 | 요청 / 응답 | 오류 |
| --- | --- | --- | --- |
| 연결 | `POST /users/me/social-accounts/{provider}` | 요청 `authorizationCode`·`redirectUri`·`state`(AUTH-05와 같음) / 201 `provider`·`linkedAt` | 409 `PROVIDER_ALREADY_LINKED`(이 회원에 같은 제공자, `uq_user_social_accounts_user_provider`), 409 `SOCIAL_ACCOUNT_IN_USE`(다른 회원에 연결됨, `uq_user_social_accounts_provider_user`), 401 `OAUTH_VERIFICATION_FAILED` |
| 해제 | `DELETE /users/me/social-accounts/{provider}` | 204 | 404 `RESOURCE_NOT_FOUND`(연결 없음) |
| 목록 | 별도 API 없음 | USR-01 `GET /users/me` 응답에 `linkedProviders`(제공자·연결 시각) 추가 | — |

- 로그인한 회원만 쓴다. 제공자 이메일이 가입 이메일과 달라도 연결할 수 있다.
- 모든 회원에 이메일·비밀번호가 있어 해제해도 로그인 수단이 남는다. AUTH-09의 "마지막 로그인 수단 해제 금지" 검사는 따로 두지 않는다.
- 제공자 사용자 ID·제공자 이메일은 응답에 넣지 않는다.

### CSRF

- Spring Security CSRF 토큰은 쓰지 않는다. 대신 세 가지를 함께 쓴다.
  - SameSite=Lax 쿠키(이미 결정)
  - 상태를 바꾸는 요청(POST·PUT·PATCH·DELETE)은 `Content-Type: application/json`만 받고 그 외는 415. 파일 업로드(PRA-02 multipart)는 그 API만 예외로 두고 Origin 확인을 반드시 적용한다
  - 상태를 바꾸는 요청에 `Origin` 헤더가 있으면 허용 도메인인지 확인해 아니면 403. 다른 도메인에 CORS를 열지 않는다
- 근거: 운영 Nginx(`infra/runtime/nginx.conf`)가 웹(`/`)과 API(`/api/`)를 같은 주소로 내보낸다. GET은 상태를 바꾸지 않는다. Android 앱은 HTTP 클라이언트의 쿠키 저장을 켜야 한다(FE 전달).
- 로컬 HTTP 개발은 `AUTH_COOKIE_SECURE=false`를 로컬에서만 쓰고 README에 적는다.

### 비밀번호 재설정

| 단계 | API | 내용 |
| --- | --- | --- |
| 인증번호 받기 | AUTH-06 `purpose = PASSWORD_RESET` | 가입된 이메일에만 실제 발송, 가입되지 않은 이메일도 같은 202(가입 여부를 알리지 않음). 재발송 60초·하루 10회 |
| 인증번호 확인 | AUTH-07 | `verificationToken` 발급(5회 제한, 1회 사용) |
| 새 비밀번호 저장 | `POST /auth/password-reset` | 요청 `verificationToken`·`newPassword`(영문·숫자·특수문자 포함 8~128자) / 204 |

- 성공하면 그 회원의 리프레시 토큰을 모두 폐기한다. 자동 로그인하지 않고 새 비밀번호로 다시 로그인한다.
- 탈퇴 대기 회원은 재설정은 되지만 탈퇴는 취소되지 않는다(로그인할 때 취소). 탈퇴 완료 회원은 이메일이 비어 대상이 아니다.
- DB 변경 없음(`email_verifications.purpose`가 `PASSWORD_RESET`을 받는다).

## 기술 선택(구현 전 확인)

| 항목 | 안 | 이유·주의 |
| --- | --- | --- |
| 보안 골격 | Spring Security + 리소스 서버(JWT, HS256) | 쿠키에서 `access_token`을 읽는 BearerTokenResolver만 바꾼다. Boot 4.1의 정확한 스타터 이름은 의존성 추가 때 `dependencyInsight`로 확인 |
| 비밀번호 해시 | Argon2 또는 PBKDF2 (BCrypt 아님) | 명세 최대 128자. BCrypt는 72바이트까지만 쓰고 Spring Security는 초과 시 예외 |
| 인증번호 해시 | 서버 비밀값 HMAC-SHA256 | 6자리라 오프라인 대입을 막으려면 비밀값이 필요. 3분·5회 제한과 함께 쓴다([저장 방식 기록](../knowledge/backend/auth-token-storage.md)) |
| 리프레시 토큰 | 임의 256비트 값, DB에는 SHA-256만 | 재발급마다 회전, 폐기 토큰 재사용 시 그 회원의 리프레시 토큰 전부 폐기(AUTH-04) |
| mergeTicket | 짧은 유효기간의 서명 토큰(제공자·제공자 ID·이메일·확인 여부) | 별도 테이블 없음. 한 번만 쓰기는 `user_social_accounts` 유일키로 보장. 간편 로그인 가입이 없어 signupTicket은 쓰지 않음 |
| 소셜 제공자 | `RestClient`로 인가 코드 교환·사용자 조회(카카오·구글·네이버 어댑터) | FE가 인가 코드를 보내는 구조라 서버 리다이렉트 로그인(oauth2-client)은 쓰지 않는다. 테스트는 대역 |
| 메일 | `MailSender` 포트 + SMTP 구현 | 발송 수단은 인프라 결정(AUTH-06 규칙 4). 테스트·로컬은 메모리 대역, 인증번호 원문을 로그에 남기지 않음 |
| 탈퇴 일괄 삭제 | `@Scheduled(cron = "0 0 4 * * *", zone = "Asia/Seoul")` 매일 04:00 KST | 대상·순서는 [DB 스키마 '탈퇴 일괄 삭제 대상'](../contracts/db-schema.md#탈퇴-일괄-삭제-대상). 녹음 파일 삭제는 PRA-02 저장소(우동균)의 삭제 포트를 호출 |

비밀값 없는 환경변수 예시(`AUTH_JWT_SECRET`, `AUTH_CODE_HMAC_SECRET`, 쿠키 Secure 여부, 제공자별 client id/secret, SMTP)를 `backend/README.md`와 `.env.example`에 추가한다.

## 작업 순서(세로 조각, 각 조각마다 테스트 포함)

1. **공통 응답·오류 형식과 보안 골격:** `{httpStatus,isSuccess,message,code,result}`·`errorCode` 응답, 공개/인증 경로, 쿠키 발급·삭제 도우미, CSRF 대응(JSON 전용 415·Origin 확인 403·CORS 닫음). 미인증 401·없는 경로 404 검사.
2. **AUTH-08 약관 목록:** code별 시행된 최신 버전만 반환.
3. **AUTH-06·07 이메일 인증:** 발송(재발송 60초·하루 10회·이전 번호 무효), 확인(5회 제한·만료·성공 즉시 무효), verificationToken 발급.
4. **AUTH-02 가입 + AUTH-01 로그인:** 약관 필수 동의·버전 검증, 토큰 1회 사용, 단소 자동 지정, 비밀번호 규칙. 로그인은 형식 400, 이메일 없음·비밀번호 불일치·DELETED는 같은 401 `INVALID_CREDENTIALS`, 같은 이메일 15분 5회 실패 시 15분 429, 대기 회원은 탈퇴 취소 후 로그인(`withdrawalCancelled`). 성공 시 쿠키 2개 발급, `last_login_at` 갱신.
5. **AUTH-04 재발급·AUTH-03 로그아웃:** 회전, 재사용 탐지, 로그아웃 시 폐기·쿠키 삭제.
6. **USR-01·02·03:** 내 정보(`linkedProviders` 포함), 악기·표기와 곡별 BPM(`user_song_settings`, 20~240), 닉네임 수정.
7. **USR-04 비밀번호 변경:** 현재 비밀번호 확인, 모든 refresh 폐기 후 현재 기기만 재발급.
8. **USR-05 탈퇴:** 현재 비밀번호 재인증, 대기 전환·토큰 전부 폐기, 대기 중 로그인 시 취소. 인증 필터가 요청마다 회원 상태를 확인해 `ACTIVE`가 아니면 401·쿠키 삭제. 가입·가입 인증번호는 409 안내. 30일 뒤 첫 04:00 KST 일괄 처리.
9. **AUTH-05 소셜 로그인:** 연결된 계정은 바로 로그인(대기 회원은 탈퇴 취소). 연결이 없고 같은 이메일 가입 계정이 있으면 409 ACCOUNT_MERGE_AVAILABLE, 없으면 거절하고 이메일 가입 안내. 신규 가입은 하지 않음.
10. **AUTH-09 계정 연결:** 제공자 확인 이메일은 동의만, 아니면 비밀번호 또는 ACCOUNT_MERGE 인증 토큰. 거절하면 로그인하지 않음.
11. **마이페이지 간편 로그인 연결·해제(새 API):** `POST`·`DELETE /users/me/social-accounts/{provider}`. 두 409는 1062 키 이름으로 구분.
12. **비밀번호 재설정(새 API):** AUTH-06·07 `PASSWORD_RESET` → `POST /auth/password-reset`, 리프레시 토큰 전부 폐기.

1~5가 끝나면 FE(송가연·권영민)가 이메일 로그인으로 연동을 시작할 수 있도록 먼저 공유한다.

## 검증

- 규칙(비밀번호·인증번호·토큰 회전·탈퇴 상태 전이)은 DB 없이 단위 테스트.
- 컨트롤러는 웹 계층 테스트로 상태 코드·errorCode·쿠키 속성(HttpOnly·Secure·SameSite=Lax, 본문에 토큰 없음)을 확인.
- Mapper·트랜잭션은 `databaseTest`(폐기 가능한 MySQL 8.4).
- 소셜 제공자·메일은 대역만 쓴다. 실제 카카오·구글·네이버 앱 연동은 앱 등록 후 별도로 확인하며 대역 테스트를 실제 연동 검증으로 보고하지 않는다.
- 병합 전 `clean build`·`databaseTest`.
