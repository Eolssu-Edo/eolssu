## 범위와 완료 조건

- AI 실행 이미지(S15P31E102-213)를 edo1 운영 Compose의 `ai` 서비스로 띄운다. 호스트 포트는 열지 않는다.
- backend에 `ANALYSIS_AI_BASE_URL=http://ai:8000`을 넣는다.
- V5(단소 율명 `pitches` 11행)를 운영 DB에 적용한다. 적용 전 `pitches` 기존 행을 확인한다.
- 완료 조건: 운영에서 업로드한 세션이 `DONE` 또는 AI 실패 코드로 끝나고, backend 로그에 `wiring missing` 경고가 없으며, AI 로그에 녹음 서명 URL이 남지 않는다. 실제 업로드 확인은 S15P31E102-178로 옮겼다(아래 '남은 일').

## 서버 반영 단계 (사용자 승인 후)

1. **AI 이미지 빌드:** develop `3c66291`의 `ai/`를 edo1 임시 폴더로 보내 `eolssu-ai:runtime`으로 빌드한다. 실행 중인 서비스에는 영향 없음.
2. **DB 백업:** V5 전에 `pitches`·`flyway_schema_history` 덤프를 root 전용 `/opt/backups/eolssu-S15P31E102-228-<시각>/`에 둔다.
3. **V5 적용:** 배포된 JAR로 일회용 컨테이너를 `db` 프로필·웹 서버 없이 운영 DB에 붙여 Flyway가 V5만 적용하게 하고 바로 멈춘다. 비밀값은 명령줄에 쓰지 않고 `.env`에서 환경으로 넘긴다. 되돌리기: `pitches` 11행과 이력 V5 행 삭제(insert만 하는 마이그레이션).
4. **Compose 교체:** 서버 Compose를 root 전용으로 백업하고 저장소 변경(`ai` 서비스, backend `ANALYSIS_AI_BASE_URL`)을 설치한 뒤 `config --quiet`로 검사한다.
5. **기동:** 배포 lock을 잡고 `ai`를 띄운 뒤 backend만 재생성한다(약 30초 backend 중단). readiness `UP`, Docker healthy, 프론트·MySQL 컨테이너 ID 유지를 확인한다. 되돌리기: 백업한 Compose로 backend 재생성, `ai` 중지.
6. **처리 시간 재측정(선택):** 일회용 컨테이너에서 `evaluation.measure_latency --methods pYIN`을 15~120초로 재서 60초 제한 판단 근거를 남긴다. 측정 중 서버 CPU 부하가 잠깐 오른다.
7. **실제 흐름 확인:** 앱으로 업로드한 세션의 상태·로그를 읽기 전용으로 확인한다. 운영 계정 로그인은 사용자가 한다.

## 결정 로그

- 2026-10-28: AI 주소는 내부망 서비스 이름이라 `.env` 대신 Compose에 직접 적는다. Jenkins CI 검사용 `ci.env.example`에 새 변수가 필요 없다.
- 2026-10-28: 이미지 태그는 backend 실행 이미지처럼 고정 태그(`eolssu-ai:runtime`)로 두고, 빌드한 커밋은 이 기록에 남긴다. Jenkins 배포는 `--no-deps`로 backend만 다시 만들므로 `ai`는 건드리지 않는다.
- 2026-10-28: 메모리 한도 6GiB. 120초 녹음 채점 약 3GiB, AI의 요청당 DTW 한도 4GiB 기준. backend 동시 분석 2개가 모두 긴 녹음이면 한도를 넘을 수 있다(운영 문서에 기록).
