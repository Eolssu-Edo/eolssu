P1에서 먼저 결정할 사항:

- Android는 `AudioRecord`에서 받은 PCM을 사용한다. PCM은 압축 전 소리 샘플이다. 분석과 파일 저장이 같은 입력을 사용하도록 하는 제안이며 아직 구현하지 않았다.
- 파일은 `MediaCodec`으로 AAC로 압축하고 `MediaMuxer`로 m4a에 담는 방안을 검토한다. 기존 규격을 유지해야 하므로 WAV 업로드로 바꾸지 않는다.
- 음높이 추정은 소리의 반복 주기를 찾는 YIN을 후보로 둔다. 새 외부 라이브러리 도입은 먼저 기존 의존성과 플랫폼 지원을 확인한다.
- 음표 전환과 입력 지연이 겹치는 구간은 곧바로 오답 확정하지 않는다. 분석 창 길이, 신뢰도, 판정 대기 조건은 설계에서 명시한다.
- 단소·소금의 기준 주파수·옥타브·조율 처리와 시김새 구간의 표시 방법을 정한다. 다른 모드의 미확정 기준을 자동으로 채택하지 않는다.
- 분석 지연·UI 지연·기기 입력 지연을 구분한다. 이 값을 합친 실측 없이 즉시 표시 시간을 보장하지 않는다.

## 검증 방법

명령은 현재 `frontend/README.md`에 존재하는 작업을 기준으로 한다. `frontend/`에서 실행한다.

```powershell
.\gradlew.bat :shared:testAndroidHostTest --max-workers=2
.\gradlew.bat :androidApp:assembleDebug --max-workers=2
```

자동 검사는 음높이 계산, 시간과 음표 연결, 상태 해제를 대상으로 한다. 실제 마이크·인코더·재생·음높이 정확도·지연은 Android 실기기에서 별도로 확인한다. iOS는 Windows 빌드로 검증했다고 보고하지 않는다.

실기기 기록에는 다음을 남긴다.

- 기기·OS·앱 버전·수행자·수행일, 사용 악기와 목표 음·옥타브, 입력 환경.
- 음을 유지하는 구간과 음이 바뀌는 구간을 구분한 입력, 무음·숨소리·메트로놈 혼입 조건.
- 확인된 정답 구간 대비 인식 비율, 옥타브 오류, 음높이 차이. 정답 구간이 없으면 정확도 측정으로 부르지 않는다.
- 입력 소리 발생부터 화면 표시까지 지연의 측정 방법·반복 횟수·분포. 내부 처리 시간만 재면 전체 표시 지연과 구분한다.
- 녹음 파일의 길이·크기·코덱, 재생과 서버 제출 결과, 중단·재시작 관찰.

실제 악기 연주자와 지연 측정 장비는 아직 확보 여부를 확인하지 않았다. 기기가 연결돼 있다는 이유만으로 실제 악기 검증을 완료로 처리하지 않는다. 사용할 수 없는 항목은 사유와 필요한 다음 확인을 남긴다.

## 위험과 되돌리기

- 원본 입력을 읽는 작업이 막히면 녹음과 분석이 함께 영향을 받을 수 있다. 입력을 읽는 곳에서 화면 갱신이나 무거운 분석을 직접 수행하지 않도록 설계한다.
- 녹음 종료 때 인코더의 남은 데이터를 저장하지 않으면 파일이 손상될 수 있다. 정상 종료와 중단을 구분해 확인한다.
- 녹음 구현을 두 개 동시에 켜서 같은 마이크를 나눠 쓰지 않는다. 기존 구현은 새 경로가 검증될 때까지 비교 기준으로 활용한다.
- 공유 오디오 인터페이스를 수정하면 다른 플랫폼과 테스트 대역에 영향이 있다. 필요한 기능의 유무를 명시하고 iOS·웹에 가짜 인식값을 제공하지 않는다.
- 문제가 생기면 시제품 연결을 제거하고 기존 Android 녹음 구현으로 되돌릴 수 있게 변경을 제한한다. 사용자 녹음과 업로드 대기 파일은 되돌리는 과정에서 삭제하지 않는다.
