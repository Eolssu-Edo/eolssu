## 설계 판단

기존에는 파일 삭제 이후 취소되면 DB만 보존하는 위험을 수용했다. 사용자 요청에 따라 기한이 지나면 취소할 수 없도록 바꾼다. 단순 시각 검사만 추가하면 만료 직전 시작한 취소 트랜잭션이 아직 커밋되지 않은 후보를 삭제할 수 있으므로, 파일 삭제 전에도 같은 회원 행 잠금으로 기존 취소의 완료를 기다린다. 저장소 호출 내내 DB 잠금을 유지하거나 새 PURGING 상태를 추가하는 대신, 기한과 짧은 사전 잠금으로 순서를 결정한다.

## 검증 결과

### 환경과 재현

- Windows PowerShell, JDK 21.0.11, 프로젝트 Gradle Wrapper 9.8.2.
- 이 Task 전용 폐기 가능한 Docker `mysql:8.4.13`, `eolssu_test` DB, loopback 동적 포트. 기존 작업의 DB는 사용하지 않았다.
- 새 컨테이너는 `mysql:8.4.13 --max-connections=512`로 준비한다. 테스트 계정은 해당 DB 권한과 `performance_schema.data_lock_waits`·`data_locks` SELECT가 필요하다. 이번 일회용 컨테이너는 root로 검사했다.
- `backend/`에서 JDK 21 `JAVA_HOME` 및 해당 DB의 `TEST_DB_URL`·`TEST_DB_USERNAME`·`TEST_DB_PASSWORD`를 설정한다.

### 실패 확인과 수정

- 기존 구현에서 `test --tests '*WithdrawalPurgeServiceTests'`: 6개 중 녹음 보존 검사 1개 실패. 후보 조회 뒤 취소된 회원의 파일 삭제 이벤트가 발생했다.
- 로그인 단위 검사에서 만료 정각·직후, 잠금 이후 만료, 누락 시각, 소셜 병합 차단 등 5개 회귀 실패를 확인한 뒤 수정해 19개 통과했다.
- 기존 구현에서 `databaseTest --tests '*WithdrawalPurgeConcurrencyDatabaseTests'`: 실제 MySQL 3개 모두 의도한 assertion 실패. 취소가 회원 행 잠금을 보유한 동안 파일 삭제, 파일 삭제 직후 로그인 취소 성공, 파일 삭제 실패 뒤 만료 계정 복구를 확인했다.
- 삭제 준비를 추가한 뒤 단위 검사 7개 통과. DB 재검사에서 Kotlin 증분 컴파일에 남은 이전 위임 클래스가 `AbstractMethodError`를 내어 `clean` 후 재컴파일했다.
- 통합 `clean build databaseTest`: 기본 검사 369개 통과, 변경 관련 이메일 HTTP 8개·소셜 HTTP 11개·경합 3개 모두 통과. DB 전체는 131개 중 33개가 MySQL `Too many connections`로 기동 실패했다(`max_connections=151`, `Max_used_connections=152`). 일회용 DB만 512로 조정한 뒤 `databaseTest` 전체 131개가 실패·오류·건너뜀 없이 통과했다. 최종 최대 동시 연결은 249개였다.
