얼쑤 QA 시연 대본

QA 담당자에게 설명하는 발표자용 · S15P31E102-936 · 2026-11-16

인용문은 화면을 보여 주면서 읽는 대본입니다. 아래의 조작과 확인 근거를 함께 봅니다. 실제 성공 결과가 나온 뒤에만 성공했다고 설명합니다.

시작하며

“왼쪽에는 연결된 기기의 실제 화면을 모았습니다. 기기가 늘면 자동으로 작게 배치되고, 가로 화면도 세로 카드 안에서 원래 비율로 보입니다. 카드를 선택하면 헤더의 제어권과 오른쪽 처리 기록이 그 기기로 바뀝니다. 녹음과 재생에는 각 기기의 마이크와 스피커를 사용합니다. 가운데 구분선을 끌면 화면과 로그의 너비를 조절할 수 있습니다.”

시연 전 준비 — 기기 연결, 이름 입장, 최신 자동 빌드 APK를 준비합니다. 같은 QA 계정·같은 곡으로 만든 전곡 기록 두 건을 준비하고 최신 기록에서 비교합니다. 실제 기기 곁에서 소리 입력·청취를 맡을 사람과 Android 파일 선택기에서 열 수 있는 테스트 악보도 준비합니다. 웹 영상에는 기기 소리가 전송되지 않습니다. 로그를 함께 볼 때는 1번에서 QA 앱을 실행합니다.

실기기 앱은 설치된 APK에 설정된 서버를 사용합니다. 서버 자동 검사는 별도의 격리 QA 백엔드·AI·DB를 사용합니다. 이 환경의 결과를 운영 서버·다른 기기·다른 앱 버전의 통과로 설명하지 않습니다. 번호 선택은 확인 항목을 여는 동작입니다. 앱 화면은 왼쪽 기기에서 직접 이동합니다.

제어권

“여러 팀원이 같은 기기 화면을 함께 볼 수 있습니다. 화면을 조작하는 권한은 기기마다 한 명에게 있습니다. 다른 사람이 제어권을 요청하면 현재 조작자가 승인하거나 거절할 수 있습니다.”
  • 조작 — 헤더에서 제어권 요청을 누릅니다. 두 번째 참여자가 있으면 요청·승인·반납을 차례로 보여 줍니다. 텍스트를 입력할 때는 기기의 입력칸을 먼저 선택합니다.
  • 보여줄 근거 — 현재 조작자 이름과 실제 터치 반응을 확인합니다. 조작 권한이 있는 동안 이름이 깜빡이고, 반납하거나 기기 연결이 끊기면 멈춥니다.

1. APK 적용·앱 실행과 로그 수집

“최신 APK 적용은 연결된 기기 중 이전 버전인 기기만 갱신합니다. 조회하지 못한 버전은 최신으로 단정하지 않습니다. 이어서 QA 앱 실행을 누르면 연결된 기기에 설치된 앱을 함께 실행합니다. 각 기기를 선택해 실제 화면과 수집된 로그를 확인합니다. 다른 사람이 조작 중이면 승인 대기로 남고, 기기 번호별 결과를 확인합니다.”
  • 조작 — 1번에서 APK 적용 대상 번호와 상태를 보여 줍니다. 업데이트는 로그 수집을 마친 뒤 진행합니다. QA 앱 실행을 누르고 각 기기를 선택해 수집 상태를 확인합니다.
  • 보여줄 근거 — 실제 앱 화면, 앱 처리 기록의 기기 번호·수집 상태, 실행 정보의 OS·앱 버전을 보여 줍니다. 처리 기록이 비어 있으면 아직 확인할 로그 근거가 없는 상태입니다. 앱 기능은 실제 화면으로 보여 주고 로그 확인은 미확인으로 남깁니다.

로그 수집 종료는 앱 처리 기록 카드 안에서 수집 중에만 표시됩니다. 수집을 마쳐도 폰 앱과 QA 웹 접속은 유지됩니다. 헤더의 연결해제는 연결된 모든 기기에서 본인의 QA 웹 세션을 끝내는 동작입니다. 각 카드의 ⋯에서 해당 기기의 포트를 바꾸고, 미연결 기기는 하단 페어링 메뉴에서 선택합니다.

2. 로그인

“로그인하면 사용자 본인의 학습 진도, 연습 기록, 내 악보를 조회합니다. 로그인 화면에서 입력을 확인하고, 성공 후 앱 화면과 실제 서버 응답을 함께 보겠습니다.”
  • 조작 — 자동 입력 버튼이 활성화된 경우 기기의 이메일 칸 선택 → 이메일 입력. 비활성화돼 있으면 기기 화면과 텍스트 입력으로 테스트 계정을 입력합니다. 이어서 비밀번호 칸을 별도로 선택하고 포커스를 확인한 뒤 비밀번호 입력을 누릅니다. 기기 앱의 로그인을 누릅니다.
  • 보여줄 근거 — 홈 화면 진입, 로그인 요청의 실제 응답, 이후 본인 데이터 조회를 확인합니다. 입력 오류를 시연했다면 실패 안내와 해당 요청 실패를 구분해 보여 줍니다.

3. 기초 콘텐츠

“학습 콘텐츠는 세 기능으로 묶었습니다. 기초부터 배우기는 악기를 익히는 단계별 학습이고, 운지법 보기는 음에 맞는 손가락 위치를 확인하는 기능입니다. 정간보 읽기는 악보에서 음높이와 길이를 읽는 방법을 익히는 기능입니다.”
  • 조작 — 홈에서 기초 배우기 → 단계 진입과 앞뒤 이동을 보여 줍니다. 홈으로 돌아와 운지법 보기 → 악기·음 선택과 예시음을 보여 줍니다. 정간보 읽기 → 예시와 단계 이동을 보여 줍니다.
  • 보여줄 근거 — 선택한 악기·음·단계와 실제 표시 내용을 대조합니다. 서버를 조회한 동작은 해당 요청을 보여 줍니다. 기기 내부 재생이나 정적 화면은 관측된 UI·재생 근거로 확인하고, HTTP 성공만으로 실제 소리가 났다고 설명하지 않습니다.

4. 연습 기록 보기

“연습 결과는 저장한 뒤 다시 열어 볼 수 있습니다. 곡이나 악기로 기록을 찾고, 상세 점수와 녹음을 확인합니다. 같은 곡의 두 기록을 비교하면 어떤 부분이 달라졌는지도 볼 수 있습니다.”
  • 조작 — 준비한 기록의 목록·필터 → 상세 → 녹음 재생 → 지난 연주와 비교를 보여 줍니다. 메모를 바꾼 뒤 화면을 나갔다 다시 열어 저장 여부를 확인합니다. 삭제는 버려도 되는 테스트 기록으로만 시연합니다.
  • 보여줄 근거 — 목록과 상세가 같은 기록을 가리키는지, 점수·메모가 다시 조회해도 유지되는지, 해당 조회·저장 요청 결과가 일치하는지 확인합니다.

5. 연습·녹음·평가

“곡을 고른 뒤 모범 연주와 구간 연습을 사용할 수 있습니다. 연주 평가에서는 기기 마이크로 녹음해 서버에 보내고, AI 분석 결과를 점수와 틀린 부분으로 확인합니다. 지금은 전송 접수와 채점 완료, 앱에 결과가 보이는 시점을 나누어 보겠습니다.”
  • 조작 — 곡·악보 선택 → 연습 또는 연주 평가 → 평가 시작 → 실제 소리 입력 → 결과 확인 → 연습 기록 저장 순서로 보여 줍니다.
  • 보여줄 근거 — 녹음 접수, AI 완료, DB 저장, 앱 결과 수신, 점수 표시의 다섯 단계와 실제 앱 결과를 대조합니다. 기록을 저장한 뒤 4번 목록에서 다시 엽니다.
“202는 녹음을 접수했다는 응답입니다. 여기서 AI 완료, DB 저장과 앱의 점수 표시까지 확인해야 전체 흐름을 설명할 수 있습니다. AI 처리 시간과 전송부터 점수가 보이기까지의 시간은 구분해서 보겠습니다.”

기본 입력은 기기 마이크입니다. 녹음 입력 변경에서 QA 테스트 소리를 적용했다면 미리 준비한 합성 입력을 사용하는 시연이라고 설명합니다. 설정은 다음 녹음부터 적용되며, 실제 사용은 synthetic_input 로그로 구분합니다. QA 앱 실행은 기기 마이크로 초기화합니다.

6. 악보 추가·편집

“내 악보를 추가하고, 변환된 음표를 검수하거나 편집해 저장하는 기능입니다. 파일 업로드가 끝난 시점과 악보 변환이 끝난 시점을 구분하고, 저장 뒤 다시 열어 편집한 내용이 유지되는지 보여 드리겠습니다.”
  • 조작 — 사진·PDF로 테스트 악보 등록 → 변환 결과 검수 → 음·길이·빠르기·장단 편집 → 저장 → 다시 열기 → 연습 진입을 보여 줍니다. 제공 곡을 내 악보로 불러오는 경로를 사용할 때는 원본과 내 악보를 구분합니다.
  • 보여줄 근거 — 등록한 파일과 변환 작업, 선택한 악보와 저장한 악보가 같은 대상인지 확인합니다. 저장 후 조회 응답과 실제 악보 화면을 대조합니다. 변환 서비스가 준비되지 않았다면 그 단계를 보류로 설명하고 완료했다고 말하지 않습니다.

서버 자동 검사로 전환하며

“지금까지는 사람이 실제 기기를 조작했습니다. 이제 앱 처리 기록에서 로그 수집을 마치고, 준비한 테스트 녹음을 API에 보내는 서버 자동 검사를 보여 드리겠습니다. 이 결과는 실제 기기의 화면 조작 검사와 구분합니다.”
누를 버튼읽을 설명보여줄 결과
평가 결과 비교“같은 악보에 기준 연주와 일부 음이 바뀐 연주를 넣어 점수와 음표별 피드백을 비교합니다.”두 점수, 바뀐 음표의 판정과 실제 평가 기록
평가 재시도“첫 AI 요청을 의도적으로 실패시킨 뒤 같은 녹음으로 재시도합니다.”첫 실패, 다음 시도 완료, 평가 저장 건수
중복 제출 방지“같은 녹음을 동시에 두 번 보내도 한 번만 채점·저장되는지 확인합니다.”202 한 건·409 한 건, AI 한 번·평가 한 건
계정 접근 차단“본인은 자신의 결과를 읽고, 다른 계정은 그 결과를 읽지 못하는지 확인합니다.”본인200·타인404와 해당 요청

각 기기의 로그 수집을 마친 뒤 서버 검사를 실행합니다. 왼쪽 색띠와 오른쪽 번호 배지는 해당 기기 문맥에서 실행한 서버 API 검사 결과입니다. 실제 기기 UI 기능의 통과를 뜻하지 않습니다. 선택한 기기의 현재 결과와 실행별 로그를 보여 줍니다.

7. 부하 테스트

“먼저 여섯 건을 동시에 제출하겠습니다. 성공은 결과 조회와 DB 저장까지 확인한 수이고, 5초 이내는 그 성능 기준을 충족한 수입니다. 성공했다고 모두 5초 이내인 것은 아니므로 두 수치를 각각 보겠습니다.”

조작 — 7번 부하 테스트 → 제출 수6 → 동시 제출 시작 → 성공/전체·실패·5초 이내 수와 제출별 상태를 보여 줍니다. 버튼의 로딩과 제출 완료를 확인하고 필요하면 중단과 이전 실행 결과를 보여 줍니다. 150~1000건 결과는 그 규모를 실제로 실행한 뒤에만 설명합니다.

측정 구간은 업로드 HTTP 송신부터 본인 결과 조회와 DB 저장 확인까지입니다. 기기 화면 표시 시간은 포함하지 않습니다. 실패·중단도 전체 제출 수에 포함하며, 서버 채점 마감은60초·클라이언트 결과 확인 마감은75초입니다.

결과를 믿을 근거 보여 주기

“이 로그는 지금 선택한 앱 동작이나 서버 검사에 연결된 기록입니다. 기기와 요청 번호, 평가 시도를 맞춰 확인하겠습니다. 서버·AI 로그와 DB 조회 기록을 나누어 보고, 근거가 없는 단계는 확인됐다고 설명하지 않겠습니다.”
  • 조작 — 앱 처리 기록에서 동작 선택 → 로그 보기 → 출처 필터 → 실행 정보의 요청 ID/시도/HTTP를 확인합니다.
  • 해석 — 앱은 기기의 요청·응답·그리기 기록, 서버/AI는 해당 프로세스 기록, DB 조회는 실제 저장 상태의 조회 근거입니다. 검사 요청은 자동 검사 도구의 요청·응답입니다.
  • 제약 — 비밀번호·토큰·쿠키·본문은 제외한 정규화 로그입니다. 최근 최대500건의 표시/보관 수를 보여 줍니다. 수집 시각 차이로 처리 시간을 계산하지 않고 기록된 경과 시간을 사용합니다. 기록 없음은 미확인이며 통과가 아닙니다.

마무리하며

“지금 보여 드린 기기와 앱 버전, 실제 실행한 기능, 결과와 로그를 검증 기록으로 남기겠습니다. 실행하지 못한 항목과 실패한 항목도 나누어 전달하겠습니다.”
